1. 目的
--------------------------------------------------------------------------------
本ドキュメントは、.NET 向け永続化対応コレクションライブラリ「Seamless」の
要件を定義する。Seamless は Microsoft.Garnet（Tsavorite）をバックエンドとし、
メモリ上限を超える規模のデータを、標準コレクションと等価な API で扱うことを
目的とする。

2. 背景
--------------------------------------------------------------------------------
2.1 メモリ常駐型 Dictionary / HashSet / List / Set はメモリ容量に律速される。
2.2 Tsavorite はハイブリッドログ（メモリ＋ストレージ）構造を持ち、巨大データを
    扱える。一方で API が低レベルで、利用者は Session、SpanByte、SessionFunctions
    などの内部概念を直接扱う必要がある。
2.3 Seamless は Tsavorite の上に薄いラッパを設け、IDictionary<TKey,TValue> 等の
    BCL 互換インターフェースで巨大データコレクションを扱えるようにする。

3. 用語
--------------------------------------------------------------------------------
- Store     : Tsavorite の TsavoriteKV インスタンスを内包するファクトリ層。
- Collection: Store から生成される利用者向けコレクション本体。
- Session   : Tsavorite のクライアントセッション。操作種別ごとに分離して保持する。
- Overflow Mutable Strategy : 変更可能領域がフルに達したかどうかを判定する戦略。
  Memory 戦略（メモリ専用）と Storage 戦略（ストレージ併用）を切り替える。

4. 要件
--------------------------------------------------------------------------------
4.1 機能要件
4.1.1 標準コレクション互換
      - Seamless.Collections.IDictionary<TKey,TValue> は
        System.Collections.Generic.IDictionary<TKey,TValue> および
        IReadOnlyDictionary<TKey,TValue> を実装する。
      - HashSet 系は IHashSet<T> を介して BCL の集合演算
        (ExceptWith / IntersectWith / IsSubsetOf / Overlaps / SetEquals 等)
        を提供する。
      - List 系は永続インデックスファイルとデータファイルからなるメモリマップド
        ファイル List を提供する。



4.1.4 永続化／ストレージ
      - メモリ専用モード: MemoryOnlyDevice により Tsavorite のログをメモリ常駐
        とする。
      - ストレージ併用モード: 任意の IDevice を受け取り、ハイブリッドログとして
        利用する。Checkpoint/Recovery のためのディレクトリを保持する。
      - Recovery 時に最終 EntryCount に基づき IndexSize を再決定できる。

4.1.5 容量制御
      - MemoryOverflowMutableStrategy はメモリ可変領域の使用量を MutableFraction
        により制限する。
      - StorageOverflowMutableStrategy はストレージ容量に対し
        StorageLimitFraction と StorageReserveBytes により上限を決定する。
      - 上限到達時の Add / Upsert は LogFull として TryAddResult.LogFull もしくは
        例外を返す。

4.1.6 列挙
      - メモリ常駐分の列挙は IMemoryCollection<T>.GetEnumerator() で行う。
      - 全件列挙は IterateLookupAll を介して Tsavorite の Scan 経由で行う。
      - 列挙中に全件をオンメモリの List に蓄積してはならない。チャンク
        （固定長配列）または ListStore による永続バッファに退避し、少しずつ返す。

4.1.7 Refresh
      - IDictionary<TKey,TValue>, IHashSet<T> は Refresh() を提供し、
        内部 Session を張り替えて Tsavorite の epoch 古参照を解放できる。
      - 既定実装は no-op。Session を持つ実装側が上書きする。

4.1.8 Dispose
      - Seamless が提供するすべての Collection / Store は IDisposable を実装する。
      - 多重 Dispose は安全（no-op）に行えること。
      - IsDisposed プロパティで状態を観測できること。

4.2 非機能要件
4.2.1 性能
      - ホットパスに仮想呼び出しを発生させない（型パラメータによる静的ディスパッチ）。
      - 大量データに対しても定数メモリで動作するイテレーションを提供する。
      - 不要なヒープ確保を避け、SpanByte / Span<T> / fixed バッファを活用する。

4.2.2 移植性 / マルチターゲット
      - Seamless 共有プロジェクトは netstandard2.0 互換コードを許容する。
      - Seamless1 / Seamless2 / Test 各プロジェクトは net10.0 をターゲットとする
        （SDK は global.json および Directory.Build.props で固定）。

4.2.3 信頼性
      - 例外型は ArgumentNullException / ArgumentOutOfRangeException /
        InvalidOperationException / KeyNotFoundException 等、用途に合致した
        具体型を投げる。Exception を catch しない。
      - Pending Status は必ず CompletePending によって解決する。

4.2.4 テスト容易性
      - public API のみを通じてテスト可能であること。InternalsVisibleTo を
        前提としない。
      - Test.Seamless1 / Test.Seamless2 はそれぞれの Tsavorite バージョンで
        同一テストを実行する（条件コンパイルによる分岐は禁止）。

4.3 制約
4.3.1 共通コーディング規約 (copilot-instructions.md) に従うこと。
      - インデントはスペース。
      - 識別子・記号間のスペースを排除し、波括弧は同一行配置。
      - if-else は片方が空でも { } を省略しない。

5. ユースケース
--------------------------------------------------------------------------------
5.1 巨大ログのキー集合化
    - ストリームから到来するイベントキーを HashSet に蓄積し、重複を除去する。
    - メモリ容量を超える規模であってもストレージにスピルする。

5.2 巨大マップの構築と参照
    - Key→Value の対応関係を Dictionary に蓄積し、後段から Lookup する。
    - Recovery により再起動後も同一の参照状態を再現する。

5.3 集合演算
    - 巨大集合同士の ExceptWith / IntersectWith / SymmetricExceptWith を
      Tsavorite Session を介して行い、メモリ上に全件を持たずに完了する。

6. 受け入れ基準
--------------------------------------------------------------------------------
6.1 公開 API が IDictionary<TKey,TValue> / ISet<T> / IHashSet<T> /
    IList<T> 互換のセマンティクスで動作する。
6.2 Managed / Unmanaged 4 組合せがコンパイルおよびテストを通る。
6.3 Memory / Storage 両モードで Add / Read / Remove / Iterate / Refresh /
    Dispose が成功する。
6.4 LogFull 条件下で TryAddResult.LogFull もしくは適切な例外が返る。
6.5 Recovery 後の EntryCount が Checkpoint 前と一致する。

7. 範囲外
--------------------------------------------------------------------------------
- 分散構成、レプリケーション。
- マルチプロセスでの同一 Store 共有。
- 任意の RDBMS へのバインディング（旧 RelationalDatabase ディレクトリの再有効化）。
