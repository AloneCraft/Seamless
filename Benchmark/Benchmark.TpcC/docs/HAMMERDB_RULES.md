## 2. 運転側(ドライバー)

### 2.1 VU と監視役

- 時間を計るスクリプトでは、指定した VU 数に 1 を足した数のスレッドを作ります。1 番目が監視役で、取引は流しません。【読】`genvu.tcl:245-248`、`mssqlsoltp.tcl:2738-2741`
- 各 VU は 500 ミリ秒おきに順に起動します(既定)。【読】`genvu.tcl:590-593`
- 各 VU は自分の接続を 1 本だけ持ち、5 つの手続き呼び出しを準備してから回り始めます。【読】`mssqlsoltp.tcl:3048-3055`
- 接続直後に暗黙の取引を切ります(implicit transactions を OFF)。つまり、文はそれぞれ自動で確定し、手続きの中の明示的な取引だけが複数文の取引になります。【読】`mssqlsoltp.tcl:3053`

### 2.2 家の倉庫の選び方

**既定(全倉庫を使わない)**

1. VU は接続直後に倉庫の番号の最大値 W を問い合わせます。【読】`mssqlsoltp.tcl:3056-3057`
2. 1..W から一様に 1 つ選び、それを計測の間ずっと家の倉庫にします。【読】`mssqlsoltp.tcl:3059`
3. VU どうしで選ぶ倉庫が重なってもかまいません。どの VU にも選ばれない倉庫も出ます。(Q-002)

**全倉庫を使う(`mssqls_allwarehouse=true`)**

この設定は、作られたスクリプトに文を差し込む形で効きます。【読】`gentpcc.tcl:3-38`、`gencli.tcl:1681-1690`

1. 取引を流す VU の数を V とします(監視役を除く)。【読】`gentpcc.tcl:9`
2. 1 VU あたりの倉庫数を k = ceil(W / V) とします。【読】`gentpcc.tcl:12`
3. 0 から数えて i 番目の VU は、倉庫 ((i + a × V) mod W) + 1 を a = 0..k-1 について受け持ちます。【読】`gentpcc.tcl:13-21`
   - 例(文書 ch04s08): W=30、V=3 なら、1 人目は 1,4,7,…,28、2 人目は 2,5,…,29、3 人目は 3,6,…,30。
   - W が V で割り切れないときは、折り返して 2 人の VU が同じ倉庫を受け持ちます。
4. 取引ごとに、受け持ちの中から一様に 1 つ選んで、その取引の家の倉庫にします。【読】`gentpcc.tcl:26-29`、差し込み位置は取引を選ぶ直前(`gentpcc.tcl:37-38`)。家の倉庫が計測中に変わるので、仕様 2.4.1.1 の「端末ごとに固定」から外れます。(Q-003)
5. Stock-Level の地区は、この設定でも VU ごとに固定のままです(2.3)。

### 2.3 Stock-Level の地区

- VU は接続直後に地区の番号の最大値(10)を問い合わせ、1..10 から一様に 1 つ選んで固定します。【読】`mssqlsoltp.tcl:3060-3062`
- 仕様は「端末ごとに (W_ID, D_ID) の組が一意」を求めますが(仕様 2.8.1.1)、HammerDB は一意にしません。(Q-004)

### 2.6 乱数の関数と NURand の定数

- `RandomNumber m M` は、Tcl の `rand()`(0 と 1 の間の実数)を使って m..M の整数を一様に返します(両端を含む)。【読】`tpcccommon-1.0.tm:55`
  - `srand` を呼んでいないので、種は各スレッドの Tcl 解釈系が時計から取ります(Tcl の仕様)。
- `NURand A x y C` は仕様 2.1.6 の式そのものです。【読】`tpcccommon-1.0.tm:57`(同じ定義が `tpcccommon-1.0.tm:172` にもう一度ある)
  - (RandomNumber(0,A) と RandomNumber(x,y) のビット和 + C) を (y−x+1) で割った余りに x を足す。
- C は姓の生成だけで使い、作成時も運転時も **123 に固定**です。【読】`mssqlsoltp.tcl:1370`・`1438`(作成)、`mssqlsoltp.tcl:2881`・`2921`(運転)
  - 仕様 2.1.6.1 は、作成時と運転時の C の差を 65..119(96 と 112 を除く)にするよう求めます。HammerDB は差が 0 です。(Q-006)
- C_ID 用(A=1023)と品目用(A=8191)の NURand は使っていません。どちらも一様です。(Q-005)
- 姓は 0..999 の数の 3 桁を、BAR, OUGHT, ABLE, PRI, PRES, ESE, ANTI, CALLY, ATION, EING の音節に置き換えてつなげたものです(仕様 4.3.2.3 と同じ)。【読】`tpcccommon-1.0.tm:59-62`(作成用)、`tpcccommon-1.0.tm:174-178`(運転用)
- 手続きの中の乱数(rbk、品目、供給倉庫、数量)は T-SQL の `RAND()` で、「小数の乱数 × 範囲 + 1 を整数に切り捨てる」形です。どれも範囲内で一様です。【読】`mssqlsoltp.tcl:651`・`663`・`664`・`673`・`678`

### 2.7 キー入力・思考時間(`KEYANDTHINK`)

既定では切ってあります(`mssqlserver.xml:32`)。比較の本線もこれを切ります。切ると、各 VU は取引を間をあけずに流し続けます(Q-011)。入れたときの動きは次のとおりです。

- 取引の前にキー入力時間、後に思考時間を、その VU のスレッドを止めて待ちます。【読】`mssqlsoltp.tcl:3069-3087`
- キー入力時間は固定の秒数です。【読】`tpcccommon-1.0.tm:180-183`
- 思考時間 = |round(ln(r) × 平均)| 秒です。r は 0 と 1 の間の一様乱数で、結果は**整数の秒に丸め**ます。上限の打ち切りはありません。【読】`tpcccommon-1.0.tm:185-189`

| 取引 | キー入力(HammerDB) | 思考の平均(HammerDB) | 仕様のキー入力(5.2.5.2) | 仕様の思考の平均(5.2.5.7) |
|---|---|---|---|---|
| New-Order | 18 秒 | 12 秒 | 18 秒 | 12 秒 |
| Payment | 3 秒 | 12 秒 | 3 秒 | 12 秒 |
| Delivery | 2 秒 | **10 秒** | 2 秒 | **5 秒** |
| Stock-Level | 2 秒 | 5 秒 | 2 秒 | 5 秒 |
| Order-Status | 2 秒 | **5 秒** | 2 秒 | **10 秒** |

- Delivery と Order-Status の思考時間が仕様と入れ替わっています。(Q-012)
- 仕様は思考時間を -ln(r) × 平均 とし、平均の 10 倍で打ち切ってよいとしています(仕様 5.2.5.4)。HammerDB は秒に丸め、打ち切りません。(Q-013)

### 2.8 立ち上がり・計測・NOPM と TPM

監視役(1 番目のスレッド)が次の順に動きます。【読】`mssqlsoltp.tcl:2742-2822`

1. 自分用の接続を開き、SQL Server の版を表示します。【読】`mssqlsoltp.tcl:2742-2749`
2. 立ち上がりの分数だけ、6 秒ずつ眠って待ちます。【読】`mssqlsoltp.tcl:2748-2758`
3. 開始の値を 2 つ取ります。【読】`mssqlsoltp.tcl:2761-2772`
   - 全地区の D_NEXT_O_ID の合計(64 ビット整数にしてから合計)
   - SQL Server の性能カウンター `Batch Requests/sec` の累積値(`sys.dm_os_performance_counters`)
4. 計測の分数だけ、6 秒ずつ眠って待ちます。【読】`mssqlsoltp.tcl:2773-2783`
5. 終了の値を同じ 2 つ取ります。【読】`mssqlsoltp.tcl:2786-2797`
6. 計算します。【読】`mssqlsoltp.tcl:2798-2809`
   - **NOPM** = (終了の D_NEXT_O_ID 合計 − 開始の合計) ÷ 計測の分数
   - **TPM** = (終了の Batch Requests − 開始の値) ÷ 計測の分数
   - 分数は設定した整数の分で、実際に経った時間ではありません。どちらも整数どうしの割り算なので小数は切り捨てます。(Q-016)
   - TPM は、カウンターが数値でない、または減っていたら 0 にします。
7. 「System achieved NOPM from TPM SQL Server TPM」の形で表示し、全 VU に止まるよう合図します。【読】`mssqlsoltp.tcl:2811-2812`、`tpcccommon-1.0.tm:384-400`
8. チェックポイントの設定が入っていれば `checkpoint` を実行します。【読】`mssqlsoltp.tcl:2814-2821`

補足:

- NOPM は「確定した New-Order の数」です。巻き戻した 1% の New-Order は D_NEXT_O_ID の増分も戻るので数えません。仕様の tpmC は巻き戻した New-Order も「完了した取引」に数えます(仕様 5.1.2、5.4.1)。(Q-015)
- TPM はサーバー全体のカウンターなので、監視役の問い合わせや、他のセッションの要求も入ります(Q-017)。1 分の試運転では、TPM 57,023 に対して手続きの実行回数の合計が 57,232(約 61 秒)で、1 取引がほぼ 1 要求に数えられていました【測】。5 つの手続きすべてで、1 回の呼び出しはちょうど 1 要求です。ただし tdbc の allrows は 1 回で 2 要求(実行と後始末)、evaldirect は 1 要求で、監視役の開始・終了の問い合わせが TPM の差に約 +4 入ります【測】。HammerDB 文書も NOPM を主指標とし、TPM は DB ごとに違うとしています(ch03s04)。
- 監視役が眠る時間は 6 秒の積み重ねなので、実際の経過はわずかに長くなります。影響は小さいと見ます【推】。
- VU は計測が終わっても自分では止まりません。止まる合図を、何取引かに 1 回だけ見ます。見る間隔は、合図を見る時間に応じて 1 から最大 1024 取引まで倍々に延びます。【読】`mssqlsoltp.tcl:3064-3066`

### 2.9 誤りの扱い

- 手続きを呼んで ODBC の誤りが返ったとき、RAISEERROR が true ならその VU は止まり、false なら表示だけして次へ進みます(既定は false)。【読】`mssqlsoltp.tcl:2843-2859` ほか各取引
- ただし手続きの中は TRY/CATCH で囲まれています。中で起きた誤り(デッドロックの犠牲を含む)は捕まえられ、巻き戻したうえで「誤り番号・重さ・状態・手続き名・行・文」を**ふつうの結果の行として**返します。運転側はこれを成功と区別しません。【読】`mssqlsoltp.tcl:743-753`(New-Order)、`825-835`、`978-988`、`1067-1077`、`1109-1119`(Q-018)
  - SQL Server の文書: TRY/CATCH は「重さ 11 以上で接続を切らない誤り」を捕まえ、捕まえた誤りは呼び出し側に返らない。
- New-Order の 1% の巻き戻しも、運転側には知らされません(ふつうの結果を返す)。【読】`mssqlsoltp.tcl:734-741`

### 2.10 そのほかの運転の形(本線では使わない)

- 試しのスクリプト(`test`): 同じ取引を、出力を表示しながら回します。計測はしません。【読】`mssqlsoltp.tcl:2287-2645`

### 6.1 New-Order(`neword`、`mssqlsoltp.tcl:591-756`)

手順【読】:

1. 取引を始めます(`632`)。
2. 顧客を (w, d, c_id) で読み、割引・姓・信用を取ります(`635-643`)。ヒントなし(READ COMMITTED)。
3. 地区を 1 回の UPDATE で、税率と次の注文番号を取りつつ次の注文番号を 1 増やします(`644-650`)。
4. rbk を 1..100 で引きます(`651`)。
5. 品目ごとに(1..ol_cnt、`658-729`):

   6. 品目データと在庫データに ORIGINAL が含まれるかの判定(brand-generic)はしません。(Q-032)

仕様との差(まとめ): 入力の多くを SUT の中で作る(Q-007)、品目と顧客が一様(Q-005)、在庫の閾値(Q-030)、在庫の集計列を更新しない(Q-031)、brand-generic と合計金額を作らない(Q-032)。

表を触る順は「顧客 → 地区 → 品目と在庫(と明細)→ 注文 → 新規注文 → 倉庫」で、仕様の書き順(倉庫 → 地区 → 顧客 → 注文と新規注文 → 品目ごと)と違います。仕様 2.3.1 は取引の中の順番を自由としているので違反ではありませんが、倉庫の行を最後に、しかも読むだけにしているので、ロックの持ち方が変わります(Q-033)。

**多区画になる率(供給倉庫が他の倉庫を含む New-Order)**【測。W=1 で 9.61%(約 31.7 万件)、W=2 で 9.63%、予測 9.52%】

## 8. 名前で引く行の位置と照合順序

- 名前で引くときに選ばれるのは、同じ (倉庫, 地区, 姓) の顧客 n 人を c_first の昇順に並べたときの **ceil(n/2) 番目** です。
  - 根拠【読】: 上から 50% を取るとき、SQL Server は端数を切り上げます(SQL Server の文書 TOP: 行数が小数になったら次の整数に切り上げる)。その中で c_first が最大の 1 人を取るので、上から ceil(n/2) 番目になります(`mssqlsoltp.tcl:886-896`、`1021-1035`)。
  - c_first が同じ顧客が複数いると、どちらを取るかは決まりません。c_first は 62 文字から選ぶ 8..16 文字なので、同じ地区の同じ姓の中で重なることはほぼありません【推】。
- 並びは c_first の列の照合順序で決まります。ディスク上の表は列に照合順序を指定しないので、データベースの照合順序(この PC では `Japanese_CI_AS` の見込み、4.1)になります。【読】`mssqlsoltp.tcl:1236`
- この PC で確かめた結果【測】: 62 文字(0-9、A-Z、a-z)だけでできた文字列 3,009 個を char(16) にして並べたところ、`Japanese_CI_AS`・`Latin1_General_CI_AS`・`SQL_Latin1_General_CP1_CI_AS` のどれでも、**「大文字にそろえてから文字コードで比べる」並びと同じ**になりました。大文字小文字だけが違うものは同じ順位です。
  - C# で再現するなら、末尾の空白を除いてから `StringComparison.OrdinalIgnoreCase` で比べる形にあたります【推。ASCII の英数字に限った話】。
  - 確かめに使った台本は `C:\Users\kazuh\AppData\Local\Temp\claude\G--GitHub-Seamless\6426d35a-b546-428d-b390-e7bc8a1bc6fd\scratchpad\collation_check.py`(一時領域。問い合わせは読み取りだけ)。
- 実データでの確認【測】: 10,000 組(10 地区×1,000 姓)すべてで、ostat と payment の名前引きが ceil(n/2) 番目と一致しました(n は 1〜69)。BIN2 の序数比較では 2,259 組(22.6%)で別の顧客になり、運転での引きは出やすい姓ほど人数が多いので、重みを付けると約 64% になります。大文字小文字を区別する非 BIN の照合(Japanese_CS_AS など)は食い違い 0 です。同順位を人工的に作ると (c_first, c_id 昇順) の ceil(n/2) 番目になりましたが、保証はありません。
- 大文字小文字を区別する序数比較(既定の `string.CompareOrdinal`)では、数字 → 大文字 → 小文字の順になり、HammerDB の SQL Server と違う顧客を選びます。(Q-019)
