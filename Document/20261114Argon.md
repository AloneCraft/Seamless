## 第1部: 現在有効な Seamless 統合仕様・不変条件 (Consolidated Specification)

### 1.1 全体アーキテクチャと共通実行基盤 (`Seamless.Execution`)
- **共通ストア (`Store`) と実行スコープ (`ExecutionScope`)**:
  - すべてのコレクション（`Seamless.Collections.Tsavorite` / `Seamless.Collections.Persisted`）、大規模 LINQ、およびデータベース（`DatabaseContainer`）は、`Seamless.Execution.ResourceBudget` の階層予算（メモリ上限・一時ストレージ上限）を共有する。
  - `ResourceBudget.CreateChild` による親子会計は、増分予約時に子と全祖先の上限を原子的に検査し、不足時は現在量・ピークを汚さずに `ResourceLimitException` を投げる。
  - 一時作業領域（`WorkStore` / `CreateWorkStore`）は親予算と寿命（`Own` / `Release` / `Dispose`）に従い、放置された一時ディレクトリは `TemporaryResourceRecovery` が二段階排他ロック確認の上で回収する。
- **配布形態と実行ホスト（旧 `20261107-manager-browser-hosting.md` 統合）**:
  1. **組み込み同期型 (`ManagementApplicationHost.CreateAsync` / `OpenAsync`)**: スタンドアロン業務アプリプロセス内に DB 実行・管理機能・Kestrel を組み込み、業務クライアントは `DB定義.dll` を同期直接呼び出しする。Manager からの DB 操作も共通の単一 DB 実行スレッドへ集約し、画面描画・通信待機・OS I/O を分離する。
  2. **Manager Webサーバー同居型 (`Seamless.Database.Server`)**: Windows / Linux の単一サーバープロセス内で DB・管理機能・ネイティブ業務通信（TCP/TLS・NamedPipe/UnixSocket）と Kestrel による共通 Razor 管理画面（Browser Manager）を配信する。別プロセス・別PCの業務クライアントは `DB通信.dll` で接続する。
  3. **Manager Webサーバー＋Seamlessサーバー分離型**: Seamless サーバーが DB を所有・実行し、別プロセスの Kestrel から管理操作を渡す。クライアントには ASP.NET Core 依存を持ち込まない。
  - ※1万接続規模を想定した Frontend / Backend 別プロセス分離（`W08-FRONTEND-BOUNDARY`）は現行 W01〜W21 完了後の別設計単位とする。

### 1.2 データベースアクセスモデル・トランザクション・ビュー・関数
2026-11-12 の利用者決定（[refactoring-designs/20261112-DBアクセスモデル.md](refactoring-designs/20261112-DBアクセスモデル.md)）により、旧方式（`TransactionMode.Legacy`、`db.Table` での暗黙トランザクション、匿名型からのビュー列推論、`GeneratedView` による行型自動合成、旧 `20261110-view-query-integration.md`）は廃止された。

| 宣言型 | 配置場所 | 役割・トランザクション契約 |
| :--- | :--- | :--- |
| **`Table<T>` / `Table<TKey, T>`** | `tx` (`Transaction`)・`r` (`IReader`)・`db` のコンテナ/スキーマ | トランザクション対象の表。表と表の式（`Where`/`Union`/`Except`/`Intersect` の結果）の共通の型で、実体は保存された表（`StoredTable`）か取引の表（`TransactionCollection`）。`tx` では読み書き可能、`r` では読み取り専用（`ISet<T>`）。`db` 側の書き込み（関係代入・`Add`・`Remove`・添字の set）は、取引の外では1回ごとに1つの暗黙の取引で確定する（2026-11-17 利用者決定。[refactoring-designs/20261117-関係代入.md](refactoring-designs/20261117-関係代入.md)）。 |
| **`Set<T>` / `Set<TKey, T>`** | `db` (`DatabaseContainer`) 直下のみ | トランザクションを介さない直接操作の表。MVCC・WAL を通さず Tsavorite を直接読み書きする。 |

- **トランザクションと読み取りの入口**:
  - **更新トランザクション (`using var tx = db.BeginTransaction();`)**: 常に **Serializable（直列化可能）**。版付き MVCC ストレージ上で動作し、`tx.Commit()` で確定、`Dispose()` で未コミット変更を破棄する。
  - **スナップショット読み取り (`using var r = db.BeginRead();`)**: 開始時点のスナップショットを一貫して読み取る `IReader` を返す。`Transaction` も `IReader` を実装するため、読み取り専用コードは `IReader` に対して記述できる。
  - **関係代入（2026-11-17 利用者決定、実装仕様は [refactoring-designs/20261117-関係代入.md](refactoring-designs/20261117-関係代入.md)）**: `T = T.Union(rows)`・`T.Except(rows)`・`T.Intersect(rows)`・`T.Where(p)`・`T = new(q)`・`T = [..q]` で表の新しい中身を書く。書き込みは追加・削除・上書きの差分だけ。同じ主キーで中身の違う行が残る結果は主キーの違反（1行も書かない）。FLinq が差分の処理の呼び出しへ書き換え、書き換えられない場所では実行時に式を読んで同じ差分を求める。取引を開いている流れで `db` 側の表に触ると、同じメソッドで見えるものはコンパイルエラー（SDB005）、見えないものは実行時の例外。表ではない式への書き込みはコンパイルエラー（SDB004）。
  - **集合演算 (`Seamless.Linq.Set`)**: `ISet<T>` を受け取り `ISet<T>` を返す `Where` / `Select` / `SelectMany` / `Join` / `Union` / `Intersect` / `Except` / `Distinct` を提供する。`Select` / `SelectMany` / `Join` は集合として重複を除去する。
- **ビューと関数の定義・展開契約**:
  - 保存する行の型は `Tables` 名前空間（`[Key]` 属性から `Keys.*`・`_Key`・コンテナ定義を自動生成、列はフラットなプリミティブ型）、ビューが返す行型は `Views` 名前空間に利用者が通常の名前付き型として定義する。
  - ビューは `Views` 内の `IReader` 拡張プロパティ（`ISet<T>` を返す）、関数は `Functions` 内の `IReader` 拡張メソッド（`ISet<T>` または `T` を返す）、ストアドプロシージャは読み取り専用なら `IReader`・更新ありなら `ITransaction` の拡張メソッドとして定義する（`StoredProcedure<T>` およびトップレベルの `MaterializedView<TKey, T>` 露出は廃止。マテリアライズドビュー（ビューの実体化）は採用しない。2026-11-15 利用者）。手続きは `<root>.Procedures` に置き、書ける入口のインターフェース `ITransaction` を生成する（未実装）。
  - ビュー・関数の所属スキーマは拡張ブロックの受け手（`IReader` か `I<スキーマ>Reader`）で決まる。本体の表は、受け手によらず常にルートからたどって `q.Database.<スキーマ>.<表>` と書く（すべての入口に、ルートの入口を返す `Database` を生成する。未実装）。
  - 行の型の旧方式（`Keys` と `Records` の二重書き）は削除する。旧方式はリリースしていないので互換性は持たない（未実装）。
  - FLinq 生成器は、呼び出し元のクエリ式に現れるビュー・関数（単一式の拡張メンバー）を呼び出し側へインライン展開し、`Seamless.Linq.Set` 呼び出しを `System.Linq` パイプライン（＋必要な `Distinct`）へ下げて単一ループへ融合する。
  - DB のビュー・関数を展開できない場合は、実行時デリゲートへフォールバックせず **`FLINQ007` コンパイルエラー** とする。
- **外部キー・副索引 (`[Index]`) と TPC / RDBMS 統一（2026-11-14 合意。実装仕様は [refactoring-designs/20261114-宣言と手続きと索引の統一.md](refactoring-designs/20261114-宣言と手続きと索引の統一.md)）**:
  - 索引の宣言の最終形・保存の形・範囲読み取りの記録の単位は未決。決まっているのは、式の索引を作らないこと、文字列の比較方法を宣言に書くこと、一意の指定、索引に対応づけられない問い合わせはコンパイルエラー（全件走査は `FullScan` プロパティを書いたときだけ）、対応づけとループの融合を別の段に分けること。
  - `[ForeignKey]`（参照整合性チェックのみ、索引なし）と `[Index]`（副索引のみ、インデックス式なし）を完全分離し、索引の有無は `Seamless.Management` と C# エディタ側（Roslyn 等）の両方でアイコン表示する。
  - クエリは索引名を指定せず純粋な LINQ で記述し、FLinq が宣言された `[Index]`（等値＋ソート済みチャンク範囲/Top-N、MVCC/WAL 統合）へ自動マッピングする。
  - TPC-C（単一コンテナ化）・TPC-E も `DatabaseContainer`（Tsavorite）へ完全統合し、`Persisted` バリアント（`PL`/`PF`）および旧 TPC 独自ラッパー（`TpcDatabaseBase` / `TableCore` / `OrderedIndex` / `TxnLog` / `VersionedTpcDomain`）を全面撤去する。

### 1.3 FLinq ソース生成器とクエリ可視化・プローブ計測
- **FLinq の評価・最適化不変条件（旧 `20261024-2208-flinq-demand-analysis.md` 統合）**:
  - `System.Linq` が評価しない要素に対してユーザーラムダを評価しない。`.Anchor` を含む副作用順序と評価回数を厳密に維持する。
  - **`DemandAnalysis`（下流要求範囲の逆向き一括判定）**: 「下流が列のどこまで・どう使うか（順序依存・重複依存・全件消費か途中停止か・停止までに評価するラムダの有無）」を `DemandAnalysis` で段の並びと終端から逆向きに一括算出し、並べ替え・`Reverse`・`Distinct` の除去可否は「結果が順序や重複に依存せず、かつ下流が全件を使うか停止までに評価するラムダが無いとき」に限定する。
  - **デリゲートインライン境界 (`W20-LAMBDA-CALLSITE`)**: 直接渡したラムダ、代入が宣言時1回のみのローカル変数、単一式の同一型メソッドグループ、`readonly` フィールドはインライン展開する。再代入される変数、非 `readonly` フィールド、外部の可変ローカルを書き換えるラムダは呼び出し時点のデリゲートを保持する（宣言時の初期化式へ巻き戻さない）。`[LinqIntercept(false)]` 指定対象は展開しない。
  - **制御構文内のスカラー終端 (`W20-IF-STATEMENTS`)**: `if` 条件内の `Sum` / `Count` 等は元の短絡評価・例外順序を保つローカル関数へ展開する。三項演算子や短絡右辺の GroupBy 集約は無条件融合しない。
- **クエリ可視化・プローブ計測・資源ヒートガント（旧 `20261109-query-visualization-plan.md`, `20261110-resource-heat-gantt.md` 統合、詳細は [refactoring-designs/20261112-FLinq計測点生成.md](refactoring-designs/20261112-FLinq計測点生成.md)）**:
  - ① 元の C# クエリ式、② FLinq 生成後の C# コード、③ 型解決済み CFG（基本ブロック・操作・戻り辺・領域）の3段階を対応付け、サンキー図・実行DAG・横時間軸ガント・資源ヒートガントで可視化する。
  - 生成後の C# 構文木からループ位置を推測する旧方式は廃止し、各フラグメントが `IQueryProbe`（通常時は空構造体 `NoProbe` でオーバーヘッド 0、計測時は `RegionProbe`）の境界メソッドを直接出力する。
  - クエリ実行実績と OS 資源ヒートは、単調時計（`Stopwatch.GetTimestamp`）で揃え、ホスト全体・プロセス・クエリ寄与・ノード寄与を区別して期間別 Tsavorite `Set`（MemoryPack ペイロード＋マニフェストハッシュ検査）へ有界キュー経由で記録する。未収集・省略区間を `0` で埋めない。

### 1.4 管理画面 (Browser Manager)・ソースワークスペース・通信・認可
- **ブラウザ管理画面とオブジェクト識別（旧 `20261109-manager-object-navigation.md`, `20261110-source-object-identities.md` 統合）**:
  - ローカル管理画面は `/manager/`（検証用固定サービスは `http://127.0.0.1:15337/manager/`）で提供し、一回限りの所有者 IPC 起動トークンと 8 時間有効期限の Cookie 認可で保護する。
  - DB一覧・選択・表示順は左ツリーで扱う。表示順は同じブラウザー・接続先で復元する。下書きが公開版と異なるときや編集中の入力があるときは、左の該当DBに `*` を表示する。
  - DB名は左ツリーに表示する。右側のDB概要は「データベース」と見出しを付け、オブジェクト文書は対象名を見出しにする。編集用ツリーはDB定義と登録関数の管理情報から構成し、展開時に稼働用DLLを読み込まない。
  - 名前変更できる項目は、左ツリーの名前をダブルクリックするか F2 で編集する。クリックは選択、矢印は展開・折り畳みを行う。
  - テーブルとビュー・DB定義内の関数の列は、左ツリーで編集する。右の作業文書はテーブル（データ・C#・アクセス履歴）、ビューとDB定義内の関数（データ・C#・実行計画・実行履歴）を扱う。新規ビューは読みやすく字下げした空集合のひな形を使い、`q.スキーマ名.テーブル名` を参照する `Select` と `from … select` の例を含める。C#編集ではクエリ本体を最初に開く。
  - Manager は対象を名前から作った ID で見分ける。表示用ID（`/* seamless-id: */` のコメント、カタログの `StableId`）は 2026-11-12 の決定で削除した。既に付けたコメントは普通のコメントとして残る。名前を変えると、開いていたタブなどは復元されない。
  - ビューとDB定義内の関数の名前変更は左ツリーから行い、そのDBのソースで対象に束縛された参照を更新する。関数の引数もツリーの行内で編集する。結果列が1つ以上なら行のレコードと `ISet<T>` を生成し、最後の列を削除するとスカラー関数になって名前の右から型を編集できる。切り替え時は利用者の処理本体を保持し、型との整合はDBの検証で確認する。ひな形の本体は空集合または既定値に切り替える。
  - ツリーの構造編集は、階層型補完・IME 変換中の Enter/Escape 誤確定防止・日英言語切替を備える。Manager が作る断片は書き込み先のファイルの改行に合わせる。新しいファイルは LF とする。
  - 列の確定前に定義が更新されたときは、対象テーブル・列・入力した型とやり直し方を表示し、入力を保持する。左ツリーに確定前の入力がある場合、DBの保管・変更確認・適用は確定または取消を案内する。
  - 関数の引数と結果列を同時に編集中でも、片方を確定するともう片方の入力が残る。どちらの順でも確定でき、先に確定した内容は最新の下書きに保持する。編集中の部分自体に別の変更があれば競合として扱う。
  - テーブルのデータは共通編集グリッドで直接入力する。編集可能な表では、末尾の `＊` 行に入力すると未保存の行になり、その下に次の `＊` 行ができる。矢印はセル移動、Enter／Shift+Enter は上下、Tab／Shift+Tab は前後のセルへ移動する。F2 でセル内を編集する。Ctrl+Enter は行追加、Alt+Delete は行の削除予約、Ctrl+S は表の「変更を保存」を行う。行の追加・更新・削除を一回の保存要求にまとめ、空の `＊` 行は送らない。
  - 初回読込に失敗した場合は失敗理由と再読込を表示する。列が定義されていない旨は、取得に成功した結果から列を特定できない場合に表示する。
  - 同じ公開版の再読込は、取得時の値・入力値・DBの最新値を照合する。変更箇所が別なら統合し、同じセルに異なる変更がある場合は利用者が値を選ぶ。削除と更新が競合する場合は行の状態を選ぶ。競合の解決まで保存を止め、読み込みに失敗した場合は入力を保持する。公開版が異なる場合は新旧の列定義を自動統合しない。
  - 左ツリーのテーブル・ビュー・関数の削除はDBの下書きに加える。消える表または列のデータをDBへ適用するときは、変更の確認で削除内容への同意を求め、旧世代のバックアップを作ってから新しい公開版へ切り替える。
  - スキーマの「下書きを保管」でサーバーへ保存する。「変更を確認」も確定済みの下書きを検証前に保管する。「未保管の変更」は編集中の画面にあり、「下書き · 稼働DBへ未適用」は再度開ける状態を示す。
  - 左ツリーからデータベースを追加するときは Enter または「作成」で確定し、Esc または「取消」で入力を取り消す。フォーカスを外しても入力を保持する。確定後は「作成中…」を表示し、処理と競合する編集を一時停止する。既存のツリーを開閉・選択でき、作成中に対象を選んだ場合は公開後もその選択を保つ。
- **ソースパッケージコホート（旧 `20261109-source-package-cohort.md` 統合）**:
  - `Publish.ps1` の配布物は専用 DB プロジェクト用の単一Seamless SDKパッケージ（8 runtime DLL、生成器2個、地域別リソース、`0.0.0-build.h<hash>`）を同梱し、`packages/source-packages.json` でサーバー DLL の SHA-256 との一致を保証する。TsavoriteとGarnetの依存DLLも同じ指紋照合に含める。Debug / Release の構成不一致は出力先作成前に `PackageFeed` で拒否し、明示適用（Apply）でのみ公開版を進める。
  - ManagerのSDK下書きキャッシュは、ソース・参照DLL・生成器の内容を使って保存先を決める。登録クエリでは参照DBの成果物と入口も含む。ホスト更新後は新しい組み合わせで下書きをビルドする。公開済み成果物の共有依存DLLが現在のホストと異なる場合は、該当DLLを示して読み込みを拒否する。
  - Runtimeの計測用指紋は、Runtimeの入力、実行・生成に用いる依存、ビルド条件で決める。Managerや管理サーバーのファイルは計測用指紋の入力から外し、管理画面の変更で共有DLLの照合が崩れるのを防ぐ。
  - 旧ホストで検証できる空DBの公開版は、明示的なオフライン保守で現ホスト用の新世代へ切り替えられる。管理領域をバックアップし、別コピーで旧世代の依存DLLと空の定義を検証する。新世代の再オープン後に公開版と下書きの基準版を同時に更新する。保存領域を持つ利用者の宣言、公開済みの登録クエリ、結果未確定の操作があるDBは対象外とする。
  - 主キー付き通常表のあるDBは、明示的な `rebuild-database-host` で行を保持して復旧できる。旧世代に一致する共有依存DLLでバックアップの検証用コピーを開き、永続化と同じ正規形式で全行を読み出す。現ホストで同じ定義から別世代を作り、制約と再オープン後の全キー・行の内容・件数を検証できた時点で公開版と下書きの基準版を切り替える。取引を通さない表・マテリアライズドビュー・公開済みの登録クエリ・結果未確定の操作がある場合は保守処理を止める。
  - IDE向けDebugでは、共有ライブラリと生成器のバイナリにリポジトリ全体のコミット識別子を埋め込まない。IDEの起動タスクのように構成を省略して既定のDebugを選ぶ場合にも同じ設定を適用する。管理画面だけのコミット後も同じソース・依存関係・ビルド条件なら公開DBの共有DLLと照合できる。共有DLLの内容の照合はSHA-256で行う。
- **管理ストレージの統一と分割 WAL（旧 `20261109-management-storage-unification.md` 統合）**:
  - 1万件規模の履歴を伴う DB 名変更でも 4MiB 単一フレーム制限に掛からない分割 WAL（形式6）と、`Users` / `UserGrants` / `ManagedTextParts` / `ServerSettings` を型付き Tsavorite テーブルで管理する形式7を使用する。ローカル DB の変更は常に明示バックアップとオフライン移行で行い、起動時自動マイグレーションは行わない。
- **ネイティブ結果ストリームとリソース制御 (`W18`, `W11`)**:
  - `NativeResultStream<T>` と `ExecuteStream<TResult>` は `await using` による一回列挙の所有型でストリーム結果を返し、途中解放・キャンセル・切断時は予約した親予算を確実に 0 へ戻す。
  - `SourceEditor` と `RuntimeCompiler` で TPA 参照メタデータ配列を共有し、繰り返しコンパイル時のメモリピークを抑制する。

### DB単位の下書きと一括適用

- 新規DBは初回適用前から左ツリーに「未公開」と表示する。テーブル・列・ビュー・DB定義内の関数・スキーマを同じ下書きにまとめる。「下書きを保管」でサーバーに保管し、同じ利用者で開き直すと復元する。「変更を確認」で検証用の成果物を準備し、「この変更を適用」で初回の実DBと公開成果物を確定する。
- 既存DBの改名とスキーマ変更は、同じ適用で公開する。移行または制約の検証に失敗した場合は、旧公開版・名前・行データ・下書きを保持する。先に新しい世代を用意し、名前・公開版・依存定義・名前に結び付いたアクセス権を一つの管理取引で切り替える。別のDBへの適用は独立する。独立した定義として登録したクエリは個別の定義として管理する。
- 既存DBの削除も下書きに保管できる。「この変更を適用」の前にバックアップへの同意が必要になる。公開済みのDB・行データ・依存する登録クエリの世代を `backups/<削除の操作ID>/` に保全してから、稼働一覧から外す。バックアップ作成または確定に失敗した場合は公開版を維持する。
- 削除したDBを復元するには、ホストを停止して `Manager.exe restore-deleted-database --root <管理領域> --operation-id <削除の操作ID>` を実行する。操作IDは適用結果のバックアップ先の末尾に表示する。同名DBが稼働中の場合は復元を中止する。保存した定義と行を検証し、元のDB IDと新しい公開版番号で稼働一覧に戻す。

## 第2部: リファクタリング歴史から抽出した教訓・アンチパターン集 (Design Lessons & Anti-Patterns)

旧 `docs/refactoring-designs/`（2026年6月〜11月の約150ファイル）およびルート直下の旧バックログ文書には、試行錯誤の過程で**棄却された設計**や**実測で退行・破綻が判明した最適化仮説**が含まれていた。新たなリファクタリング時に同じ失敗を繰り返さないためのガードレールを以下にまとめる。

### 2.1 Database アクセスモデル・ビュー・関数のアンチパターン

#### (1) `db.Table` での暗黙トランザクションと直接操作の混在（廃止）
- **ダメだった設計**:
  - 同じ `Table<T>` に対して、`db.Orders.Add(...)` のような直接操作（内部で1操作ごとの暗黙トランザクションや即時ロックを取る）と、`using var tx = db.BeginTransaction();` によるトランザクション操作の両方を許し、さらに `TransactionMode.Legacy` と `Versioned` を実行時オプションで切り替える設計。
- **何が起きたか**:
  - 表がトランザクション対象なのか直接共有メモリなのかが型から分からず、暗黙トランザクションのオーバーヘッドやロック昇格デッドロックの温床となった。また 2 方式の併存で生成コード・テストの組み合わせが倍増した。
- **ガードレール**:
  - 第1部 1.2節のとおり、トランザクション用の `Table<T>` と直接操作用の `Set<T>`（`db` 直下のみ）を型レベルで分離し、旧 Legacy 方式は再導入しない。
  - 例外（2026-11-17 利用者決定）: `db` 側の `Table<T>` への書き込みは、取引の外では1回ごとに1つの暗黙の取引（版付き方式の通常の取引）で確定する。取引を開いている流れでは `db` 側の表に触れない（コンパイルエラー SDB005 または実行時の例外）ので、どの取引の状態を読み書きしているかは曖昧にならない。

#### (2) ビュー・関数の実行時デリゲート保持と行型の自動生成（廃止）
- **ダメだった設計**:
  1. **初期案（`View<T>` / `TableFunction<T>` 実行時ラッパー）**: `CreateView(db => ...)` でラムダを登録し、実行時にデリゲートを呼ぶ方式。呼び出し側の LINQ（`Where` / `Join` 等）と融合できず、毎回ビュー全体の列挙やボクシングが発生した。
  2. **中間案1（匿名型からの結果列自動推論・ユーザーソース書き換え）**: ビュー本体の匿名型戻り値から `readonly record struct` の列を推論してソースを書き換える方式。手書き投影や条件分岐で推論不能ケースが頻発し、CRLF/LF の改行コード差異で OS 間の `ArtifactHash` 不一致まで引き起こした。
  3. **中間案2（`partial record struct` + `GeneratedView` による生成器側での行型合成、旧 `20261110-view-query-integration.md`）**: 利用者が `partial` 行型の中に `Query` だけ定義し、列プロパティや `Rows` を生成器が合成する方式。型の定義とクエリ本体が密結合し、C# の通常の型設計から外れた。
- **ガードレール**:
  - 行型は利用者が `Views` 名前空間に通常の名前付き型として定義し、ビュー・関数は `IReader` への C# 14 拡張メンバーとして FLinq が呼び出し元へコンパイル時展開する（展開不能時は `FLINQ007` コンパイルエラー）。

### 2.2 FLinq コード生成・JIT 最適化のアンチパターン

#### (1) `.NET 10 [UnsafeAccessor]` とジェネリック含有型の制限（`Methods1<T>` 退行）
- **ダメだった設計**:
  - ターゲットメソッド群をジェネリック型（例: `Methods1<T>`）の非 public メンバーとして配置し、FLinq 生成器から `[UnsafeAccessor]` で呼び出す設計。
- **何が起きたか**:
  - `.NET 10` ランタイムではジェネリック含有型の非 public メンバーに対する `[UnsafeAccessor]` 解決がランタイム制限により失敗（`MissingMethodException` / `NotSupportedException`）し、45件の Dynamic ケースが一斉に失敗した。
- **ガードレール**:
  - `FLinqIncrementalGenerator.UnsafeAccessor.cs` では、アクセサ署名（含有型・戻り値・引数）に型パラメータが含まれる非 public メンバーへの `UnsafeAccessor` 生成を拒否する。ジェネリック型内のターゲットメンバーや補助メソッドは可視性を `internal` 以上に上げて直接参照させる。

#### (2) `SelectMany` の `List<T>` インデックスループ置換と静的 `Enumerator` フィールドの罠
- **ダメだった設計**:
  1. `SelectMany` の内側列が `List<T>` のとき、`GetEnumerator()` ではなく `for (int i = 0; i < list.Count; i++)` のインデックスループへ置き換える最適化。
  2. アロケーション削減のため、`List<T>.Enumerator` を生成クラスの `static` フィールドに保持して再利用する最適化。
- **何が起きたか**:
  1. インデックスアクセス（`list[i]`）は `List<T>.Enumerator.MoveNext()` が行うコレクション変更バージョン検査（`_version != _list._version` による `InvalidOperationException`）を行わないため、列挙中に `List` を変更する異常系テストで `System.Linq` と例外挙動が食い違った。
  2. `static` フィールドへの `Enumerator` 退避は、再帰や並行実行で破綻するだけでなく、コレクション初期化子内のラムダ巻き上げと衝突して状態破壊を起こした。
- **ガードレール**:
  - `List<T>` の列挙は必ずローカル変数の構造体 `List<T>.Enumerator`（`list.GetEnumerator()`）を使い、変更検知セマンティクスと再入安全性を守る。

#### (3) 終端・パイプラインの過剰な直接ループ展開による JIT 退行
以下の最適化候補は「アロケーションや抽象化を減らせば速くなるはず」という仮説で実装されたが、**実測で明確に退行（速度悪化）したため不採用・撤回**された。同じ手法を再導入してはならない。

| 候補ID | 試みた最適化内容 | 実測結果 | 退行の根本原因 |
| :--- | :--- | :--- | :--- |
| **C-ZipTuple-05** | `Zip` の 2 入力がどちらも `Span` 化可能なとき、`ZipEnumerable` 構造体を経由せず Consume で直接 2 本の `ReadOnlySpan<T>` ループを出力する | Int32 100件で **+6.2% 悪化**、String 100件で **+8.6% 悪化** | 呼び出し先メソッド内に 2 本の `TryGetSpan` 分岐とフォールバック経路がインライン展開され、メソッドの IL サイズが肥大化して JIT のレジスタ割り当てとループ最適化が劣化した。コンパクトな `ZipEnumerable.TryGetNext` 構造体に任せた方が速い。 |
| **C-Reverse-02** | `Reverse().Consume()` を `ReverseEnumerable` 構造体経由ではなく、`ArrayPool<T>.Shared` を直接確保・逆順ループするコードへ展開する | Int32 100件で **+4.6% 悪化**、ValueType16 100件で **+3.9% 悪化** | 呼び出し元に `try/finally` と `ArrayPool` 返却コードが直接展開されることで、周辺コードの JIT レジスタ退避が増えた。 |

#### (4) GroupBy 集約の条件分岐内での無条件融合バグ・下流要求範囲の散在バグ
- **ダメだった設計**:
  - `GroupBy(...).Select(g => skip ? 0 : g.Sum(x => ...))` のように、三項演算子 `?:` の選択枝や短絡演算子 `&&` / `||` / `??` の右辺、条件付きアクセス `?.` の内側にある集約終端（`Sum` / `Count` 等）を、無条件の GroupBy 集約ループへ事前融合する設計。
  - `Any` / `All` / `Contains` の直前の `OrderBy` / `Reverse` を、間に `Where(x => 10 / (x - 3) > 0)` のような例外を起こし得る述語があっても無条件で削除する書き換え。
- **何が起きたか**:
  - `skip == true` のとき本来呼ばれないはずの `Sum` 内ラムダが全要素に対して実行され、または `OrderByDescending` 除去により `System.Linq` と異なる順序で `Where` が評価されてゼロ除算例外の有無が食い違った。
- **ガードレール**:
  - 条件分岐の選択枝・短絡右辺にある集約は事前融合の対象外とし、並べ替え・`Reverse`・`Distinct` の除去は `DemandAnalysis` で下流に途中停止時評価ラムダが無いことを確認できた場合に限定する。

#### (5) 生成 C# の AST 形状推測によるプロファイリング埋め込み（廃止）
- **ダメだった設計**:
  - FLinq が最終的な C# コード文字列を生成した**後**で、その構文木を走査して `while` / `for` ループや `+=`、変数名パターンから「どこがどの LINQ 演算子か」を逆推測して計測コードを差し込む方式（`QueryProfileSource` のヒューリスティック注入）。
- **何が起きたか**:
  - 演算子融合や最適化でループ構造が変わるたびに推測が外れ、ノード帰属の欠落や構文破損が起きた。
- **ガードレール**:
  - 生成後の AST 推測は全面禁止。各演算子フラグメント自身が `Render` 時に `IQueryProbe`（`NoProbe` / `RegionProbe`）の境界を出力する（[refactoring-designs/20261112-FLinq計測点生成.md](refactoring-designs/20261112-FLinq計測点生成.md)）。

### 2.3 ベンチマーク・性能測定のアンチパターン

#### (1) 非対称な LoopCount 較正と短時間測定バイアス
- **ダメだった設計**:
  - FLinq と比較対象（`System.Linq` / `ZLinq`）で別々にループ回数を決めたり、JIT の Tier1（Dynamic PGO）昇格前にループ回数を確定する測定。
- **何が起きたか**:
  - 片側だけが Tier0 や OSR（On-Stack Replacement）で走り、2倍〜60倍の虚偽の速度比が観測された。
- **ガードレール**:
  - JIT コンパイル数の静穏（200ms 以上新規コンパイルなし）と呼出速度の安定を確認するウォームアップを完了してから、目標時間を満たす `LoopCount` を確定し、全比較列を**完全に同一の `LoopCount`** で測定する（[architecture/ベンチマーク測定仕様.md](architecture/ベンチマーク測定仕様.md)）。

#### (2) `EventListener`（`MethodLoadVerbose`）による Tiered JIT 昇格の凍結
- **ダメだった設計**:
  - ベンチマークワーカー内で JIT 完了を検知するため、`EventListener` で `Microsoft-Windows-DotNETRuntime` の `MethodLoadVerbose` イベントを購読しながら単一コア Affinity（1論理CPU固定）でウォームアップを回す設計。
- **何が起きたか**:
  - 単一コア上では、フォアグラウンドのウォームアップループと `EventListener` のイベント配送処理がバックグラウンド JIT スレッドから CPU を奪い合い、約50%の確率で Tier1 への昇格が永久に完了しない現象が発生した。
- **ガードレール**:
  - ワーカー内で重いランタイム ETW/EventPipe イベントを常時購読しない。`JitInfo.GetCompiledMethodCount` と短い `Thread.Sleep(1)` によるバックグラウンド JIT への CPU 譲歩を組み合わせる。

#### (3) `TieredPGO=false` の独自ハーネスでの `[MethodImpl(AggressiveOptimization)]` 判定
- **ダメだった設計**:
  - 簡易検証ハーネスで `DOTNET_TieredPGO=0` のまま `[MethodImpl(MethodImplOptions.AggressiveOptimization)]` の有無を比較し、「速くなった」と判定して本番コードへ付与する。
- **何が起きたか**:
  - 本番の `.NET 10` 既定（`TieredPGO=1`）では、`AggressiveOptimization` を付けると PGO プロファイル収集（Tier0 Instrumentation）をスキップしていきなりプロファイルなしの Tier1 コードを生成するため、仮想呼び出しの脱仮想化（Guarded Devirtualization）が効かず、**最大16倍遅くなる退行**を引き起こした。

### 2.4 ストレージ・WAL・プロセス管理のアンチパターン

- **単一4MiBフレーム上限の Prepare WAL（形式5）**:
  - 管理 DB の更新トランザクション（DB名変更など）で影響する全履歴エントリを単一の WAL フレーム（上限 4 MiB）へまとめて書き出すと、履歴 10,000 件状態で上限超過により失敗した。分割 WAL（形式6）および型付き Tsavorite 管理テーブル（形式7）を使用する。
- **隔離コピー DB と稼働中 Manager の Unix Domain Socket 衝突 (`W13-CLONE-IPC`)**:
  - 稼働中 Manager の DB ディレクトリをそのままコピーして同じ `TMPDIR` で別ホストを起動すると、`InstanceId` が同一のため `$TMPDIR/seamless-manager-<InstanceId>.sock` が衝突し、稼働中ホストのソケットを消失させた。隔離コピー起動時は必ず専用の所有者限定 `TMPDIR` を割り当てる。
- **Windows における `Process.WaitForExitAsync` 直後のファイルロック競合 (`W10-LOCK`)**:
  - 子プロセスの終了を `await process.WaitForExitAsync()` だけで待った直後に `management.lock` 等を再取得すると、OS カーネルのハンドル解放完了前で `IOException (Sharing violation)` が散発した。同期ハンドル待機（`process.WaitForExit()`）と所有者ロック解放確認を併用する。
- **値型 `DictionarySlim` の引数なし `new()` による未初期化バグ (`W20-CARRIER-DICTIONARY`)**:
  - `struct` の軽量辞書で既定の `new()` が呼ばれたときに内部バケット配列と比較子が `null` のままになり `NullReferenceException` を起こした。コレクション `struct` には明示的な引数なしコンストラクタを定義する。
- **`MemoryPack Version="1.*"` の浮動バージョン指定によるアセンブリ不一致**:
  - 一部プロジェクトの `1.*` 指定が共有キャッシュ内の `1.22.0` を拾い、`1.21.4` 固定プロジェクトとの間で `MSB3277` 警告を起こして Publish が停止した。原因は版の指定がプロジェクトごとに混ざっていたこと。
  - 2026年11月15日、利用者が MemoryPack を常に最新にすると決めた。MemoryPack の参照はすべて同じ `1.*` にそろえ、混在させない。Gateway の回収できる型の後始末と通信の配置の事前検査は、版の番号ではなく主版（1.x）と内部の入れ物の形を起動時に確かめる。
