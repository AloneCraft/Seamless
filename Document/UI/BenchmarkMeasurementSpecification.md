# Benchmark Measurement Specification

## 目的

通常Benchmark UIのLoopCount系タブにおいて、FLinqとZLinqを公平な条件で測定し、指定測定時間へ到達する前に「完全完了」と表示されることを防止する。

本仕様は `BenchmarkWorkloadAxis.UsesLoopCount` が真となる比較行に適用する。Scalable系タブの要素数打ち切り規則は変更しない。

## 用語

- 測定時間: Workerが返す最終1バッチ全体の合計実測時間。単位はnsで保存する。
- 表示時間: 合計実測時間をLoopCountで除した1回あたりの時間。表ではns、us、ms等に整形して表示する。
- 指定測定時間: UIの「測定時間」で選択された値。1024 msを選択した場合は `1,024,000,000 ns` とする。
- 完全完了: 同じ比較行のFLinqとZLinqが、同一LoopCountの最終バッチで、ともに指定測定時間以上となった状態。

表示時間と判定用の合計実測時間は別の値である。表示が数十nsであっても、`表示時間 × LoopCount` に相当する保存済み合計実測時間で到達判定する。

## 測定順序

1. 実行単位を「比較行 → LoopCount → 左右ケース」とする。
2. 同じ比較行のFLinqとZLinqは、各段階で常に同じLoopCountを使用する。
3. 左右両方の成功結果が揃ってから、各合計実測時間を指定測定時間と比較する。
4. 片側でも指定測定時間未満ならLoopCountを2倍にし、次のLoopCountでFLinqとZLinqの両方を再測定する。
5. 同一LoopCountで左右とも指定測定時間以上になった場合だけ、その比較行を完全完了にする。
6. `int.MaxValue` のLoopCountでも片側が指定測定時間へ届かない場合は、理由を記録して失敗とする。

片側が先に閾値へ到達しても、その側だけを以前のLoopCountの結果で確定してはならない。次段階では到達済み側を含めて左右とも再測定するため、完全完了時の最終LoopCountは必ず一致する。

## 状態管理と再開

- 動的LoopCountは、SourceTab、Type、Method、ArgumentKey、比較ペアで識別される比較行単位で管理する。
- ある比較行で増加したLoopCountを、別メソッド、別引数、別比較行の開始値として共有しない。
- `ProgressState.ElementCounts` にはユーザーが選択した初期軸だけを保持し、実行中に生成した動的LoopCountを追加しない。
- 中断・再開時は、行固有の履歴から左右とも成功している最大の共通LoopCountを確認し、その段階の判定後、未到達なら次のLoopCountへ進む。
- 片側だけ保存された段階は完全完了ではない。再開後に同一LoopCountの不足側を測定し、左右が揃ってから判定する。
- 複数CPUで実行しても、動的LoopCountは行キーに閉じ、行間で共有しない。

## 完全完了の必要条件

LoopCount系の比較行は、次をすべて満たす場合だけ完全完了とする。

- 行が測定対象として選択されている。
- FLinqとZLinqの両方が成功している。
- 左右のLoopCountが同一である。
- 左右それぞれの合計実測時間が保存されている。
- 左右それぞれの合計実測時間が指定測定時間以上である。

次の状態から完全完了へ補完または昇格してはならない。

- 測定値が1件以上存在するだけの状態
- 通常進捗が完了しただけの状態
- 片側だけが指定測定時間へ到達した状態
- 現在保存されている最大軸を、要求された最終軸とみなした状態
- 失敗、例外、タイムアウト
- LoopCountまたは合計実測時間を復元できない旧形式スナップショット

## 保存と復元

- スナップショットは左右それぞれの `LoopCount` と `TotalNanoseconds` を保存する。
- 完全完了行を保存するときは、左右が成功し、LoopCountが一致し、両方の合計実測時間が指定測定時間以上であることを検証する。不整合時は保存処理を失敗させる。
- 復元後の完全完了状態は、保存されたLoopCount、合計実測時間、ステータスから再計算する。
- 旧形式でLoopCountまたは合計実測時間がない結果は測定値として表示できるが、完全完了にはしない。
- Schema version 15では `BenchmarkSnapshotMeasurement` に左右別のLoopCountと合計実測時間を保存する。

## 回帰履歴

### 2026-07-10: `Any` が1024 ms未到達で完全完了した不具合

System.Arrayの `Any` はLoopCount 524,288で、FLinqの合計実測時間が34.8 ms、ZLinqが43.2 msだった。両方とも指定された1024 msへ届いていないにもかかわらず、測定値の存在と通常進捗完了を完全完了へ昇格するUI補完により、行とタブが完全完了になった。

同時に、動的LoopCountを `ProgressState.ElementCounts` へ追加して全行で共有していたため、先行行が追加した524,288を後続の `Any` が初期最大軸として受け取った。動的倍増を開始する条件は元の初期最大軸との一致を要求していたため、`Any` は524,288の1回だけで倍増を終了した。

対策として、動的LoopCountを比較行ローカルに変更し、左右同一LoopCountでの合計時間判定に統一した。測定値の存在、通常進捗完了、片側閾値到達による完全完了補完は削除した。

## 実装上の回帰防止条件

- 先行行の動的LoopCountが後続行へ影響しないこと。
- 各LoopCountで左右が同じLoopCountを使用すること。
- 片側だけ到達した次段階でも左右とも実行されること。
- ns単位の表示時間ではなく合計実測時間で判定すること。
- 左右の到達LoopCountが異なる場合は完全完了にしないこと。
- 失敗結果や合計時間の欠落した復元結果を完全完了にしないこと。
