# DBの読み書きの入口とビュー・関数の型の作り直し

## 背景

機能の棚卸し（[20261111-機能の棚卸し.md](20261111-機能の棚卸し.md)）で、利用者は次を決めた（2026年11月12日）。

- `View<T>`・`TableFunction<T>`は読取専用の集合、`ScalarFunction<T>`は値で足りる。ビューはプロパティ、関数はメソッド。
- 表は宣言で「トランザクションで使う表（`Table<T>`）」と「直接使う表（`Set<T>`）」に分け、同じ表で両者を混ぜられないようにする。
- 直接使う表への書き込みはトランザクションではない（WAL・版の管理を通さず、取り消せない）。
- 入口は`db.BeginTransaction()`（読み書き、常にシリアライザブル）と`db.BeginRead()`（読み込み専用、開始時点のスナップショット）の2つ。分離レベルは選ばせない（当初の「`BeginReadCommitted`・`BeginSnapshot`と書き込みの方式を選ぶ」案は取りやめた）。
- ビューは直接表現し、最適化で呼出元へ展開する。列挙ごとに定義を評価する仕組みは指示になかった。

## 現状の観察

- `Seamless.Database.Table<T>`・`Table<TKey,T>`はTsavoriteの`HashSet`を中に持ち、取引中かを自分で探して変更を振り分け（暗黙の取引）、取引外はDB全体の読み書きゲートで保護する。版付き方式（SharedV2）では中身を持たず、生成される`TypedTransaction`のプロパティ（`Seamless.Transactions.Collections.TransactionCollection<TKey,T>`）を使う。
- `View<T>`は定義ラムダを持ち、列挙・`Contains`・`Count`のたびに定義を評価して重複を除く。`TableFunction<T>`は列挙のたびに評価するだけで集合ではない。`ScalarFunction<T>`は値と名前の入れ物。いずれも`Name`を持つ。
- `Seamless.Collections.ISet<T>`は`IReadOnlySet<T>`を継承した読取専用の集合で、Tsavoriteの`Set`・`HashSet`、`Table`、`View`が実装する。`Where`・`Select`などで`ISet`を保つ拡張はない（2026年4月に`ISeamlessSet`の`Select`の構想がコメントで残ったが未実装）。
- 種類の判定は型名で行っている箇所がある：`NativeCatalog`（`TableFunction<>`・`ScalarFunction<>`・`StoredProcedure<>`）、`NativeDatabaseCompiler`、Managerの設計器、DB生成器、FLinqのビュー認識。

## 目的

- 利用者が書くコードを、型が意味を表す最小の形にする。
- 書き込みの入口を表ごとに1つにし、トランザクションと直接操作の混在をコンパイル時に防ぐ。
- 分離の方式は1つに固定し（書き込みはシリアライザブル、読み込みはスナップショット）、試験と挙動を単純に保つ。
- ビュー・関数は通常のLINQ式として書き、FLinqが呼出元で展開する。

## 非目的

- マテリアライズドビュー・ストアドプロシージャの見直し（棚卸しで別に判定する）。
- Gatewayの通信方式の変更。
- 既存DBの保存形式の自動変換。

## 提案設計

### 1. 宣言

```csharp
public sealed partial class ManagedDb{
    public Table<Order> Orders=>...;      // トランザクションで使う表
    public Set<AccessLog> Logs=>...;      // 直接使う表（Tsavorite Set）
}
```

キー付きはそれぞれ`Table<TKey,T>`・`Set<TKey,T>`。`Table<T>`の表は`db.Orders`を生成しない。`Set<T>`の表は`tx.Logs`・`r.Logs`を生成しない。

### 2. 読み書きの入口

```csharp
db.Logs.Add(x);                                    // 直接。取り消せない

using(var r=db.BeginRead()){ r.Orders... }         // 読み込み専用。開始時点に固定

using(var tx=db.BeginTransaction()){                 // 読み書き。常にシリアライザブル
    tx.Orders.Add(a);
    tx.Commit();                                     // 呼ばずに抜けると取消
}
```

- `r.X`は読取専用の集合`ISet<T>`。`tx.X`は書ける`Table<T>`（現在の`TransactionCollection`を改名・整理）。
- 未確定の変更は、どの方式でも他から見えない。
- 書き込みのトランザクションは読んだ行・範囲を記録し、確定時に開始後の他の確定と照合する（大きな走査は表単位の粗い記録）。衝突したら取消し、再試行は呼び出し側が行う。
- 非同期版（`BeginTransactionAsync`など）は同じ規則で揃える。
- 同じ表で直接操作とトランザクションを混ぜる手段は生成しない。

### 3. ビュー・関数

```csharp
namespace Database.Views{ public readonly record struct ActiveRow(int Id); }
namespace Database.Functions{ public readonly record struct FindRow(int Id); }

public static class ManagedDbQueries{
    extension(ManagedDb.IReader q){
        public ISet<Views.ActiveRow> Active=>q.Orders.Where(o=>o.Active).Select(o=>new Views.ActiveRow(o.Id));          // ビュー
        public ISet<Functions.FindRow> Find(decimal minimum)=>q.Orders.Where(o=>o.Total>=minimum).Select(o=>new Functions.FindRow(o.Id)); // テーブル関数
        public decimal Amount(int id)=>q.Orders.Where(o=>o.Id==id).Sum(o=>o.Total);                                    // スカラー関数
    }
}
```

- `View<T>`・`TableFunction<T>`・`ScalarFunction<T>`とそのラッパー、`GeneratedView`、定義ラムダの再評価・子scope・循環検出は削除する。
- 本体は生成される入口の共通インターフェース`IReader`（`r`・`tx`が実装）への拡張メンバーとして1回だけ書く。どの入口から呼ばれたかで参照する表が決まる。
- 匿名型は返せない。結果は名前付きの行型で、ビューは`<ルート>.Views`、テーブル関数は`<ルート>.Functions`に宣言する。生成器が行型を作る方式（`GeneratedViewRow`）は廃止する。
- 名前は目録（`DatabaseObjects`）から得る。`Name`プロパティは持たない。

### 4. `Seamless.Linq.Set`

`Seamless.Collections.ISet<T>`を受け取り`ISet`を返す拡張。コピーを作らず、中身を読んだ時点で計算する式として結果を表す。

| 演算 | 結果の集合 | `Contains` | 重複除去 |
|---|---|---|---|
| `Where` | 元の部分集合 | 元の`Contains`と条件 | 不要 |
| `Select` | 写した集合 | 列挙で探す | 必要 |
| `Join`・`SelectMany` | 組合せの集合 | 列挙で探す | 必要 |
| `Union`・`Intersect`・`Except`・`Distinct` | 集合演算 | 両方の`Contains`から | `Union`のみ必要 |

FLinqは呼出元で展開するとき、後段が重複に影響されない場合（`Any`・`Contains`・`Distinct`など）は重複除去を省く。

## 不変条件

常に守る性質。「守り方」は、コードで強制する手段（予定を含む）。2026年11月12日時点では実装途中で、まだ守られていない。

| # | 不変条件 | 守り方 |
|---|---|---|
| I1 | 表の種類は宣言で決まる。`Table<T>`の表は`tx.X`・`r.X`からだけ触れ、`db.X`は生成しない。`Set<T>`の表は`db.X`（DBの型`Seamless.Database.Set<T>`。2026年11月15日まではTsavoriteの`Set<T>`そのもの）だけで、`tx`・`r`には生成しない。同じ表を直接操作とトランザクションの両方で使えない | 生成器（生成しないメンバーへの参照はコンパイルエラー） |
| I2 | 入口は`db`・`db.BeginTransaction()`・`db.BeginRead()`の3つだけ | 公開API |
| I3 | 書き込みのトランザクションは常にシリアライザブル。`Commit`まで未確定で、取消・例外で全体を戻す。自分の未確定の変更は自分に見える | 取引基盤・回帰テスト |
| I4 | 読み込みは開始時点のスナップショット。他のトランザクションの未確定の変更はどの入口からも見えない | 取引基盤・回帰テスト |
| I5 | 分離レベルの選択肢を持たない（READ COMMITTEDなどは用意しない） | 公開API |
| I6 | `Set<T>`の表はWAL・版の管理を通らず、取り消せず、障害後の復旧は保証しない | 本書・利用者向け文書に明記 |
| I7 | ビュー・テーブル関数は読取専用の`ISet<T>`、スカラー関数は値`T`を返す。`View<T>`・`TableFunction<T>`・`ScalarFunction<T>`の入れ物は使わない | 型（旧型の削除） |
| I8 | ビューはプロパティ、関数はメソッドとして、生成される`IReader`への拡張メンバーに1か所1回だけ書く | 生成器・解析器 |
| I9 | ビュー・関数は呼出元で展開する。展開できなければ呼出元でコンパイルエラー。遅延評価・実行時フォールバックはしない | FLinq生成器の診断 |
| I10 | ビュー・関数の本体から読めるのは`Table<T>`の表だけ。`Set<T>`の表やコンテナの参照はエラー | 解析器の診断 |
| I11 | 匿名型を返さない。行型は名前付きで`<root>.Views`・`<root>.Functions`に宣言し、Managerでテーブルの列と同様に編集する（キーなし） | 解析器・Manager |
| I12 | `Seamless.Linq.Set`の演算は`ISet`をコピーせずに返し、結果に重複はない | 型・単体テスト |

### ガードレール

- 指示にない機能を足さない。指示が曖昧なときは仕様を決めずに利用者へ確認する。
- 展開・型検査に失敗したときに、黙って別の動きへ切り替える回避（フォールバック）を入れない。
- I9・I10は型だけでは守れないため、文書だけに頼らず診断としてコードに置く。

## 影響範囲

- `Seamless.Database`：`Table`・`KeyedTable`・`View`・`TableFunction`・`ScalarFunction`・`DatabaseContainer`（取引・読取の入口、ゲート）・`DatabaseTransaction`。
- `Seamless.Transactions.Collections`：`TransactionCollection`の改名・読取専用版。
- `Seamless.Linq`：`Set`の新設。
- `Shared/Database.Generation`：`db`・`tx`・`r`・`s`のプロパティ生成、宣言の診断、ビューの行型生成。
- `Seamless.FLinq.Generator`：ビュー・関数の展開、`Set`演算子の扱い。
- `Seamless.Management*`：設計器のテンプレート・種類の判定、目録、実行の入口。
- Gateway・Native目録・SQL登録、サンプル・試験。

## 移行手順

1. `Seamless.Linq.Set`と単体試験（2026年11月12日済み。既存の呼び出しで`Set`へ結び付くものは0件。FLinqの`Set`の展開は手順3で、`Set`の呼び出しを`System.Linq`の形へ下げ、元の集合を素通しする目印を根の組み立てで外す方式を予定）。
2. 宣言の分離（`Table<T>`／`Set<T>`）と入口（`BeginRead`・`BeginTransaction`）・`IReader`の生成。
   - 2026年11月12日済み（版付き方式の上）：生成器が`IReader`（スキーマごとに入れ子の`I<スキーマ>Reader`）・`Reader`・`BeginRead()`／`BeginReadAsync()`を生成し、`TypedTransaction`が`IReader`を実装し同期の`Commit()`・`Rollback()`・`Dispose()`を持つ。`IReader`から見た表は読取専用の集合（`ReadOnlyTransactionCollection`、`Contains`は行全体の一致、`Count`は走査）。書ける表（`TransactionCollection`）自体は集合にしない（集合にするとFLinqの取引用の経路が変わるため）。
   - 2026年11月12日済み：直接使う表`Set<T>`・`Set<TKey,T>`（行型は`IRecord<TKey>`）を`this.Set<T>()`で宣言できる。DBを閉じたときだけチェックポイントを書く。取引・`IReader`には生成しない。キー付きの行型は表と同じく`[MemoryPackable]`が必要。
   - 2026年11月15日に作り直した（`20261115-取引を通さない表の作り直し.md`）：`db.X`の型はDBの`Seamless.Database.Set<T>`・`Set<TKey,T>`。中で並列区間を常に開き、スレッドごとの置き場のマルチ用で読み書きするので、複数のスレッドから同時に使える。件数の見込みを超えると止めて広げる。表の版（成功した書き込みの回数、`Version`）を持つ。データ本体は取引とは別の共通ストア（予算の管理を持つ）に置き、保存先は`<DB>/direct-v2`。11/12〜11/15の形（`<DB>/direct/<名前>`）は自動では読み替えず、開くと明示の例外になる。
   - 2026年11月12日済み（旧方式の削除の前半(a)）：利用者の決定で旧方式（Legacy）を廃止した。`DatabaseTransactionMode`と`DatabaseContainerOptions.Transactions`を削除し、取引は版付き方式だけになった。旧方式専用の保存（表ごとのTsavorite保存領域）、専用WAL（`database.wal`の追記・回復・保存後の保管）、取引の外からの書き込みの経路を削除した。旧方式で作ったDBは開けない（変換もしない）。生成されたコンテナでは`db.BeginTransaction()`（同期）が型付きの取引を返し、`tx.BeginTransaction()`（入れ子）と`tx.Commit(metadata)`（確定の付随情報）も生成する。試験・サンプル・テンプレートは`tx.X`で書く形へ移した。旧方式の内部（旧WAL・読取セッションのゲート・表ごとのメモリ割当・キーなし表の旧来の取消）だけを確かめていた試験16件を削除し、旧方式を選ぶ場合を含めていた試験2件(Manager)は版付き方式だけにした（本文は`F:/Seamless/set-linq-20261112/removed-tests`）。
   - 未着手（後半(b)）：暗黙の取引（基底の`DatabaseTransaction`。`db.X`への書き込みを開いている取引へ振り分ける）と、取引の外の`db.X`からの読み取りの廃止。非版付きのGateway（共通WAL）、実行時SQLの動的な表、Managerの管理用ストア（`ManagementDatabase`）とNative実行がこの仕組みを使っているため、それらを型付きの取引へ移してから消す。これが済むまでI1（`Table<T>`の表は`db.X`から触れない）は守られていない。
   - 2026年11月15日の決定で変更：既定の`Exclusive`でも、版付きの保存（履歴の設定）があるときは、読み込み専用の取引（`BeginRead`）は順番待ちに並ばず、開始時点の版を読む。`Exclusive`で1つずつ動くのは書き込みの取引だけ（以前は読み込みも含めて1つずつ動き、`BeginRead`の最中に別の流れで書き込みを始めると待った）。書き込みどうしを並行させるのは`Optimistic`（履歴の設定が必要、メモリ内でも可）。また、取引は非同期の流れ（AsyncLocal）ごとに1つの根しか開けず、同じ流れで2つ目を開くと例外になる（既存の仕様）。
3. ビュー・関数を`ISet<T>`／`T`へ置き換え、3つの型と`GeneratedView`を削除する。FLinqの展開を新しい形へ接続する。
   - 2026年11月14日済み(FLinq側)：`Seamless.Linq.Set`の呼び出しを、`IEnumerable<T>`への変換を挟んで`System.Linq`の同じ演算へ下げてから展開する(`SetCallLowering`。`Select`・`SelectMany`・`Join`の後に`Distinct`を足す)。拡張ブロックのプロパティ・メソッド(ビュー・関数)の本体を呼び出し側の式へ取り込んで1つのループにする(`MemberBodyInlining`。受け手と引数が定数・書き換えられない変数などのときだけ。2026年11月15日から、生成される入口のスキーマのプロパティと`Database`をたどった受け手(`r.Person`など)も含む。取り込めないビュー・関数はFLINQ007のコンパイルエラー)。FLinqが拡張メンバーそのものを差し替えの対象にしないようにした。(DB側は次の項目)。
   - 2026年11月14日済み(DB側)：DB生成器が、生成する入口のインターフェース(`<コンテナ>.IReader`、スキーマは`I<スキーマ>Reader`)への拡張メンバーからビュー・関数を見つけて目録に載せ、名前で呼ぶ入口`DatabaseQuery`(`db.Queries`。読み込み専用の入口を開いて呼ぶ)を生成する。受け手の型は生成前で解決できないので、書かれた「コンテナ型.インターフェース名」の形から読む。表の無いスキーマにも入口のインターフェースを作る。`View<T>`・`TableFunction<T>`・`ScalarFunction<T>`・`GeneratedView`・定義の再評価(循環検出・子scope)・行型の生成(`GeneratedViewRow`・SDB004)・FLinqのビュー専用の融合と条件の押し下げを削除した。Managerの目録・実行・設計器(作成・読み取り・本体と構造の編集)、SQL変換(`NativeDatabaseCompiler`)、SQL Serverからの取り込み(関数を`<名前空間>.Functions.<スキーマ>`の拡張メソッドとして出す)、Gatewayの関数の結び付け、サンプル・試験を新しい形へ移した。ビュー・テーブル関数は集合なので並びを持たず、重複除去は既定の等値比較(DBのcodecによる正規化をしない)。関数の種類(スカラー⇔テーブル)の変更は設計器ではできず、C#で編集する。未着手：I10(本体から`Set<T>`の表・コンテナを読めないことの解析器の診断)。
4. シリアライザブルの検査（読み取りの記録、表単位の粗い記録、衝突時の取消）。
5. Manager・目録・Gateway・SQL登録の追従、サンプル・試験の移行。
6. 正式候補の受入と固定URLへの反映。

## テスト計画

- `Set`：各演算の結果・`Contains`・`Count`・重複除去・コピーしないこと。
- 宣言：混在がコンパイルエラーになること（生成されないメンバー）。
- 分離：`BeginRead`での開始時点の固定、未確定の不可視、`BeginTransaction`での自分の書き込みの可視性とシリアライザブルの衝突検出。
- 直接操作：取消できないこと、WALを通らないこと。
- ビュー・関数：値・FLinq展開・入口ごとの表の参照。

## リスクと対策

- 影響範囲が広い：手順ごとに近接試験を通し、各段階で既存の動作の差を記録する。
- 暗黙の取引を使う既存コード（サンプルの注文処理・障害復旧ほか）：`tx`へ移す。
- 直接使う表は障害時の復旧の保証の外：型の名前（`Set<T>`）と設計書で明示する。

## 未決事項

- [x] ビュー・関数の本体が参照する表を、呼び出した入口に合わせる方法（2026年11月12日決定）：DB生成器が入口の共通インターフェース（例：`ManagedDb.IReader`、表を読取専用の集合`ISet<T>`として持つ）を生成し、`r`・`s`・`tx`が実装する。利用者はC#14の拡張メンバー（`extension(ManagedDb.IReader q){...}`）でビューをプロパティ、関数をメソッドとして1回だけ書く。本体の写しは生成しない。FLinqは呼出元で受け取り側の実際の型へ差し替えて展開し、展開できない呼び出しはフォールバックせずコンパイルエラーにする。必要な改修：FLinqのstaticクラスのメンバーを傍受の対象外とする制約の解除、インターフェース経由の表参照の実際の型への差し替え、展開失敗のエラー化。
- [x] ビュー・関数の結果の型（2026年11月12日決定）：匿名型を返すことを禁止する（利用者のC#でも匿名型は戻り値に書けないため）。結果は名前付きの行型で、ビューは`<ルート>.Views`、テーブル関数は`<ルート>.Functions`の名前空間に宣言する（例：`Database.Views.View0`）。Managerは行型の列を、テーブルの列と同じツリーの行内編集で追加・編集する。キーは指定しない。スカラー関数は行型を持たない。これにより、生成器の行型生成（`GeneratedViewRow`・SDB004）とManagerの列推論・行型宣言の切替（`InferredViewColumns`・`SynchronizeViewResult`）は廃止し、「結果列は処理本体から決め読取専用」とした以前の仕様を置き換える（[20261111-2141-view-generated-row-type.md](../20261114Argon.md)の方式は本決定で終了）。
- [x] 分離の方式（2026年11月12日決定。それ以前の「読み込みは`BeginReadCommitted`・`BeginSnapshot`で選び、書き込みも方式を選べる」案を置き換える）：方式は選ばせない。`db.BeginTransaction()`は読み書きのトランザクションで常にシリアライザブル。中で読むと開始時点のスナップショットに自分の未確定の書き込みを重ねた内容が見え、確定時に読んだ内容が開始後に他から変えられていれば失敗（取消）する。`db.BeginRead()`は読み込み専用で、開始時点の確定済みの内容（スナップショット）に固定され、書き込みの入口を持たない。未確定の変更はどこからも見えず、開始後に確定した変更は新しく`BeginRead()`を始めるまで見えない。確定は1列の順番で公開されるため、読み込み専用はスナップショットのままでシリアライザブルと同等になる。READ COMMITTED・方式の型引数は用意しない。書き込みのトランザクションには、読んだ行・範囲の記録と確定時の検査、大きな走査では表単位の粗い記録、衝突時の取消と再試行の扱いが必要。
- [x] 直接使う表（`Set<T>`）の参照（2026年11月12日決定）：ビュー・関数とトランザクションからは読めないようにし、静的な制約だけで実現する（実行時の検査は持たない）。DB生成器は`IReader`・`BeginRead()`・`BeginTransaction()`の入口に`Set<T>`の表を生成せず、入口からコンテナ自体へもたどれないようにする。ビュー・関数の本体（`IReader`への拡張メンバー）でコンテナ型や`Set<T>`の表を参照した場合は、DB生成器の解析器がコンパイルエラーの診断を出す。通常のメソッドで`tx`と並べて`db.X`（`Set<T>`）を使うことは許す。
