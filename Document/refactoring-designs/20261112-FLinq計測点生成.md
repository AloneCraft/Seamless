# FLinqの計測点を生成時に部品から出す（案A）

## 背景

2026年11月12日、利用者は、LinqDB（`G:\GitHub\LinqDB`）が全演算を計測していることを踏まえ、FLinqの計測の作り方を検討するよう求め、本書の案Aを選んだ。

- LinqDBは実行時に式木を書き換え、ほぼ全ノードの評価の前に呼出回数の加算と「実行中」の書き換えを入れる。時間は全体の1個のStopwatchを呼出回数の比で割り振る推定で、1msタイマーのサンプル数は表示だけに使う。「実行中」をノードの出口で戻さないため、サンプルは最後に評価へ入ったノードに付く。
- 利用者の指摘：サンプル数は実行していた確率に比例するので、ノードの時間の近似になる。これは正しく、サンプルの振り分けを出口で戻す形に直せば成り立つ。

## 現状の観察（2026年11月12日、コードで確認）

- 工程1（正規化・最適化）：利用者のメソッド本体の構文木を`CSharpSyntaxRewriter`で書き換え、書き換えごとにCompilationのファイルを差し替えて意味モデルを取り直す（`TryRebindRewritten`、上限8回）。
- 工程2（ループへの展開）：最適化後の構文木と意味モデルから部品（Fragment・Pipelineの段）を作り、各部品がC#を文字列で出して`StringBuilder`でつなぐ。融合後のコードには演算子の境目が残らない。
- 工程3（後処理）：`GeneratedNameRenamer`と`GeneratedThisQualifier`がそれぞれ生成コードを`ParseText`で読み直す。計測（`QueryProfileSource`）は、本体を`ParseStatement`で読み直し、`while`（`MoveNext`・`TryGetNext`）・`span`の`for`・`+=`の集計の形から入力の数え上げ位置を推測して差し込み、通常版と計測版の2本を書き出す。入口で`QueryProfiler.Current`を1回読んで選ぶ。
- 計測できるのは、部品が1つで、同期の`Sum`または`SupportsQueryProfile`の終端の形だけ。区間は`FusedPipelineInclusive`で、元の演算子へ時間を配分しない（`QueryProfileProjection`も配分しない）。
- 関係する試験：`Tests/Management.Tests/QueryProfiler.cs`・`ObjectExecutionProfiling.cs`・`NullableSumSemantics.cs`。

## 目的

- 計測点を、演算子・段階の境目を知っている工程2の部品が、自分のコードと一緒に出す。生成したコードの形から位置を推測しない。
- 計測しないときのループの機械語を、計測のない今の通常版と同じにする。
- 本体を1本だけ生成し、計測の有無と段階を型引数で選ぶ（静的ストラテジ）。工程3の計測の読み直しをなくす。
- 将来、測る項目を全演算子・ラムダ・分岐へ広げられる土台にする。

## 非目的

- 測る項目を広げること（段階1〜3の追加）。棚卸しで実行の記録・計測の行（`QueryTraceContracts`・`ObjectExecutionProfile`など）の判定が「未」のため、判定後に別の手順で行う。
- 名前の付け替えと`this.`の後処理の方式の変更（2026年10月23日の決定を守る）。読み直しを1回にまとめることは別の手順で行う。
- OSのサンプリング（実行位置と生成コードの行の対応表）。

## 提案設計

### 計測点を型で受け取る本体

```csharp
// 生成器が出す形の例（名前は仮）
public static long Run<TProbe>(Source source,ref TProbe probe) where TProbe:struct,IQueryProbe{
    probe.Begin(0);                       // 区間の開始(演算子・段階の番号)
    long sum=0;
    foreach(var row in source){
        probe.Input(0);                   // 部品が自分の入力の位置で出す
        if(row.A>0){sum+=row.B;}
    }
    probe.Output(0);probe.End(0);
    return sum;
}
```

- `IQueryProbe`は`Seamless.Execution`に置く。計測点のメソッドは区間の開始・終了・入力・出力・失敗の5種類から始める（今の`QueryProfileRegionScope`の`Input`・`Output`・`Succeeded`・`Fail`に対応）。
- `NoProbe`はすべて空の本体を持つ構造体。JITは値型の型引数ごとに別の機械語を作るので、`Run<NoProbe>`では空の呼び出しがインライン化されて消える見込み。
- `RegionProbe`は今の`QueryProfileRegionScope`へ記録する構造体。計測値はスタック上の構造体に貯め、区間の終わりで1回だけプロファイラーへ渡す。

### 入口

```csharp
var profiler=QueryProfiler.Current;            // 呼出し1回につき1回だけ読む
if(profiler is null){var none=default(NoProbe);return Run(source,ref none);}
var region=new RegionProbe(profiler,target);return Run(source,ref region);
```

### 部品の出し方

- Fragment・Pipelineの段の出力に、計測点の呼び出しを出す場所（入力の位置・出力の位置・段階の境目）を持たせる。今の計測版が推測している位置（入力の取り出し直後、集計の加算の前、戻り値の直前）を、部品が直接指定する。
- 計測点の呼び出しは`probe.`で始まる固定の形にし、名前の付け替えの対象外にする。

## 移行手順

1. `IQueryProbe`・`NoProbe`・`RegionProbe`を`Seamless.Execution`に追加する。
2. 今計測できる形（`Sum`・`SupportsQueryProfile`の終端）の部品が計測点を出すようにし、入口を型引数の選択へ置き換える。`QueryProfileSource`の読み直し・書き換えと、通常版・計測版の2本の書き出しを削除する。
3. 既存の計測の試験と、FLinqの全試験・Database・Managementの近接試験を通す。
4. Headlessの対測定で、置き換え前の通常版と速さが変わらないことを確かめ、JITの機械語で計測の命令が消えていることを確かめる。
5. 計測の項目を広げる設計（段階0〜3：リリースは0〜2、Debugは0〜3の案）は、棚卸しの判定の後で別に決める。

## 進み具合（2026年11月12日）

- 済み：計測点の目印（`QueryProbeMarkers`、注釈`/*flinq-probe:input*/`・`/*flinq-probe:unknown*/`）を、`Sum`・`Sum_selector`の部品が入力の位置とSIMDの一括加算の位置に出す。計測版の組み立て（`QueryProfileSource`）は、根が`Sum`・`Sum_selector`のとき目印の位置へ記録を差し込み、ループの形から推測しない。目印は計測版の組み立てでだけ使い、通常版・実行計画・ハッシュ・出力のソースからは取り除くので、通常版の生成ソースは目印の導入前と1バイトも変わらない。
- 目印を注釈にした理由：呼び出し(`QueryProbeMarker.Input()`など)にすると、`Seamless.Execution`を参照しない利用者のプロジェクトでコンパイルできない。注釈は名前の付け替えの後処理でも残り、局所関数への展開(`DrainRemainingEnumerator`)でも残る。同じ行で`)`の後ろに書いた注釈は文の前ではなく`)`の後置に付くので、両方を見る。
- 確認：既存の計測の試験53件、Transactions.Tests(105成功・既存失敗15件は変更前と同一)、Query(114成功・既存失敗2件)、Core(98件)。FLinqの試験(Benchmark.Dynamic.Tests)は、メモリ不足以外で失敗した試験のクラスを変更前と変更後で回し、失敗35件が一致した(今回の変更による退行なし。35件は既存の失敗とメモリの見張りによる中止)。
- 済み（同日、続き）：`PipelineTerminal`の`Sum`は、全経路が足し込みの文を共通の`Sum.Accumulate`で作っているので、その先頭に目印を付けた（17か所すべてに入る）。計測版の組み立てから、ループの形・集計変数の`+=`・`SumSpan`の呼び出しを見て位置を推測する処理をすべて削除し、目印だけで差し込む形にした（P5達成）。確認：計測の試験53件、FLinqの試験は変更前と失敗35件が一致、Transactions（既存失敗15件は同一）、Query 73件。
- 通常版の生成ソースは変更前と同一（目印は出力前に取り除く）なので、この段階ではP1・P2（通常版の速さ・機械語）は変わらない。
- 済み（同日、続き。利用者が「段階はどうせ増やすので置き換える」と決めた）：本体を、計測点を型引数で受け取る1本（`<名前>__Normal<…,__TFlinqProbe>(…,ref __TFlinqProbe probe) where __TFlinqProbe:struct,IQueryProbe`）にした。入口は計測していなければ`NoProbe`で本体を呼び、計測中は小さな計測用の入口(`__Profiled`)が区間を開いて`RegionProbe`で同じ本体を呼び、戻った後に出力件数と成功を記録する。根の部品の局所関数には口を`ref`の引数で渡す。実行時の型は`Seamless.Execution/QueryProbe.cs`。
- 確認：計測の試験53件、FLinqの試験は失敗34件(変更前の35件から1件減。新しい失敗なし。減った1件の原因は未確認)、Transactions(既存失敗15件は同一)、Query 73件。機械語(段階的JITなし・最適化あり、`Where(x=>x>1).Sum()`)：本体は入口へインライン展開され、要素ごとのループは読み込み・比較・加算・あふれ検査だけで、計測点の呼び出しは残らない(P1)。
- 未確認：段階的JITとTieredPGOを有効にした本番の設定での機械語と、対測定による速さ(P2)。Debugビルドでは最適化されないので空の呼び出しが残る(想定どおり)。
- 未了：測る項目を広げる段階（段階1〜3）。

## 段階1（件数）の設計案

利用者が「段階はどうせ増やす」と決めた（2026年11月12日）ことを受けた、最初に足す段階の案。測る項目の範囲は棚卸しの実行の記録・計測の行の判定に従う。

### 測るもの

| 項目 | 単位 | 正確さ |
|---|---|---|
| 入力件数・出力件数 | 実行計画の部品（`fragment…`）とパイプラインの段（`stage…`）ごと。Where の絞り込み率、Take の打切り位置、終端が受け取った値の数など | 実測 |
| 部品に固有の件数 | Join の構築側・照合側・一致した組、GroupBy のグループ数と最大の大きさ、Distinct・Union で除いた件数、OrderBy の要素数 | 実測 |
| 段階ごとの時間 | ハッシュ表の構築、並べ替え、グループの集計など、部品の中で別の段階になる処理の開始と終了 | 実測（`Stopwatch.GetTimestamp`） |
| 資源 | 段階ごとのメモリ予算の最大値と一時領域への退避量（実行の範囲を使う部品だけ） | 実測 |

測らないもの（後の段階）：ラムダの呼出回数と、ラムダの中の分岐ごとの回数。利用者のラムダの本体を書き換える必要があるため、段階3で扱う。並列の作業者（worker）の件数は、最初は「未収集」と表示する（今の`WorkerNotCollected`の診断と同じ）。

### 仕組み

- 目印に「どの部品・どの段の、どの計測点か」を書く：`/*flinq-probe:in:f12*/`（部品12の入力）、`/*flinq-probe:out:f12.s2*/`（部品12の段2の出力）、`/*flinq-probe:count:f12:groups*/`（部品固有の件数）、`/*flinq-probe:phase-begin:f12:build*/`・`phase-end`。番号は部品が描画時に持つ番号（`番号`）と段の位置。
- 実行計画（`ExecutionPlanDocument`）を作るとき、部品と段の番号から計画のノード識別子への対応表も作る。計測版の入口は、目印を小さな整数の添字に置き換え、添字からノード識別子への表を区間の情報と一緒に渡す。
- 計測点の口（`IQueryProbe`）に `Input(int)`・`Output(int)`・`Count(int,int)`・`PhaseBegin(int,int)`・`PhaseEnd(int,int)` を足す。`NoProbe` はすべて空。件数を数える新しい口 `CountProbe` は、計測時にだけ確保する`long`の配列へ加算し、呼び出しの終わりに1回だけプロファイラーへ渡す。
- 計測の段階は、計測を始める側が`QueryProfiler.Begin(段階)`で選ぶ。入口は`QueryProfiler.Current`を1回読み、段階に応じて`NoProbe`・`RegionProbe`・`CountProbe`のどれかで同じ本体を呼ぶ。生成していない段階を指定したときは、黙って下げずにエラーにする。
- 結果は、今の区間（`QueryProfileRegion`）に、ノードごとの件数・部品固有の件数・段階の時間の一覧を加えた形にする。Managerは、すでにある「ノードごとの入出力件数」（`NodeQuantities`）と区間（`VisualizationInterval`）へ写して表示する。測れなかったノードは「未収集」と表示する。

### 最初の対象

1. パイプラインの段（Where・Select・Take・Skip・Distinct など）と、すべての終端（Sum・Count・Any・First・ToList・ToArray など）の入出力件数。
2. Join・GroupBy・OrderBy の部品固有の件数と段階の時間。
3. 残りの部品は、対応するまで「未収集」と表示する。

### 不変条件（段階1で加えるもの）

- 計測していないときの機械語は段階0と同じ（`NoProbe`の呼び出しが消える）。
- 件数は、同じ入力なら何度測っても同じ値になる（推定や間引きを含まない）。
- 測れなかったノードを0件と表示しない（「未収集」と区別する）。

## テスト計画

- 既存：`QueryProfiler.cs`・`ObjectExecutionProfiling.cs`・`NullableSumSemantics.cs`がそのまま通ること。
- 追加：計測していないときの生成コードに計測の呼び出しが残らないこと（`NoProbe`の本体が空）。計測できない形では今と同じく診断（`UnsupportedQueryShape`）だけを報告すること。
- 速さ：Headlessの対測定（`--operator-harness`）を置き換え前のビルドと交互に回す。

## リスクと対策

- JITが空の呼び出しを消さない：段階的なJIT・TieredPGOの設定で変わり得る。本番と同じ設定で機械語と速さの両方を確かめることを完了の条件にする（自作ハーネスでTieredPGOを切って見逃した過去の事例がある）。
- `ref`の構造体を局所関数・ラムダへ渡せない場合がある：今の計測版も局所関数へ区間を引数で渡している（`__compute`）。同じ方法で渡し、ラムダの中には計測点を出さない。
- 生成コードの大きさ：本体は1本になるので、今の通常版・計測版の2本より小さくなる見込み。
