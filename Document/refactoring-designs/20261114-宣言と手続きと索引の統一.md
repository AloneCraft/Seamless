## 現状の観察

コードを読んで確かめた内容。「推測」と書いたものは実行して確かめていない。

### 宣言と生成

- 行の型の生成経路は2つある（`Shared/Database.Generation/DatabaseSchemaGeneration.cs`）。
  - 新方式：`<root>.Tables` の型に `[Key]` を付けると、キーの型（`<root>.Keys`）・行の実体・コンテナの表のプロパティを生成する（100〜287行、`DatabaseContainerGeneration.cs` の `CollectDeclaredObjects`）。
  - 旧方式：`<root>.Keys` と `<root>.Records` に同じ表を2回手で書き、コンテナの表のプロパティも手で書く（289〜379行）。
- 旧方式は今も使われている：SQL Server からの取込の出力（`Seamless.Database.Rdbms/CSharpDatabaseGenerator.cs` 223・332行）、試験用のDB定義など約110ファイル、システムの目録の型（`Seamless.Database.System.Records.DatabaseObject`）。`Tables` を宣言しているのは9ファイル。
- 旧方式の生成経路だけが持つ機能が4つある：回収できる型（`Collectible`）、通信用の配置の属性（`NativeWireLayout`）、再生用の読み取り（`INativeReplayDecoder`）、計算列（`[ComputedColumn]`）。フィールド配置の最適化（`OptimizeFieldLayout`）は、新方式が常に似た並べ替えをしている（`DatabaseSchemaGeneration.Layout.cs`）。
- 新方式では `Tables` の型がすべて保存する表になる。旧方式の `Records` には、ビュー・関数の結果の行や、列の型として使う入れ子の型も入っている。

### 入口・ビュー・関数・手続き

- 生成される入口は `IReader`（スキーマは `I<スキーマ>Reader`）・`Reader`・`TypedTransaction`。書ける入口のインターフェース（`ITransaction`）は無い（`DatabaseContainerGeneration.cs` 528〜664行）。
- スキーマ用の入口が持つのは、そのスキーマの表と下のスキーマだけ。ルートや他のスキーマへ戻る手段が無い（同594行）。
- ビュー・関数の種類はメンバーの形で決まる（`ISet` を返すプロパティ＝ビュー、`ISet` を返すメソッド＝テーブル関数、それ以外を返すメソッド＝スカラー関数。同174行）。所属スキーマは拡張ブロックの受け手で決まる（同163行）。
- FLinq が呼び出し側へ取り込むのは、本体が式1つのメンバーだけ。引数は定数・書き換えない変数や引数・readonly のフィールドに限る（`Seamless.FLinq.Generator/SourceGenerator/MemberBodyInlining.cs` 143・261行）。
- FLinq が表として認識するのは具体的な型だけ（`TransactionCollection`・`ReadOnlyTransactionCollection`・`TransactionRows`・`Table<,>`。`FLinqIncrementalGenerator.ProviderFacts.cs` 49行）。推測：インターフェース型（`ISet<T>`）越しの表は、索引も高速な経路も使えない。
- 推測：本体を `from〜select` の構文で書いたビュー・関数は取り込みの対象にならず、エラーにもならない（`MemberBodyInlining.cs` 158行は、メソッド呼び出しの形の LINQ だけを見ている）。
- 名前で呼ぶ入口（Manager・Gateway 用）は `BeginRead()` を開いて呼ぶ形だけで、引数は `object?[]`（`DatabaseContainerGeneration.cs` 207行）。
- AdventureWorks の取込結果は、ビュー20個が定義を持たない写し（`MaterializedView`）、手続き11個がすべて「未対応」の例外（`Tests/Seamless.TestKit/Databases/AdventureWorks2017/AdventureWorks2017.cs`）。`MaterializedView` は元の表が変わっても更新されない。

### 取引・外部キー・索引

- 確定時の衝突検査は「キー1個」と「表全体の走査」の2種類だけ（`Seamless.Transactions/TransactionCoordinator.Optimistic.cs` 140〜168行）。
- `Exclusive` は読み取りも含めて取引が1つずつ動く（`TransactionCoordinator.cs` 112行）。
- 外部キーの検査は、書き込みの取引の確定ごとに子の表を全件読む（`Seamless.Database/DatabaseRelations.cs` 51行、`TransactionCoordinator.cs` 324行）。属性はコンテナの表のプロパティに付ける形で、主キー全体への参照だけを許す。取引の外からの書き込みは暗黙の取引に乗っている（`DatabaseRelations.cs` 63行）。
- 版付きの表は、キー＝主キーのバイト列、値＝版番号・削除の印・行で、書くたびに追記し前の記録の位置を持つ（`Seamless.Collections.Tsavorite/Stores/HistoryStore.cs`）。回収は詰め直しを呼び、キーごとに最新の1件だけを残す（同31行）。
- 現行の TPC の索引（`Benchmark/Benchmark.Tpc.Core/Storage/OrderedIndex.cs`）は、見出し（まとまりの値→先頭・末尾のチャンク番号・件数）とチャンク（まとまりの値＋番号→32個の固定長配列）の2つの入れ物で作る。追加のたびに見出しの件数を書き換える（140行）。満杯のチャンクの途中へ入れると押し出しが末尾まで続くことがある（267〜301行）。要素は固定長。
- 現行の索引は TPC-C に3個、TPC-E に18個。うち2個は式をキーにしている（`CustomerByName` の大文字化した名、`CompanyByName` の名前のハッシュ）。索引は明示の呼び出しで引き、LINQ は取り出した配列の後処理にだけ使っている（`Shared/TpcC.Transactions/Queries/TpcCQueries.cs`）。
- TPC-C は区画ごとの専用スレッドで並列に動く（`Benchmark/Benchmark.TpcC.Server/TpcCPartitionedSut.cs`、`Seamless.Transactions/PartitionExecutor.cs`）。TPC-C に版付きの変種は無い。

## 目的

- 利用者が書く宣言を1通りにする（旧方式を消す）。
- ビュー・関数・リレーション・手続きを、すべて入口への拡張メンバーとして書けるようにする。
- 索引を `DatabaseContainer` の機能にし、TPC と取込が同じ仕組みを使うようにする。
- 実装できる部分と、未決のため実装できない部分を分け、順番に進められるようにする。

- T-SQL のビュー・手続きの定義を LINQ へ訳す機能そのもの（本書は訳した結果の置き場所と形だけを決める）。
- ビューの自動の実体化（未決）。
- 1万接続規模の分離（`W08-FRONTEND-BOUNDARY`）。

## 提案設計

### 1. 名前空間と宣言

| 種類 | 置き場所 | 生成器の扱い |
|---|---|---|
| 保存する行（表） | `<root>.Tables`（スキーマ別は `<root>.Tables.<スキーマ>`） | 保存先・キーの型・コンテナの表のプロパティを生成する |
| キーの型 | `<root>.Keys`（生成物） | `[Key]` から生成する。利用者は書かない |
| ビューの結果の行 | `<root>.Views`（同 `<root>.Views.<スキーマ>`） | 何も生成しない（普通の名前付きの型） |
| テーブル関数の結果の行 | `<root>.Functions`（同 `<root>.Functions.<スキーマ>`） | 同上 |
| 手続き（本体と結果の型） | `<root>.Procedures` | 目録の種類を手続きにする |

- 旧方式（`Keys` と `Records` の二重書き、コンテナの表のプロパティの手書き）は削除する。互換性は持たない。
- 旧方式だけが持つ4つの機能は新方式の生成経路へ移す。
  - 回収できる型：Manager の実行時コンパイルと Gateway の実行時SQLのときは、MemoryPack の共通の登録先へ型を登録しない。
  - 通信用の配置の属性：`Seamless.Database.Client` を参照するときに付ける。
  - 再生用の読み取り：クライアントの結果のバッファ読み取りが型の制約として要求するので実装する。
  - 計算列：Gateway が式を登録したときは読むたびに計算し直し、登録が無いときは保存した値を返す。
- フィールド配置の最適化の指定（`OptimizeFieldLayout`）は移さない。
- 本体を書く静的クラスの名前と置き場所は自由。行型をルート名前空間に置き本体を静的クラス `Views`・`Functions` に書く案、型の中の静的メンバーの有無で種類を見分ける案は採らない（前者は同名ビューの衝突・複数プロジェクトへ分けられない・取込の出力との衝突、後者は静的プロパティが入口を受け取れない・生成器が表の型にも静的メンバーを作る、が理由）。

```csharp
namespace Shop{
    internal static class DatabaseGenerator;
    public sealed partial class ShopDb:global::Seamless.Database.DatabaseContainer;
}
namespace Shop.Tables{
    public partial struct Order{
        [global::Seamless.Database.Key] public partial int Id{get;init;}
        public partial int CustomerId{get;init;}
        public partial decimal Total{get;init;}
        public partial bool Active{get;init;}
    }
}
```

### 2. 入口

- `IReader`（読む）に加えて、書ける入口のインターフェース `ITransaction` を生成する。`ITransaction` は `IReader` を継承し、書ける表を持つ。スキーマは `I<スキーマ>Transaction`。
- すべての入口（ルートとスキーマ、読む側と書く側）に、ルートの入口を返す `Database` プロパティを生成する。ルートの入口では自分自身を返す。
- `Database` は表の名前として使えない（スキーマ内は今も予約済み。ルートにも予約を足す）。

### 3. ビュー・関数

- ビューは `ISet<行>` を返す拡張プロパティ、テーブル関数は `ISet<行>` を返す拡張メソッド、スカラー関数は値を返す拡張メソッド。本体は式1つ。
- 所属スキーマは拡張ブロックの受け手で決める。`extension(ShopDb.IPersonReader q)` のビューは、目録では `Person.<名前>`、呼び出しは `r.Person.<名前>`。
- 本体の表は、受け手がルートでもスキーマでも、自分のスキーマの表も含めて、常にルートからたどって書く（`q.Database.<スキーマ>.<表>`、ルートの表は `q.Database.<表>`）。LinqDB が常に `this.Container.<スキーマ>.<表>` で生成しているのと同じ考え方。取込の出力と文書の例はこの書き方にする。`q.<表>` と短く書くことは禁止しない。

```csharp
namespace Shop.Views{ public readonly record struct ActiveOrder(int Id,decimal Total); }
namespace Shop.Functions{ public readonly record struct CustomerOrder(int Id,decimal Total); }

public static class ShopQueries{
    extension(ShopDb.IReader q){
        public ISet<Views.ActiveOrder> ActiveOrders=>
            q.Database.Order.Where(o=>o.Active).Select(o=>new Views.ActiveOrder(o.Id,o.Total));
        public ISet<Functions.CustomerOrder> OrdersOf(int customerId)=>
            q.Database.Order.Where(o=>o.CustomerId==customerId).Select(o=>new Functions.CustomerOrder(o.Id,o.Total));
        public decimal TotalOf(int customerId)=>
            q.Database.Order.Where(o=>o.CustomerId==customerId).Sum(o=>o.Total);
    }
}
```

### 4. リレーション

- 入口への拡張メンバーとして書く。親→子は `ISet<子>`、子→親は親の行を返す。
- 両方向を同じ名前にし、引数の行の型で呼び分ける。型は具体的に書く（総称にしない）。

```csharp
extension(ShopDb.IReader q){
    public ISet<Tables.Order> FK_Customer_Order(Tables.Customer c)=>
        q.Database.Order.Where(o=>o.CustomerId==c.Id);
    public Tables.Customer FK_Customer_Order(Tables.Order o)=>
        q.Database.Customer.Single(c=>c.Id==o.CustomerId);
}
```

- 整合性を検査するものの区別と、子側の索引の扱いは未決。

### 5. 手続き

- 読むだけの手続きは `extension(<コンテナ>.IReader)`、更新する手続きは `extension(<コンテナ>.ITransaction)` のメソッドとして、`<root>.Procedures` に書く。
- 複数の文を持つ手続きは呼び出し側へ取り込めないので、FLinq が具体的な型（`Reader`・`TypedTransaction`）で本体を写したメソッドを作り、呼び出しを差し替える。式1つのビュー・関数は従来どおり取り込む。
- 名前で呼ぶ入口（Manager・Gateway 用）は、更新する手続きのとき取引を開いて呼び、成功したら確定する。C# から直接呼ぶときは、呼び出し側が自分の取引を渡し、自分で確定する。
- `out` 引数は結果の型へ畳む（例：`uspLogError(out int? ErrorLogID)` は `LogErrorResult uspLogError()`）。
- 訳せない構文を含む手続きは、別の動きへ切り替えず `NotSupportedException` にする。

### 6. 取込

- 表は `<root>.Tables` と `[Key]` の形で出す。
- ビューは、定義を LINQ へ訳せるまでは、取り込んだ時点の写しを `<root>.Tables` の普通の表として出す。元がビューだったことを示す属性は付けない。`MaterializedView` 型は出さない。訳せるようになったビューは、入口への拡張プロパティへ置き換える。
- 関数・手続きは提案設計3・5の形で出す。

### 7. 索引

決まっていること：

- 式の索引は作らない。
- 文字列の列を含む索引は、宣言に比較方法を書く。問い合わせ側が同じ比較器を書いたときだけ索引に対応づけ、違えばコンパイルエラーにする。
- 一意の指定を持てる。書き込みのとき、同じ値の行がほかにあれば例外にする。
- 索引に対応づけられない問い合わせはコンパイルエラーにする。全件走査は `FullScan` プロパティ（`r.Customer.FullScan.Where(...)`）を書いたときだけ許す。
- 「索引への対応づけ」と「ループの融合」を別の段に分ける。ベンチマークの比較は、LINQ 側が対応づけだけ有効、FLinq 側が両方有効。利用者のソースは同じ。

決まっていないこと（未決事項）：宣言の最終形、保存の形、読み取りの記録の単位。

### 8. TPC の統合

「過去設計から引き継ぐ仕様」のとおり。TPC-C の版付きの変種は今は無いので、`Exclusive` と `Optimistic` の比較は TPC-C では新規に作る。

### 9. 表示

索引の有無を、`Seamless.Management` の画面と C# エディタの両方でアイコン表示する。エディタ側の絵の表示は解析器だけでは出せず、エディタの拡張が要る。

## リスクと対策

- **B は1回で切り替える範囲が広い**：手順 B の1〜3を新旧が共存できる形で順に進め、最後に4で旧経路を消す。新方式は `Tables`、旧方式は `Records` と名前が違うので共存できる。
- **入れ子の型**：旧方式の `Records` にある、列の型として使う入れ子の型は、新方式の「列は平らな基本の型」と合わない。移し先を決める（未決事項）。
- **回収できる型**：新方式は型ごとに MemoryPack へ登録する。移植を忘れると Manager で古い定義がメモリに残る（推測）。
- **通信**：新方式の行に通信用の配置の属性と MemoryPack の読み書きを移し（B の1）、`[Key]` をクライアントから届く `Seamless.Collections` へ移した。サーバーとクライアントが同じ行の型でやり取りすることは、テンプレートの自己試験で確かめる。
- **手続きの本体の写し**：写しと元の本体が食い違わないよう、写しは毎回生成し、利用者のソースには書かない。
- **索引の未決が長引く**：A〜D は索引に依存しないので先に進める。
- **`from〜select` の本体**：取り込まれずエラーにもならない見込み。確かめて、I9（展開できなければコンパイルエラー）に合わせる。
