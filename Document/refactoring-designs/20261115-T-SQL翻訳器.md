# T-SQL を FLinq の C# へ訳す翻訳器

## 背景

- SQL Server のサンプルDB（AdventureWorks 2016〜2025・DW、Northwind、pubs、WideWorldImporters・DW）のビュー・関数・手続きが Seamless で動くことを、本物の SQL Server との自動の比較で証明したい。
- 以前の試作 LinqDB（`G:\GitHub\LinqDB`）は、この証明のために作ったものだった。2026年11月15日に調べると、次のことが分かった。
  - 翻訳器が2本あり、同じ処理を二重に実装していた。
    - 式木版：`変換_TSqlFragmentからExpression.cs`、10835行
    - C# ソース版：`変換_TSqlFragmentからSyntaxTree.cs`、11831行
  - ほかの巨大ファイルは使われていないか、ファイル全体が `#if false` で無効だった。
  - AdventureWorks のビューの検証は、翻訳器の出力ではなく手で書いた LINQ と比べていた。判定は `Debug.Assert` だけだった。
  - 再帰の WITH は自分自身を参照できなかった。UNION ALL も重複を除いていた。
  - XQuery の名前空間の宣言は扱っていなかった。
  - 関数の実装にも誤りがあった（ROUND、DATEADD のミリ秒・四半期、マイクロ秒とナノ秒の換算）。
- Seamless の今の状態：
  - 取込は、ビューを取り込んだ時点の写しにし、関数と手続きを未対応の例外にしている。
  - Gateway は、ビューの定義をインタプリタ（`Seamless.Database.Query`）で毎回解釈している。
  - 2026年11月12日に、SQL を FLinq の C# に変換してコンパイルする形へ作り直すと決めた（[機能の棚卸し](20261111-機能の棚卸し.md) 380行）。

## 利用者の決定（2026年11月15日）

- 翻訳器は Seamless に新しく作る。LinqDB は参考にするだけで、構成は作り直す。
- マテリアライズドビュー（ビューの実体化）は採用しない。`MaterializedView<TKey,TRecord>` は消す。
- 定義を訳せないビューは、取り込んだ時点の写しを普通の表として出す。訳せたビューは、読み取りの入口への拡張プロパティにする。
- 訳したビューも、仕様どおり `ISet<T>` で重複を除く。本物が同じ行を複数返すビューは、比較で「不一致」として数える。
- XQuery は SaxonCS-HE（NuGet `SaxonCS-HE` 13.1.0、net10.0 向け）を使う。ライセンスは、パッケージを取り込むときに同梱のファイルで確かめる。
- 外部サーバーへの問い合わせ（OPENQUERY・4部名）と全文検索（CONTAINS・FREETEXT・CONTAINSTABLE・FREETEXTTABLE）は、仕様上「再現できない」とする。
  - サンプルを実行するためだけに、近い動きの模擬を置く。
  - 模擬は、SQL と同じことができるかを見るためのもので、本物と同じ結果を約束しない。
  - 訳すときに「再現不可・模擬」の警告を出す。比較では「一致」に数えない。
  - これは「フォールバックを入れない」の例外ではない。黙って切り替えるのではなく、警告付きの模擬である。

## LinqDB から改める点

1. 出力は1本にする。構文木 → 束縛済みの中間表現 → C# ソース（FLinq の LINQ）。取込も Gateway の実行時も、同じ C# を使う。
2. 段ごとにクラスを分ける。
   - 構文
   - 束縛（スコープ・カタログ・名前解決）
   - SQL の型規則
   - 書き換え（CTE・PIVOT・APPLY・ウィンドウ関数を基本の演算へ落とす）
   - C# 出力

   各段は前の段の結果だけを受け取る。
3. 対応するノードだけを受け、それ以外は1か所で「未対応：構文名（行・列）」の診断にする。全ノードの空の基底クラスは作らない。
4. 組み込み関数は1関数1か所に置く（`[SqlFunction]` 属性と `SqlFunctionCatalog`）。分類は Microsoft Learn に合わせる。手で同期する関数の表は作らない。
5. 名前は英語の PascalCase にし、説明は日本語のコメントに書く。
6. 対応の度合いは「対応」「再現不可（模擬で実行）」「未対応」の3段で明示する。黙って無視する箇所は作らない。
7. 試験は本物の SQL Server と比べ、Assert で落とす。接続文字列はソースに書かず、環境変数 `SEAMLESS_SQLSERVER_TEST_CONNECTION` から読む。
8. 死んだコード（試していない分岐、コメントアウトした旧版、`#if false`）を持ち込まない。

## 段階1：翻訳器の骨組み

- 入口は `SqlViewTranslator`。ビューの定義（CREATE VIEW）と目録（`TranslationCatalog`。表・ビューの列と型、生成された C# の名前）を受け取る。
  - 訳せたときは、行の型（`<root>.Views.<スキーマ>.<ビュー>` の record struct）と、読み取りの入口 `I<スキーマ>Reader` への拡張プロパティを返す。
  - 訳せないときは、診断（コード・位置・構文名）を返す。
- 段は次のとおり分けた。
  - 構文：ScriptDom。`SqlViewTranslator.Parse` だけが構文の種類を見る。
  - 束縛：`SqlBinder`。名前と型を解決し、中間表現（`Bound*`）を作る。
  - 型の規則：`SqlTypeRules`。
  - C# 出力：`CSharpEmitter`。
- C# の名前は、取込の生成器と同じ規則で付ける（`CSharpNameScope`）。たとえば、型名と同じ名前の列は `_` とハッシュ8桁を付ける。
- 出力の形：
  - 集合の演算は `Seamless.Linq.Set`（`Where`・`Select`・`SelectMany`・`Join`・`Union`・`Intersect`・`Except`）だけを使う。
  - 値の演算は関数の部品（`SqlCompare`・`SqlArithmetic`・`SqlLike` など）を呼び、NULL と三値論理を本物に合わせる。
  - 集約と副問い合わせの中の列挙は `System.Linq.Enumerable` を静的に呼ぶ。`ISet` の `Select` は重複を除くので、集約の前に値だけを取り出すと SUM などが変わってしまうため。
  - 行は、集約が終わるまで表の行（結合ではタプル）のまま持ち回り、最後の `Select` でビューの行にする。
- 結合：
  - `=` で左右の表を結ぶ条件は、`Set.Join`（ハッシュ結合）のキーにする。
  - WHERE の条件のうち2つ以上の表にまたがるものは、それらを含む一番下の内部結合へ移す。左外部結合の NULL になりうる側へは移さない。
  - 左外部結合は `SelectMany` と `DefaultIfEmpty`、右外部結合は左右を入れ替えた左外部結合で出す。
- GROUP BY：キーの集合を作り、キーごとに元の行を集め直して集約する。文字列のキーは照合順序で等しいもの（大文字小文字の違い・末尾の空白）を同じキーにする（`SqlCollation.GroupKey`）。
- 本物との照合：
  - **一時表の照合**：2026年11月15日、SQL Server 2025 の一時表と同じデータで41問を照合し、行の集合とエラー番号がすべて一致した。照合した内容は次のとおり（`Tests/Database.SqlTranslation.Tests` の `MatchesSqlServer`）。
    - NULL と三値論理、照合順序、LIKE、IN と NULL
    - CASE・COALESCE・NULLIF
    - 整数・decimal・money の算術とその型
    - CAST・CONVERT
    - 内部・左・右・クロス結合
    - GROUP BY・HAVING・COUNT DISTINCT
    - EXISTS・IN の副問い合わせ・相関の副問い合わせ
    - UNION・EXCEPT・INTERSECT
    - 0での割り算（8134）・桁あふれ（8115）・2行を返す副問い合わせ（512）
  - **実データの照合**：訳したサンプルDBのビューを、本物のサンプルDBの表のデータで実行し、本物のビューの結果と比べる（`SampleViewsMatchSqlServer`）。2026年11月15日の結果：訳せた101個がすべて本物と一致した（不一致0・時間切れ0、全体で約3分）。途中の実行では、Northwind の9個が real の計算の違いで不一致、vIndividualCustomer（18,508行）が左外部結合の総当たりで時間切れだったが、それぞれ単精度の計算と `Set.LeftJoin` で直した。報告は試験の出力の sample-views-report.txt。
- 照合で分かった本物の型の規則（`SqlTypeRules` に反映）：
  - 整数のリテラルは、decimal との算術では桁数を精度にした decimal(n,0) として結果の型を決める。たとえば `Credit/3` の 3 は decimal(1,0) なので、結果の桁は6になる。money との算術ではこの規則を使わない。
  - money の割り算は、小数4桁で切り捨てる（250.25/3 は 83.4166）。
  - real（単精度）が混ざる算術は、単精度のまま計算する（float が混ざれば倍精度）。倍精度で計算すると、Northwind の明細の割引（real）を使う集計が 0.02 ずれた。
- 段階1で訳せないもの（診断のコード）：
  - TOP・ORDER BY・OFFSET（SQLT030・033）
  - APPLY・PIVOT・派生表（SQLT053・054）
  - XML のメソッドとユーザー定義関数（SQLT090）
  - ウィンドウ関数（SQLT091）
  - WITH（SQLT004）
  - geography などの型（SQLT010）
- 左外部結合は、ON の条件が「左右を = で結ぶもの」と「右の表だけを見るもの」に分けられるときは `Set.LeftJoin`（右側をキーで引く）で出す。右の行は Nullable にして渡し、対応の無い左の行で右が null になるようにする。それ以外の条件（左右にまたがる不等式など）を含むときは、左の行ごとに右を全部見る。
- GROUP BY の無い集約（`SELECT COUNT(*) FROM t`）は、`Set.Of(0)`（要素が1つの集合）から、絞り込んだ行の全体を集約する。表が空でも1行を返す（本物と同じ）。
- `Set.LeftJoin` と `Set.Of` は、2026年11月15日に利用者の承認で `Seamless.Linq.Set` に足した。FLinq は `Set.LeftJoin` を `System.Linq.Enumerable.LeftJoin` に下げ、Join と同じく重複を除く（`SetCallLowering`）。FLinq での展開そのものは、取込へつなぐ段階4で確かめる。

## 段階3：問い合わせの機能を広げる

- 派生表（FROM の中の SELECT）は、行を値のタプル（列は Item1・Item2…）にして FROM の1つの表として扱う。派生表は外側の問い合わせの範囲（相関）だけを見る。
- 重複を除かない派生表（GROUP BY・集約・DISTINCT・UNION の無い SELECT と UNION ALL）は、タプルの最後に元の行（`(object)(番号,元の行)`）を持たせる。同じ値の行が1つにまとまると、外側の SUM・COUNT が本物と変わるため。照合で、同じ値の明細2行を PIVOT で合計する問いが本物と違ったことから見つけた。
- PIVOT は本物と同じ意味の GROUP BY（集める列と並べ替える列を除いた列でまとめ、IN の値ごとに 集約(CASE WHEN 並べ替える列 = 値 THEN 集める列 END)）に書き換えて、派生表にする。
- varbinary から文字列への変換（`CAST(DECOMPRESS(...) AS nvarchar(1000))`）は、nvarchar なら UTF-16、varchar なら照合順序の文字コードで読む。
- xml のメソッドは SaxonCS-HE（MPL-2.0）で XQuery を評価する（関数の部品の `XmlFunctions`）。
  - value() は結果の文字列を、CONVERT と同じ変換で指定の型にする。結果が2つ以上なら 2389。
  - query() は、取り出した節の中で使わない名前空間の宣言を書かない（本物と同じ）。
  - nodes() は CROSS APPLY・OUTER APPLY の右側として扱い、左の行ごとに選んだ節（`SqlXmlNode`。同じ文書の中の位置を保つ）を右の行にする。等しさは同じ節かどうかで決める。
  - WITH XMLNAMESPACES は XQuery の先頭の宣言にして足す。読んだ文書は文字列ごとに使い回す。
  - 型付きの XML も型の無い XML として読む。sql:column・sql:variable・modify() は扱わない。
- 2026年11月15日の照合：一時表の60問がすべて一致（xml の7問を含む）。実データでは訳せた163個のうち157個が一致、不一致0。XML を使うビュー（vJobCandidate・vPersonDemographics・vAdditionalContactInfo・vProductModelCatalogDescription など）もすべて一致した。残る6個は vTargetMail（DW の6つの版）で、6万行を1万8千のグループにまとめる GROUP BY が60秒で終わらなかった。GROUP BY はキーごとに元の行を全部見直す形なので、計算量が グループ数×行数 になる（下の未決事項）。

## 段階2：組み込み関数の部品

- プロジェクト：`Seamless.Database.SqlServer.Functions`。試験は `Tests/Database.SqlServer.Functions.Tests`。
- 値は CLR の型の NULL 許容（`int?`・`string?`・`DateTime?` など）で受け渡す。
- 結果がセッションで変わる関数は `SqlSession` を受け取る。対象は DATEPART の週と曜日、DATENAME、GETDATE、USER_NAME など。
- 照合順序で結果が変わる関数は `SqlCollation` を受け取る。対象は CHARINDEX、REPLACE、UPPER、ASCII、CHAR など。
- datetime・smalldatetime などの型の精度への丸めは、翻訳器が式の型に合わせて `SqlTemporal` で行う。たとえば `DATEADD(ms,-2,datetime)` は .997 になる。
- エラーは `SqlFunctionException` で、本物と同じエラー番号を持つ。

実装した関数：
- 日付と時刻：GETDATE、GETUTCDATE、SYSDATETIME、SYSUTCDATETIME、SYSDATETIMEOFFSET、YEAR、MONTH、DAY、DATEPART、DATENAME、DATEADD、DATEDIFF、DATEDIFF_BIG、EOMONTH、DATEFROMPARTS、DATETIMEFROMPARTS
- 文字列：ASCII、CHAR、NCHAR、UNICODE、LEN、DATALENGTH、LEFT、RIGHT、SUBSTRING、LTRIM、RTRIM、TRIM、SPACE、UPPER、LOWER、CHARINDEX、PATINDEX、REPLACE、STUFF、TRANSLATE、REPLICATE、REVERSE、CONCAT、CONCAT_WS、QUOTENAME、STR、FORMAT、SOUNDEX、DIFFERENCE
- 数学：ABS、SIGN、CEILING、FLOOR、ROUND、POWER、SQRT、SQUARE、EXP、LOG、LOG10、PI、SIN、COS、TAN、COT、ASIN、ACOS、ATAN、ATN2、DEGREES、RADIANS
- 変換：日時と文字列の相互変換（style 番号つき）、float・money・decimal・bit・uniqueidentifier の文字列化、文字列から数値・bit・uniqueidentifier・バイト列への変換
- システム：NEWID、DECOMPRESS、HASHBYTES（MD5・SHA・SHA1・SHA2_256・SHA2_512）
- 権限：USER_NAME、ORIGINAL_LOGIN、IS_MEMBER、IS_ROLEMEMBER、SESSION_CONTEXT
- 集約：SUM、AVG、STRING_AGG（COUNT・MIN・MAX は型の規則で決まるので翻訳器が扱う）

本物との照合：
- 2026年11月15日、SQL Server 2025（17.0.1155.3）に Windows 認証で接続し、320件あまりの式を照合した。全件一致した。
- 照合のときは、セッションを us_english・DATEFIRST 7・DATEFORMAT mdy にそろえた。
- 照合で見つけて直した、本物の振る舞い：
  - SUBSTRING・LEFT・RIGHT の長さが負のときのエラーは、どれも 536。
  - POWER のあふれは 232。
  - DECOMPRESS に正しくない入力を渡すと 9826。
  - SOUNDEX：H と W も母音と同じく、前の子音の番号を切る（Ashcraft は A226）。先頭の文字が英字でないとき（空白を含む）は 0000。
  - CONVERT の style 127 は、datetimeoffset 以外では Z を付けない。
  - style 0・100 は datetime2 でも `Jul  1 2004  3:04PM` の形になる。style 9・13・14 の小数秒の区切りは、datetime では `:`、datetime2 では `.`。
  - float の style 0 は有効6桁の一般形式。指数が -5 以下か 6 以上のときは `1.234e-005` の形で、仮数の末尾の0を省く。
  - CHAR() はデータベースの既定の照合順序の文字コードを使う（COLLATE 句ではない）。932 では先頭バイトに当たる番号は NULL。
  - SOUNDEX・DIFFERENCE は照合順序で結果が変わる。master（Japanese_CI_AS）では、英語の名前でも違う結果になる。

実装しない関数と理由：
- 計算の仕方が公開されておらず、本物と同じ値を作れない：CHECKSUM、BINARY_CHECKSUM、RAND。
- 圧縮の結果のバイト列が本物と一致する保証が無い：COMPRESS。DECOMPRESS は一致する。
- .NET に実装が無い：HASHBYTES の MD2・MD4。呼ぶと `NotSupportedException`。
- 本物との照合がまだ：DATENAME の us_english 以外の言語、date・time・datetimeoffset の CONVERT の style 0・100。どちらも `NotSupportedException` にしている。

既知の差：
- `SQL_` で始まる照合順序の varchar は、本物では SQL 独自の並び順を使う。ここでは Windows の照合順序と同じ比較で代用している。記号を含む文字列の大小が本物と違うことがある。
- `Seamless.Database.Query` の `SqlValues`（LIKE・照合順序の比較）と、この部品の `SqlLike`・`SqlCollation` は、同じ働きの実装が2つある状態になっている。インタプリタは段階5で置き換えるので、そのときに一本化する。

## 未決事項

- GROUP BY の効率のよい形。`Seamless.Linq.Set` の今の演算では、キーごとに元の行を全部見直すしかない。`Set` に GroupBy を足すかどうか（新しい公開の演算なので利用者の判断が要る）。
