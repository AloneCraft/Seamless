# 取引を通さない表（`Set<T>`）の作り直し

2026年11月15日。Manager の照合の段階6（`20261115-Managerの設計と実装の照合.md` の6章）の設計。

## 決まっていること

- 11/15 の利用者の決定：`Set<T>` は常に並列区間を開き、操作用オブジェクトを使い回し、多くなりすぎたら止めて区間を閉じ、広げて開き直す。`db.X` の書き込みも読み取りも DB の入口を通るので、表の版（変更の回数）も DB で持てる。
- 11/15 の計測（照合の文書の「複数スレッドの計測」）：共有の棚に排他を付けて貸し出すと、スレッドを増やすほど遅くなる。スレッドごとの置き場にマルチ用を置く形なら、スレッドごとに1つ持つ形の8〜9割まで伸びる。

## 形

- `db.X` の型を Tsavorite の集合から、DB の型 `Seamless.Database.Set<TKey,TRecord>`・`Seamless.Database.Set<TRecord>` に変える（取引で書く表 `Seamless.Database.Table<…>` と対になる名前）。宣言は今と同じ `public Set<…> X=>this.Set<…>();`。
- 中では、データ本体（Tsavorite の `SetStore`・`HashSetStore`）に並列区間を常に1つ開いておく。
- 1操作は、自分のスレッドの置き場（`ThreadLocal`）のマルチ用を使う。置き場には「使用中の深さ」と「使用中の印」を持つ。操作の始めに印を立て（全体の順序を保つ書き込み）、保守中でなければそのまま使い、終わりに下げる。共有の排他は取らない。
- 同じスレッドの中で入れ子に使ってよい（走査の中で別の操作をする、など）。入れ子の内側は保守中でもそのまま進む（外側が終わるまで保守は待つ）。
- 保守（止めて広げる）：保守用の排他を取り、保守中の印を立て、全部の置き場の使用中が下がるのを待つ。全部のマルチ用を破棄して区間を閉じ（件数が確定し、索引が混んでいれば広がる）、広げる見込みの件数で区間を開き直す（メモリの表ではログも広がる）。保守中に来た操作は、保守が終わるのを待ってからやり直す。
- 保守のきっかけ：(1) 追加でログが満杯になった（Tsavorite の専用の例外 `TsavoriteLogFullException`、`OutOfMemoryException` の派生）。(2) 件数の見込みが区間を開いたときの見込みを超えた（置き場ごとの増減を一定回数ごとに足して確かめる）。どちらも見込みを今の件数の2倍にする。
- 件数：区間を開いたときの件数に、置き場ごとの増減の合計を足す（その時点の値。他のスレッドが書いている途中なら前後する）。
- 表の版（変更の回数）：置き場ごとに成功した書き込みを数え、閉じた置き場の分と合わせた合計。値が同じなら、その間に Manager・業務アプリのどちらからも書き込みが無かった。DB を開き直すと0に戻る。
- 走査（`foreach`・FLinq の `Iterate`）の間は置き場が使用中のままになる。列挙を破棄しないと保守が待ち続ける（`foreach` と FLinq は必ず破棄する）。
- DB を閉じるときは、保守と同じ手順で全部を止めて区間を閉じ、その後に今と同じくチェックポイントを書く。
- FLinq は、新しい型を `Iterate` と `Contains`・件数を持つ根として展開する。

## 守ること

- 取引・WAL・版の管理を通らず、取り消せず、障害後の復旧は保証しない（I6 は変わらない）。
- `tx`・`r` には生成しない（I1 は型の名前だけ変わる）。
- 並列区間で使う表のページが既定の 4KB だと、複数スレッドの追加が遅くなる（計測）。既定の大きさは今回は変えず、表ごとの大きさ（`TableStorage`）で広げられることを利用者向けに書く。

## 残すこと・やらないこと

- 拡張中に止まる時間の上限は決めない（未決のまま）。
- Manager の目録・行の一覧・編集に `Set<T>` を足すのは、この後の別の手順。
