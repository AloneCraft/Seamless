# 使う表だけを開く（表ごとに共用の変更の記録を当て直す）

## 背景

- 2026-11-16、別のセッション（「1116新しいDLL読み込みフロー」）が、Manager の設定では表が17個以上の DB を書けないことを見つけ、こちらへ引き継いだ（`Document/作業ツリー.md` の W04-MIGRATION-SPEED）。
- 試験 `Tests/Management.Tests/ManyTableDatabases.cs` で再現した：表17個は公開できても最初の行の書き込みで、表24個は公開の時点で `ResourceLimitException`（上限 268,435,456 バイト）。
- 利用者の指摘（11/16）：「DB に含まれる表の数だけ開くのではなく、画面に表示している表だけ開けば1つで済むのでは」。
- 利用者の指示（11/16）：先に (1) DB の上限を共通ストアへ渡す不具合の修正と、(3) Manager の DB の上限を表の数に合わせて広げる対処を入れ、この設計書を書く。

## 現状の観察

事実（コードで確かめたもの）：

- 表ごとに保存の仕組み（Tsavorite のストア）が1つある。どれも DB の共通ストア（`Seamless.Execution.Store`）の子資源として、DB の保存フォルダーの中にある。
- 表を開くと、その表の索引・ページの分のメモリを、共通ストアの予算から先に取り置く（`Seamless.Collections.Tsavorite/Stores/CollectionStore.cs` の `RequiredNativeMemory`、見積もりの式は `TsavoriteMemoryAccounting.Required`）。Manager の設定（索引 1024 バケット・ページ 1MB・ログのメモリ 16MB）では、空の表でも約15MB（試験で 14,779,520 バイト）。うち予備のページの分が約6MB、残りの内訳は確かめていない。
- 表のプロパティは、最初に読んだときに表を作る（遅延）。ただし DB は、最初の取引（読み込み専用も含む）を始める前に、全部の表を作る：`DatabaseTransactions.cs` の `EnsureSharedReady` が `EnsureTransactionSchema` を呼び、生成器が作る `EnsureTransactionSchema` は `EnsureTablesCreated`（全部の表のプロパティを読む）を呼ぶ（`Shared/Database.Generation/DatabaseContainerGeneration.cs` 459・556行）。
- 全部の表を開く理由は、変更の記録（WAL）の当て直し。WAL は DB で1本を全部の表が共用し、1件の記録 `WalEntry` は表の番号 `TableId` を持つ（`Seamless.Transactions/WalContract.cs`）。開くときに、前回の保存点（`sharedCheckpoint.Lsn`）より後の記録を全部読み、表の番号から表を探して当て直す（`TransactionCoordinator.RecoverCore` の `ResolveReplayParticipant`）。表が開いていないと当て直せない。
- 保存（`Store.Save`、`Seamless.Execution/Store.cs`）は、登録されている（開いている）子資源の状態だけを新しい保存点に書く。開いていない表を単に飛ばすと、その表の状態が新しい保存点から抜け、データを失う。前の保存点を消す子資源があると（`InvalidatesOlderSaves`）、前の保存点の記録も消える。
- Manager は DB を開くときに全部の表のプロパティを読む（`NativeRuntime.cs` の `DatabaseInstance.Open`）。DB 自身も最初の取引で全部開くので、Manager 側だけやめても変わらない。
- (1) の不具合：共通ストアの予算は DB の予算の子として、ストア自身の上限（`StoreLimits.MemoryBytes`、既定 256MB）で作られる（`Store` のコンストラクター）。`Seamless.Database` は上限を渡していなかったので、DB の上限 `ManagedMemoryLimitBytes` を上げても 256MB のままだった。

推測：

- 業務アプリでも、表が多く、ログのメモリを大きくした DB は同じ上限に当たる（既定の `MemorySize` で先取りが小さければ当たりにくい）。確かめていない。

## 過去設計から引き継ぐ仕様

- `20261112-DBアクセスモデル.md`：表の読み書きは DB の入口（取引・`IReader`）を通す。取引で書く表は WAL を通り、落ちた後に当て直せる。
- `20261115-取引を通さない表の作り直し.md`：取引を通さない表（`Set<T>`）のデータは、取引とは別の共通ストア（`<DB>/direct-v2`）にあり、WAL を通らない。本設計の当て直しの対象ではない（ただし開くときの先取りは同じ）。
- `20261115-Managerの設計と実装の照合.md`：Manager の DB は版付きの保存を使っていない（段階5で切り替える予定）。表の版（`epochs`）は版付きの保存のときだけある。
- 記憶の事実（EXP-0005）：詰め直し（Compact）はファイルを消さず、保存点が後で古いファイルを消す。マニフェストの書き出し前に強制終了すると開けなくなる。保存点を変える変更は、この順序を壊さない。

## 目的

- DB を開いても、使う表だけが保存の仕組みを開き、メモリを取り置く。表の数ではなく、同時に使う表の数でメモリが決まる。
- 開いていない表のデータを、保存・落ちた後の当て直し・WAL の切り詰めのどれでも失わない。
- Manager の行の一覧・行の編集は、表示している表だけを開く。

## 非目的

- 使わなくなった表を閉じてメモリを返すこと（後の段階。開いたままにする）。
- 取引を通さない表（`Set<T>`）の遅延の開き方の変更（すでに使うときに開く）。
- 表ごとのログのメモリの大きさの見直し（別の判断）。
- 保存の形式の互換の破棄（既存の保存はそのまま開けること）。

## 提案設計

### 1. 表ごとの「当て直し済みの位置」を持つ

- 今は保存点の WAL の位置（`sharedCheckpoint.Lsn`）が DB で1つ。これを表ごとにも持つ：表の保存の状態（`IStoreComponent.Save` が返す状態文字列、または `sharedCheckpoint` の表ごとの欄）に「この表は WAL のどの位置まで当て直したか」を書く。
- 既存の保存（表ごとの位置が無い）は、全部の表が DB の位置まで当て直し済みとみなす。

### 2. 開いていない表の状態を保存点へ引き継ぐ

- `Store.Save` に、開いていない子資源の前の状態文字列をそのまま新しい保存点へ写す仕組みを足す（名前で前の保存点から引く）。その子資源のファイルは消さない。
- `InvalidatesOlderSaves` で前の保存点を消すときも、引き継いだ子資源の状態は新しい保存点にあるので失われない。

### 3. 表を開くときに、その表の分だけ当て直す

- 表を最初に開くとき（プロパティを読む・取引の中で初めて触る）、その表の当て直し済みの位置より後の WAL を読み、その表の番号の記録だけを当て直す。
- 当て直しは取引の調停の門の中で行い、同時に走る取引から、当て直し途中の表が見えないようにする。
- 取引の中で初めて触った表は、その場で開いて当て直してから読み書きを続ける（開く時間の分、取引が待つ）。

### 3a. 「登録」と「開く」を分ける（11/16、実装の途中で分かった事実による）

- 事実：取引の調停は、最初の取引の前に全部の表が登録されていることを前提にしている。始まった後の登録は例外にする（`Seamless.Transactions/TransactionCoordinator.cs` の `Register`：「Register the complete typed schema before starting transactions.」）。
- そのため、表の登録（取引の調停への参加者の登録）は今までどおり最初の取引の前に全部行う。登録は軽い入れ物だけにし、表の保存の仕組み（Tsavorite のストア。メモリを取り置く）は、その表を初めて読み書きするときに開く。
- 当て直し（3・4）は、参加者が「保存の仕組みが開いているか」を見て、開いていなければその記録を飛ばし、開いたときに自分の分を当て直す。

### 4. DB を開くときの当て直しは、開いている表だけにする

- `EnsureSharedReady` は全部の表を作らない（`EnsureTablesCreated` を呼ばない）。WAL を読みながら、開いていない表の記録は飛ばす。DB 全体の「当て直し済みの位置」は、WAL の終わりまで進める（開いていない表の分は、その表を開くときに当てる）。
- 版付きの保存（`RecoverVersioned`）は、版の番号の採番が記録の順に依存するので、同じ形でよいか別に確かめる（未決）。

### 5. WAL の切り詰めを、開いていない表の位置で止める

- WAL を切り詰めてよい位置は、全部の表の当て直し済みの位置の最小。開いていない表に当てていない記録が残る間は、その位置より前を消さない。
- WAL が長く伸び続けるのを防ぐため、保存のときに、当てていない記録が一定量を超えた表は、開いて当て直してから保存する（その表はメモリを取り置く）。量の決め方は未決。

### 6. Manager

- `DatabaseInstance.Open` で全部の表のプロパティを読むのをやめる。
- 行の一覧・行の編集・目録の件数などで表を触ったときに、その表だけが開く。
- 公開し直すときの移行（全部の表を写す）は、表を1つずつ開いて写す。使い終えた表を閉じる仕組みは非目的なので、移行の間は開いた表の分を取り置く（必要なら (3) の上限で受ける）。

## 影響範囲

- `Seamless.Database`：`DatabaseTransactions.cs`（`EnsureSharedReady`・表の作成・当て直し）、`DatabaseVersionedTransactions.cs`、`DatabaseContainer.cs`。
- `Seamless.Transactions`：`TransactionCoordinator.cs`（表ごとの当て直し、記録を飛ばす）、WAL の切り詰め（`SharedWal`・準備付きの WAL）。
- `Seamless.Execution`：`Store.Save`（開いていない子資源の状態の引き継ぎ）。
- `Shared/Database.Generation`：生成器の `EnsureTransactionSchema`。
- `Seamless.Database.Gateway`：Gateway の共通の領域（`GatewayProfile`）の当て直しも全部の表を前提にしている見込み（確かめていない）。
- Manager：`NativeRuntime.cs`（`DatabaseInstance.Open`、移行）。
- 業務アプリ：同じ DB の DLL を使うので、開き方が変わる（表を初めて触ったときに開く待ち時間が出る）。

## 移行手順

1. （済み・11/16）共通ストアに DB の上限を渡す。Manager の DB の上限を表の数に合わせて広げる（表16個までは従来の 256MB、それ以上は 64MB＋表の数×16MB）。
2. `Store.Save` の引き継ぎ（2）を入れる。開いていない子資源が無い今の動きは変わらない。
3. 表ごとの当て直し済みの位置（1）を保存に足す。既存の保存の読み方（全部の表が DB の位置まで当て直し済み）を試験で固める。
4. 表を開くときの当て直し（3）と、DB を開くときに開いていない表を飛ばす（4）を入れる。版付きの保存は別の手順に分ける。
5. WAL の切り詰め（5）を表ごとの位置に合わせる。
6. 生成器の `EnsureTransactionSchema` を変え、Manager の `DatabaseInstance.Open` の全部の表の読み込みをやめる（6）。
7. (3) の Manager の上限の対処を残すか戻すか決める。

## テスト計画

- 表を開かずに取引・保存・開き直しを繰り返し、開いていない表のデータが残ること（保存点の引き継ぎ）。
- 表Aだけ書いて落とし（保存の前に強制終了）、開き直して表Bを使ってから表Aを開くと、表Aの書き込みが当て直されていること。
- 開いていない表に当てていない記録があるとき、WAL がその位置より前で切り詰められないこと。保存を繰り返しても、上限を超えたら表を開いて当て直すこと。
- 既存の形式の保存（表ごとの位置が無い）を開けること。
- 取引の中で初めて触った表が、当て直し済みの状態で読めること。同時に走る取引から、当て直し途中が見えないこと。
- 表100個の DB を Manager で公開し、1つの表だけを読み書きしたときの取り置きが、表1つ分程度であること。
- 既存の試験：DB の取引（`-Suite Transactions`）、Gateway（`-Suite Gateway`）、Manager の公開・行の編集。

## リスクと対策

- 当て直しの取りこぼし（データを失う）：表ごとの位置と WAL の切り詰めの最小を、試験の強制終了の繰り返しで確かめる。最初は、保存のときに当てていない記録がある表を必ず開いて当て直す（5 の量を0にする）安全側から始められる。
- 表を初めて触るときの待ち時間：記録が多いと長い。保存の頻度と 5 の量で抑える。
- 外部キー・集計の表（`MaterializedView`）：別の表を参照・更新するので、関係する表を一緒に開く必要がある見込み（確かめていない）。
- Gateway・版付きの保存：全部の表を前提にした処理が残っていないか、手順4で洗う。

## 実施の記録

- 手順1（11/16、`3bd9e028`）：共通ストアに DB の上限を渡す。Manager の DB の上限を表の数に合わせる。
- 手順2（11/16、`83852e7d`）：`Store.KeepUnopened` で知らせた名前は、開いていなくても保存のときに前の状態を引き継ぐ。
- 手順3〜5（11/16）：キー付きの表（`Table<TKey,TRecord>`）は、保存の仕組みを初めて使うときに開く（`KeyedTable.cs` の `OpenRows`）。取引の調停への登録は今までどおり最初の取引の前に行い、当て直しは保留する（`TransactionCoordinator.DeferReplay`）。開いたときに、その表の位置より後で当て終えた位置までの記録のうち、その表の分だけを当てる（`OpenDeferred`）。保存点（`SharedCheckpoint.TableLsn`）に、開いていない表とその位置を書く。WAL は、開いていない表の位置より前を消さない。対象は、素の WAL・版付きの保存なし・Gateway なし・書き込みを1つずつ通す方式（`Exclusive`）の永続の DB（Manager の DB はこれ）。ほかの条件では今までどおり全部を開く。キー無しの表と集計の表（`MaterializedView`）は今までどおり作るときに開く。試験：`Tests/Seamless.Database.Transactions.Tests/LazyTableStorageTests.cs`（保存せずに落とした後、開いていない表の記録を残して保存し、開き直して当て直されること。開いていない表はメモリを取り置かないこと）。DB の取引 124件・取引の調停 184件・Gateway 502件・Manager 28件が成功。
- 手順6：不要になった。表の入れ物を作っても保存の仕組みを開かないので、生成器の `EnsureTablesCreated` と Manager の `DatabaseInstance.Open` が全部の表のプロパティを読んでも、メモリは取り置かない。
- 注意（新しい事実）：`TableLsn` を持つ保存点を古い版の製品で開くと、古い版は全部の表を保存点の位置まで当て直し済みとみなし、開いていなかった表の記録を当てずに失う。新しい版から古い版へは戻せない。
