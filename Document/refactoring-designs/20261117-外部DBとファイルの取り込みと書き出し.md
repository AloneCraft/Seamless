# 外部DBとファイルの取り込みと書き出し（2026-11-17）

Manager から、SQL Server の DB と、表ごとのテキストファイル（CSV・zip）のデータをやり取りする。
作業の枝は `rdbms-transfer`（親 `manager-alignment`）。作業ツリーの台帳は `Document/作業ツリー.md` の W23-RDBMS-TRANSFER。

## 利用者の決定（2026-11-17）
1. 対象の製品は SQL Server だけ。読み書きの部品は製品を差し替えられる形にする（他の製品は後回し）。
2. 接続文字列の履歴は、パスワードを除いて画面の利用者ごとの保存に残す。パスワードは Manager を動かす機械の Windows 資格情報マネージャーに置き、保存するかは毎回選ぶ。
3. 取り込みで生成した C# のプロジェクトは、その DB のソースとして作業領域に残す（後で編集できる）。
4. CSV・zip の取り込みと書き出しも同じ計画で作る。DB 接続を先にする。
5. 書き出しでは、表と制約（全ての型・主キー・一意キー・外部キー・既定値・IDENTITY・CHECK）を作り、ビュー・関数も T-SQL に訳して作る。訳せないものは書き出す前に理由つきで示し、利用者が「外して続ける」か「やめる」かを選ぶ。
6. 取り込みでは T-SQL 翻訳器の段階4（取込へつなぐ）を行う。
7. 同じ名前の DB があるときの置換は、丸ごと作り直す。Seamless 側は取り込んで件数を確かめてから入れ替え、古いものを退避に残す。SQL Server 側は確認してから作り直し、消す前にバックアップを取るかを選べる。
8. ファイルの形式の既定は CSV（RFC 4180、UTF-8、1行目は列名、引用符は二重引用符、NULL は空の欄、空文字列は `""`）。画面で TSV と Shift_JIS に切り替えられる。
9. 取り込みの目的は SQL Server と同じ動きをすること。同じにならない所（訳せないビュー・関数、再現していない SQL Server の機能など）は、回避策を添えて下見と最後の報告の両方で示す。黙って代わりの動きにしない。

## 差の報告と回避策（決定9）
- 型は `Seamless.Database.Rdbms` の `CompatibilityIssue`（対象の種類・スキーマ・名前・列・差の種類のコード・何が同じにならないか・回避策の候補）と `CompatibilityWorkaround`（回避策の種類のコード・説明・下書き）。取り込みも書き出しも同じ型で返す。
- 回避策は候補として示すだけで、利用者が選んだものだけを使う。選ばれなかったものは「外した」と報告に残す。
- 今ある差の種類のコード：
  - 翻訳器の診断のコード（`SQLT…`）：そのビューは訳せないので取り込まない。
  - `NO_DEFINITION`：ビューの定義を読めない（暗号化・権限）。
  - `DEPENDENCY`：使っているビューを取り込めないので、このビューも取り込めない。
  - `SNAPSHOT`：利用者が選んで写し（表）にしたビュー。元の表を変えても中身は変わらない（残った差）。
  - `ROUTINE_BODY`：関数・手続きの中身を C# に訳していないので、呼ぶと NotSupportedException になる。
  - 訳せたが本物と同じにならない所は、翻訳器の警告（再現できない動きの模擬）を残った差として入れる。
- 回避策の種類のコード：`Rewrite`（訳せる形への書き直し方）・`ManualCSharp`（手で書く C# の下書き）・`Snapshot`（写しにする）・`FixDependency`・`ReadDefinition`。

## 段階4：取り込むビューを C# のビューへ訳す
- 生成器 `CSharpDatabaseGenerator.Generate(catalog, ViewImportOptions)` が、ビューを `IViewTranslator` で訳す。Rdbms は翻訳器を参照せず、窓口（`IViewTranslator`・`ViewTranslationRequest`・`ViewTranslationResult`）だけを持つ。SQL Server の実装は `Seamless.Database.SqlServer` の `SqlServerViewTranslator`（`Seamless.Database.SqlTranslation` を使う）。
- 翻訳器に渡す目録は、生成器が自分の付けた C# の名前（スキーマ・表・列）で作る。翻訳器の `TranslationCatalog.SchemaIdentifiers` で、生成器が付け替えたスキーマの名前を受け取る。
- 訳せたビューは `Queries/Views.cs` に、行の型（`Views.<スキーマ>`）と読み取りの入口への拡張プロパティ（`Queries.<スキーマ>Views`）として出す。生成物の `Views`（`GeneratedViewBinding`）に置き場所を返す。行は取り込まない（表の束縛に入れない）。
- 訳せないビューは取り込まない（ファイルも束縛も出さない）。写しは `ViewImportOptions.SnapshotViews` に挙げたビューだけ。訳せないビューを使うビューも取り込めないので、変わらなくなるまで訳し直す。
- 生成物の指紋に、翻訳器の版（`IViewTranslator.Version`）と写しにするビューを混ぜる。
- 取り込んだ bit の列（`Seamless.Database.SqlServer.Types.Bit`）を翻訳器が `bool?` として読めるよう、`Bit` に `bool` への明示の変換を足した。
- 指定の無い従来の生成（`Generate(catalog)` など）は、今までどおりビューを写しにする。

## 取り込みの書き込み（共通の部品）
- `Seamless.Database.Transfer` の `GeneratedDatabaseLoader`。まだ公開していない新しい領域（`DatabaseContainer.BeginUnpublishedSnapshot`）へ全部の行を書き、外部キーなどの関係をまとめて検査してから公開する。失敗したら公開しない。
  - 理由：生成したコンテナの `ImportTables` は全表を1つの取引に入れるので、変更の記録（WAL）の1回分の上限（`Transaction exceeds the WAL frame bound`）を超え、大きな DB が入らない。
  - 外部キーの順に表を並べなくてよい（全部を書いてから検査する）。
- 取り込み先の設定は `GeneratedDatabaseLoader.Options`：保存形式は canonical（公開前の領域へ書くのに要る）。メモリの上限は Manager と同じ規則（64MB+表の数×16MB）に、測った表のメモリの合計を足す（既定の 256MB では表1つで約15MB を先に取るため、表の多い DB が入らない。W04-MIGRATION-SPEED-TABLES）。
- 表ごとの保存の大きさ（`SqlServerImportSizer`）は、行を保存の形に符号化したときの長さの上限で見積もる。canonical はバイト列を1バイトごとに印付きで書くので約2倍、文字列は1文字2バイト。どの列も「2×DATALENGTH+17」を超えない。キーの無い表は行の全部がキーなので、1件はその2倍。
  - 前は SQL Server の DATALENGTH の合計で見積もっていたので、大きなバイト列の行（AdventureWorks の `Production.Document` は 47KB が符号化で 94KB）がページに入らなかった（`Entry does not fit on page`）。

## 書き出し（SQL Server へ）
- 定義の読み直し：`Seamless.Database.Transfer` の `SeamlessCatalogReader.Read(コンテナの型)` が、DB の表・列・型・キー・制約を製品に依存しない目録（`DatabaseCatalog`）に読み直す。
  - 取り込んだ表は、取り込みの生成器が残した元の形から戻す。列は `ImportedDatabaseColumn`（型名・長さ・照合順序・精度・小数部の桁）、表は `ImportedDatabaseObject` の制約の記録（主キー・一意キー・外部キー・CHECK・既定値・IDENTITY・計算列・トリガー）。
  - 主キー：取り込んだ表は元の主キーに従う（生成器は主キーの無い表を「全部の列がキー」にするが、それを主キーにしない）。C# で書いた表は `[Key]` の列。
  - C# で書いた表は、C# の型を値を変えずに持てる SQL Server の型へ対応させる（`ulong` は `decimal(20,0)`、`DateTime` は `datetime2(7)` など）。C# の `decimal` は桁が値ごとに変わるので、既定の `decimal(38,10)` で書き出す前に `DECIMAL_SCALE` として報告する。対応の無い型は `UNSUPPORTED_TYPE` で、その表は外すか型を変えるまで書き出さない。外部キーは `[ForeignKey]`。
  - 元のビューの定義は `ImportedDatabaseView`（取り込みの生成器がアセンブリに付ける）から読む。訳せずに取り込まなかったビューも、元の製品へは元の定義のまま作り直せる。
- 文：`Seamless.Database.SqlServer` の `SqlServerSchemaScript.Create(目録)`。順番は「スキーマ → 表（列・IDENTITY・既定値・計算列・主キー・一意キー）」→ 行 →「外部キー・CHECK（WITH CHECK）→ ビュー → トリガー」。外部キーと CHECK は全部の行を入れてから付ける（表の順番に頼らない）。トリガーは行を入れた後に作る。
- 実行：`SqlServerDatabaseExporter.ExportAsync`。
  - DB を用意する：無ければ作る（名前は変えられる、ファイルの置き場所を指定できる）。あれば `ReplaceExisting` のときだけ、（指定があれば）バックアップを取ってから消して作り直す。指定が無ければ止める。
  - 行は DB の読み取りの入口（`BeginRead`）から同じ時点の中身を読み、`SqlBulkCopy` で入れる（IDENTITY の値は保つ）。計算列と rowversion は SQL Server が作るので入れない。入れた後に件数を照合する。
  - ビューは元の定義のまま作る。ほかのビューを使うビューのため、作れたものがある限り残りを繰り返し試す。最後まで作れなかったビューは `VIEW_CREATE_FAILED` として報告に入れる。
- 取り込みの生成器の直し：外部キーの列の組（タプル）が JSON に書かれず `[{}]` になっていたので、名前付きで書くようにした。主キー（名前・列の順と向き・索引の種類）も制約の記録に残すようにした。
- XML スキーマコレクション（型付きの xml の列が従う形の決まり）：目録（`DatabaseCatalog.XmlSchemaCollections`、列の型の `XmlSchemaCollectionSchema`・`XmlSchemaCollectionName`・`IsXmlDocument`）、取り込みの生成器の印（`ImportedDatabaseColumn` の同じ名前の引数と、アセンブリの `ImportedDatabaseXmlSchemaCollection`）、読み直し、書き出しの文（表より先に `CREATE XML SCHEMA COLLECTION`、列は `xml(CONTENT|DOCUMENT 決まり)`）で持ち回る。
  - 理由：AdventureWorks2022 の書き出しで、`Person.Person.Demographics` を型の無い xml で作ったため、その列を XQuery で書き換えるトリガー（`iuPerson`）を作る時点で SQL Server が型の検査で断った（「'replace value of' の対象は…単純型のコンテンツを含む要素」）。
  - 取り込みでは値をそのまま持つが、Seamless で書き換えるときに形の検査をしない。これは残った差 `XML_SCHEMA` として下見と報告に出す。

## 確かめたこと
- `Tests/Database.Verification.Tests/TranslatedViewImport.cs`（本物の SQL Server が要る。`SEAMLESS_SQLSERVER_TEST_CONNECTION`、対象は `SEAMLESS_SAMPLE_DATABASES` で絞れる）：サンプルDBをビューを訳す指定で取り込み、訳したビューの結果が本物のビューの結果（重複を除いた行の集合）と一致すること、訳せないビューが回避策つきで報告されて取り込まれないことを確かめる。
- `Tests/Database.Verification.Tests/SqlServerExportRoundTrip.cs`（本物の SQL Server。対象は `SEAMLESS_EXPORT_DATABASES`、既定は Northwind と pubs）：サンプルDBを取り込み、別の名前の新しい DB へ書き出して、元と同じであることを確かめる（表ごとの全行、列の型・NULL・照合順序・IDENTITY・既定値・計算列、主キー・一意キー・外部キー・CHECK、ビューの結果）。書き出した DB は最後に消す。2026-11-17 に Northwind（表13・3308行）と pubs（表11・255行）で一致。
- 観察（既存の動き）：保存した datetime は `DateTimeKind.Utc` で戻る。SQL Server の datetime には時差の種類が無いので、比べるときは種類を見ない。値は同じ。

## Manager の取り込み（2026-11-17 設計）
- 入口：DB の木の「データベースを追加」の隣と、コマンドの一覧に「外部DBから取り込む」。開くと取り込みの文書（タブ）が出る。
- 操作はサーバーの「OS の所有者だけが使える通り道」（ローカルの名前付きパイプで所有者を確かめたもの。開発ソースの操作と同じ）に足す。接続文字列とパスワードを扱うので、ほかの利用者の接続には出さない。窓口は `IManagementTransferOperations`、対応の印は `OwnerExternalTransferV1`。
- 流れ：
  1. 接続：接続文字列（パスワードを除く）とパスワードを入れ、つないで DB の一覧を出す。パスワードを Windows 資格情報マネージャーに保存するかは毎回選ぶ（決定2）。保存した資格情報は、接続文字列のサーバー名と利用者名で引く。
  2. 下見：元の DB・取り込み先の名前・プロジェクトの保存先を選んで下見する。表ごとの行数、訳せたビュー、訳せないビュー・中身の無い関数・型付きの xml の列などの差（回避策つき）を出す。写しにできるビューは、利用者が選んだものだけ写しにする（決定9）。取り込み先に同じ名前の DB があれば「置き換える」を選ばないと進めない。
  3. 取り込み：下見の後に元の DB の形が変わっていたら止める（下見の印＝生成物の指紋）。生成した C# を DB 定義の下書きにし、確認（Preview）してから適用する。適用では、古い DB から行を写す代わりに、SQL Server の行を公開前の新しい領域へ入れ（`GeneratedDatabaseLoader`）、表ごとの件数を確かめてから公開する。置き換えるときは、古い世代をバックアップに残す（決定7。適用のバックアップと同じ場所）。
  4. 最後に、生成した C# を DB のソースのプロジェクトとして保存先に書く（決定3。新しい DB を作ったときの「専用C#プロジェクトを保存」と同じ作り方）。
  5. 報告：表ごとの行数、差と回避策（選んだもの・外したもの）、バックアップの場所。
- 進み具合：取り込みはサーバーの裏で動かし、画面は操作の番号で状態（段階・表・行数）を見に行く。
- 取り込んだ DB のコードが使う部品：bit の型（`Seamless.Database.SqlServer.Types.Bit`）と、訳したビューが呼ぶ組み込み関数（`Seamless.Database.SqlServer.Functions`）。`Bit` は SQL Server へつなぐ部品（SqlClient などの重い部品を持つ）から、組み込み関数の部品へ移す（名前空間は変えない。元の部品からは型の転送で引き継ぐ）。取り込んだ DB の成果物が SqlClient を持たずに済む。Manager の内蔵のコンパイル・下書きの SDK ビルド・DB のソースのプロジェクトは、組み込み関数の部品を参照に入れる（使わない DB の成果物には入らない）。

## Manager の取り込みの実装（2026-11-17）
- サーバー：`ExternalTransferService`（接続・下見・取り込み・進み具合）、`ManagementService.ApplyExternalImport`（外の行で新しい世代を作る適用。`NativeRuntime.Publish` の `fill`）、`WindowsCredentialStore`（資格情報マネージャー）。通り道はパイプの `externalConnect`・`externalPreview`・`externalImport`・`externalStatus`（所有者だけ）と、同居の `ConcurrentManagementOperations`。
- 画面：左の木の「外部DBから取り込む」と、コマンドの一覧の同じ名前の項目から開く窓（`外部DB取り込み.razor`）。接続文字列の履歴は `external-history.js` で、表示状態と同じ「インスタンス・利用者」の鍵でブラウザーに残す（パスワードを含むものは残さない）。
- 置き換えのとき、個人の下書きに公開していない編集があれば止める（黙って上書きしない）。
- 取り込みの進み具合はサーバーのメモリにだけある。Manager を起動し直すと消える（公開の結果は DB の履歴「Imported」と操作の記録に残る）。
- `Bit` を `Seamless.Database.SqlServer.Functions` へ移し、内蔵のコンパイル・下書きの SDK ビルド・DB のソースのプロジェクト（使うときだけ）・パッケージ一式の作成（`tools/management/New-SourcePackageFeed.ps1`）に組み込み関数の部品を足した。今ある `Work/VirtualDbFeed` には、この部品がまだ入っていない（一式を作り直すまで、取り込んだ DB のプロジェクトは手元でビルドできない）。

## 確かめたこと（2026-11-17 の続き）
- 書き出しの往復：Northwind・pubs は一致。AdventureWorks2022 は XML スキーマコレクションの直しで最後まで書き出せる（表71・760,837行）。残った違いは下の2つ。
- 試験の照合の道具（`SqlRowSet`）は、hierarchyid などの SQL Server の独自の型をバイト列で比べる（.NET の型の部品 Microsoft.SqlServer.Types を読み込まない）。

## まだ作っていないもの
- 書き出しで、利用者が定義した別名の型（AdventureWorks の `dbo.Flag`・`dbo.Name` など）を作っていない。その型を引数に使う手続き（`HumanResources.uspUpdateEmployeeHireInfo`・`uspUpdateEmployeeLogin`）が作れず、報告に `OBJECT_CREATE_FAILED` で出る。
- 書き出しで、DB の既定の照合順序を新しい DB に付けていない（`CREATE DATABASE … COLLATE`）。照合順序を列に書かない計算列（`Sales.Customer.AccountNumber`・`Sales.SalesOrderHeader.SalesOrderNumber`）が、書き出し先の SQL Server の既定（Japanese_CI_AS）になる。取り込みの生成器は DB の既定の照合順序を生成物に残していないので、残す所から直す。
- Manager からの SQL Server への書き出しの操作と画面。作りの案：下見で、表（書き出せないものは `Blocked`）・ビュー（取り込んだ元の定義があるものは元のまま作る、C# で書いたものは T-SQL へ訳していないので外さないと進めない）・差を出す。利用者が外す表・ビューを選び、同じ名前の DB があれば「作り直す」と「消す前のバックアップ（SQL Server の機械の上のパス）」を選ぶ（決定5・7）。公開中の DB は DB の鍵を持ったまま読む（読む間は同じ DB の適用を待たせる）。
- 書き出しのうち、C# で書いたビュー・関数の T-SQL への訳。
- CSV・zip の取り込みと書き出し、ファイルを落とす画面。取り込み先（既にある DB の表へ入れるのか、ファイルから新しい DB を作るのか）と、ファイルに無い表の扱い（そのまま残すか、空にするか）は利用者に確かめる。
