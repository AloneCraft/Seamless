# 関係代入（表への集合の代入）

作業ツリー：`F:\Seamless\wtr`（枝 `relational-assignment`、main 356f67bf から分岐）。
計画と利用者の回答は 2026-11-16〜17 の会話。この文書が正本。

## 目的

今までの表への書き込みは `Add`・`Remove`・添字の set の1行ずつだけだった。
これに加えて、表の新しい中身を集合の式で書けるようにする。

```csharp
db.dbo.T = db.dbo.T.Union(rows);      // 和集合：無い行だけを足す
db.dbo.T = db.dbo.T.Except(rows);     // 差集合：全列が等しい行だけを消す
db.dbo.T = db.dbo.T.Intersect(rows);  // 積集合：rows に無い行を消す
db.dbo.T = db.dbo.T.Where(x => x.IsActive); // 条件を満たさない行を消す
db.dbo.T = new(query);                // 置き換え(差分だけを書く)
tx.dbo.T = tx.dbo.T.Union(rows);      // 取引の中でも同じ書き方
```

書き込みは、全件を消して入れ直すのではなく、追加・削除・上書きの差分だけにする。

## 決定（利用者の回答）

| 番号 | 決定 |
|---|---|
| 1 | 右辺は `IEnumerable<R>` と `ISet<R>` を受ける。`IQueryable`・式木は使わない。 |
| 2 | 関係代入は `db` 側にも `tx` 側にも書ける。`db.dbo.T = …` はその1文で暗黙の取引を開いて確定する。`tx.dbo.T = …` は開いている取引の一部になる。 |
| 3 | `db` 側の1行ずつの書き込み(`Add`・`Remove`・添字の set)も残す。1回ごとに1つの暗黙の取引で確定する。手順 D の「db.X の撤去」は書き込みについては取りやめる。 |
| 4 | 取引を開いている流れで `db` 側の表に触る(読む・書く・右辺で使う)のはエラー。同じメソッドの中で見えるものはコンパイルエラー(SDB005)、見えないものは実行時の例外。 |
| 5 | 差分への書き換えは FLinq が行う。書き換えられない場所(Main・試験メソッド・ラムダ・仮想メソッドなど)では、set に届いた式の木を実行時に読んで同じ差分を求める。全消し・入れ直しはしない。 |
| 6 | 型は `Table<K,R>` / `Table<R>`。式も表す共通の基底にする(案 B)。保存された表(`StoredTable`)と取引の表(`TransactionCollection`)はその派生。 |
| 7 | 表ではない式への書き込み(例 `T.Union(rows).Add(x)`)はコンパイルエラー(SDB004)。実行されたときも例外。 |
| 8 | 書き方はできるだけ簡潔に。コレクション式(`T = [a, b]`・`T = [..q]`)、`List<R>`・`R[]`・`HashSet<R>` からの暗黙の変換、`T = new(q)`。インターフェースの変数を `T = q` と直接代入する形だけは C# の決まりで書けない。 |
| 9 | 「同じ行」は行の型の `Equals`(全列の値の比較、文字列は Ordinal、null 同士は等しい)。照合順序は扱わない。 |
| 10 | 同じ主キーで中身の違う行が残る結果(`Union` など)は主キーの違反(`PrimaryKeyViolationException`)。勝手に上書きしない。違反のときは1行も書かない。 |
| 11 | 置き換え(`new(q)`・`[..q]`・別の表)では、同じキーで中身が違う行は上書きする。`q` の中でキーが重なるときだけ違反。 |
| 12 | 代入先は集合なので順序と重複に左右されない。右辺の並べ替え・重複除去を取り除くなど、そこから言える最適化を入れる。 |
| 13 | キーの無い表も対象。行そのものをキーとする。 |
| 14 | 利用者が手で書く `db` 側の表のプロパティは partial プロパティにする。宣言だけを書き、中身は生成器が作る。 |
| 15 | 件数(`Count`・`LongCount`)は基底の `Table` に置く。取引の表と式は全件を数える(O(n))。 |
| 16 | 保存された表だけが持っていた操作(`Update`・`Merge`・`Replace`・`Remove(行)`・`Keys`・`MergeWith`)は基底に置く。 |

## 型の作り

```
Seamless.Collections(名前空間 Seamless.Database)
  Table<TKey,TRecord>            表と表の式の共通の基底。Where/Union/Except/Intersect は自分のメソッドで Table を返す。
  Table<TRecord> : Table<R,R>    キーの無い表。
  TableExpression<K,R>           式の木(内部)。
  TableAssignment                差分の適用(内部)。
  TableBuilder                   コレクション式から表の式を作る。
  TableExtensions.Remove(行)     キーの無い表でキーと行の呼び分けがぶつからないよう拡張メソッドにした。
  PrimaryKeyViolationException
  MergeResult                    Seamless.Database から移した。
Seamless.Database
  StoredTable<K,R> : Table<K,R>  保存された表(旧 Table<K,R> の実体)。
  StoredTable<R>   : Table<R>    キーの無い保存された表(旧 Table<R> の実体)。
  StoredTableExtensions          生成コードが基底の型から GetQueryRows/GetGatewayTransactionRows を呼ぶ入口。
Seamless.Transactions.Collections
  TransactionCollection<K,R> : Table<K,R>   取引の表。
```

- 基底を `Seamless.Collections` に置いたのは、`TransactionCollection`(`Seamless.Transactions.Collections`)が `Seamless.Database` を参照せずに継げるようにするため。`[Key]` と同じ前例。
- 表のプロパティの型は、`db` 側も `tx` 側も `Table`。get と set が同じ型でなければならないため(C# の決まり)。
- 読む側(`IReader`・`r.X`)は今のまま `ISet<R>`。
- `tx.X.Rows`(取引の表の FLinq 用の入口)は、基底の型からは見えない。FLinq は取引の入口の表のプロパティを見つけると自分で `Rows` へ変換するので、利用者は `tx.X` と書く。

## 差分の適用(実行時)

`TableAssignment`(`Seamless.Collections\TableExpression.cs`)。式の木の形で分ける。全部検査してから書く。

| 右辺の形(左辺と同じ表が根) | 処理 | 表の全件を読むか |
|---|---|---|
| `Union` だけ | 右の行のキーを表で引き、無い行だけ足す。同じキーで中身が違えば違反。 | 読まない |
| `Except` だけ | 右の行のうち、表にあって全列が等しい行だけ消す。 | 読まない |
| `Where`・`Except`・`Intersect` の組み合わせ | 表を1回読み、どれかの条件から外れる行を消す。 | 1回 |
| それ以外(置き換え・別の表・混ざった式) | 新しい中身をキーで集め、古い中身と突き合わせて消す・上書き・足す。 | 1回 |

## db 側の暗黙の取引

`DatabaseContainer.ImplicitTransactions.cs`。

- 取引の外で `db` 側の表に書く(関係代入・`Add`・`Remove`・添字の set・`Update`・`Merge`・`Replace`・`MergeWith`)と、1回の呼び出しを1つの暗黙の取引で確定する。確定時に外部キーを検査する。
- 暗黙の取引の中では、右辺が `db` 側の表を読むと、その取引の表を読む。
- 取引(`tx`・`BeginRead`)を開いている流れで `db` 側の表に触ると例外。
- 従来の取引(`DatabaseTransaction`)・取込中の直接書き込み・Gateway は今までの経路のまま。

## FLinq の書き換え

`Seamless.FLinq.Generator\SourceGenerator\RelationalAssignmentLowering.cs`。本体を組み立てる前に構文を書き換える。

| 書いた形 | 書き換えた形 |
|---|---|
| `T = T.Union(R1)…` | `T.AssignUnion(R1,…)` |
| `T = T.Except(R1)…` | `T.AssignExcept(R1,…)` |
| `T = T.Where(p)` | `T.AssignWhere(p)` |
| `T = new(q)`・`T = [..q]` | `T.AssignRows(q)` |

- 行の集まりの末尾の `OrderBy`・`OrderByDescending`・`ThenBy`・`ThenByDescending`・`Order`・`OrderDescending`・`Distinct()`・`AsEnumerable` を取り除く(決定12)。並べ替えの鍵を求める関数は呼ばれなくなる。統合仕様書 1.3節の「順序・重複に依存しない全件消費」と同じ考え方。
- 関係代入を含むメソッドは、`Enumerable` の呼び出しが無くても書き換えの対象にする。
- 表の型の `Where`・`Union` などを、結果を LINQ が受け取る読み取りの問い合わせでは `System.Linq` の同じ演算へ下げる(`SetCallLowering`)。
- 元データの判定：表のプロパティの型が基底の `Table` なので、プロパティを持つ型で振り分ける(取引の入口なら取引の表、コンテナ・スキーマなら保存された表)。
- 書き換えた形が型の誤りになる場合や、上の表に無い形は書き換えず、表の set が実行時に同じ規則で差分を求める。
- 取引を自分で開くメソッドは、今の FLinq の制約(本体を組み立て直せない場合は対象外)により実行時の経路になることがある。

## 制約・注意

- 手書きの partial の表のプロパティの中身は `this.Table<K,R>(static row=>row.Key)` で作る。行の型が `Key` を持たないとコンパイルエラーになる(`Tables` の行の型は生成器が `Key` を付ける)。
- `T.Union(rows).TryGetValue(…)` のように、式をキーで引くことはできない(例外)。列挙・`Contains`・件数はできる。
- `Remove(行)` は拡張メソッド(`TableExtensions`)なので、`using Seamless.Database;` が無いソースからは見えない(キーの無い表でキーと行の呼び分けがぶつからないようにするため)。`Remove(キー)` はそのまま見える。
- 置き換えは新しい中身をメモリ上の辞書に集める。非常に大きい置き換えはメモリを使う。
