# テーブル別の保存先

## 合意済みの設定

専用JSONに DB名、テーブル名、保存先の絶対パスを記述する。スキーマ付きのテーブルは `schema.table` で指定する。指定のないテーブルには従来の保存先を使う。

```json
{
  "db1": {
    "table1": "C:/db1/table1/",
    "table2": "C:/db1/table2/"
  },
  "db2": {
    "table3": "D:/db2/table3/",
    "table4": "F:/f/db2/table4/"
  },
  "db3": {
    "table5": "G:/f/db3/table5/"
  }
}
```

## 現状と実装案

取引対象のテーブルにはそれぞれ Tsavorite の資源がある。`DatabaseTransactions.cs` の `EnsureSharedStorage` がDB全体のWALと共通ストアを開き、個々のテーブルを共通ストアの子資源として登録する。保存点は `Seamless/Execution/Store.cs` がまとめて管理する。現行の公開世代バックアップは `NativeRuntime.BackupGeneration` が世代フォルダー配下をコピーする。

サーバーに配置表を渡し、テーブル資源の生成時に保存先を解決する。指定パスはテーブル専用の親フォルダーとして扱い、その配下で公開世代ごとに領域を分ける。新しい世代を準備するときは、公開中の世代のファイルを保持する。DBのWALと保存点の管理はDB単位のままとし、復旧時に保存点と各テーブルの世代が対応することを確認する。指定先の障害は、対象テーブルとパスを添えて通知する。

管理領域のバックアップには、公開世代の復元に必要な外部テーブル資源を含める。テーブルを開く箇所に加え、公開、再起動、バックアップと復元を検証する。指定あり・なしが混在するDBで複数テーブルを同じ取引で更新し、確定と異常終了後の復旧を確認する。

## 既存テーブルの扱い

初回実装は新規テーブルが対象。既存DBへの追加を含む。公開済みテーブルに異なる設定先が指定されたら確認と適用を止める。同じテーブルの名前変更やDBの再公開では、公開済みの配置を引き継ぐ。

## 実装上の境界

管理領域の `table-storage.json` をホストが読み込む。指定した親の下に世代固有のディレクトリを作る。各公開世代にテーブルと保存場所の対応を記録し、再オープン時は公開時の記録を使う。世代のWALと保存点は共通ストアに残し、Tsavoriteのテーブル子資源だけに保存先を渡す。バックアップでは外部の子資源を同梱し、復元先から同梱された実体を開けるようにする。元の設定先は記録に保持する。

- 配置の指定はホスト起動時に読み込む。ファイルの設定後にホストを再起動し、そのテーブルを含むDB下書きを確認して適用する。
- 保存先には、管理領域や別のテーブルの保存先と重ならない専用フォルダーを指定する。外部配置された世代を開くときは世代の識別子と保存先の所有記録を照合する。
- `backup` と削除時バックアップは外部のテーブル資源も同梱する。復元直後はバックアップに含まれる資源で開く。そのDBを再公開するときは、元の保存先の親配下に新しい世代を用意する。
