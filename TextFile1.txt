Plan: TPC_H テスト失敗(42/44)の原因特定と修正
Context
tests/Test.Seamless/Database/TPC_H.cs の TpchTests を実行すると 44 件中 42 件が失敗する (./tests/Test.Seamless/bin/Debug/net10.0/Test.Seamless.exe -class "*.TpchTests")。 ユーザーは「以前は匿名型がメソッドチェーン中間にあることが原因だったが、今回は治ったはず」と推測していたが、 実際には 同じ根本原因がまだ残っている ことを確認した。失敗は表面上 2 パターンに見えるが、根は 1 つ。

根本原因（確認済み）
TPC-H の Q02/Q03/Q05/Q08/Q11/Q21 等は .Join(...) を複数連鎖し、各 resultSelector が (part,partsupp) => new { part, partsupp } のような匿名型を生成する。2 段目以降の Join/Where/Select 等は、 前段が生成した匿名型を要素型とするラムダ を受け取る。

TryBuildJoinLikeFragment (Pipeline.cs:344-389) は outerKeySelector/innerKeySelector を services.BuildFunc(...) で構築する際、delegate 型 Func<TOuter,TKey> の TOuter が匿名型になる。
関数フラグメント生成12 (interceptor.cs:1743-1751) は 「ラムダの引数型に匿名型を含む」場合 TryCreateLambdaFuncFragment 失敗時に throw せず return false する （匿名型は名指しできないため delegate 型を解決できない＝コメントにも明記: "ソースが匿名型などは投げずに return false"）。
結果 BuildFunc が false を返し、TryBuildJoinLikeFragment が false、 TryBuildFragmentBackedStage (Pipeline.cs:185-186) で throw Unsupported($"method 'Join' could not be built as a Fragment-backed Chain IR stage.") → カテゴリB: Direct interception could not inline 'QxxMethod' ... Join could not be built as a Fragment-backed Chain IR stage.
カテゴリAも同根: Chain IR 構築が失敗した QxxQuery/一部 QxxMethod は、生成器が System.Linq.Enumerable への実行時委譲を含むコードにフォールバックする（SEAMLESS001/部分最適化）。 ところが「サイレントフォールバックは作らない」方針により、そのフォールバック実装を含むローカルメソッドを 外側から forwarding/inline することは禁止されており (interceptor.cs:4865)、 DirectMethod/DirectQuery の switch から c.QxxQuery() 等を呼ぶ際に Local method interception could not inline '...'. Forwarding is disabled for methods that contain System.Linq.Enumerable calls. という実行時例外を throw するコードが生成される → カテゴリA。

つまり両カテゴリとも「匿名型がメソッドチェーン中間にあると後続ステージへ展開できない」という同一の制約が原因であり、 ユーザーの想定に反してまだ修正されていない。 直近のコミット/作業中変更（SelectManyResultName 衝突回避、 && の括弧付け、using global:: 名前空間ループ）は別の不具合に対する修正であり、本件の根本原因には届いていない。

修正方針
根本対応は、本セッションで既に承認済みの設計「匿名型→ジェネリック struct record 透過置換による Full Fusion」を実装することである。 要点を再掲する：

AnonymousStructRecordRegistry: 匿名型のメンバー名列 (ImmutableArray<string>) を正規キーとして、 ジェネリック struct record（例 __Anon2_Price_Name<T0,T1>）を生成・キャッシュする。同じ形には常に同一の生成型を割り当てる。
検出・置換: Select/SelectMany/Join/GroupJoin/GroupBy の resultSelector 等が匿名型を生成する箇所 (Pipeline.cs:580 等、 311/731 の bail-out 箇所) で currentElementType を「閉じたジェネリック struct record 型名」に置換して後続ステージへ伝播する。 これにより TryBuildJoinLikeFragment の outerKeySelector/innerKeySelector が「名指し可能な型」を TOuter として受け取れるようになり、カテゴリBの BuildFunc 失敗が解消する。
Rewrite: 匿名オブジェクト生成式 new { part, partsupp } → new __Anon2_part_partsupp<...>(part, partsupp) への変換のみを行う（中間ラムダ本体のメンバーアクセスはプロパティ名一致につき書き換え不要）。 既存 AnonymousToRecordRewriter/RecordToAnonymousRewriter (OptimizeVisitor.cs:14-42) の一般化として実装する。
Restore: 終端要素型が匿名型のままの場合のみ、終端直前に __AnonK<...> → new {...} への復元 Select ステージを 合成し、既存の ReplaceAnonymousTypesWithTResult (interceptor.cs:4063-4072) に乗せる。
これにより匿名型は内部的に常に「名指し可能な struct record」として扱われ、 System.Linq.Enumerable へのフォールバック自体が発生しなくなるため、カテゴリA（forwarding 禁止）も連鎖的に解消する。 フォールバック経路は作らないというユーザー方針に従い、本設計のみで全パスをカバーする（部分実装で妥協しない）。

設計の妥当性確認（ユーザー3質問への回答）
Q1: 置換で問題はすべて解決するか → 原理的に YES。 TPC_H の全失敗は、コードベースが多数の箇所で強制する単一の不変条件 「生成コードに匿名型の型名を絶対に書かない」に帰着する。具体的には interceptor.cs:1732/1857 の delegate 保持、ReplaceAnonymousTypesWithTResult と各 Fragment の UseResultTypeParam、interceptor.cs:1747 の return false、NamedTypeAccessibilityRisk が匿名型に対し true、Pipeline.cs:311/731 の bail-out。匿名型を名指し可能な generic record struct に置換すれば、この不変条件の発火点が一斉に消滅し、 カテゴリB（Join key selector の TOuter が名指し可能に）とカテゴリA（SLE フォールバック非発生 → forwarding 禁止が無効化）が同時に解消する。 完全性の前提（必須）: 置換は匿名型の全生成点と全出口境界で漏れなく適用し、終端で復元すること／ record struct で値等価とメンバー順序を保つこと／生成 record struct を可視なアクセシビリティで出力すること。

Q2: 匿名型 delegate 呼び出しの件は削除できるか → YES（ただし対象を限定）。 AnonymousDelegateFuncFragment は 1732/1857 の 2 箇所でのみ、いずれも ContainsAnonymousType ガード下で生成され、 匿名型を名指ししないためだけに存在する。置換後はこれらのラムダが通常通りインライン化されるため、 本クラスと RequiresResultTypeParameter/UseResultTypeParam（TResult プレースホルダ機構）は dead code となり削除可能。 ただし DelegateFuncFragment（interceptor.cs:1647）は残す — これは実 ReturnType を持つ汎用 delegate 保持で匿名型専用ではない。 削除は置換が緑になった後の第2パスとして行い、差分をレビュー可能に保つ。

Q3: p => new { a = p, b = new { p } } のような入れ子も解決できるか → YES（再帰置換＋再帰復元）。 内側 new { p } → __Anon1_p<T0>、外側 → __Anon2_a_b<T0,T1> を __Anon2_a_b<TP, __Anon1_p<TP>> として閉じる。 生成式 rewrite は最内から再帰、終端 Restore は record struct→匿名型を再帰的に復元し、 ユーザーコードからは new { a = …, b = new { p = … } } が見える。 record struct の値等価は入れ子を含め匿名型の構造的等価と一致するため、GroupBy/Distinct/Equals のセマンティクスが保たれる （delegate 方式より厳密）。

実装ステップ
AnonymousStructRecordRegistry と AnonymousStructRecordInfo を新設し、 メンバー名列キー→ジェネリック struct record 定義のキャッシュ・合成ロジックを実装する。 生成した struct 定義は既存の SupportingMemberSources/JoinStaticMethods 経路 (Pipeline.cs:70) に乗せて出力する。
PipelineBuildServices に ResolveAnonymousStructRecord(ITypeSymbol, out string closedTypeName) 相当のフックを追加し、 Select/SelectMany/Join/GroupJoin/GroupBy/AggregateBy/Cast/OfType の匿名型検出・bail-out 箇所 （Pipeline.cs の 311, 580, 731 ほか）に挿入して currentElementType を置換する。
匿名オブジェクト生成式の rewrite を新設クラスとして実装し（既存 __R 用ロジックには触れない）、 interceptor.cs:4112 の TryGetLambdaExpressionBody 直後・NormalizeExpressionText 前に適用する。 入れ子対応（Q3）: AnonymousObjectCreationExpressionSyntax を最内から再帰的に書き換え、 new { a = p, b = new { p } } → new __Anon2_a_b<...>(p, new __Anon1_p<...>(p)) とする。
終端直前の Restore ステージ合成を実装し、ContainsAnonymousType が真の終端要素型に対してのみ挿入する。 入れ子対応（Q3）: record struct → 匿名型の復元は再帰的に行い、入れ子メンバーも元の匿名型形状に戻す。 record struct の値等価がそのまま匿名型の構造的等価に対応することを確認する。
関数フラグメント生成12 の「引数型に匿名型を含む場合 return false」分岐 (interceptor.cs:1743-1751) は、 置換後は到達しなくなるはず（要確認）。到達する場合は原因を再調査する。
第2パス（置換が緑になった後・別コミット）: 死蔵化する匿名型専用 delegate 経路を削除する（Q2）。
AnonymousDelegateFuncFragment クラスと、その生成箇所 (interceptor.cs:1732/1857)。
RequiresResultTypeParameter／各 Fragment の UseResultTypeParam（TResult プレースホルダ機構）。
DelegateFuncFragment（interceptor.cs:1647）は削除しない（匿名型専用ではない汎用経路）。
検証方針
まず dotnet build でジェネレータ＋テストをビルドし、生成コードに System.Linq.Enumerable への委譲が 残っていないこと（obj/Debug/net10.0/generated の TPC_H 関連生成物を確認）。
./tests/Test.Seamless/bin/Debug/net10.0/Test.Seamless.exe -class "*.TpchTests" を実行し、 44/44 が通ることを確認する（dotnet test --filter は使えない。[[linq-consume-and-fragmentcoverage]] 参照）。
既存の Intercept/System/Linq/Chain1、Chain2 系テストにも回帰がないことを同ランナーで確認する。
匿名型 Select→Where→ToList、単一メンバー匿名型、同一形状の匿名型が複数箇所に出るケースをユニットテストとして追加し、 生成コードが struct record ベースで完全フュージョンされていること、registry が型を再利用していることを確認する。
入れ子匿名型（Q3）: p => new { a = p, b = new { p } } のケースをユニットテストに追加し、再帰置換・再帰復元が正しく動くこと、 入れ子匿名型を GroupBy/Distinct のキーにしたとき値等価が保たれることを確認する。
第2パス後: AnonymousDelegateFuncFragment/RequiresResultTypeParameter 削除後も全テストが緑であること、 DelegateFuncFragment を使う非匿名 delegate ケースに回帰がないことを確認する。
