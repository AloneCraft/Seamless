## 状態の読み方

| 表記 | 意味 |
|---|---|
| Fact / 実装確認 | 現在のソース・設定・テスト定義に存在することを確認した。今回の実行成功を意味しない |
| 未実装確認 | 呼び出し経路の明示的な未実装、欠けている配線等をソースで確認した |
| 制限 / 明示対象外 | 意図した境界。自動的にバグや必須追加機能にはしない |
| 歴史的観測 / 再確認待ち | QA 記録や古い計測に記載があるが、この作業では再現していない |
| Hypothesis | 現在の根拠からの原因候補。実験前には確定しない |
| Decision / 提案 | 今後採用することを提案する判断。現行の実装保証と区別する |
| NEEDS_HUMAN | 自動確認で代替できていない操作、またはユーザーによる製品判断が残る |

今回は文書作成のための静的調査であり、ビルド、単体・統合テスト、UI 実行、SQL Server 接続、性能測定、クラッシュ実験は行っていない。既存テストの存在や過去の成功件数を、現在の受け入れ完了には使わない。

## 確定した優先方針

Q-01 はユーザー回答「1」により確定した。既存機能の正しさ・データ保全・検証の再現性を最優先で固め、その後に未実装機能と高速化を進める。計画上は `正しさ・データ保全 → 検証の再現性 → 明確な機能不足 → 性能と保守性 → 配布と移行完了` の順序を採用する。旧 API の廃止、SQL の対応範囲、UI の統廃合、対象 OS は別の判断事項として残す。

既存の Store、トランザクション、WAL、Verification、CI を「これから一式作るもの」として重複計画しない。SQL routine の実行スタブ、共通 Store に接続されていない AppendOnlyList、実装範囲から除外されている Dynamic ケース、旧 API 利用側の移行等を分けて扱う。

## 更新規則

1. Phase 着手時に HEAD、dirty 差分、対象成果物、関連テスト結果を更新する。
2. 実装変更で契約が変わる場合は、対応する機能 ID・不変条件 ID・受け入れ ID を同じ作業で更新する。
3. 既存仕様と食い違う記述は [未実装・既知問題・確認事項](05_GapsAndDecisions.md) に根拠付きで記録する。このフォルダ外の仕様書を書き換える場合は、その Phase のスコープに含める。
4. 不採用の仮説や古い性能値は現在仕様に混ぜず、必要なものだけ既存 history / backlog の証跡へリンクする。
5. Phase の終了はチェック項目の消化と証跡で決める。時間枠の終了、コンパイル成功、狭いテストの成功だけでは終了しない。
