# 00 全体像と共通ルール

## このシステムが行うべきこと

メモリに載り切らない件数のデータを、.NET の普通のコレクション・LINQ・宣言的 DB の書き方のまま、ストレージへ分散して扱えるようにする。LINQ はコンパイル時に展開して速くする。その速さと正しさを、ベンチマークと検証基盤で測り続ける。

- 【確認】README の定義：「ストレージ backed のコレクションと、コンパイル時 LINQ 書き換えを提供する .NET ライブラリ群」（`README.md:3`）。
- 【記録】承認済み再設計の方針：「本質は大規模なコレクションをストレージへ分散すること」（承認済み計画「背景」）。

## 全機能に共通する10項目

機能別文書（01〜10）は、ここに書いた項目を前提にしている。

### 1. 不変条件

1. **Persisted だけを参照した利用者に Garnet を持ち込まない。** 共通ストア（`Seamless.Execution`）を Garnet に依存させない。【確認】`README.md:18`、承認済み計画「壊してはいけない結合点」。
2. **静かなフォールバックをしない。** 展開や退避ができないときは、別の意味の処理へ黙って切り替えず、理由つきの例外や診断で知らせる。
   - FLinq：展開失敗は `LinqInterceptorFailure` を投げるコードを生成する（`FLinq.md` §12、診断 `FLINQ002`：`Seamless.FLinq.Generator/SourceGenerator/LinqGeneratorModels.cs:64-68`）。
   - 大規模 LINQ：退避が必要になった時点で通常 LINQ へ切り替えない（`docs/execution-and-database.md`「大規模LINQ」）。
   - SQL Server 取り込み：未対応の構文・型は `NotSupportedException` にする（`Seamless.Database.SqlServer/SqlServerTypeMapper.cs:30`、`SqlServerRoutineAnalyzer.cs:28`）。
3. **保存済みデータや DB を自動で移行・削除しない。** アプリ起動、スキーマ版の増加、自動削除を移行手段にしない。
   - 【確認】`AGENTS.md`「Database Change Policy」、`docs/execution-and-database.md`「旧データからの移行」、`Verification.Infrastructure/VerificationRepository.cs:14`（未対応のDBは例外で止め、自動移行しない）。
4. **等値性は2系統を混ぜない。**
   - スコープ付きクエリ・ストアの既定：シリアライズ後のバイト列の一致。
   - スコープ外で FLinq が `System.Linq` を展開するとき：元の .NET の等値性。
   - 【確認】`docs/execution-and-database.md`「等値性とCodec」、`Seamless.Collections.Tsavorite/Collections/HashSet.cs:6`。
5. **件数の正本は `long`。** `int` の `Count` は範囲外で `OverflowException`（`docs/execution-and-database.md`「Database」）。
6. **資源は所有者が必ず片付ける。** 一時フォルダは所有メタデータと排他ロックを持ち、回収は「正しい形式で、ロックを取れたもの」だけにする（`Seamless.Execution/TemporaryResourceRecovery.cs:8-14`）。

### 2. 禁止事項

- 共有ソースの `.projitems` を、対応する `.shproj` と `Seamless.slnx` への登録なしに追加・移動しない（`AGENTS.md`「Shared Project Visibility Policy」）。
- ローカル DB（例：`Work/UI/Benchmark.db`）のスキーマ変更を、起動時処理・版の増加・自動削除に任せない。変更は対象 DB へ直接行い、事前に明示バックアップを取る（`AGENTS.md`）。
- 条件分岐で症状だけを避ける、待ち時間や再試行を増やす、例外を握りつぶす、警告を隠す、を修正とみなさない（グローバル AI ルール §6）。
- Visual Studio や MSBuild が常駐している間に、同じソリューションを並列ビルドしない（`Work/QA_WORKFLOW.md` §7【記録】）。
- 性能の良し悪しを、自作の簡易計測で判断しない。基準は Worker/BenchmarkDotNet の実測（`Work/UI/Benchmark.db` または検証基盤）とする（ベンチ運用の記録）。
- 比較条件（ケース版・入力・意味論・Codec 版・測定方法・OS/ランタイム・CPU・構成）が一致しない結果どうしを比べない（`docs/verification.md`「検証スイート」）。

### 3. 前提条件

- 対象フレームワークは `net10.0`（`README.md`「対象フレームワーク」、`global.json`）。
- インターセプター（C# preview 機能）を使う。利用側プロジェクトは `InterceptorsPreviewNamespaces` に `Intercept` を含める（例：`Benchmark/Benchmark.Optimization.NoPredicatePushdown/*.csproj`）。
- 参照を含む型を保存する場合、利用者は `[MemoryPackable]` を付け、MemoryPack を自分で参照に加える（`README.md`「ファイル backed のコレクション」）。
- Windows 上での開発を前提とする（MAUI の UI は `net10.0-windows`）。
- C# の書き方は `AI_SYNTAX_RULES.md`（空白を詰める、`this.` を付ける、三項演算子を使わず if/else など）。UI コードの識別子は日本語。

### 4. 変更範囲 / スコープ

- 1回の変更は、「何を直した結果か」を説明できる大きさにする。無関係な整理を混ぜない（グローバル AI ルール §5）。
- 根本原因を直すために複数箇所の整合が必要なら、中途半端な局所修正より整合を優先する。
- コードを変えて仕様・不変条件・操作方法が変わったら、同じ作業で関連文書も直す（同 §13）。

### 5. 非対象 / Out of Scope

- 外部ライブラリ（Garnet/Tsavorite、MemoryPack、ZLinq、BenchmarkDotNet、Syncfusion）そのものの修正。
- 旧形式の保存データ（旧 Tsavorite チェックポイント、旧 UI DB、旧検証 DB）との互換。【確認】承認済み計画 決定11「保存済みデータの互換性は求めない」、`Database.md`「UI SQLite」。

### 6. 完了条件 / 成功条件（作業単位の共通条件）

グローバル AI ルール §20 に従い、次をすべて満たしたときに完了とする。

- 問題を再現した、または原因を説明できる。
- 修正前に失敗し、修正後に成功するテストか再現手順がある。
- 関連テストが通り、回帰確認をした。新しい警告・エラーを増やしていない。
- 古くなった仮説・コメント・文書を整理し、仕様・コード・テストが矛盾していない。

### 8. 移行条件（共通）

- 旧 API から新 API への切り替えは、プロジェクト群ごとに「ビルドが通り、回帰がない」状態で区切る（【記録】`Work/qa/handoff.md`「次に再開する作業」）。
- 保存形式・DB を変える場合は、新しい宛先を作ってから検証し、確認できた後で切り替える。旧データは読み取り専用のバックアップとして残す（`docs/execution-and-database.md`「旧データからの移行」）。

### 9. ロールバック条件（共通）

- 回帰（HEAD では通っていたテストの失敗、正しさの不一致、性能の `Regressed`）が出たら、その区切りの変更だけを戻し、前の「ビルドが通り、回帰がない」状態へ戻す。
- DB を変えた作業は、取っておいたバックアップへ戻す。新しい宛先を破棄し、旧データを使う。

### 10. 既知の問題 / 許容事項（全体）

- HEAD から失敗・不安定なテストがある（BUG-0006/0008/0010/0011。BUG-0005 は 2026-09-25 に解消、未コミット）。回帰判定では「HEAD と同じ失敗か」で区別する。詳細は [20](20_未実装と既知の問題.md)。
- ルート直下の仕様書（`FLinq.md`、`Collection.md`、`Database.md`、`UI.md`）と `Document/` は一部が古い。実装が正。
