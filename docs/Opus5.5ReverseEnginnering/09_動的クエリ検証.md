# 09 動的クエリ検証（Benchmark.Dynamic）

## 行うべき機能

型つきのクエリ木（Query IR）をランダムに作り、同じクエリを4つの経路で実行して意味が一致するかを確かめ、3系列で性能を測る。失敗したクエリは縮小して再現しやすくする。

| 機能 | 内容 | 状態 | 根拠 |
|---|---|---|---|
| ソース8種 | System の配列・IEnumerable・範囲・リスト・Persisted・Tsavorite、Seamless の Persisted・Tsavorite | 実装済み | `Benchmark.Dynamic.Core/SourceModel.cs:19-28` |
| 実行経路4種 | `SystemLinq`、`FLinqNoOptimizations`、`FLinqOptimized`、`ZLinq` | 実装済み | `SourceModel.cs:30-35` |
| 演算子集合 | 全ソース共通（Common）と選択ソース共通（Maximum） | 実装済み | `SourceModel.cs:37-40` |
| 乱数クエリ生成 | Seed 固定で決定的に生成 | 実装済み | `DeterministicRandom.cs`、`RandomQueryGenerator.cs` |
| 実行時コンパイル | Roslyn で1クラスへ生成し、回収可能な AssemblyLoadContext で読み込み・解放 | 実装済み | `Benchmark.Dynamic.Worker/DynamicQueryCompiler.cs`、`DynamicAssemblyLoadContext.cs:10` |
| 失敗の縮小 | 失敗の署名を保ったまま入力とクエリを小さくする | 実装済み | `QueryShrinker.cs`、`Benchmark.Dynamic.Tests/CoreQueryShrinker.cs` |
| 履歴 DB | `Work/UI/Benchmark.Dynamic.db`、スキーマ版 2、論理削除（ごみ箱） | 実装済み | `InfrastructureRecords.cs:4-6`、`Schema/001_initial.sql:23-29`、`:219` |
| 演算子の網羅 | 実在 API を「対応／能力限定／未対応」に分類し、対応分を全経路で試験（計画 Phase 9） | **一部**（46 演算子） | `OperatorCatalog.cs:68` 以降 |

未収載の演算子（【確認】FLinq の展開部品にはあるが、`OperatorCatalog.cs` に無いもの）：`AggregateBy`、`Append`、`Prepend`、`Cast`、`OfType`、`Chunk`、`CountBy`、`DefaultIfEmpty`、`Index`、`LeftJoin`、`RightJoin`、`SequenceEqual`、`Shuffle`、`Single`、`SingleOrDefault`、`SkipLast`、`SkipWhile`、`TakeLast`、`TakeWhile`、`Zip`。`GroupBy` は `ToIntGroup` として一部だけ（【推測・中】名前からの判断）。

## 1. 不変条件

1. **意味が一致しない・呼び出し先が不正・最適化が収束しないクエリは、性能を測らない**（`Benchmark.Dynamic実装計画.md` §1）。
2. **能力（Capability）の外にある演算子は、生成の前に除外する。`System.Linq` への実行時フォールバックはしない**（同上）。
3. **コンパイルの失敗を能力の判定に使わない**（同上 Phase 8 Gate）。
4. **個別のクエリの失敗は保存し、処理を続ける**（同上）。
5. **既存の FLinq の既定動作を変えない。** 大域固定点は明示指定のときだけ（[05](05_FLinqソース生成.md) 不変条件6）。
6. **履歴 DB の版が違えば書き込まない（例外）。自動移行しない。** 移行はスクリプトで明示的に行う（`DynamicDatabase.cs:86-110`、`Storage/Apply-BenchmarkDynamicMigration.ps1`）。
7. **既存の `Work/UI/Benchmark.db` とその WAL/SHM は変えない**（`Benchmark.Dynamic実装計画.md` §2）。
8. **読み込んだアセンブリは実行ごとに解放する**（`DynamicAssemblyLoadContext.cs:7-10`）。

## 2. 禁止事項

- 通常 Benchmark UI・既存 Worker・`UI.Core`・`UI.Storage` へ直接依存しない（`Benchmark.Dynamic実装計画.md` §1）。
- 既存の DB で WAL モードを切り替えない（読み手がいると読み取り専用エラーになる：`DynamicDatabase.cs:75-77`）。
- 演算子を足すとき、記号・意味・件数・順序のテストを揃えずに能力へ加えない（同 Phase 9 Gate）。

## 3. 前提条件

- Roslyn 5.3.0、ZLinq 1.5.6、Microsoft.Data.Sqlite（同 §2）。
- `FLinqIncrementalGenerator` を Worker から直接登録して使う。

## 4. 変更範囲 / スコープ

- `Benchmark/Benchmark.Dynamic.*/**`、`Benchmark.Dynamic.Tests/**`、`Benchmark.Dynamic.UITests/**`
- 演算子を足す場合：`OperatorCatalog.cs`、`QuerySourceEmitter.cs`、`CapabilityProfile.cs`、Capability/OperatorSet の版。

## 5. 非対象 / Out of Scope

- 通常 Benchmark UI の比較（[08](08_ベンチマーク基盤.md)）。
- FLinq 自体の修正（ここで見つけた不一致は [05](05_FLinqソース生成.md) で直す）。

## 6. 完了条件 / 成功条件

- 生成→コンパイル→4経路の意味検証→3系列の測定→DB 保存→UI 表示が、全8ソースで動く（計画の完了条件）。
- 決定的テストで、深い子・左右の部分木・連鎖した書き換え・固定点・意味の保存を直接確かめられる。
- 実在する演算子すべてが「対応／能力限定／未対応」に分類され、対応分が全経路で試験されている（未達）。

## 8. 移行条件

- 演算子を足すたびに OperatorSet の版を上げ、古い版で作った履歴とは比べない。
- DB スキーマを変える場合は、`Apply-BenchmarkDynamicMigration.ps1` で対象 DB へ明示的に適用する（事前にバックアップ）。

## 9. ロールバック条件

- 新しい演算子で経路間の不一致が多発し、原因が生成器側と確定できなければ、その演算子を能力から外す。
- DB 移行に失敗したら、バックアップへ戻す。

## 10. 既知の問題 / 許容事項

- 演算子の網羅が途中（上の未収載一覧）。
- 【不明】ソース8種すべてで端から端まで通ることを、最新のコードで確かめた記録は今回見つけていない。
