# 10 検証基盤（Verification）

## 行うべき機能

テスト・通常ベンチ・Scalable・Parameter Sweep・動的クエリを、同じ「計画 → 実行 → 保存 → 比較 → 再現」の流れで扱う。CLI（`seamless-verify`）と MAUI アプリは同じ `VerificationWorkspace` を使う（`docs/verification.md`）。

| 機能 | 内容 | 状態 | 根拠 |
|---|---|---|---|
| 初期化 | 検証 DB を新規作成。既存 DB は上書きしない | 実装済み | `docs/verification.md`「コマンド」 |
| 計画 | Git の差分・未追跡ファイル・参照関係・`.projitems` から対象と理由を作る | 実装済み | `Verification.Infrastructure/RepositoryInspection.cs` |
| 実行 | 計画時とソース指紋が同じことを確かめて実行 | 実装済み | `Verification.Core/VerificationRunner.cs` |
| アダプター | `dotnet-test`、`headless-benchmark`、`scalable-worker`、`parameter-sweep`、`dynamic-worker` | 実装済み | `Verification.Infrastructure/*Adapter.cs` |
| 比較 | 基準（baseline）と候補を比べ、`Passed`/`Regressed`/`Incompatible`/`Incomplete`/`Inconclusive`/`CorrectnessFailure` | 実装済み | `Verification.Core/VerificationModels.cs:4`、`VerificationComparison.cs:4-52` |
| 基準の固定 | 全ケース成功の run だけを明示的に基準にする | 実装済み | `docs/verification.md` |
| 再現・再開・縮小 | `replay`・`resume`・`shrink` | 実装済み | `docs/verification.md`、`DynamicShrinkVerification.cs` |
| 異常終了の扱い | 所有者のいない `run.lock` を見つけたら run と実行中ケースを `Interrupted` にする | 実装済み | `docs/verification.md`「異常終了と再現性」 |
| CI | 通常 CI と、手動・夜間の full 計画 | 実装済み | `.github/workflows/dotnet-ci.yml`、`verification.yml` |
| 旧性能ゲートの整理 | `BenchmarkPerformanceGate.cs` と `Benchmark.Headless/PerformanceGate*` は旧互換のためだけに残っている | **未整理**（削除の判断待ち） | `docs/verification.md`「旧性能ゲート」 |

## 1. 不変条件

1. **検証 DB を自動で作らない・移行しない。** 未対応の版は例外で止める（`Verification.Infrastructure/VerificationRepository.cs:14`、`:29`）。
2. **計画の版は1だけを受け付ける**（`Verification.Core/VerificationRunner.cs:9`）。
3. **条件（ケース版・入力ハッシュ・意味論・Codec 版・測定方法・OS/ランタイム・CPU・構成）が一つでも違えば `Incompatible`。性能を比べない**（`VerificationComparison.cs:8`）。
4. **結果のダイジェストが違えば、性能とは別に `CorrectnessFailure`**（`VerificationComparison.cs:14`）。
5. **性能ケースは有効な測定が各5回以上ないと `Inconclusive`**（`VerificationComparison.cs:39-42`）。
6. **中央値が許容劣化率（既定 5%）を超えたら `Regressed`**（`VerificationComparison.cs:4`、`:52`）。
7. **容量スイープは最大成功件数と失敗種別で比べる**（`VerificationComparison.cs:30`）。
8. **基準は成功しただけでは更新しない。`baseline` を明示したときだけ切り替える。** 校正値は本測定として保存しない（`docs/verification.md`）。
9. **時間枠に入らなかったケースは `NotRun`/`Cancelled` のまま。成功にしない**（同上）。
10. **`changed` で所属を特定できない変更は、狭い対象を推測せず共通スイートを選ぶ**（同上）。
11. **Dynamic の replay は、保存した `replay-request.json` の SHA-256 を照合してから使う。** 改変、成果物ルート外へのパス、異なる失敗署名は拒否する（同上）。
12. **ホストが違う run は比較不可。** 一般のホステッド CI の結果を固定性能基準に流用しない（同上「CIと固定性能環境」）。

## 2. 禁止事項

- 条件の違う結果を比べて「速くなった／遅くなった」と判断しない。
- 失敗を含む run を基準にしない。
- 大きな成果物（ログ・生成コード・再現入力）を SQLite に直接入れない。`Work/Verification/Artifacts/<run-id>/` に置き、相対パス・SHA-256・長さで参照する（`docs/verification.md`）。
- 旧性能ゲート（固定 run ID、11 対象、N=4096）を新しい判定に使わない（同上「旧性能ゲート」）。

## 3. 前提条件

- 検証 DB の正本は `Work/Verification/Verification.db`（【記録】2026-09-12 に初期化済み、run 6 件）。
- 各アダプターの対象（テストプロジェクト・Worker・Headless）がビルドできること。

## 4. 変更範囲 / スコープ

- `Verification.*/**`、`Verification.Tests/**`、`.github/workflows/verification.yml`

## 5. 非対象 / Out of Scope

- 各アダプターが呼ぶ対象そのもの（ベンチ本体、Worker、テスト）。
- 固定性能環境の用意（CPU と条件が固定されたマシン）。

## 6. 完了条件 / 成功条件

- 変更ごとに `plan --suite changed` → `run` で回帰を確かめられ、結果が DB と成果物に残る。
- 性能の基準 run が固定環境で作られ、候補と条件一致で比べられる。
- 旧性能ゲートの扱い（削除か残すか）が決まっている（未決）。

## 7. 検証項目 / 受け入れ条件

| 確かめること | 手段 |
|---|---|
| 比較の判定規則 | `Verification.Tests/VerificationComparison.cs` |
| プロファイル | `Verification.Tests/VerificationProfiles.cs` |

| 実行と中断 | `Verification.Tests/VerificationRunner.cs`、`VerificationWorkspace.cs` |

## 8. 移行条件

- 旧性能ゲートから新しい判定へ移す場合：Headless と通常 UI の性能ゲートを使っている箇所をなくしてから削除する。旧 run（249 など）との比較が要らないことをユーザーに確かめる。
- 検証 DB の版を上げる場合：新しい DB を `init` で作り直す（自動移行しない）。

## 9. ロールバック条件

- 比較規則の変更で、既存の基準との判定が説明できない形で変わったら、規則の変更を戻す。

- MAUI アプリは Windows 専用。
