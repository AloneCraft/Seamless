# 30 実装計画（優先順位つき）

## 優先順位の決め方

上ほど先に行う。

1. **正しさと後始末**：データを失う、DB を閉じられない、など。
2. **回帰を判定できる状態**：テストが最後まで走り、既知の失敗が一覧になっていること。後のすべての Phase の検証がこれに依存する。
3. **承認済みで途中の再設計の完了**：新旧 API が並んでいる状態は二重保守になり、誤用を生む。
4. **不変条件を破っている可能性がある箇所**：スコープ付きクエリの暗黙の全件メモリ処理。
5. **検証の網羅と性能**。
6. **新機能**：SQL Server のルーチン実行。
7. **整理と改善**。

## Phase 1：DB を正しく閉じられるようにする（BUG-0007 → BUG-0005）

> **状態：完了（2026-09-25、実行枠 QA-RW-20260925-01）。修正は未コミット。**
> - 原因（確定）：終端の `Compute(TEnum source)` への値渡しで、内側の列挙子を作ったコピーが破棄されなかった。生成器の `Compute` を参照渡しにし、インライン経路を try/finally にした（生成器 26 ファイル）。
> - 検証：新規テスト7件（修正前 FAIL → 修正後 PASS）、Database 群 136/136 と正常終了、`Test` 全体 1598/1606（残り8件は無関係の BUG-0010・BUG-0011）、Linq の FLinq 5フレーバーと `Execution.Tests` は HEAD と同じ失敗の組、性能は変化なし（幾何平均 0.999）。
> - 証拠：`Work/qa/artifacts/BUG-0007/`。

### 1. 不変条件
- トランザクションか読み取りセッションが残っている間は `Dispose` できない、という検査は残す（`Seamless.Database/DatabaseContainer.cs:707`）。
- FLinq で展開したコードは、元の `System.Linq` と同じ時点で列挙子を破棄する。
- WAL の順序（書く→flush→反映）は変えない。

### 2. 禁止事項
- `Dispose` の検査を外す、例外を握りつぶす、テストの待ち時間を伸ばして終わらせる。
- 原因を確定しないまま、DB 側で読み取りセッションを強制的に解放する。

### 3. 前提条件
- Q-002 が「直す」。
- 再現手順：`Work/qa/artifacts/BUG-0005/TpchDisposeDiagnostic.cs.txt`（`container.TotalAccountBalance()` の後に `Dispose`）。foreach で同じ合計を取ると起きないことが分かっている。

### 4. 変更範囲 / スコープ

- 原因が DB 側なら：`Seamless.Database/Table.cs`（`GetEnumerator`、読み取りゲート）。
- 回帰テスト：`Test/Seamless/Database/` と `Test/SourceGenerator/`。

### 5. 非対象 / Out of Scope
- 共通ストアへの移行（Phase 4）。
- 集計の性能改善。

### 6. 完了条件 / 成功条件
- 再現テストが修正前に失敗し、修正後に成功する。
- `Sum` 以外のスカラー終端（`Count`、`LongCount`、`Min`、`Max`、`Average`、`Any`、`All`、`First`、`Aggregate`）でも、`Table` をソースにしたあと `Dispose` できる。
- `Test/Test.csproj` の Database 群が最後まで終了する（BUG-0005 の解消）。

### 7. 検証項目 / 受け入れ条件

## Phase 3：新 API を仕上げる（互換を壊さない追加・内部変更）

### 1. 不変条件
- [02](02_Tsavoriteコレクション.md)・[03](03_Persistedコレクション.md) の不変条件すべて。特に：等値の既定はバイト一致、件数の正本は `long`、索引拡張は並行中に行わない、保存は明示保存だけ。
- 既存の利用側（旧 API）のビルドと挙動を変えない（壊す変更は Phase 4 へまとめる）。
- FLinq が前提にしている型名・メンバー（`HashSet`、`Dictionary`、`Iterate`、`.Count`、`.Contains`、`AsSpan`）を保つ。

### 2. 禁止事項
- この Phase で公開 API の署名を壊さない（`TryAdd` の戻り値、辞書の型引数、型名の変更は Phase 4）。
- 全件をメモリへ集める経路を新しく足さない。

### 3. 前提条件
- Phase 2 の既知失敗の一覧と基準 run。
- 最小サイズのテストを `TsavoriteTuning`（`internal`）で書ける状態。

### 4. 変更範囲 / スコープ
- Tsavorite：`HashSet` に `IReadOnlySet<T>` を実装（U-06）、誤った並行使用（同時に2つの操作が入ること）を Release でも安価に検出して例外（U-07）。作成スレッドとの一致では判定しない（DB は1つの操作用オブジェクトを直列化のもとで別スレッドから順に使うため）、辞書生成を静的なジェネリック分岐へ（U-08）。
- Persisted：`CreatePersistedAppendOnlyList`（U-09）、辞書 `Compact` と `SerializedList.Rewrite` を逐次化（U-09）、固定長リスト生成のリフレクション除去（U-09）、`SerializedSet<T>`/`SerializedDictionary` の不要な `struct` 制約の削除（BUG-0004）。
- テスト：標準コレクションとの差分テスト（同じ操作列を両方に流す）、メモリ上限の小さい環境での Compact。

### 5. 非対象 / Out of Scope
- 改名・旧 API 削除・利用側の移行（Phase 4）。
- 比較子の指定（保存形式の設計が要るので Phase 4 の段階3d と一緒に行う）。
- Scoped 系（`ScopedByteIndex`、`ScopedStoredSequence`）。

### 6. 完了条件 / 成功条件
- 上の各項目が実装され、修正前に失敗するテストが修正後に通る。
- 並行使用の検出は、操作ごとに原子的な出入りの記録1組程度の費用で済む（ベンチで悪化が 5% 以内）。
- DB（`Seamless.Database`）のように、直列化のもとで別スレッドから順に使う場合は例外にならない。
- 辞書 `Compact` が、ストアのメモリ上限より大きい件数でも上限内で終わる。

### 7. 検証項目 / 受け入れ条件
- `Test/Seamless/Stores/StoreExtensions.cs`、`Test/Seamless/Persisted/StoreExtensions.cs`、`Test/Seamless/Tsavorite/HashSet.cs`。
- 追加：`IReadOnlySet<T>` 経由の関係演算、2スレッドからの同時操作で例外・別スレッドからの順次操作は成功、AppendOnlyList の保存・復元、大量件数の Compact。
- 回帰：Phase 2 の一覧と同じ結果。
- 性能：`seamless-verify run --suite benchmark` で Tsavorite・Persisted の代表ケースを基準と比べる。

### 8. 移行条件
- 追加だけなので利用側の移行は不要。新しい API を使うのは新しいテストだけ。

### 9. ロールバック条件
- 並行使用の検出で既存テストが落ちたら、まず本当に同時に使っているかを確かめる。誤用ならテスト側を直す。順次使用を誤検出したなら検出の変更を戻す。

### 10. 既知の問題 / 許容事項
- Q-004 の制約はそのまま。
- 旧 API は Phase 4 まで残る（二重保守の期間）。

## Phase 4：一括移行と旧 API の削除（段階3b・3d・5）

承認済み計画の決定11（旧 API は一括で置き換える）と段階5 に従う。1つの作業枠に収まらないので、**プロジェクト群ごとに「ビルドが通り、回帰がない」状態で区切る**。順序は DB → LINQ → テスト・ベンチ。

### 1. 不変条件
- WAL→反映→checkpoint の順序（`DatabaseContainer.cs`）。
- FLinq の型名照合（`HashSet`、`Dictionary`）とネイティブ走査への展開。
- 各区切りでビルドが通り、Phase 2 の一覧以外の失敗がない。
- Persisted だけを参照した場合に Garnet を必要としない。

### 2. 禁止事項
- 保存済みデータを自動変換しない（互換は求めない：決定11）。
- 旧 API を `[Obsolete]` のまま長く残さない（一括置き換えの方針）。
- 最小サイズを使うテストを、公開 API の引数で最小サイズにしない（`internal` の `TsavoriteTuning` へ移す）。
- 共有ソースを動かすとき、`.projitems`・`.shproj`・`Seamless.slnx` の同時更新を忘れない。

### 3. 前提条件
- Phase 3 完了。
- 移行対象の棚卸し（2026-09-25：旧 `Tsavorite.Store.Create(` 49 ファイル、Persisted 旧静的 API 46 か所。2026-09-19 の記録：デバイス直渡し 90、番号指定の保存・復元 92、型名 57）。
- VS・MSBuild が常駐している場合は並列ビルドしない。

### 4. 変更範囲 / スコープ
- **API の破壊的変更**：`HashSetStore<T>`→`HashSet<T>.Store`、`DictionaryStore<K,V>`→`Dictionary<K,V>.Store`（U-02）、辞書の型引数を2つに（U-03）、比較子の指定（U-04）、`TryAdd` を `bool` に・容量超過は専用例外（U-05）。
- **旧 API の削除**：設定値 struct の `Store`、多数の `Create`、`IDevice` を受け取る公開 API、公開 `TsavoriteKV` フィールド（U-02）、Persisted の静的 `Store.Create*`/`CreateTemp*`（U-09）。セッションまわりを作り直し、BUG-0001・BUG-0002 を解消。
- **利用側**（U-01）：`Seamless.Database/DatabaseContainer.cs:364-554` と `DatabaseContainerOptions`（Index/Page/Segment/Memory を上限へ）、`Seamless.Linq`（`ProviderEnumerators.cs`、`ProviderValueEnumerable.cs`、`Contains.cs`、`DiskLookup.cs`）、`Tests/Seamless.TestKit/HashSetStrategy.cs`、`Shared/Common/TestInfrastructure/{TsavoriteBase,PersistedBase}.cs`、8フレーバーの `Route.cs`、`Shared/Tsavorite.Collections/Stress/*`、Scalable の `Bases.cs`、`Benchmark.Dynamic.Worker/SourceFixtureFactory.cs`。
- **FLinq**：型名は変えないが、生成コードが前提にするメンバーが残ったかを確かめる。Persisted の件数方針で `.Count` を変える場合は Persisted ルートの生成を直す。
- **文書**：`README.md` の Collections 節、`Collection.md`（新 API で書き直す）、`Document/Code/Basic/{ModuleBreakdown,LayerMapping}.md`、`docs/execution-and-database.md`。

### 5. 非対象 / Out of Scope
- 旧形式の保存データの変換。
- Tsavorite の並行時の索引拡張の制約の解消（Q-004）。
- キーつきレコードの Codec（U-17、Phase 8）。

### 6. 完了条件 / 成功条件
- リポジトリ内に旧 API の参照が無い（`Tsavorite.Store.Create(`、`.Create<T>(logDevice,objDevice)`、Persisted 静的 `Store.Create*` の検索で0件）。

- 規模：`Test.Scalable.*` で、メモリ上限を超える件数（例：1,000万件）の追加と `Contains`。プロセスのピークメモリが上限内、ディスク上限超過で例外。

- 性能：`seamless-verify` の benchmark スイートで Tsavorite・Persisted の代表ケースを基準と比べる（同条件だけ）。
- 結果は run ID つきで記録する。

### 8. 移行条件
- 区切り1：Tsavorite/Persisted ライブラリの API 変更＋ DB の移行。ビルドと DB テストが通れば次へ。
- 区切り2：LINQ（`Seamless.Linq`）と FLinq の確認。LINQ の8フレーバーが通れば次へ。
- 区切り3：テスト基盤（`TestKit`、`Shared/Common/TestInfrastructure`、`Route.cs`、Stress）。
- 区切り4：ベンチ（Scalable、Dynamic の `SourceFixtureFactory`、Parameter Sweep）。
- 区切り5：旧 API の削除と文書の更新。
- 保存済みの DB・コレクションは作り直す。

### 9. ロールバック条件
- 区切りの中で回帰が出たら、その区切りの変更だけを戻し、前の区切りの状態へ戻す。
- DB の代表クエリの結果が一致しなければ、区切り1を戻す。
- 基準は Phase 3 完了時のコミット。

### 10. 既知の問題 / 許容事項
- Q-004 の制約（辞書代入後の O(n)、並列中の索引拡張なし、`%TEMP%`）。
- 比較子を指定した場合のディスク上の表現は、この Phase の最初に設計を決める（未設計）。
- ベンチの過去の実行 ID との比較は、ストアの作り方が変わるので同条件にならない場合がある。

## Phase 5：スコープ付きクエリの暗黙フォールバックを止める

### 1. 不変条件
- 退避が必要になったら、通常 LINQ へ暗黙に切り替えず理由つきで失敗する（[04](04_LINQランタイムと大規模LINQ.md) 不変条件7）。
- 既存の演算子の結果と順序（安定ソート、初出順のグループ、外側順の Join）を変えない。

### 2. 禁止事項
- 解析器のエラーを抑止可能にして回避させない（既存診断は `NotConfigurable`）。
- 新しい演算子を、通常 LINQ との一致テストと予算超過テストなしに公開しない。

### 3. 前提条件
- D-06 の回答。
- Phase 2 の基準。

### 4. 変更範囲 / スコープ
- 禁止：`Seamless.Linq.Analyzers` に「`ScopedQuery<T>` に対する一覧外の `System.Linq` 呼び出し」を検出する診断を追加する（まず警告、利用箇所がなくなったらエラー）。
- 実装（必要なものから）：`GroupJoin`、`LeftJoin`、`RightJoin`、`ToLookup`、`Reverse`/`Last`（ToStorage 経由の逆順読み）、集計（`Sum`/`Min`/`Max`/`Average`/`Aggregate` は退避不要の逐次なので明示メソッドとして追加）。
- `Seamless.Linq/Scoped*.cs`、`DiskLookup.cs`、`Execution.Tests/ScopedQuery.cs`、`docs/execution-and-database.md`。

### 5. 非対象 / Out of Scope
- スコープ外の FLinq の意味。
- 並列クエリ。

### 6. 完了条件 / 成功条件
- 一覧外の演算子を `ScopedQuery<T>` に使うと、コンパイル時に診断が出る。
- 追加した演算子が、通常 LINQ と同じ結果・順序を返し、予算超過の入力で `ResourceLimitException` か正しい結果になる。
- 使える演算子の一覧が文書にある。

### 7. 検証項目 / 受け入れ条件
- 解析器のテスト（正例・負例）。
- 演算子ごとに：通常 LINQ との一致、順序、予算超過、キャンセル、スコープ破棄後の例外。
- `Execution.Tests` 全体。

### 8. 移行条件
- 診断は警告で入れ、リポジトリ内の該当箇所を直してからエラーへ上げる。

### 9. ロールバック条件
- 追加演算子で通常 LINQ との不一致が出たら、その演算子を外し、診断の対象（禁止）へ戻す。

### 10. 既知の問題 / 許容事項
- `ToList`/`ToArray` の予約量は推定値のまま。

## Phase 6：検証の網羅と性能

### 1. 不変条件
- 意味が一致しないクエリは性能を測らない。能力外の演算子は生成前に除外する（[09](09_動的クエリ検証.md)）。
- 性能は同条件・5回以上・中央値で比べる（[10](10_検証基盤.md)）。
- FLinq の既定の意味を性能のために変えない。

### 2. 禁止事項
- 自作の簡易計測で性能を判断しない。
- 却下済みの最適化候補を同じ仮説で繰り返さない（`FLinq-Optimization-Candidate-Backlog.md` の規約）。
- `AggressiveOptimization` をファイル単位で一律に付けない。

### 3. 前提条件
- Phase 2 の基準 run。Phase 4 以降ならストアの作り方が変わっているので、基準を取り直す。

### 4. 変更範囲 / スコープ
- Dynamic：未収載の20演算子（`AggregateBy`、`Append`、`Prepend`、`Cast`、`OfType`、`Chunk`、`CountBy`、`DefaultIfEmpty`、`Index`、`LeftJoin`、`RightJoin`、`SequenceEqual`、`Shuffle`、`Single`、`SingleOrDefault`、`SkipLast`、`SkipWhile`、`TakeLast`、`TakeWhile`、`Zip`）を「対応／能力限定／未対応」に分類し、対応分を追加（U-13）。`Shuffle` は乱数を使うので「能力限定」の候補。
- FLinq の性能：劣位の行を原因別（測定方式・実装）に分け、実装が原因のものだけを直す（U-18）。

### 5. 非対象 / Out of Scope
- 計測方式の変更（変える場合は [08](08_ベンチマーク基盤.md) の移行条件に従い、ユーザーの承認を得る）。

### 6. 完了条件 / 成功条件
- 実在する演算子すべてが分類され、対応分が全経路で試験されている。
- FLinq が劣位の行が、原因の説明つきで一覧になっている。

### 7. 検証項目 / 受け入れ条件
- 演算子ごとに記号・意味・件数・順序のテスト（計画 Phase 9 の Gate）。
- `seamless-verify run --suite dynamic`、`--suite benchmark`。

### 8. 移行条件
- 演算子を足すたびに OperatorSet の版を上げる。古い版の履歴とは比べない。

### 9. ロールバック条件
- 新しい演算子で経路間の不一致が多発し、原因が確定しなければ、その演算子を能力から外す。
- 性能改善で意味テストが落ちたら戻す。

### 10. 既知の問題 / 許容事項
- 1行の再測定ノイズは ±21% 程度ある（【記録】）。比率だけで行を選ばない。
- `.NET 12` を対象にすると `BenchmarkWorkerRuntime.cs:10-11` の `#error` で止まる（意図的）。

## Phase 7：SQL Server ルーチンの実行

### 1. 不変条件
- 訳せない構文があれば、ルーチン全体を明示的な未対応にする（部分的に訳して違う結果を返さない）。
- 生成コードの署名（`TableFunction<T>`・`ScalarFunction<T>`・`StoredProcedure<T>`）を変えない。
- 取り込みの安全性（staging→検証→公開、backup を消さない）。

### 2. 禁止事項
- 未対応の型・構文を別の意味へ暗黙変換しない。
- 副作用のあるルーチン（`INSERT`/`UPDATE`/`DELETE`/`MERGE`）を、トランザクションと WAL を通さずに実行しない。

### 3. 前提条件
- D-07 の回答。
- Phase 4 完了（DB が新しいストアで動いている）。

### 4. 変更範囲 / スコープ
- `Seamless.Database.SqlServer/SqlServerRoutineAnalyzer.cs`（関係代数の操作列を詳しくする）、`Seamless.Database.Rdbms/RelationalAlgebra*.cs`、`CSharpDatabaseGenerator.cs:190-241`（スタブを実行コードへ）。
- テスト：`Test/Seamless/Database/SqlServer/*`、サンプル DB を使った結果比較。

### 5. 非対象 / Out of Scope
- 動的 SQL（`EXEC` 文字列）。
- トリガーの実行。

### 6. 完了条件 / 成功条件
- D-07 で決めた範囲のルーチンが C# で実行でき、サンプル DB で SQL Server と結果が一致する。
- 範囲外のルーチンは、今までどおり呼び出し時に明示的な例外になる。

### 7. 検証項目 / 受け入れ条件
- ルーチンごとに SQL Server との結果比較（行・順序の扱い・NULL）。
- 取り込みの統合テスト（`DatabaseToolImportIntegrationTests.cs`）。

### 8. 移行条件
- 取り込み済みの DB は再生成・再取り込みする。

### 9. ロールバック条件
- 結果が一致しないルーチンの種類は、スタブ（明示的な例外）へ戻す。

### 10. 既知の問題 / 許容事項
- `sql_variant` など未対応の型は残る。
