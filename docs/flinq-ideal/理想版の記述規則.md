# 理想版の記述規則

手書きの理想ループ版(`Benchmark.System.Linq.Enumerable.*.Ideal` など)は、FLinq の出力が理論上最良かを測る物差しである。次の規則で書く。

## 目的と位置づけ

- 演算子×ソース種別ごとに「人が書く素直な最速ループ」を書き、FLinq・ZLinq と同じ行に並べて比べる。
- FLinq と同じ前提の下での下限になるよう書く。FLinq のほうが確実に速い行は、理想版の不備として理想版を直す。

## ベンチの枠は FLinq と同一にする

- 反復回数(`IterationCount`)、ソースの取得(`srcCount`・`src2Count`・`srcOne`・`srcMinusPlusCount`・`srcNestedCount`)、順序依存ベンチの `ExecuteOrderDependent(() => this.X_Impl())` の包み、`consumer.Consume` の呼び方は `Shared/Linq.Enumerable/Base.cs` と同じにする。
- 理想化するのは `X_Impl` の本体だけ。定数と補助関数(`Number`・`Mod` など)は `IdealBase.cs` に写し、写しのずれはテストで検査する。
- メソッド名と具象型の直接の基底型名(`Array<T>`・`List<T>`・`IEnumerable<T>`)は既存と同じにする。行の突き合わせに使われる。

## 意味は System.Linq と揃える

- 要素はすべて処理する。ラムダの本体は System.Linq と同じ回数・同じ順で評価する(例: 配列・List の `LastOrDefault(predicate)` は System.Linq と同じく末尾から評価する)。
- 例外(空の `First` など)、安定ソート、集合演算の出力順、グループの初出順を揃える。結果ダイジェストが ZLinq と一致することをテストで検査する。

## 使ってよいもの・いけないもの

- 使ってよい: BCL の公開 API(`Array.Sort`・span の `Sort`、容量指定の `HashSet`/`Dictionary`、`CollectionsMarshal`、`MemoryExtensions` の検索・比較、`Vector<T>`、`ArrayPool`)。
- 型による特殊化は `int` などのプリミティブ型だけ(`typeof(T)==typeof(int)`)。ベンチ固有の型(`ClassInt32`)向けの特殊化はしない。
- ソースの形から自明に分かる値(配列・List の長さと添字、Range の個数・範囲・添字・値が一意で昇順であること)は使ってよい。Range 同士の集合演算・等値結合は区間の計算にしてよい。値の集計(合計・平均・述語付きの件数など)は要素を回して求める。IEnumerable 起点では、静的な型から分かる以上の実行時の型判定はしない(例外: 演算子そのものが判定である `TryGetNonEnumeratedCount`)。
- 使わない: System.Linq・ZLinq・Seamless の LINQ 実装の呼び出し(テストで検査する)、値を使った数学的変換(和の公式、単調性の利用)。

## FLinq と同じ純粋性の仮定は許す

- FLinq が既に前提にしている変換は理想版でも行う。引数なしの静的メソッドや定数引数の補助メソッドの呼び出しをループの外へ出す(`HoistInvariant.Value()`、`this.QuarterCount(...)`)、複合連鎖の押し下げ・並べ替え・射影の融合がこれにあたる。

## 結果に現れない中間物は作らない

- `ToArray().Consume(...)` の配列、結果選択子が使わないグループ要素の保存などは省いてよい。
- 上の純粋性の仮定の下で結果に影響しない計算も省いてよい(例: 結果選択子が内側を使わない `GroupJoin` の探索表。FLinq も Range 起点で省いている)。それ以外のハッシュの構築・探索は行う。
- `ToDictionary` は重複キーで例外になるので、全件を入れてから列挙する(例外の前に消費しない)。
