# Kestrel移行のWindows検証結果（2026-11-04）

## 実装範囲

管理TCP/TLS、Native RPC、TDS、HTTPをKestrel公開APIへ差し替えた。要求の認証・認可、DB処理、取引、結果列挙、永続操作ID、保存・WAL・世代公開はSeamless側へ残した。CurrentUserOnlyの管理IPCも残し、同じ管理要求処理へ接続する。クライアントの通信形式は変更していない。

DBコードのコンパイラーへ通信基盤の参照が加わるため、Seamless.Transportを対応範囲から除外した。追加テストで変更前は3ケースともコンパイルでき、変更後はManagementCodePolicyで拒否することを確認した。任意コードのサンドボックスという位置付けではない。

## 環境と証拠

Windows、実行時.NET 10.0.12、Releaseの性能試験。所有する全計算処理の子孫を同じaffinity 0xFF・最大8論理CPUへ制限した。Dを作業・実データ、Fをログ・キャッシュに使用し、共有BGOは使用していない。実運用DBの再初期化や変更、共有サービス・OS・NIC・TCP設定の変更は行っていない。

証拠の親ディレクトリは`F:\CodexTemp\SeamlessKestrel-20261104-01`。開始時の作業ツリーは`baseline-source`、移行前のRelease DLLは`baseline-binaries`へ保存した。既存の未コミット変更をHEADと比較して今回の変更に数える方式は使っていない。

追加の境界確認には、分割ヘッダー・分割本文・連結フレーム・受信バッファより大きい本文、不正な長さ・種別・途中切断、停止中の結果列挙の解放、未確定取引の切断時ロールバック、借用Pipeの寿命、出力停止時の取消、接続枠の回収、IPv4/IPv6、HTTPS証明書・ホスト名不一致を含む。

分割JSONの試験では、ref Utf8JsonReaderによる復元だけでは末尾の別JSONを見逃す不備を再現し、フレーム全体の検査を追加した。不正Nativeフレームの試験では、切断後にテスト自身がTcpClient.GetStreamを再取得していたため、元のStreamで切断を確認するよう試験を修正した。

終了境界では、取消にまだ応じないアプリ処理を残すと、接続の停止が約31秒で先に完了することを実行で再現した。アプリ処理を登録・完了管理する内部ApplicationLifetimeを追加し、TCP・HTTPとも35秒後までfinallyが終わらなければホストの破棄を完了しないことを確認した。修正後の通信・取引・接続枠の関連17件と、独立したHTTP長時間要求1件がDebug/Releaseそれぞれ成功した。

途中で並行編集されたSeamless.Linq/QueryGrouping.csにSystem.IOのimport不足が発生した。該当編集を上書きせず、成功済み依存DLLで境界を切り分けた。その後、並行編集側でimportが修正され、最終サーバーの通常publishとテンプレートの通常ビルドも成功した。

## 性能比較

同一PCのLoopbackで、サーバーとクライアントを別プロセスにした。正式NativeQueryServer/Clientと、同じMemoryPack・DB処理・通信契約を使い、Gateway DLLだけを移行前・後で差し替えた。独立したechoサーバーや物理NICの測定ではない。公開メソッドの小さい計算結果と、同じ32KiBの行ペイロードを1,024回返す軽いモジュールで通信を測り、実業務のLINQや毎行の直列化費用を代表するとは扱わない。Nativeは既存どおりTLSなしのLoopback用入口である。

初回群にはKestrelが速い回もあったが、反復で結果が変動した。最終修正後の回では小RPCと大結果が速くなったが、再接続・接続集中は遅く、待機メモリも増えている。過去回には小RPCと大結果が遅い結果もあり、安定した改善を判定するには試験を長くする必要がある。低レベル受付・TLS・バッファ寿命を既存基盤へ委譲した効果と、性能改善の達成を分ける。完全ゼロコピーや一律高速化・メモリ削減は主張しない。

### 負荷生成側の制約

IPv4一時ポートは49,152開始・16,384個。短時間に反復した回ではTIME_WAITが15,679件になり、クライアントでSocketException 10048が発生した。最初のプローブには、接続不足を記録してもサーバー正常終了だけで終了コード0にする不備があったため修正した。接続失敗があれば終了コード1とし、部分測定を1万接続成功へ数えない。

修正後の連続比較でも、旧経路の10,000接続に続くKestrel回は6,447確立・3,553失敗となり、正しく不合格で停止した。TIME_WAITが93件へ回復した後のKestrel単独回で10,000接続を成功した。最終表は停止寿命修正後、両方式の前にTIME_WAITを確認して同じツールで正常完了した回を使う。最後の比較では旧80件、新61件で開始し、方式間の回復待ちは約132秒だった。不合格の過去回の証拠も保存した。失敗した過去回の全例外種別・個別期限超過の内訳までは採取していない。

## 行数・配布サイズ

対象8既存C#ファイルと新しい通信基盤6ファイルを、空行を含む物理行で数えた。開始時に凍結した作業ツリーが基準であり、GatewayServerのオプション追加とRuntimeCompilerの条件追加だけは、その明示的な編集から変更前を復元して別記した。

本体は932→1,074行、332行追加・190行削除、差し引き142行増加。分割フレームの所有権処理・検査を共通化したため、低レベル責務の委譲が総行数の減少になったとは述べない。テスト、測定器、PS1、XML/JSON、文書はこの本体C#の集計に含めない。ファイル別の内訳はsource-size.jsonに保存した。

最終Windowsサーバーはframework-dependentで、ZIP 18,209,971 B、展開後61,852,618 B。SDKと共有ランタイムは同梱していない。Seamless.Management.Server.dllは凍結前298,496→296,960 B、新しい通信DLL・PDBのサイズはbinary-size.jsonに別記。同条件の旧ZIPは採取していないためZIP全体の差は比較完了として扱わない。これらのファイルサイズと実行時Private Bytes・Working Setは別の指標である。

MITと出荷するNuGet実行時資産のメタデータ・通知を配布へ保持した。パッケージに条文がないApache依存には公式コミットの条文、DiskANNには公式MITとNOTICEを含めた。DiskANNパッケージはビルドコミットを持たないため、取得元のコミットをバイナリのビルド元と断定していない。

## 未実施・残作業

- Linux実行検証。WSLにはdocker-desktopがあるが、Docker daemonは利用できず、既存サービスの起動・設定変更はしていない。
- DataGrip実GUI、VS/VS Codeのマルチ起動プロファイルのUI操作。公開契約は変更せず、SQL ClientのTDSテストとローカル起動情報の既存テストは実施した。
- 物理NIC・別PC、1万TLS接続の集中、1万の同時認証・問い合わせ・取引・結果転送。待機TCP接続の試験で代替しない。
- 全体の接続・実行・準備の枠、フレーム復元・出力の総予算、低速送受信の独立期限、HTTPの認証・本文上限。既存にない境界は[通信仕様](kestrel-transport.md)へ明記した。
- 接続維持・アイドル解放・操作後切断の三方針のGUI、プールと推奨設定、自動調整。
- SDKのないクリーン環境での配布起動・DBコードのコンパイル。今回の実行環境にはSDKが導入済み。
- Managerで作った定義と外部.csprojの自動同期・未適用タブ・選択的取り消し。方針は[外部ソースの設計](refactoring-designs/20261104-external-source-draft-state.md)へ保存した。テンプレートのビルド成功と同一視しない。
