# 公開更新問い合わせの監査と転記状態

監査テーブルを持つ管理領域で新しく作成したDBは、公開された更新問い合わせの確定時に、変更行と監査情報を同じWALへ保存する。監査情報には利用者、DB・問い合わせ、実際のDLL、取得できる元メソッドの識別情報、取引IDを含む。引数・結果は保存しない。従来の管理アカウント経路では共通認可の版が渡されないため、権限版は未記録となる。

監査テーブルへの転記はバックグラウンドで行う。監査検索への反映には遅れがある。転記先への保存後に処理済み位置を保存し、途中停止後の再送は同じイベントを重複登録しない。元のWALは転記前に削除しない。旧世代の未転記分も再起動後に確認する。

## 画面で確認する

1. 管理ツールの「監査ログ」を開く。
2. 「表示」で「更新監査の転記状態」を選び、「更新」を押す。
3. 稼働版・旧世代、転記状態、未処理LSN、状態更新UTC、問題を確認する。
4. 行を選ぶと、DBのDLL識別、WAL ID、確定済み・処理済みLSNを確認できる。

一覧は最大100世代ずつ取得する。「続きを取得」で次のページへ進む。時刻や検索語はこの状態表示に適用しないため、対応する入力欄は非表示となる。必要なサーバー能力は`AuditDeliveryV1`、現在の閲覧権限はサーバー管理権限である。

未処理LSNはログの位置の差であり、イベント件数ではない。表示は最後に保存された確認結果であり、その後の更新をすべて反映した実測値ではない。転記済みと表示されている旧世代のデータを削除する操作ではない。

## 既存DBと障害時の扱い

導入前のDBは、この一覧に含まれない。管理テーブルの`upgrade-audit`だけではユーザーDBのWAL方式は変更しない。起動・保存・通常のスキーマ適用でも旧方式を維持する。旧DBへの導入専用CLIは未実装であり、設定ファイルへ利用側の名前を追加して開き直す方法は使用しない。

転記失敗時も記録を破棄せず、問題を状態へ残す。容量上限、識別情報・保存内容の不一致などを確認する。処理済み位置や転記元レコードを手作業で進めて解消しない。原本の保護と、バックアップを伴う復旧が必要となる。未転記分が増え続ける場合は保存資源の上限に達し得る。

この機能の対象は、導入済みのDBで管理サービスが実行する公開更新問い合わせである。SQL・業務用ネイティブRPC等の全入口、失敗した要求の詳細監査、正常読み取りの集計は、これだけでは完成していない。
