# 公開更新問い合わせの監査と転記状態

監査テーブルを持つ管理領域で新しく作成したDBは、公開された更新問い合わせの確定時に、変更行と監査情報を同じWALへ保存する。監査情報には利用者、DB・問い合わせ、実際のDLL、取得できる元メソッドの識別情報、取引IDを含む。引数・結果は保存しない。従来の管理アカウント経路では共通認可の版が渡されないため、権限版は未記録となる。

監査テーブルへの転記はバックグラウンドで行う。監査検索への反映には遅れがある。転記先への保存後に処理済み位置を保存し、途中停止後の再送は同じイベントを重複登録しない。元のWALは転記前に削除しない。旧世代の未転記分も再起動後に確認する。

## 画面で確認する

1. 管理ツールの「監査ログ」を開く。
2. 「表示」で「更新監査の転記状態」を選び、「更新」を押す。
3. 稼働版・旧世代、転記状態、未処理LSN、状態更新UTC、問題を確認する。
4. 行を選ぶと、DBのDLL識別、WAL ID、確定済み・処理済みLSNを確認できる。

一覧は最大100世代ずつ取得する。「続きを取得」で次のページへ進む。時刻や検索語はこの状態表示に適用しないため、対応する入力欄は非表示となる。必要なサーバー能力は`AuditDeliveryV1`、現在の閲覧権限はサーバー管理権限である。

未処理LSNはログの位置の差であり、イベント件数ではない。表示は最後に保存された確認結果であり、その後の更新をすべて反映した実測値ではない。転記済みと表示されている旧世代のデータを削除する操作ではない。

## 既存DBと障害時の扱い

導入前のDBは、この一覧に含まれない。管理テーブルの`upgrade-audit`だけではユーザーDBのWAL方式は変更しない。起動・保存・通常のスキーマ適用でも旧方式を維持する。既存DBへの導入には、次の停止・バックアップ付きCLIを使用する。設定ファイルへ利用側の名前を追加して開き直す方法は使用しない。

## 既存DBへ明示的に導入する

1. 対象インスタンスのサーバーを停止する。実行中のサーバーが管理領域を使用している場合、コマンドは拒否する。
2. 管理領域に監査テーブルがない場合は、別の空の退避先を指定して`upgrade-audit`を先に実行する。
3. 公開済みのユーザーDB名、管理領域、独立した空の退避先を指定して実行する。`system`は対象にできない。

```powershell
.\Seamless.Management.Server.exe enable-update-audit --root D:\Seamless\Management\Instance1 --database Sales --backup D:\Seamless\Backups\Sales-before-audit --operation-id 8748bc61-864a-458e-bbd4-b122be2e09b3
```

`--operation-id`は省略でき、その場合はコマンドが生成する。最初のJSON行は要求した操作IDを示す`Requested`であり、成功を示すものではない。最終JSONの`state`を確認する。終了コードは成功時0、失敗・取消・結果不明時1となる。バックアップ前など操作を記録する前の失敗では、最終結果ではなく標準エラーへ理由を出力する。

全管理領域のバックアップが完了してから、対象DBを新しい非公開世代へコピーする。最終的な参照整合性と依存する公開済み問い合わせの再ビルドに成功した後、DB・問い合わせ・監査転記元・履歴・操作成功を一度に公開する。現在のC#ソースとデータを使い、前回のスキーマ変更の変換式を再実行しない。個人下書き・権限・他DBは変更しない。対象DBと依存問い合わせの共有版は進むため、既存下書きの適用には基準版の再確認が必要になる。

確定前の失敗・取消では旧世代を維持する。Ctrl+Cの取消は、バックアップのファイル間や移行・公開前の確認点で処理する。既に確定した変更を取消済みとは表示しない。応答が失われた場合は、サーバーを停止した状態で操作IDを照会する。

```powershell
.\Seamless.Management.Server.exe get-operation --root D:\Seamless\Management\Instance1 --operation-id 8748bc61-864a-458e-bbd4-b122be2e09b3
```

`Succeeded`なら導入が確定している。中断された実行中の操作は`OutcomeUnknown`として返し、成功・取消と推測しない。操作がない場合も成功とは判断しない。同じIDで再実行する場合にも、新たな空の退避先が必要になる。同じ要求の記録があれば追加移行せずその状態を返す。既に導入済みのDBへ別IDで実行しても、追加のDB世代を作らない。

成功後にサーバーを再起動すると、更新監査と転記状態を確認できる。導入前のバックアップへの復元は別の復旧操作であり、導入後の業務更新を自動で保持したまま元へ戻す機能ではない。旧世代や失敗した非公開世代の自動削除は行わないため、バックアップとコピーのための空き容量を確保する。

転記失敗時も記録を破棄せず、問題を状態へ残す。容量上限、識別情報・保存内容の不一致などを確認する。処理済み位置や転記元レコードを手作業で進めて解消しない。原本の保護と、バックアップを伴う復旧が必要となる。未転記分が増え続ける場合は保存資源の上限に達し得る。

更新監査の対象は、導入済みのDBで管理サービスが実行する公開更新問い合わせである。正常読み取りの集計は以下の明示設定で利用できる。SQL・業務用ネイティブRPC等の全入口と、失敗した要求の詳細監査は引き続き残っている。

## 管理領域の集計識別を更新する

新しい管理領域は形式5を使う。既存の形式3/4は起動時には変換しない。形式4の読み取り集計を新しい値ベースの識別へ更新する場合も、サーバーを停止し、独立した空の退避先を指定する。

```powershell
.\Seamless.Management.Server.exe upgrade-audit --root D:\Seamless\Management\Instance1 --backup D:\Seamless\Backups\Instance1-before-format5
```

形式4からは既存の監査イベント・利用者・権限・定義・下書き・転記元を維持し、集計索引を再構築する。同じ論理キーが複数行に分かれていた場合は件数を合算する。同じ瞬間を表すUTCと日本時間のオフセット差で集計を分けない。ユーザーDBのスキーマやWAL方式は、この操作では変更しない。切替途中で停止した場合は通常起動を止め、`rollback-audit-upgrade --root <管理領域>`で明示的に元のsystemへ戻す。確定済みの更新を取り消す操作とは異なる。

更新後は監査検索を最初からやり直す。新しいバッチは値に基づくハッシュを持ち、再送時に未使用バイトや日時オフセットの表現差で二重加算しない。旧形式の処理済みバッチにはrawハッシュしかなく、元の差分が残っていないため、不一致を値の同一性として証明できない。この場合は`LegacyReplayUnverifiable`で拒否する。別IDで再送すると二重加算になる可能性があるため、保存済みの集計を確認する。

## 正常読み取りの集計と既定値

形式5の管理領域では、通常のCLIサーバー起動で1分単位の集計を有効にし、5秒ごとに保存する。利用者・DB・問い合わせ・実際のコード版・権限版ごとに別の集計とし、その1分間の行へ保存周期ごとの回数を加算する。次の指定は既定と同じ60秒を明示する例である。

```powershell
.\Seamless.Management.Server.exe serve --config .\seamless-management.local.json --read-audit-window-seconds 60
```

集計期間は`--read-audit-window-seconds`、保存間隔は`--read-audit-save-seconds`で変更できる。保存間隔だけを指定した場合も、期間は既定の60秒となる。指定できる集計期間は1秒〜1日の整数秒、保存間隔は0.01秒〜1日。`--no-read-audit`で明示停止できるが、期間・間隔と同時には指定できない。設定は起動時に読み取り、変更にはサーバーの再起動が必要である。

既存の形式3/4では設定省略時に収集を有効にせず、明示設定した場合は`upgrade-audit`による形式5への更新を要求する。起動や設定だけで既存形式を変換しない。埋め込み用途では`new ManagementService(store,new ReadAuditOptions())`で同じ既定構成を指定できる。既存のオプション省略またはnullの埋め込みAPIは、収集未設定の動作を維持する。

管理サービスで公開読み取りを最後まで取得した成功を、利用者・DB・問い合わせ・実際のDLL・UTCの時間帯ごとに集計する。現在の管理認可から権限の版は渡されないためnullとなる。失敗、取消、列挙中断、検証DB、下書きの試験実行はこの成功数に含めない。引数や結果データをバッファへ入れない。

保存を検索の完了条件にせず、バックグラウンドで処理する。バッファの既定上限は処理中の分を含む65,536キー・概算64MiBで、一度の保存は最大1,024キー。同じIDと内容を再送することで保存の応答喪失後の二重加算を防ぐ。保存障害中に上限へ達した新しい集計は記録せず、既知の欠落として件数を示す。終了時は残りの保存を試み、確実な未送信の欠落と、送信後の結果未確認を区別する。

管理画面の「監査ログ」→「通常読み取りの集計」で検索すると、保存済みの結果に加え、本起動の受付・保存確認・既知の欠落・待機量・保存間隔・問題を表示する。閲覧にはサーバー管理権限と`AuditReadBufferV1`の能力が必要である。カウンターは今回の起動についての値で、異常終了時の最後の未保存分の欠落量は分からない。既知の欠落が0でも、すべての読み取りが永続化済みという意味ではない。

### 集計をコード上の名前から探す

集計の「問い合わせID」と「実行メソッド」を別の列で表示する。`Model.Query.Run`のような名前空間・型・メソッドの完全修飾名や、シグネチャでも検索できる。例えば`Model.Query.Run Native`は、両方の語を持つ集計を探す。行を選ぶと、実際のDLLに対応するモジュールID・メタデータトークンと、権限の範囲内のクエリテンプレートを表示する。

メソッド情報は、その集計に記録されたDLL識別に対応する保存済みのビルド情報から取得する。現在の定義へ置き換えて推測しない。情報が保存されていない場合は「未登録」、名前の一部が未記録の場合は「一部未記録」と表示する。形式5の既存集計をそのまま参照でき、表示のために問い合わせやアセンブリを実行しない。

対応するサーバー能力は`AuditReadMethodsV1`である。未対応のサーバーではその旨を案内し、問い合わせIDによる既存の集計検索を利用できる。

メソッド名・引数と戻り値のシグネチャは管理閲覧の対象で、クエリテンプレートには対象DBの編集権限も必要である。権限がない場合は本文を返さず、本文にだけ含まれる語で検索しても一致しない。検索は大文字小文字を区別しないAND条件で、1ページは最大100件・4096レコード・検索文字列約1Mi文字まで。0件でも続きが残る場合は「続きを取得」で先へ進める。
