# 開発中に得られた技術的知見と落とし穴 (Lessons Learned & Pitfalls)

Seamless の開発過程では、並行処理、OS のファイルシステム、ハードウェアの特性、言語仕様の境界において、数多くの困難な問題に直面し、それを解決してきました。

ここでは、技術者が興味を持ち、同様の高パフォーマンスシステム開発にも役立つ「リアルな教訓」を共有します。

---

## 1. 非同期・並行処理における「20秒間の競合問題」

### 問題の発生
高負荷な単体テスト（`DatabaseTransactionTests`）を長時間ループ実行した際、「数周に1回、ごく稀に一時ディレクトリの破棄が `IOException (Sharing violation)` で失敗する」という謎のエラーが発生しました。

### 原因の究明
調査の結果、以下の競合シナリオが判明しました：
1. スレッド A が一時スコープを破棄しようとし、フォルダ内の所有者ロックを手放す。
2. そのわずかな隙間に、放置された一時資源を回収するバックグラウンドプロセス（`TemporaryResourceRecovery`）が起動。
3. 回収プロセスから見ると「放置されたフォルダ」に見えるため、`owner.json` のロックを取得しにいく。
4. スレッド A がフォルダを物理削除しようとした瞬間、回収プロセスとファイルアクセスが衝突（共有違反）する。

実験計測では、**わずか 20 秒間の作成・破棄・回収の同時実行で、34,961 回中 259 回の共有違反エラー** が記録されました。

### 解決策（二段階ハンドシェイクと期限付き再試行）
- **回収側のルール変更**:
  回収プロセスは「まず所有者ロックを排他で取る」ことを義務付け、取れない（他者が使用・破棄処理中）のフォルダの `owner.json` には一切触れず、次回の回収サイクルへスキップする。
- **破棄側のルール変更**:
  破棄処理は、回収側が手を離すまで **期限付き（2秒間）で指数バックオフ再試行** を行う。

この二重のプロトコル改善により、**20秒間の同負荷テストにおけるエラー発生回数は「259回 → 0回」へと完全に解消** されました。

## 2. 浮動小数点数（+0.0f と -0.0f）のビット表現の罠

### 問題の発生
.NET の `float` や `double` において、`+0.0f == -0.0f` は言語仕様上 `true` を返します。
しかし、データベースの主キー（Primary Key）や `GroupBy`、集合演算（`Distinct`）に `float` を使用した際、**「`+0.0f` と `-0.0f` が別のキーとして扱われてしまう」** という不一致が発生しました。

### 原因の究明
- 通常の C# の等価比較（`EqualityComparer<float>.Default`）は IEEE 754 のルールに従い `+0.0` と `-0.0` を等しいとみなします。
- 一方、超高速化のためにメモリブロック（`Span<byte>`）やバイナリハッシュを直接比較するエンジンでは、**`+0.0f`（`0x00000000`）と `-0.0f`（`0x80000000`）のビットパターンが異なるため、全く別のハッシュキーとして判定** されていました。

### 解決策
- スコープ付きクエリおよびハッシュ計算において、浮動小数点型のキーを扱う際は、正規化（`-0.0f` を `+0.0f` へ統一）を行う専用の比較セマンティクスを導入し、バイナリ比較の高速性を維持しながら言語仕様との完全な整合性を達成しました。

## 3. ベンチマークにおける「非対称計測バイアス」

### 教訓
自作ライブラリ（FLinq）と比較対象ライブラリの性能を公平に測定するため、Stopwatch による簡易計測を行ったところ、特定のケースで実際と乖離した極端な結果が出ることがありました。
片側の処理が JIT コンパイルのタイミングや OS スケジューラのコア移動（マイグレーション）の影響を強く受け、計測値に非対称なバイアスが生じていたためです。

### 解決策
1. **プロセス分離ワーカー**:
   ベンチマーク実行を UI や親プロセスから完全に切り離し、独立したワーカープロセスで実行。
2. **CPU Affinity の固定**:
   ワーカープロセスを特定の物理コア（同一 L3 キャッシュ）にピン留めし、スレッド移動を禁止。
3. **BenchmarkDotNet への完全統合**:
   ウォームアップ、JIT 事前コンパイル、反復回数の統計的処理を標準化。

この厳格な計測基盤の構築こそが、信頼できるミリ秒・ナノ秒単位の最適化サイクルの基盤となりました。
