## 目的

1. 適用された設定と実行経路を利用者が説明できる。
2. 複数ストア・Scope・再構成の同時生存分を親予算で制限できる。
3. 生成器の意味判断を描画から切り離し、一経路から段階移行する。
4. ノイズや弱い照合を性能改善の証拠として採用しない。

## 非目的

新しいプラグイン基盤、生成器全面置換、旧APIの無関係な整理、実測なしのOptimized範囲拡張、既存DBの自動移行、他タスクの再開・停止・送信、pushは行わない。

## 再設計

### 説明情報

既存ProfileResolverの結果を不変な説明データへ投影する。要求プロファイル、採用プロファイル、ID/版、実設定、Growth、根拠Run ID、採用理由と不足条件を含める。説明を取得するためにストア作成・列挙・DB接続を行わない。実行前に確定しない経路は推定・実行時判断として区別する。まずライブラリAPIとScalable側の説明を接続し、既存UIの命名規則に合わせて表示する。

### 親予算

ResourceBudgetに子予算を作る契約を追加し、子の増分予約が親と子の両方で成功した場合だけ確定する。失敗時は両者を不変に保つ。予算階層は生成後不変とし、固定したロック順序を採用する。解放・Resizeの二重操作も同じ同期規則で扱う。

既存の単独予算コンストラクタを維持し、StoreとExecutionScopeに親予算を明示指定できる入口を追加する。Scalableの残額スナップショットを共有親予算へ置き換え、再構成時は旧・新ストアの同時使用を計上する。予約はページ・チャンク単位で行い、毎要素のロックを増やさない。予約会計とプロセス実メモリは別指標とする。

### 生成器

最初の対象をJoin→Countの一経路とする。既存Demand結果から、出力値の必要性・評価保存の要否・順序・保有資源を不変な型付き計画へ確定し、描画はその計画のみを見る。Anchor、評価順、例外、副作用が必要な計算を、未使用変数という理由で削除しない。既存traceへ判断理由を接続し、命名の整形と意味の最適化を別に検証する。GroupByはこの経路の受入後に同じ手順で移行する。

### 測定とプロファイル

- 条件・正しさ・測定不足の既存判定を先に行い、その後で性能を判定する。
- 分散が大きい測定を判定保留にできる、版付き比較ポリシーを追加する。標本内変動と独立実行間の再現性を区別し、固定seedの再標本化を使う場合も統計的な前提と限界を記録する。
- PeakWorkingSet64はプロセス全体の高水位として明記し、区間観測値と予約ピークを別名で記録する。サンプリングの取りこぼしを真のピークと称さない。
- Scalableの既存読取件数・合計検査を保持し、小規模の全内容照合と大規模の複数指標によるストリーミング照合を追加する。ハッシュ照合を数学的な完全一致証明とは扱わない。正しさ検証の時間は性能区間と分けて記録する。
- Optimized証拠にライブラリ/Codec/測定方式の版、必要なI/O条件を結び付ける。旧証拠は不明として保持し、新しい版の候補選定へ黙って流用しない。利用アプリは引き続き測定DBへ依存させない。

## 影響範囲

`Seamless.Execution`、`Seamless.Linq`のScope接続、`Benchmark.Infrastructure`、`Benchmark.Scalable.Core`、関連UI、`Seamless.FLinq.Generator`のJoin経路、既存の対応テストと公開文書。新プロジェクトは原則追加しない。必要になった場合はSeamless.slnxと生成されるfocused solutionsを同じ変更単位で整合させる。

## 移行手順

1. 対象へのGitアクセスと書込権限を確保し、最新HEAD・既存差分・対象ファイルの帰属を確定する。本設計を対象リポジトリのdocs/refactoring-designsへ保存する。
2. 説明APIを追加し、採用理由と実行前の不確定項目を表示する。
3. 比較・照合・指標の区別を先に固定し、新旧の測定結果を誤比較しない状態を作る。
4. 親予算、Store/Scope接続、再構成時の合算を実装する。
5. Joinの不変計画と描画を分離し、意味を保存してからGroupByへ進む。
6. Debug/Releaseで関連回帰を確認し、実施・未実施・性能未確定を記録する。性能向上は測定後のみ主張する。

## テスト計画

- 説明：入力を列挙しない、実行しない、未知条件・Minimum復帰・明示設定の優先が分かる。
- 予算：兄弟の合算、親/子上限、失敗時の原子性、Resize/Dispose、並行予約、再構成失敗時の原データ保持。
- 比較：明確な悪化、許容内、ノイズによる保留、0時間、NaN/不足標本、条件差、内容不一致を区別する。乱数依存の不安定なテストは作らない。
- 照合：件数・合計が同じ異内容、重複、順序、空入力、JoinとSortを含める。
- 生成：結果・例外型・ラムダ別評価回数・Anchor・Dispose・診断・trace・incremental cacheを確認する。
- ストレージ測定を行う場合はD/Fの許可と保存先を別途確認する。設計作成時点ではテスト・ベンチマークとも未実行。今回の検証結果は下記に追記する。

## 実装した契約

- `ProfileResolver.Explain` / `ScalableRequest.Explain`、Scalable UIの説明ボタン、DB初期化前に返すCLIのexplainを接続した。既存Resolverの優先順とGrowthの明示指定を使用する。
- `ProfileEvidence` でExecutionのビルド識別子(MVID)、Codec、測定方式、比較ポリシーを束ねた。旧証拠は保持し、未知・不一致の証拠から現行Optimizedを選定・発行しない。同梱の旧版1もMinimumへ戻し、その理由を説明する。新しい性能上の推奨範囲は作らない。
- 予算階層は一つのロックを共有し、全祖先を検証してから一括計上する。予約状態も同じロックで同期する。予約量の読取りはVolatileとし、予約・Resize・Disposeのロックを重ねない。
- Scalableは標本ごとの親予算をStore/Scope/旧・新Storeで共有する。Systemの作業領域は推定量、Native外部ソートはチャンク・I/Oと最大一時領域をまとめて予約する。再構成失敗時は元ストアを保持する。
- Join→Countは既存Demandから不変な `JoinConsumptionPlan` を作り、結果の評価を保持したまま探索表の選択を描画へ渡す。GroupByは `GroupByConsumptionPlan` と集約候補のスナップショットを使い、候補のGroupLimitを書き換えない。判断理由は既存Base64形式のtraceへ接続する。
- 比較ポリシー `noise-v1` は7標本以上と標本内の相対標準偏差20%上限を使用する。統計的有意差の証明や再標本化は行わず、独立実行の改善検査とは区別する。
- 測定方式 `scalable-content-v2` で追加の全内容/ストリーミング照合と時間を分離し、区間観測WorkingSet・プロセス生存期間の高水位・親予算の予約ピークを別フィールドで記録する。既存の件数・合計・昇順検査を保持する。
- 新プロジェクト、既存DBのスキーマ変更、既存測定の補造、コミット、pushは行わない。
