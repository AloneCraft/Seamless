# ライブ検証の要求件数とWorker上限の整合

承認済み統合計画の、通常・ライブ実行の正しさと履歴保存を満たすための修正である。

## 観察と原因

Releaseのライブ画面でシード再現を開始すると、Workerが完了通知なしで終了した。通常実行と固定参照比較は成功している。ライブのランダム段階は一要求100万件を指定するが、Workerは一要求1,000件までを受け付ける。三段全組み合わせも上限を超える可能性がある。従来の実Workerテストはペアの最初の6件で止めており、この境界を検査していなかった。

## 修正方針

- Workerの1,000件上限を維持し、共有プロトコルの定数にする。
- ライブは上限内のバッチへ分割する。QueryIndexOffsetとSeedを保ち、次のバッチを直前の終端から開始する。件数を単に削って探索を終わらせない。
- 各バッチの正常終了・取消・失敗を共通履歴へ記録する。段階の表示はバッチ境界で最初へ戻さない。
- 実Workerでランダム段階の開始と中止を確認し、バッチ境界を越える要求の通番・件数はテストで検証する。
- 予期しない終了では取得可能な標準エラーを診断へ含め、完了通知なしの終了を合格扱いにしない。

## 検証と運用

全段階の要求上限、連続バッチ、独立Run ID、Seedと通番、取消後の保存を確認する。既存のペア・文字列・通常履歴・固定参照にも回帰を行う。CLIは共通資源調停のA/cliで実行し、GUI adapterがあるとは扱わない。実OS入力試験は利用者が明示許可した対象アプリに限定する。D/Fと物理メモリ上限を維持する。

## 回帰結果

修正前は上限検査3件中、三段27,720件とランダム1,000,000件の2件が失敗した。修正後はライブ関連11件すべて成功した（Release、D SSD、物理メモリ最大65%）。末尾1,500件が1,000件と500件に分かれ、通番・シード・独立Run ID・履歴を保持する。実Workerでペアint/string、ランダム開始と取消、計測不能の結果も詳細履歴へ保持することを確認した。途中取消を正常完了へ置き換えない。

## 対象変換の順序属性

ライブのseed 0x1018_2026は30件進んだ後、DistinctByを含むIRの実行対象変換で順序属性エラーとなった。IR生成・検証はDistinctByをUnorderedとするが、WorkerHost.Unaryを変換はDistinctだけを特別扱いし、DistinctByに入力のOrdered属性を付けていた。DistinctByも同じ変換規則へ追加し、検証規則を緩めない。配列・List・IEnumerable・Rangeの対象変換をWorkerHostのプロトコル経路で検査する。
