# Seamless DB定義の双方向変換と独立した一致検証

## 背景

Seamlessへ取り込んだDBだけでなく、手書きのSeamless DB定義・LINQ・ルーチンもRoslynで読み取り、ベンダー別SQLに変換する。生成SQLで再構築したDBと移行元DBについて、スキーマの意味・動作・データを比較する。

## 現状の観察

- `Seamless.Database.Rdbms/CSharpDatabaseGenerator.cs`にはDBカタログからC#を生成する実装がある。
- `Shared/Database.Generation`にはRoslynのSemanticModelでDB・スキーマ宣言を扱う実装がある。
- `Seamless.Database.Compilation`にC#の処理本体からSQL Server / MySQL向けSQLを生成する初期実装と、SQL定義からC#へ変換する初期実装を追加した。対応範囲は`tools/sql-migration/README.md`を正とし、全SQL機能への対応を意味しない。
- `Samples/Sample.NetShop.Core/Shop/商店DB.cs`は、表・ビュー・関数・ストアドを宣言し、別メソッドのLINQや手続き処理を呼び出す。
- 同サンプルの手書きレコードにはstringなどのCLR型があるが、それだけではSQLの最大長・照合順序などを確定できない。
- SQL Server以外の構文解析入口が存在することと、そのDBMSの実行意味論に対応していることは区別する。

## 過去設計から引き継ぐ仕様

`20261102-datagrip-native.md`の専用JDBC・構造化メタデータ・共通実行基盤・世代管理・元DB保護を引き継ぐ。進行中の変更は実装開始時に再確認する。

これまでの利用者回答で確定した事項:

- SQL Server、MySQLの順で対応し、その後ほかのDBMSへ拡張する。
- 比較用SQL Serverの全ユーザーDBと、MySQLのSakila・Employees・worldを対象とする。
- DB内の全オブジェクトとデータを収集する。未対応の定義・依存関係・理由も保持して部分確認を継続する。
- 移行可能な関数・ストアドは実処理を移行する。ベンダー固有の環境情報には互換用実装を設け、Seamless上ではSeamlessの情報を返す。
- 最初の動作比較は読み取りまでとし、更新系・トリガー・DDL・取引の動作比較は後続とする。
- DataGrip接続基盤の完成も今回に含める。最初の受け入れは接続・一覧・定義参照・データ閲覧・読み取りSQLとルーチンの実行までとする。
- 正しさを確認できた読み取り処理から、専用環境で性能を比較する。SQL経路とネイティブ直接・リモートを分けて測る。
- ネイティブ処理は共通解析結果から自動生成する。
- MySQLはGドライブに比較専用として新規配置する。専用SQL Serverを含め、性能測定の資源・保存条件を揃える。
- 「動画確認」は「動作確認」の意味である。

従来の取り込み比較へ、C#をRoslynで解析してDBMSへ再出力する往復検証を追加する。元SQLの再出力だけを逆変換の検証にしない。

## 目的

- Seamlessのネイティブな型・実行意味・保存性能を設計の基準とする。SQLへの出力はベンダー別の変換境界で対応する。
- 取り込み生成C#と、手書きのSeamless DB定義・LINQ・ルーチンの両方をSQL生成の入力とする。
- C#から取り出した構造・処理をベンダー別SQLへ変換し、専用DBを再構築する。
- 再構築DBにはSeamlessの保存データを読み出して投入し、元DBのデータと比較する。
- 移行元DB、Seamless、再構築DBの動作を比較し、対応・未対応・未検証を追跡する。

## 非目的

- 任意のC#プログラム全体を、制限なくSQLへ変換できると保証すること。
- 未対応コードを固定値や空処理へ置き換えて移行成功とすること。
- 読み取り試験の合格だけで更新系を含む完全移行を証明したと報告すること。

## 提案設計

### ネイティブ優先の型と意味

2026-11-02の利用者指示により、固定容量文字列はTsavorite/Persisted向けの保存・実行上の必要性を理由に設計する。数値や日時をSQLの型仕様へ合わせることを目的として、ネイティブの型を変更しない。

- float、double、decimal、DateTimeなどは.NETの型とその実行意味を基準とする。用途に応じたDateOnly、TimeOnly、DateTimeOffsetなども、ネイティブな意味から選択する。
- SQLの精度・小数桁・日時精度へ合わせるためのDecimal18_4やDateTimePrecision3などを、手書きDBの必須型として導入しない。以前のチャットで提示したその方向の提案は採用しない。
- 手書きC#のDB宣言に、SQL出力のための精度指定を一律に要求しない。必要なベンダー別の型選択・補助表現・設定はSQL出力プロファイルと変換器の責務とする。
- 元DBのSQL型・精度などは、取り込み・往復検証・出力に必要な対応情報として保持する。これをネイティブ型の意味と混同しない。
- Roslynで得たネイティブの演算・比較・丸め・日時の意味を共通モデルに保持し、生成SQL側で対応する。SQLへ合わせるために元のC#の処理や値を暗黙に変更しない。
- 対象DBMSの型・演算で同じ意味を表現できない場合は、必要な明示変換・補助処理を変換側で扱い、再現できない箇所を診断する。精度落ち・切り捨てを隠して合格にしない。
- 元DBからの取り込みでネイティブの表現範囲に収まらない値や意味がある場合も、情報を失う取り込みを成功とせず診断する。移行元との意味の一致は実行比較で別途確認する。

### 解析と生成

1. 対象プロジェクトの参照・コンパイル条件・source generatorを解決し、RoslynのCompilationを構築する。
2. SemanticModelと操作ツリーでDB宣言、型、式、LINQ、ルーチン本体、到達する補助メソッドを解析する。文字列の識別子一致だけでAPIを判定しない。
3. DB構造・型・NULL・演算・制御フロー・依存先を表す共通モデルへ変換する。
4. 方言別の変換器でDDL、ビュー、関数・ストアドおよび比較用呼び出しSQLを生成する。
5. 未対応の構文・API・状態依存・外部作用には、コード位置と依存先を含む診断を返す。

取り込み時のDB固有情報は、ネイティブの型・処理と区別した宣言情報または対応情報として保持する。手書きC#の通常の型をSQL仕様へ寄せることは要求しない。元SQLは証跡として保存してよいが、処理本体のRoslyn解析を迂回する再出力には使わない。

### 固定容量の文字列値型

取り込み時に最大長が分かる文字列列へ固定容量型を自動適用し、生成レコード・保存形式・SQL変換をまとめて対応する。大きい文字列は通常のstringで保持し、その列を含む行は参照を含む保存経路を使用する。初期実装は`FixedText<TBuffer>`とInlineArrayの16 / 32 / 64 / 128 / 256 UTF-16要素を使用し、既定では埋め込み512バイト以下、行の概算4096バイト以下に制限する。SQLの論理最大長とバッファ容量は区別する。

- 参照を含まない通常のstructに、InlineArrayの文字バッファと実際の長さを保持する。Span自体は永続フィールドにせず、操作中の参照ビューに使う。
- 固定容量はネイティブの物理的な保存方式とする。SQLのCHAR/VARCHAR、Unicode・文字コード、長さの単位、照合順序、NULL、末尾空白の規則は、取り込み元の意味とSQL出力の対応情報として区別する。
- 検索・比較・ハッシュ・文字列操作は可能な範囲でSpan上に実装し、string化を必要とするAPI境界での割当と区別する。
- stringからの変換では容量を検査し、暗黙の切り捨てを行わない。NULL・空文字・default値の扱いを仕様化する。
- 大容量を値に埋め込むと行サイズ・コピー量が増えるため、大きい文字列は通常のstringで保持する。専用の本文領域と固定長IDによる長文保存は今回の採用方式に含めない。
- Equals/GetHashCode、SQL照合順序に従うキー比較、未使用領域の扱い、保存形式の版を明示する。
- 利用者回答により、手書きC#で固定容量型の==とEqualsを使う場合は、通常stringと同じ、大文字・小文字を区別するOrdinal比較とする。同じ内容には整合するハッシュ値を返す。DB照合順序による比較は専用APIまたは比較器で明示する。
- 取り込んだSQLの比較、およびDBのキー・制約の比較は移行元の照合順序を維持する。生成C#にも対応する比較操作を明示し、通常のOrdinal演算へ置き換えない。RoslynからのSQL生成でも両者を区別する。
- Roslynはこの文字列型の容量・論理型情報・メソッド呼び出しを共通モデルに復元する。内部のバッファ操作を文字列処理の意味として逐一推測する方式を中心にしない。

コード調査の観察:

- TsavoriteのStore/DictionaryStoreとPersistedのStore/Dictionaryには、RuntimeHelpers.IsReferenceOrContainsReferencesによるシリアライズ方式の分岐がある。
- DBのDatabaseTransactionsにはCanonicalV1のシリアライザーを明示指定する経路がある。型をunmanagedにするだけで全経路が生バイト保存になるとは判断しない。
- CodecRegistryの通常の値型処理はフィールド列挙を使うため、FixedText専用のUTF-16内容codecを追加した。InlineArray全般に対応するものではない。固定容量文字列の末尾要素までの保存復元と再オープンを試験する。
- 固定容量型と通常stringの速度・割当・保存サイズは未測定であり、性能優位は仮説として扱う。

### データと比較

- スキーマ・処理の入力はC#、データの入力は同じ構築世代に属するSeamlessのデータスナップショットとする。
- 元DBと取り込みデータの基準時点を揃える。比較中に元DBが変化した場合は差分を混同せず、その比較を再実行対象とする。
- 型・精度・NULL・制約などの構造上の意味と、実際の読み取り結果を別々に比較する。
- 全表の値・件数・NULL・重複を逐次照合する。内部の取り込み行IDは元DBの列として再出力しない。
- 手書きで追加した処理など元DBに対応物がないものは、同じ初期データ・引数で実行したネイティブC#の動作を基準に生成SQLを比較する。元DBとの比較対象とは区別し、独立した期待値fixtureも併用する。

## 影響範囲

RoslynによるDB解析、共通カタログと実行表現、C#生成、ベンダーSQL生成、データ出力、再構築・比較ランナー、DataGripメタデータと検証資産。

### 責務と依存方向

実装中の利用者指示により、相互変換と一致検証は独立した機能として分離する。

- 定義・処理の変換は製品ライブラリとする。C#とベンダーSQLの解析・生成、型や演算の対応付け、変換診断を担当する。元DBとの比較や合否判定、ベンチマークは持たない。
- データ転送・DB構築は実行アダプターとする。接続、逐次データの取り込み・出力、生成DDLの適用を担当する。比較の合否判定は持たない。
- 一致検証は`tools/Database.Verification`が担当する。構築済みの接続とネイティブ行の供給元を受け取り、変換やDB構築を内部で行わない。性能測定はこの合否判定とも別の実行段階とする。
- 試験を組み立てる側が変換・転送・検証を個別に呼ぶ。各モジュールは共通のRdbms定義契約へ依存し、相互参照を持たない。製品の変換ライブラリから検証モジュールを参照しない。変換診断と比較実行の合否を別々に保持し、依存境界をテストする。
- CLI・GUIは変換だけを単独利用できる。変換を依頼しただけで比較環境の作成や元DBの試験実行を開始しない。

## 移行手順

既存変更・過去設計を再確認し、追加経路として小さな手書きfixtureと取り込みfixtureから実装する。既存の取り込み・実行経路を維持しながら対象サンプルへ拡張する。DB再構築は所有する専用領域で行い、既存DBの変更には明示的なバックアップを伴わせる。

## テスト計画

- 生成C#・手書きC#の双方について、構造・LINQ・補助メソッド・ルーチンの解析を検証する。
- C#の処理本体を変更すると、生成SQLと再構築DBの動作に反映されることを確認する。
- 元SQLの保存物へアクセスできない条件でも、対応済みC#からSQL生成できることを確認する。
- 固定容量文字列を採用する場合は、容量境界、NULL・空文字、Unicode、末尾空白、比較・ハッシュ、全バッファ要素の保存復元と再起動を検証する。通常stringに対する割当・コピー・保存量・検索性能も比較する。
- 数値・日時はネイティブ実行を基準にSQL変換の境界値と表現不能ケースを検証する。SQLへ合わせるための暗黙の精度縮小や日時の丸めがネイティブの保存・実行へ混入しないことを確認する。
- 共通の変換バグを往復だけで見逃さないよう、独立した期待値fixtureと実DB比較を併用する。
- 元DB、Seamless、再構築DBのスキーマ相当情報・全表データ・読み取り結果を比較する。
- 未対応箇所、欠けたメタデータ、依存先の未対応を成功へ数えない。
- Debug・Release、JDBC経路、DataGrip実画面、直接・リモート経路の結果を分けて記録する。

## リスクと対策

- C#の型だけでは元DBの仕様を復元できない: 取り込み元の対応情報を保持し、SQL出力プロファイルで扱う。ネイティブ型をSQL仕様へ変更して埋め合わせない。
- C#とSQLのNULL・算術・文字列・例外の意味が異なる: 共通モデルに意味を保持し、方言ごとの実行比較で検証する。
- 任意メソッドや外部状態をSQLへ移せない: 対応範囲と診断を明示する。
- 定義取得・生成・実行・検証を混同する: 状態を独立して記録する。
- 既存の並行作業を壊す: 未コミット変更、所有情報、lockを確認し、局所的に変更する。

## 未決事項

- ネイティブ型からベンダーSQLへの具体的な出力プロファイルと、補助表現・表現不能診断の契約。手書きC#へSQL用の精度指定を一律に要求する方針は採用しない。
- 元DBの文字数・UTF-16要素数・バイト数と固定容量の対応、全照合順序・文字列キーの意味を維持する変換。固定容量型の物理容量・基本変換契約は初期実装済み。
- Ordinal比較とDB照合順序による比較を区別する具体的なAPI・比較器の契約。手書きC#の固定容量型の==とEqualsをOrdinal比較にする方針は確定済み。
- SQL Serverの小さなfixtureから公開サンプル全体へ拡張する際の、制約・ビュー・関数・ストアド・更新・例外・取引の対応。MySQL実機の往復検証と性能比較は未完了。
