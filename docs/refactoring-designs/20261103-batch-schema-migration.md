# DB作成・一括スキーマ変更・参照整合性

## 背景
2026-11-03に提示した計画について、利用者から実装指示を受領。system表示、空DB作成、GUIと実際のC#プレビュー、DB単位の下書き・一括移行を対象とする。

## 実装した動作
新規DBは名前の入力から空のDBを公開する。テーブル設計とC#編集は同じ個人下書きへ保存し、明示適用まで稼働データを移行しない。移行ではスキーマ配下を含む全表の対応付け・変換・削除を扱う。ネイティブ外部キーは通常更新と移行の最終状態で検査する。

## 過去設計から引き継ぐ仕様
20261102-native-management.mdと20261103-management-usability-local-ipc.mdのC#正本、個人下書き、権限、TLS/同一利用者IPC、明示適用、永続操作ID、既存データの自動変換禁止を維持。

## 目的
複数のスキーマ変更を一つのDBの最終形として一度に移行する。通常更新と移行で自己参照・循環参照を取引全体の最終状態で検証する。移行システムのデバッグを同じ変換コードで実施可能にする。

## 非目的
複数DBの原子的公開、自動連鎖操作、新しい二次索引、実運用DBの自動複製・自動部分抽出。

## 採用設計
- systemをシステムDB名とし、既存保存先と識別子を変更しない。
- 名前入力から空DBを作成し、既存の保存・検証・プレビュー・適用を経由して公開する。
- 最終ソースと明示的な移行定義を同じ下書きで保持し、ハッシュと版照合に含める。名前の推測、暗黙の破壊的変換をしない。
- テーブル・列の対応付け、値変換、削除指定を移行定義に記録。破壊的変更にはバックアップと明示確認を必要とする。
- 関係は同一DB内の主キー参照。複合キー・自己参照・循環参照を含め、通常更新は最外取引の確定前、移行は全表変換後に検証。
- 取引検査の読み取りを競合検出へ参加させ、WAL確定前に拒否可能とする。単独更新も検査を迂回できない。
- スキーマ配下の表を再帰的に列挙し、実体初期化・移行・検証で共用。
- canonical SharedV2の移行先は既存の非公開snapshot構築を使い、全件の変更集合や単一の業務WALフレームを作らない。全表投入後の検査と保存が成功した候補だけを公開する。失敗した候補は再利用せず破棄し、旧世代を維持する。
- GUI設計のC#は参照・コピー可能とし、同じ下書きをC#編集へ渡す。

## 影響範囲
Database、Transactions、Management契約・サーバー・GUI・Tests。既存SQL経路の公開契約を維持し、ネイティブ管理でSQLを生成しない。

## 移行手順
既存DBを起動時に変換しない。新しい宣言・移行情報は明示編集・適用によって導入する。過去版へ戻す操作は、適用前の失敗による旧世代維持と区別する。

## テスト計画
メモリ主体で同じ移行処理を反復し、関係形状と件数を独立に変える。ストレージでは再読込、WAL、取消、容量不足、公開前後の停止と復旧を検査する。GUIは空DB作成、設計とC#一致、一括変更・未適用表示を検査する。Debug/Releaseを明示し、Linux未実行を合格としない。

## リスクと対策
行ごとの外部キー検査は禁止。循環を投入順で解決しない。参照検査は確定前に行い、エラーでDB全体を故障扱いにしない。変更中の他者のソース・プロセスを保護する。

## 検証と運用上の境界
具体的な操作・復旧手順は`tools/management/SchemaChanges.md`、構成別の実行結果は`tools/management/README.md`に記載する。GUI試験はアプリ内部の操作と描画を検証し、OS入力やIDEのF5操作を実行した試験とは区別する。Linux向けpublishとLinux上の実行は区別し、実行可能なLinux環境がない本環境では後者を合格としない。

破壊的変更前に作るDB世代単位のバックアップは、管理領域全体のオフラインrestore入力とは別物である。世代単位を自動復元するCLIは今回追加しない。適用成功後の逆移行・データ復旧は別の明示的な作業として扱う。全資源不足・全停止点・巨大スキーマ・全既存経路の網羅的な製品受け入れは、選択した回帰試験の成功と区別する。
