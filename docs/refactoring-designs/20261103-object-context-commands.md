# 対象から始める管理画面の操作設計

操作配置の方針を維持し、表示・設計の統合、タブ群を下書きとする構成、保存によるビルド・移行については`20261103-object-tab-drafts.md`の追加指示を優先する。新規ノードのEnterは名前の確定までとし、サーバーへの作成・反映は保存時に行う。

## 背景
利用者から、通常DBを追加したい場所と作成ボタンの場所が離れている、DB名の入力は別ダイアログよりツリー内のF2編集が自然、仕様を知らなくても操作位置を予測できるように見直したいとの指摘を受けた。コンテキストメニューだけへ操作を隠すことも求められていない。

## 改修前の観察
- `管理ウィンドウ.カタログ.cs`は作成ContextMenuを`稼働カタログ`（「データベース」）だけに設定し、「通常のデータベース」に専用の操作を用意していない。
- `管理ウィンドウ.設計.cs`の`DB作成Async`は名前入力の専用ダイアログを開く。ツリーノードは文字列Headerで、F2編集はない。
- 上部の操作列に作成・編集・検証・実行・管理が並び、中央の一覧にも同じ作成ボタンがある。対象と関係の薄い操作まで表示する。
- テーブルの変更は、一覧で表を選んでいても別の選択ダイアログで表を選び直す。
- サーバーの`SaveDraft`は既存定義のDB名の変更を拒否する。DB検索、問い合わせの所属、権限、検証DBもDB名を利用している。既存DBの名前変更を表示ラベルの変更だけで実現してはならない。

## 過去設計から引き継ぐ仕様
`20261103-batch-schema-migration.md`のC#正本、個人下書き、最終形への一括適用、競合検出、操作ID、既存DBの自動変換禁止を維持する。`20261103-management-usability-local-ipc.md`の対象・環境・状態の可視化、必要時だけの属性表示、明示実行、段階取得を維持する。

## 目的
利用者が対象を見つけた場所から操作を始められるようにする。同じ操作はツリー、一覧、キーボードのどこから呼んでも同じ対象・権限・処理を使う。画面が現在の対象と操作の結果を示す。

## 非目的
全操作の右クリックへの集約、名前の表示だけの変更、起動時のDB変換、右クリックによる問い合わせの暗黙実行、システムDBの編集許可。

## 提案設計

### 操作の置き場所
| 対象 | 右クリックの主要操作 | 常時見える補助入口 |
|---|---|---|
| 通常のデータベース | 新しいデータベース、更新 | 分類行の追加ボタン。空の場合は同じ場所の作成案内 |
| 通常DB | 開く、新しいテーブル、新しいクエリ、名前の変更、プロパティ | DB名を見出しにした中央領域の操作列 |
| スキーマ／テーブル分類 | 新しいテーブル、更新 | そのスキーマ／分類の一覧見出し |
| テーブル | 開く、設計、名前の変更、C#定義、依存関係 | 選択したテーブルの見出しと操作列 |
| 下書き | 開く、変更を検証、変更を適用 | 「未適用の変更」の見出しと操作列 |
| system | 開く、構造、更新 | 参照専用の説明。作成・名前変更・適用を表示しない |

対応していない機能は、見せかけの実行項目として追加しない。破壊的操作は既存のバックアップ・明示確認を経由する。右クリック時にはクリックしたノードを対象とし、以前の選択対象へ命令を送らない。キーボードのメニューキー／Shift+F10も同じメニューへ接続する。

### 新規DBの名前入力
1. 「通常のデータベース」を右クリックして「新しいデータベース」、または分類行の追加ボタンを選ぶ。
2. その配下に未作成の仮ノードを置き、名前を選択状態のテキスト入力にする。利用者を別ダイアログへ移動させない。
3. Enterで名前を下書きに確定する。サーバーへの作成は保存時に既存の空DB作成処理を使って開始する。入力中にはサーバーのDBを作らない。Escapeではサーバー変更なしで名前編集を取り消す。
4. 入力からフォーカスが離れただけでは作成しない。入力した仮の名前を保持し、再編集できるようにする。
5. 空・予約名・長さ・重複のエラーをノードの近くに表示し、名前を保持して編集へ戻す。サーバー側でも再検証する。
6. 処理中は同じノードを「作成中」とし、二重Enterや更新による二重要求を防ぐ。操作IDを保持する。
7. 成功時は同じ位置で通常ノードへ移し、作成したDBを選択する。応答喪失時は「結果確認が必要」とし、失敗や未作成と断定せず操作IDを照会する。

### F2と既存の名前変更
- F2／右クリックの「名前の変更」は、そのノードの名前だけをインライン編集する。版番号・状態は名前とは別の表示要素にする。
- Enterは編集内容の確定、Escapeは編集開始前の名前へ復帰とする。
- テーブル・列など稼働スキーマの変更は同じDBの下書きに記録し、明示適用まで稼働名を変えない。ツリーにも「旧名 → 新名・未適用」の対応を表示し、下書き側の名前が稼働名に見える状態を作らない。
- 仮DBノードのF2は未作成の名前入力であり、既存DBの名前変更とは処理を分ける。
- 既存DBのF2変更にはサーバー側の正式な名前変更を追加する。内部のDB識別子を維持し、所属問い合わせ・権限・下書き・検証環境などの参照を整合させる。履歴は当時の名前を保持し、同一DBとして追跡する。現在のDB名変更拒否を単純に削除しない。
- 既存DB名の変更も未適用の変更へ載せ、適用時に競合・権限・名前の衝突を再検査する。名前だけの変更によって行データの移行を起こさない。

### 全体のコマンド整理
- 上部の共通領域は接続・アプリ全体の操作を中心とし、選択対象の主要操作はその対象の見出しへ置く。
- オブジェクトタブ内に構造・C#・データ・関係を統合し、選択中のタブの保存とDBのすべて保存を対象の近くへ置く。実行・静的計画・差分は作業内容に応じて表示する。
- テーブルを選んで「設計」を呼んだら、そのテーブルを直接開く。選び直すダイアログを挟まない。スキーマからの作成ではそのスキーマを引き継ぐ。
- ツリーと一覧の同じ対象には同じメニューを提供し、対象IDを渡す共通コマンドへ接続する。表示上の選択、非同期処理中の選択変更、現在編集中の定義を暗黙に混ぜない。
- 対象が変わった際に別DBの編集内容を黙って破棄しない。操作中の対象DB／稼働版／下書き状態を表示する。

## 影響範囲
WPFのツリーノード、右クリックとキー処理、対象別の操作列、DB作成導線、テーブル設計への対象受け渡し。既存DBの名前変更には管理契約・サーバー・権限参照・永続操作の追加が必要になる。

## 移行手順
既存データの初期化や自動変換はしない。作成導線は既存の空DB作成処理を再利用し、同じ処理を複数箇所へ複製しない。既存DB名の変更は名前を使う参照の調査とサーバー側の整合性保証を完了してから画面のF2と接続する。

## テスト計画
実画面で分類の右クリック→仮ノード→名前→Enter→作成、Escape、空／重複／予約名、フォーカス移動、二重Enter、切断後の結果照会を確認する。選択と右クリック対象が異なる場合、表の直接設計、スキーマの引継ぎ、権限不足、systemの参照専用、未保存編集の保持を回帰確認する。既存DB名の変更は依存問い合わせ・権限・下書き・検証DB・履歴・再起動後の整合性と、名前変更だけで行移行が起きないことを検査する。

## リスクと対策
インライン編集の確定と稼働版への適用を混同させない。作成途中の仮ノードを通常DBとして列挙しない。失敗・結果不明で名前や操作IDを失わない。一般的な操作は右クリックだけへ隠さず、対象の近くの見える入口も残す。

## 実装範囲

上部の共通操作を「下書き」「検証・実行」「サーバー」に整理した。新規DBは通常DBの分類行、新規テーブルはDB・スキーマ・テーブル分類、既存表の設計と削除予定は対象表から開始する。分類行の「＋」とDBの一覧見出しにも作成の入口を用意した。ツリー内の新規DB名はF2で再編集でき、「作成」を押すと既存の空DB作成処理を呼ぶ。対象別の手順は[テーブルタブの操作](../object-table-tabs.md)を参照する。

既存DBの名前変更はサーバー側の参照整合性を伴うため、F2の実装範囲は新規DBの入力行に限る。
