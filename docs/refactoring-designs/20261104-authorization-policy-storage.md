# 共通認可ポリシーのシステムDB保存

## 背景と観察
`20261103-authorization-runtime.md`を引き継ぐ。`AuthorizationManager.ApplyDatabaseChange`は確定コールバックの後でメモリの版を公開するが、実際のsystem DBへの保存・復旧は未接続である。管理操作・ネイティブ・SQLで共通認可を使うため、先にこの確定境界を接続する。

## 守る仕様
DB内の通常権限はDB管理者へ委任できる。管理権限の再委任はサーバー管理者だけに許可する。明示拒否、対象ID、基準版、開始時の権限と監査を保存する。通常の変更は開始済みリースを変更せず、次の操作から反映する。未知・破損した保存状態を旧権限への自動フォールバックで通さない。

## 実装
`Seamless.Security`へ版付きの不変な保存文書を置き、スナップショットからの取得と再構築で同じ構造検査を使う。リソース・ロール・規則・割り当てを決まった順で並べ、文書の識別を安定させる。

管理サーバーに`StoredAuthorization`を置く。既存のEntriesと監査テーブルを使い、ポリシー・不変の過去版・小さい変更索引・PermissionChange監査を一つの`ManagementStore.Write`で確定する。インスタンスIDと内容のハッシュを照合する。初期設定は認証済みのサーバー管理者が明示的に呼ぶ内部ホストAPIとし、起動では作成・変換しない。監査テーブルのない形式3には明示的な更新が必要である。

操作を開始するセッションは保存ホストを経由する。同じストアを使う複数のホストでも基準版を照合する。確定後・メモリ公開前の失敗では保存版から再同期し、その結果を確認できなければ新しい操作を拒否する。既に開始したリースは維持する。

ストア内にプロセス限りの変更カウンターを置き、同じストアのポリシーをWALへ確定した後だけ進める。準備中の観測で未確定版を公開しない。ロールバック時はカウンターも戻す。要求ごとのJSON再読込・再構築は行わない。カウンターは保存形式を変更せず、再起動時は保存文書を読み直す。カタログの閲覧対象が変わるため、ポリシー確定では既存のカタログ世代も進める。

一つの操作IDで確定するロール変更は一回とし、操作IDから版・内容識別・変更者を照会できる。複数の規則や割り当ては一つのDB変更要求にまとめる。履歴の一覧は小さいメタデータを100件ずつ返し、ポリシー全文は必要な版を明示して取得する。

`DatabaseTransaction.Commit`は確定要求を記録し、実際のWAL確定はスコープの`Dispose`で行われる。管理ストアはその完了をtry内で待ち、失敗時はメモリ内ヘッダーも戻す。確定結果が未確認ならキャッシュを無効化して保存状態の再確認を要求する。認可の公開を既存の未確定の管理書込へ入れ子にすることは拒否する。入れ子の通常書込が取消状態にした外側の取引も、成功として返さない。

## 検証
JSON往復・並び順・不正文書、権限の継承と拒否、再起動、同じ基準版からの同時変更、DB管理者の委任境界、確定前の例外と監査失敗、確定後の応答喪失、旧リースと次の操作、チャンクをまたぐ大きな文書、破損・別インスタンス・形式3の拒否を確認する。開発用の障害注入点をネットワークAPIへ公開しない。

## 導入と残る作業
今回は保存ホストと操作リースの実装段階である。既存の利用者・DBを自動で新しい主体・対象IDへ変換しない。管理・ネイティブ・SQLへの接続、認証元設定、アカウント無効化の永続化、GUIの権限編集、Linuxの実行検証は引き続き必要である。保存ホストの完成だけで、既存の通信経路が共通認可で保護済みとは扱わない。

利用者から承認済みの共通認可・システムDB保存・明示移行の実装を進める。稼働中の利用者DBや既存設定に対する導入操作はこの作業では行わない。
