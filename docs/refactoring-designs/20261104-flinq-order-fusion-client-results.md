# FLinqの順序・融合とクライアント結果の保存

## 背景と目的

同じ結果を返す範囲で、キー型の生成、ハッシュと比較、繰り返し走査、中間結果の保持、通信前後のコピーを減らす。Join・集合演算の順序、拡張メソッドと展開時の責務、クライアント側の結果の寿命を別々に決める。

## 提案設計

### Joinと集合演算の順序

順序には、式の評価順、Lookup等を準備する順、結果を返す順の三つがある。内部の準備を並列化しても、利用者から見える式の評価と出力の順序は別途保つ。

| 操作 | 標準経路 | 条件付きの高速経路 |
| --- | --- | --- |
| Join・GroupJoin | 内側Lookup、外側の初出順、各一致列の内側順 | 適合する同一snapshotの索引で内側を点・範囲照合する。別の構築側やMerge Joinは、比較規則・重複・null・内側順とcallbackの評価を維持できる計画だけに限定する。再整列が要る場合は費用を含めて測る。 |
| Union・UnionBy | 左を読み、次に右を読む。キーごとに最初の行を下流へ流す。 | 同じ比較規則の連続Unionは訪問順を保ったまま一つのseen集合で処理する。 `Any` 等では、判定とcallbackの契約から重複除去の省略を証明できるときだけ省く。 |
| Intersect・ExceptとBy系 | 右のキーを準備し、左を左の順序で走査して代表行を選ぶ。 | 安定した既存キー集合の照合、値域が確認できる整数のbitset、索引・ハッシュの使い回し。右の準備を省く条件には、右の列挙の副作用と失敗も含める。 |
| OrderBy・ThenBy | 同じキーは上流順。ThenByは直前の整列に追加する。 | 既知の順序と比較規則が一致すれば整列を省く。 `OrderBy().Take(k)` は上流順で同順位を解決する有界top-k候補。キーの評価回数・順序を保つ。独立したOrderByの連鎖は前段が後段の同順位を決める。 |

公開順序を要求しないSQLの内部計画では、依存関係のない結合の構築側や結合順を候補にできる。LINQの `a.Join(b).Join(c)` は、キーや投影の依存、例外、副作用、出力順を持つため、既定では式の順序で扱う。 `Take`、Anchor、カスタム比較器、未知のcallback、再列挙可能性、別snapshotは変形を止める境界として扱う。

例として、左に `(Id: 3, Name: "旧")`、右に `(Id: 3, Name: "新")` がある `UnionBy(Id)` は「旧」を返す。後続が `Name == "新"` を調べると、正しい結果は空になる。この条件をUnionByの両入力へ押し込むと「新」が代表になり、結果が変わる。高速化後も最初に選ぶ行は元の訪問順で決める。

#### 主キーで照合するJoin

取引コレクションの `TryGetValue` は、自己変更を先に確認し、更新・挿入を返し、削除は欠損として扱う。その後は同じ取引の読取版から読む。生成器が候補にできるのは、同一取引が所有する内側の未加工の表と、比較規則を含めて一意な主キーそのものを読む内側キー式を証明できる場合。表のキー型とセレクターの戻り値型が一致するだけでは不足する。たとえば `row => row.Id % 64` は同じ整数型でも主キー索引を使えない。列名による推定も避け、生成された表定義を根拠にする。

外側を元の順序で進め、各行から最大1件を照合する。外側が空なら内側を開かない。通常Joinは、内側に有効なキーがないときに外側キーを評価せず終了するため、最初の外側行を得た後に内側の有効行の有無を確認する。GroupJoinは空の内側でも各外側行を処理するため、同じ早期終了は適用しない。独自比較器、途中のフィルター・射影、任意コードを実行する内側セレクターは、現行Lookup経路へ残す。

版付きの現行経路では走査が表単位の読取りを記録する。点照合はヒット・ミスの双方でキー単位の読取りを記録するため、単純な置換では競合判定が変わる。最初の実装では、外側が空でないときに、従来と同じ表単位の読取りを維持する。内側が空なら最初の挿入も観測対象にする。表単位の観測を外す案は、直列化可能性と既存の競合挙動を個別に検証する。

##### 宣言上のキーと実体のキーの照合

`Table<TKey,TRecord>(selector, name)` はコンテナ内で名前により表を共有する。最初に同じ名前で作った表が、実際のキー式を決める。試験では `ById => Table(row => row.Id)` と `ByOther => Table(row => row.Other, nameof(ById))` が同じ表を参照した。`ByOther` を先に開くと、`ById` を走査する通常Joinは `Id=7` の行を返したが、`ById.TryGetValue(7)` は失敗し、`TryGetValue(31)` で同じ行を取得した。先に `ById` を開くと索引結果は逆になった。証跡は `F:/CodexTemp/Seamless/flinq-index-proof-20261104/comparison-88e22525`。

採用候補は、表実体を初めて作るときに、索引を作ったキー式・比較契約と一緒に識別情報を記録し、FLinqが生成した期待値と照合する方式。表プロパティを構文解析しただけでは採用しない。キー式の証明は、最初は副作用のない直接のメンバー読み取りで、宣言とJoin双方のメンバーシンボルが一致するものに限定する。表作成時の証明がない場合、同名別定義が先に表を作った場合、比較器が異なる場合は、内側を再評価せず同じ取得済み表から現行Lookupを構築する。既存の通常表や手書きの表は、実体側の証明を伴うまで従来経路を使う。

表は作成時のキーdelegateを既に保持している。試作では宣言側と照合側が同じ名前付きstaticキー関数を使い、表が保持するdelegateと比較した。同名の別定義が先の場合はLookup、正しいキー定義が先の場合は点照合が選ばれ、どちらも同じ行を返した。試作のreflectionは既存のprivateフィールドを観測するためだけに使った。製品では表または取引参加者の内部で照合し、既定比較規則も検証する。生成器が名前付きキー関数を共有できる表から始めれば、キー名を別途永続化する必要はない。証跡は `F:/CodexTemp/Seamless/flinq-index-selector-identity-20261104/comparison-80de6c69`。

点照合には、既定の等値比較と物理索引のキー表現が同じ値を同一視するという条件も必要。SharedV2のCanonicalV1表で、挿入した `decimal` の `1m` を `1.00m`、`double` の正のゼロを負のゼロで照合すると、通常LINQのJoinは両方で一致し、同じ取引の `TryGetValue` は両方で欠損を返した。挿入値と同じ表現での照合は成功し、対照の `int` でも両方式が一致した。実装の初期対象は、既定のCanonicalV1で符号化と等値比較の対応が確認できる整数キーとする。浮動小数点、decimal、利用者定義のcodecや複合キーは、個別にこの条件を確認するまでLookupへ送る。証跡は `F:/CodexTemp/Seamless/flinq-index-key-encoding-20261104/comparison-539edc11`。

取引行ソースに生成コード用の `TryGetJoinIndex` を追加した。読取り専用取引が使う実際の版付き参加者で、独自codecのないCanonicalV1整数キーと、生成器が証明したキーdelegateの一致を確認する。成功時は同じ取引の点読み取りだけを行える値型ハンドルを返す。この判定は行を読まない。生成コードは外側の最初の行を得た後に内側の有効行を確認し、判定に通らないときは同じ内側ソースからLookupを構築する。

FLinqは、未加工の取引行を内側に取り、表のキー型が一致する既定比較の `Join` で、値型の直接メンバーを読む名前付き静的関数を確認できる場合に分岐を生成する。生成された型付き取引の表を直接参照する場合は、`row => row.Id` のような内側ラムダが読むメンバーと、対応する表宣言の名前付きキー関数が読むメンバーをRoslynのシンボルで比較する。一致したときは、表宣言にあった関数を実行時の実体照合に渡す。点照合では最初の外側行を得た後に内側の先頭だけを調べ、空なら外側キーを評価せず終了する。判定に通らなければ同じ内側ソースでLookupを一度だけ構築し、結果の処理後に解放する。整列専用終端、明示的な複数実行枠、`GroupJoin`は既存経路を使う。

表宣言が `Table<int,Row>(static row => row.Id)` の場合も、整数キーと、生成コードからアクセスできる副作用のない直接メンバー読取りを証明できれば対応する。FLinqは表を作る呼び出しを傍受し、同じメンバーを読む名前付き静的関数を渡す。Joinも同じ関数を実体確認に使う。最初に別のキーで作られた同名表は実体確認で拒否される。行の形式とキーの符号化は変わらない。対象はInterceptorsが有効な同じコンパイル内の式本体の表プロパティ。対象外の宣言は従来の表作成とLookupを使う。内側のソースまたはキー式に `Anchor` がある場合も、内側を走査するLookupを使う。

既存の `QueryResultBuffer<T>` は構築時の配列とpayloadを予約し、配列を呼び出し元へ渡す。結果ハンドルで受信後も予算を管理する場合は、ハンドルのDisposeまで予約も保持する。メモリ側は固定長の分割領域を候補とし、全体の再配列化や容量拡大時の全コピーを避ける。ファイル側へ切り替える間は、読み出しているメモリ領域と書き込んだファイルの両方を計上し、書き終えた分からメモリを返す。

`IAsyncEnumerable<T>` から集める場合は、列挙開始時点で格納方法を選べても、列挙子が返す時点で各行のデコードは済んでいる。直接保存を製品に載せる場合は、列挙子の後段ではなく、`NativeQueryClient.QueryProjectedAsync` の行フレームを受け取る場所で格納方法を分ける。モジュール・結果型の契約、接続ゲート、取引の入退場、CompletedとRecoverableErrorの処理を一つの受信ループで扱い、行を型へ変換するか、検査して所有結果へ追記するかを選ぶ。保存側を別のアダプターに置けば、逐次受信だけを使うクライアントの依存はMemoryPackのままにできる。結果型に対応する検査器と確認済みのデコード経路がそろわない場合は、通信開始前に型付き経路を選ぶ。受信途中で保存予算を使い切った場合は部分結果を破棄する。書込みを伴う可能性がある要求は、この失敗を理由に自動で再送しない。

### クエリ内部の並列化を明示指定に移す案

現行では、DBクエリの通常・整列付きJoin／GroupJoinと、通常・整列付きGroupByの4つの生成経路が、キー型と比較器から `allowParallel` を指定する。実際の起動にはcodecとCPU枠も必要。表走査とselectorはproducerが担当し、`PartitionedLookupBuilder` が格納用workerを起動する。調査したクエリ実行の生成器とランタイムでは、独立した内部workerを起動する箇所はここに集約されている。取引の保守タスクは別に扱う。

既定はクエリ内1 workerとし、独立したクエリがCPU枠を分け合う方向で検討する。提案する `.Parallel(2)` は直前の対応演算子に付けるヒントで、その演算子に使うCPU実行枠をproducer込みで最大2とする。たとえば `outer.Join(...).Parallel(2).OrderBy(...)` では、JoinのLookup構築が対象。後続の整列には適用しない。融合や書き換え後も元の演算子との対応を保持する。既存の `MaximumQueryWorkers` は設定上限として残し、実際の並列数はヒント、設定上限、利用可能CPU枠、安全条件に従う。

展開の差はLookup構築の指定枠。1枠ではproducerが走査・キー評価・Lookup登録をその場で実行し、追加のタスクとバッチキューを作らない。2枠を使えるときはproducerが走査とキー評価を行い、1つの追加タスクがキューからバッチを取り出してLookupへ登録する。両方とも、最初の外側行を確認してから内側のLookupを構築し、構築完了後に外側の行を順に照合する。2枠は二分割という意味ではなく、現行モデルに沿えばproducerとLookup構築担当が1つずつ動く。現行の `PartitionedLookupBuilder.WorkerCount` はLookup側の担当数で、インライン構成でも1なので、ヒントの値とは区別する。

ユーザー合意済み。上限はproducer込みとする。引数がコンパイル時に1と分かる場合は逐次構築を選ぶ。実行時にのみ決まる場合は式を一度評価し、結果が1を超える場合のworker起動経路を用意する。実際の値が1ならworkerを起動しない。ランタイムの `PartitionedLookupBuilder` に `maxExecutionSlots` を追加し、値と既存の設定上限・CPU容量の最小を使う。既存のbool引数は引き続き同じ動作で呼べる。

生成器は、専用の取引Lookup終端へ接続できるJoin／GroupJoin／GroupByの直後に、一つの拡張構文のヒントを受け取る。対応経路では、ヒントなしと定数1は `allowParallel:false` を生成し、それ以外は式を一度評価・検証する。比較器やcodecが並列化条件を満たさない場合は逐次で構築する。Join／GroupJoinではヒントを入力断片に固定し、その後の段を通常どおり正規化する。GroupByでは集約融合や射影の取り込みで段を作り直す際にヒントの印を引き継ぎ、正規化後の段に再接続する。明示指定のGroupByをキーだけの走査に置き換える変形は保留する。生成器がパイプラインを構築する際に、未対応の指定位置、複数指定、専用の取引Lookup終端へ接続できない形を検出した場合は、既存の展開失敗警告 `FLINQ002` と、理由を含む例外を生成する。生成器を通らない呼び出しでは、拡張メソッドが引数を検証して入力列を返す。

MemoryPack 1.21.4で、負の値を拒否するコンストラクターとsetterをそれぞれ持つ型を試した。正しい1メンバーのフレームを作り、整数だけを7から-1へ書き換えた。両方とも `NativeWireValidation` の構造検査を通過し、デシリアライザーは `ArgumentOutOfRangeException` を返した。正常値を一度デコードして型付きで保持し、2回再列挙した場合は、コンストラクターやsetterの呼出しは増えなかった。証跡は `F:/CodexTemp/Seamless/flinq-client-decoder-contract-20261104/probe-59904507/run/stdout.log`。

直接保存の自動選択には、構造を検査できることに加えて、再生で使うデコーダーを制御できることが必要。製品候補は、生成器がフィールドへ直接書き込み、配列やネストした型にも同じ条件を確認できる結果型から始める。公開のレイアウト属性はフィールド構造の情報として使う。利用者のコンストラクター、setter、カスタムformatterを呼ぶ型は、受信時にデコードし、行が復元できた時点で型付きの保存へ渡す。デコードに失敗した場合、Completedを受け取る前に部分結果を破棄する。
