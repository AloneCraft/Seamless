# 管理APIのソース閲覧境界

## 背景と観察
共通認可への接続調査で、現行のGetDefinition・VersionがViewだけでC#ファイルと移行式を返し、ObjectSourceもカタログ閲覧から同じ定義を返すことが分かった。AnalyzePublishedとPlansもソース由来の表示・デバッグ情報を返す。「本体ソースとデバッグ情報は許可された開発者だけ」という合意と整合しない。

## 引き継ぐ仕様
現在のManagementPermissionではEditを開発者のソース閲覧権限として使う。公開メソッドの名前・引数/戻り値のシグネチャ、オブジェクトの構造、許可された公開問い合わせの実行は一般の閲覧・実行とする。Seamless.SecurityのReadSourceへ統合する際も、この境界を維持する。

## 設計
定義全体・過去版・ソースに対応する解析/計画にはViewとEditを要求する。ObjectSourceは利用者DBでEditも確認する。カタログの列・型・キー・引数・戻り値はViewで取得できるが、ソース位置・ファイル名はEditがない場合に返さず、Permissionの理由を表示する。systemは構造参照のままとする。

definitionInfoという本文を含まない取得を追加し、定義ヘッダー・公開版・DLL識別とテンプレートを除いたメソッド情報だけを返す。公開問い合わせはExecuteでもこの公開契約を参照できる。既存の定義一覧は本文を持たず、実行は引き続きサーバー側のExecuteを確認する。CreateValidationは定義をサーバー内で使用し、View/Validateを確認して本文を返さない。

GUIでは編集権限がない公開定義の選択で本文を要求せず、公開情報と権限の案内を表示する。公開問い合わせの実行は選択したノードの近くの操作から行い、既存のJSON引数入力と結果表示を使う。オブジェクトの構造は閲覧でき、本文への入口は権限不足と未登録を区別する。未保存編集の切替確認を維持する。旧サーバーでもクライアントから無権限の本文を要求しない。

## 検証と境界
View/Execute/Validateのみの利用者が現在定義・過去版・解析・計画・オブジェクトソースを取得できないこと、開発者が取得できることを先行テストで確認する。構造と公開情報・実行・検証DBの操作は必要な権限で利用でき、応答に本文のマーカーが含まれないことを確認する。TLS/IPCとWPF内部操作をDebug/Releaseで実行する。旧テストのViewでソース解析/計画を取得する期待は、明示済みの製品方針に合わせて更新する。

保存データや既存DBの権限を自動変換しない。全入口の共通認可・操作リース・権限版の監査への接続は引き続き残る。今回の修正だけで統合認可を完成とは扱わない。
