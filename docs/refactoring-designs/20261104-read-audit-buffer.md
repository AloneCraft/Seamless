# 正常読み取りの有界集計バッファ

## 背景と引き継ぐ仕様
形式5の値ベースの集計識別とバッチ再送を使い、正常読み取りを既定5秒ごとに保存する。検索の応答で保存を待たず、保存障害時も検索を継続する。待機メモリ上限に達した分は欠落として表示する。集計期間は質問への回答待ちであり、保存間隔から推測しない。

## 設計
ReadAuditOptionsは集計期間を必須にし、保存間隔の既定だけ5秒とする。既存のサービス生成契約を維持し、明示オプションがない場合は収集未設定と表示する。CLIではread-audit-window-secondsで期間を明示設定でき、read-audit-save-secondsで保存間隔を変更できる。形式3/4は明示更新が必要で、自動移行しない。

公開済みの正常な読み取りが列挙を完了し、DBの読み取りスコープと資源を解放した後に、利用者・DB・問い合わせ・実DLL・権限版が取得できた範囲のキーへ1件を加える。日時はUTC固定窓へ束ねる。検証DB、下書き、失敗、取消、列挙中断を成功数へ加えない。引数や結果は保持しない。現在の管理認可では権限版が渡らないためnullとする。

バッファはキー数と概算保持バイト数で制限する。記録は短いメモリ内lockだけとし、DBアクセスや保存待ちを行わない。一度に最大1024キーを不変のID・配列へ切り出し、保存はlock外で一つずつ行う。応答喪失・保存失敗では同じIDと内容を保持して再送する。処理中の分も容量上限へ含め、新しい記録を別のバッファへ追加する。1回の保存周期の処理量も上限を持ち、新着のために無限に保存を続けない。

保存周期の開始時の受付順序を境界にし、その後に追加された新しいバッファ行は次の周期へ回す。保存中に同じキーの新着が続いても、そのキーを同じ周期に繰り返し保存して他のキーが処理されなくなる状態を防ぐ。

状態は起動セッションごとの受付・保存・既知の欠落・待機キー/バイト・保存障害・最終保存時刻を返す。異常終了で最後の未保存分が失われる量は分からないため、既知の欠落が0でも完全な監査とは表示しない。APIは管理権限を要求し、GUIの集計表示へ取得状態を併記する。例外の本文・パス・引数を状態へ返さない。

終了時は新規受付を止め、実行中の保存を待ってから残りを保存する。保存失敗で停止した残りは、未送信なら既知の欠落、送信済みで確定を確認できなければ結果未確認として区別する。保存済みのバッチを成功応答喪失で再加算しない。同時に終了を要求した呼出しは同じ終了Taskを待ち、片方だけ早く戻さない。詳細な更新監査とは別の経路とする。

## 検証
先行テストで、複数キーの合算、処理中の同キー追加、保存応答喪失後の再送、容量超過でも記録側が待たないこと、同時記録、停止時の保存・失敗時の欠落、既定5秒の周期を確認する。実行経路では公開読み取り成功、失敗・列挙中断・検証DBの除外、保存された実DLL識別を確認する。管理APIの権限・TLS/IPC、GUI状態と既存操作をDebug/Releaseで確認する。

## 境界と未決事項
集計期間の既定、指定DB/問い合わせの詳細読み取り記録、共通認可からの権限版、他通信入口、Linux・1万クライアントの性能は別の残作業。既存の合意に沿う内部接続とし、未回答の期間を既定値で補わない。
