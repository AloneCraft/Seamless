# Gateway HTTP APIの認証と認可

## 背景

HTTP APIはKestrelで待ち受ける。インターネット公開を運用上選択できるようにする。利用者と組織の認証、DB・スキーマ・オブジェクトの認可を、合意済みの共通ポリシーへつなぐ。

## 現状の観察

- `HttpServer.ServeAsync` は接続の中断とホスト停止を要求の取消へ結び付ける。`HttpEndpoints` は `X-Seamless-Session` から `HttpSessionStore` の状態を取得する。このトークンはHTTP取引の継続用で、利用者の認証とは独立している。
- `SqlExecutionEngine` は既定DBのほか、`USE`、DB名付き参照、ビューやルーチンを解決する。入口の `database` パラメーターだけを判定しても、実行時にアクセスする対象は制限できない。
- `OidcTokenVerifier` は設定した発行元・APIの対象・署名・期限・scopeを確認し、認証元から現在の所属を取得する。`OidcAuthorizationSession` と `AuthorizationLease` は本人確認、所属の鮮度、操作と明示取引の期間を扱う。
- 管理サーバーの `StoredAuthorization` は管理領域にポリシーを保存する。スタンドアロンの保護Gatewayは同じ実装を使い、起動時に管理領域を排他取得する。

## 過去設計から引き継ぐ仕様

[共通認可とOIDCの実装境界](20261103-authorization-runtime.md)と[認可ポリシーの保存](20261104-authorization-policy-storage.md)に従う。対象には安定した論理IDを使い、権限の継承と明示拒否を適用する。通常の権限変更は新しい操作に適用し、無効化は実行中の操作にも取消を要求する。所属の既定の鮮度は5分、明示取引の既定の上限は30分。

## 目的

HTTPSのHTTP APIで、検証済みのアクセストークンに対応する主体と最新の権限で操作を受け付ける。SQL、オブジェクト一覧、HTTPセッション、操作結果照会で同じ主体を使う。

## 非目的

既存DBや認可ポリシーの自動移行、クライアント申告の主体やグループへの信頼、接続トークンによる権限付与、認証プロバイダーの独自実装は扱わない。

## 提案設計

1. 保護するHTTPリスナーを明示設定する。Bearer資格情報を受け付けるリスナーではHTTPSを要求する。Kestrelと `HttpEndpoints` の間で、設定したAPI用のアクセストークンを `OidcTokenVerifier` で検証する。IDトークンはAPI資格情報として受け付けない。主体情報やトークンの本文をログに出さない。
2. 信頼できるポリシーをホストから取得し、`AuthorizationManager` を共有する。HTTP側は非同期に操作リースを取得し、その主体が検証済みトークンと一致することを確認する。取得に失敗した場合は新しい要求を止める。Gatewayと管理サーバーのプロセスが分かれる場合は、インスタンスと版の一致を検証する。静的なコピーを最新ポリシーとして扱わない。
3. セッションを認証元IDと主体IDの組へ束縛し、セッション取得と取消・終了でも照合する。セッションを使わない要求も各操作で認可する。結果の照会は対象操作への権限を検査する。
4. カタログは許可済みの対象に絞る。DBの解決結果は、操作開始時のポリシー内のDB種別と同名の対象へ対応する場合だけ使用する。SQLは実行時に解決したDB、スキーマ、表、ビュー、ルーチンを共通認可へ渡す。修飾名、`USE`、複文、遅延列挙、ビューや関数の展開が認可を迂回できないようにする。保護モードで対象の解決と認可が実装されていない経路は拒否する。
5. HTTP取引の操作では開始時に取ったリースを確定・取消まで保持し、緊急停止と継続時間上限を取引へ伝える。HTTPの複数要求にまたがるセッションは、各要求の接続寿命とは独立している。途中の要求の切断と、セッションの明示終了・期限切れを区別し、未確定変更を解放する。

## 影響範囲

`HttpServer`、`HttpEndpoints`、`HttpSessionStore`、`SessionContext`、SQLの対象解決、Gateway起動設定、認可ポリシーの取得経路、配布時の依存物を対象とする。既存のURL・JSON・セッション・取引のヘッダーは維持する。

### 対象IDと実行経路の確認

- 永続GatewayのDBは共通WALのIDと数値のDB IDで区別される。生成テーブルは `GatewaySchemaCatalog` の永続テーブルIDを `TableMetadata.StableObjectId` に反映する。これらのIDと認可側のUUIDを、対象インスタンスに束縛して照合する境界が必要である。DB名・スキーマ名・テーブル名は表示と対応の整合性確認に使う。削除後に同名で再作成した対象へ旧IDの許可を引き継がない。IDを確定できない対象は保護モードで隠す。
- `GET /api/tables` は、要求のDBを解決した後、実際に列挙したテーブルごとにIDを取得し、操作開始時のスナップショットで `Discover` を確認してから列名と型を返す。テーブルの行を返す `GET /api/tables/{table}` は `Read` の確認を必要とする。認可と読み取りに同じ世代のアダプターと同じ解決結果を使う。DBの一覧権限をテーブルの一覧・行取得へ代用しない。
- SQLの `DatabaseRegistry.FindTable` は、実テーブルに加え、ビュー、一時表、システムカタログも返す。保護HTTPで有効な単一SELECTは、物理テーブルの解決と読み取り権限を結び付ける。ルーチン解決、複文、実行プランの再利用は独立した入口である。これらを開く場合は、対象解決時と実行時に操作リースと対象世代を検査する。

埋め込みホストのテーブル参照では、ホストが解決済みDBアダプターと永続テーブルIDから共通認可のリソースIDを取得できる場合だけ、表一覧・表の行取得を開く。リースの対象が表であることに加え、表名、スキーマ、親DBを確認する。公開世代のDB読取リースを取得し、表の解決と行の取得に同じアダプターを使う。対応付けがない、IDが変わった、または別スキーマ・別DBのIDが返った表は一覧から外し、直接取得も拒否する。任意のSQLと配布CLIの認可接続はそれぞれ別の段階で検証する。

追加の回帰条件には、同名で異なるDB、別スキーマの同名テーブル、削除して同名で再作成したテーブル、同じSQLを別主体が再実行する場合を含める。古い対象への許可が引き継がれず、権限不足で拒否した更新が一部も確定しないことを確認する。

## 移行手順

明示取引は、保護HTTPセッションと開始時の認可リースに束縛する。`BEGIN TRANSACTION` には有効なサインインを要求する。継続要求は既存のセッショントークン、取引ID、開始時と同じBearer資格情報を使う。資格情報のダイジェストだけをメモリに保持し、取引内ではサインインの期限切れや通常の権限変更でリースを差し替えない。上限超過・無効化・通信途中の取消で未確定取引を解放し、確定後は次の要求に新たな認証と認可を要求する。

外部の認可元を待つホストは、取消トークンを受け取る取引開始コールバックを使う。認可の取得待ちにはHTTP要求の取消を伝え、取得した取引用リースの寿命は要求の寿命から独立させる。取得完了前に要求が取り消された場合は、返されたリースを破棄してDB取引を開始しない。

通常要求の認可も、取得直後に要求の取消を確認し、取り消されていれば返却されたリースを破棄する。実行中の取消は、要求と認可リースの両方から受け取る。遅れて返ったリースが要求トークンを保持しない場合でも、切断済みの要求を実行しない。

単独の `INSERT`・`UPDATE`・`DELETE` は既存のSQL更新経路を使い、取引内で解決した物理テーブルを行変更前に認可する。更新種別の権限を要求し、更新・削除で対象行を条件や式から参照するため `Read` も要求する。利用者が記述した式は保護カタログで束縛する。保存定義に含まれる既定値・計算列・制約はDB内部の処理として引き続き検査する。明示取引では各文を別のHTTP要求として受け付ける。複文は拒否する。

定義の公開者は `SqlObjects` の各エントリに、定義内で読むことを許す同一DBのテーブルのリソースUUIDを `DelegatedReadResources` で指定できる。委任は定義の公開世代に固定し、入口の `Read` または `Execute` を要求する。呼び出し元の明示拒否は優先する。委任はその定義のバインド中に限り、外側のSQL、関数の呼び出し引数、別のビュー・関数の定義へは継承しない。委任対象は正しい種類・親DB・テーブルの永続ID対応を持つ場合に限る。

保存カタログに永続オブジェクトIDを持たないビューとSQL定義のスカラー関数は、WAL・DB・公開世代・種類・スキーマ・名前をポリシーのUUIDへ明示的に対応付ける。公開世代のIDは再起動で維持され、再生成で変わる。同名再作成や定義変更に古い対応を引き継がない。ビューの `Read` とスカラー関数の `Execute` を検査し、展開した定義内の参照にも呼び出し元の権限を適用する。定義を検査できない生成済みデリゲートは別段階とする。

保護HTTPのSQLは単一の `SELECT` または `INSERT`・`UPDATE`・`DELETE` を共通SQLバインダーと更新経路へ接続する。既存の互換プロファイルやバッチ実行器を経由させず、要求ごとのカタログを使って実際に解決したDBと物理テーブル・ビュー・SQL定義のスカラー関数の権限を検査する。既存の世代検査と読取リースを使い、主体とリースを保持した計画は共有キャッシュに置かない。ストアドプロシージャ・テーブル関数・システムカタログ・一時表・`USE`・複文は、対応する認可経路が完成するまで拒否する。

スタンドアロンの保護モードでは、Gatewayプロセス自身が指定した管理領域を排他取得し、`StoredAuthorization` を同じプロセス内で使う。初期登録で検証したOIDC設定はポリシーと同じ取引で保存し、起動時は保存済みの発行元を使う。起動設定で管理インスタンスIDとGatewayの共通WAL IDを固定し、解決したDBの永続IDと表IDをポリシーのリソースUUIDへ対応付ける。HTTPSがない場合、保存済みの設定がない場合、インスタンスが違う場合は起動を拒否する。初期版のこの起動経路では、同じ管理領域を別のWindowsServerと同時に開けない。別の管理プロセスからの更新を接続するには、同一ホスト化または認可専用の通信経路が必要である。

隔離環境でOIDCとポリシーの注入を接続し、先にカタログとセッションの主体を検証する。次にSQLの解決箇所を保護し、実行と取引まで検証する。互換用の既存HTTP入口は公開用の認証済み入口と区別して記録する。既存の公開範囲や運用データを自動変更しない。

## テスト計画

- HTTPSで有効なAPIアクセストークンを検証する。欠落、期限切れ、誤った発行元・対象、署名不一致、IDトークンを拒否する。認証失敗は401、認証済みだが権限不足の場合は403で確認する。
- ブラウザー向けのCORS事前確認にBearerを要求せず、認証拒否とポリシー障害の応答にもCORSヘッダーを付ける。保護リスナーの応答には `Cache-Control: no-store` を付ける。Windows Debug／ReleaseのHTTPS実接続で、事前確認、401、503、認可済み一覧の各応答を確認した。
- 他主体のセッショントークン、別DBへの修飾名、`USE`、複文、ビュー・関数内の参照を使って認可の回避を試みる。拒否した文で書き込みや履歴が部分適用されないことを確認する。
- 権限変更後の次の操作、開始済み取引、取引期限切れ、利用者無効化、所属再確認の障害、ストリーミング中の切断を検証する。
- WindowsとLinuxで隔離プロバイダーを使い、実際のHTTPS接続と配布成果物を確認する。

## リスクと対策

認証の入口だけが通っても、SQL経路の認可が済むまで公開向けの受け入れ条件を満たさない。ポリシー版の取得と対象解決のどちらかが不確かな場合は、保護モードで要求を拒否する。通信エラーを理由に更新要求を自動再送しない。

## 未決事項

保護HTTPは、トークンを検証した後、要求ごとにホストから認可リースを取得する。現行ポリシーを確認できずホストがリースを返さない場合は、既存HTTPセッションの操作も503で拒否する。開発用認証元を使ったWindows Debug／ReleaseのHTTPS実接続で、拒否とポリシー取得再開後のセッション継続を確認した。オンラインのDB権限編集は後述の認可専用管理RPCへ接続した。外部の組織認証元での互換性、未対応SQLの対象解決と認可、GUIからの権限編集と永続アカウント無効化は引き続き検証・実装する。

Windows Debug／Releaseの関連試験は各37件合格した。HTTPSで主体・DBの誤対応を拒否し、管理DBに権限の解除を確定した直後の要求からDB一覧が変わることを確認した。TRXは `F:/CodexTemp/SeamlessTdsHeader-76f75b77/gateway-pkcs-final` の `https-subject-scope-fixed-result-Debug` と `https-subject-scope-fixed-result-Release`。永続ポリシーの更新側とHTTP側は一つのプロセスで同じ管理DBを所有する構成で検証した。

実際のHTTPS接続で、API用トークンとIDトークンの区別、DB一覧の絞り込み、他主体のHTTPセッションの拒否、認可元が利用不能な場合の拒否を確認した。対象の対応付けがない状態では表一覧・表の行取得・SQLを拒否する。別試験では管理DBに確定したポリシーを次のHTTP要求に適用した。TRXは `F:/Seamless/Verification/gha31d444ec`。認可を注入して起動した試験サーバーでの確認で、配布CLIからの起動は対象に含まれない。

配布CLIと同じ起動処理を通す試験では、許可済み表のCTEと集約、結合先・別DB・別主体の拒否、更新文・`SELECT INTO`・複文の拒否、本文超過の応答と次の要求を確認した。認可関連のWindows Debug／Releaseは各35件合格。TRXは `F:/Seamless/Verification/hsq18459d24` の `result-Debug` と `result-Release`。

ビューとスカラー関数を追加した後、Windows Debug／Releaseの認可関連試験は各35件合格した。許可したビューと関数、定義内の未許可参照、同名で世代IDが一致しない設定を実接続で確認した。TRXは `F:/Seamless/Verification/hsob8d33b35` の `result-Debug` と `result-Release`。

明示取引を追加した後、Windows Debug／Releaseの認可関連試験は各35件合格した。サインイン期限後の確定、別の資格情報の拒否、明示ロールバック、取引期限超過後の未確定行の解放を確認した。TRXは `F:/Seamless/Verification/htx2391f15a` の `result-Debug` と `result-Release`。

権限更新と取消の関連試験はWindows Debug／Release各36件合格。取引中に通常権限を剥奪した場合の継続と次要求の拒否、アカウント無効化時の未確定行の解放、取引認可待ちの切断、通常認可の遅延完了を確認した。通常認可の遅延完了は、サーバー側の要求取消を観測してからリースを返す試験で検査する。処理先への呼出し回数と返却リースの破棄を確認し、停止完了後に未処理ハンドラーを残さない。TRXは `F:/Seamless/Verification/hrce1fe7934`。

管理領域は `ManagementStore` が `management.lock` を排他保持する。別のGatewayプロセスが同じディレクトリを直接開いて管理サーバーと同時に読み取る構成は使えない。配布CLIへ接続する場合は、管理DBを所有するホスト内から認可を注入するか、別プロセスなら現行版と取消を確認できる専用経路を通す。初回起動時のコピーだけで新しい要求を認可すると、権限剥奪・緊急停止を反映できない。

## オンラインのDB権限編集

Gatewayが所有する管理ストアと`StoredAuthorization`を、同じプロセスの管理RPCリスナーで共有する。別プロセスからストアを開かず、クライアントは既存の長さ付き管理RPCをTLSで呼ぶ。追加リスナーは明示設定した場合だけ起動し、既存管理GUIの利用者認証・IPCを変更しない。GatewayのHTTP証明書を共用し、待受アドレスとポートを明示する。

このリスナーではOIDC APIアクセストークンを毎回検証し、DB権限の取得・編集と本人が開始した編集結果の照会だけを公開する。通常の管理アカウントのトークンやローカル利用者名をOIDC主体へ読み替えない。既存の管理RPCホストへ追加の要求処理を接続し、TCP/TLSやフレーム処理を二重実装しない。

編集は対象DB・期待するポリシー版・クライアント生成操作IDを持つ。DB管理者による他DBの編集と管理権限の再委任を既存の共通認可で拒否する。変更内容・操作ID・開始時の主体と権限版は一つの管理DB取引で確定する。切断後も確定済み操作の結果を同じ主体から照会でき、通信失敗時の自動再送はしない。取得する編集情報は対象DB内へ限定し、他DBやサーバーロールの割り当てを返さない。

編集情報はリソース、ロール名、ロール内の個々の規則、割り当てを別の項目として100件ずつ取得する。大きな一つのロールも複数ページに分ける。保存済みの不変文書を列挙し、毎回全ポリシーの複製や全項目の配列化は行わない。続きの要求ではDB・版・カーソルを指定し、変更が確定していれば競合として最初から再取得する。応答は件数とシリアライズ容量で制限し、一つの項目が上限を超える場合も明示的な容量エラーを返す。

Windows Debug/Releaseで実際の管理TLS RPCからの編集、対象外操作・誤ったトークン・他主体の結果照会の拒否、同じ版からの競合、再起動後の結果保持と次のHTTP要求への反映を確認する。GUIへの権限編集画面と永続アカウント無効化は別の未完了項目として維持する。

オンライン編集を含む認可関連はWindows Debug/Release各38件合格、失敗・スキップなし。CLI起動からの編集と次のHTTP要求への反映、再起動後の本人の操作結果、205規則を持つロール、日本語名の容量分割と単一項目の容量拒否を実接続で確認した。証跡は `F:/Seamless/Verification/aoneadb7da4` の各 `result-*/authorization.trx`。同じ場所の `debug-source-verification.json`・`release-source-verification.json` で、今回変更した製品・テストの11ファイルと成果物のPDBが一致した。

JSON要求の容量と、管理WALへ記録する容量は異なる。既定4 MiBのフレーム上限を超える変更は原子的に確定できず、WAL要求前の拒否として個別中止する。この場合も旧ポリシーを保持し、同じストアで次の小さい変更を確定できる。複数フレームによる大容量の原子的保存と明示的な導入・移行は残る。[WAL要求前の拒否](20261105-wal-preparation-rejection.md)

## 合意状態

OIDC先行、開発用認証環境、対象単位の共通認可、取引中の権限保持、利用者無効化時の取消は合意済み。この文書はHTTP経路への接続設計であり、稼働環境への導入は未実施。
