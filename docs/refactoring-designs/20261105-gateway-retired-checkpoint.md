# Gatewayの共通チェックポイントと廃止世代

## 背景

世代公開直後から復旧したGatewayで、保守処理中に読み取り取引の受付期限に達した。失敗した実行では、廃止予定の旧世代にもローカルスナップショットを保存したが、直後に公開した共通チェックポイントの保持対象にはその世代が含まれなかった。絞り込み実験では、SELECT Rv が保守処理の間に約772 ms待った。保存通知の最後から取引受付の再開までにも約313 msあった。

## 保つ条件

- 共通チェックポイントのファイル置換前は、従前の共通チェックポイントと残存WALから復旧できる。従前のチェックポイントが参照する世代の既存スナップショットとログを、置換前に破棄しない。
- ファイル置換後は、新しいチェックポイントが参照する世代に対応するローカル保存が済んでいる。WALの整理が済む前に停止しても復旧できる。
- Published Previousによるファイル保護、退役前の取引排出、確定結果、既存の受付期限を維持する。

## 変更候補

共通チェックポイントの開始時に、今回の退役対象をゲート内で確定する。同じ集合で世代ごとの保存、共通チェックポイントの保持対象、削除計画を判定する。今回の共通ファイルが参照しない退役世代のローカル再保存を省く。別の保守処理の途中から退役要求が合流する場合は、進行中のチェックポイントの集合を変更せず、保存済みのチェックポイントが必要とするファイルを保護する。

旧世代の保存を省く前に、永続ストアの切り捨てがローカル保存の確定まで保留されることと、退役世代の既存スナップショットから置換前の復旧ができることを検証する。退役に伴う物理回収の範囲と取引受付の仕様は別の変更単位とする。

## 検証

1. 世代変更前の共通チェックポイントを保存し、変更確定後の回収で共通ファイルの置換直前と直後にそれぞれプロセスを停止する。
2. 停止位置と共通ファイルの内容を照合する。再起動後の複数DBの行・型、WALの確定結果、行バージョン、公開クエリを検証する。
3. 保存の省略を入れた後は、旧世代のローカル保存が進まないことと、新しい共通チェックポイントから対象世代が除外されることを確認する。
4. 保存通知数、受付待ち、チェックポイント各工程の時間を変更前後で比較する。絞り込みとWindows Debug／Releaseの全件回帰を分けて実行する。

## 退役世代の再保存を省いた後の検証

Windows Debug全件回帰では、共通チェックポイントの物理処理が5秒を超え、復旧後のDB BのSQL読み取りが受付期限に達した。同じ成果物の復旧17件を単独で実行した場合と、観測した並走試験を再構成した42件の計測では再現しなかった。[検証結果](../kestrel-verification-20261104.md)

次に計測する単位は、現役DBのデータハッシュ、ストアごとのスナップショット生成・耐久書き出し・マニフェスト確定、カタログ保存、共通ファイルの置換と回収対象確定、WALの確定結果・同期・保持情報、参加先の再取得とする。受付期限に達した試験と同じ保守シーケンスに対応付ける。時刻はメモリへ記録し、計時中の追加ファイル出力を避ける。

`SEAMLESS_TEST_RECOVERY_TRACE=1` を指定した復旧試験では、`Seamless.Checkpoint.*` の計測を有効にする。共通チェックポイントのシーケンスと子工程の開始時刻・所要時間を記録し、試験のホスト終了後に `checkpoint-timing.json` へ出力する。計測対象の隔離ディレクトリはテスト内で照合し、テレメトリーのタグに含めない。強制終了試験の `recovery-timeline.json` と合わせると、SQLの受付と物理保守全体の時刻も照合できる。

現役ストア間の直列保存が支配的であることを確認できた場合は、同じ保存順の保証と総資源予算の下で、独立したストアを小さい並行度で保存する案を比較する。WAL同期が支配的な場合は、同じロックの下で書き込みのない同期済みセグメントを識別し、再同期だけを省く案を比較する。どちらも現時点では採用未決定であり、容量不足、途中失敗、共通ファイルの置換直前・直後、WAL整理前の停止からの復旧を採否の条件にする。

## 独立ファイルの耐久書き出し

同じ隔離ビルドで、1並行と2並行をAB/BA順に切り替えて複合DDL復旧を実行した。12件すべて合格した。耐久書き出しの中央値は599 msから421 msへ、共通チェックポイント全体は931 msから703 msへ短縮した。比較元は `F:/Seamless/Verification/ab238b166f`。各回のDBは同じ手順で作り直した。

Tsavoriteの単一ストア内に限り、同じパス文字列の重複を除き、耐久書き出しを最大2並行とする。複数のスナップショットが同じ索引情報ファイルを列挙しても、同じパスは一つの処理へ割り当てる。開始した書き出しがすべて終了してから戻り、失敗時は未書き出しの保存番号を除去せず、ストアのマニフェスト確定へ進まない。単一の失敗は元の例外を伝える。スナップショットの生成、各ストアの保存完了、共通ファイルの置換とWAL整理の順序は従来どおりとする。

書き出しの並行度と失敗時の合流をテストし、既存のストア保存・詰め直し・Gateway強制終了試験を再実行する。過去の5秒超が発生した条件での受付改善は、全件回帰と工程計測を使って引き続き確認する。

## 復旧時に見つかった廃止世代の回収と受付開始

復旧後の最初の読取が終わると `CloseVersioned` が自動回収を開始する。直後の要求が、復旧で既に見つかっていた廃止世代のチェックポイントを待つ。強制終了試験では、計測開始から約394 msで最初のSQL読取が戻り、共通チェックポイントの公開は約2,389 ms、次の取引受付は約3,013 msだった。別の全件回帰では同じ経路で5秒の受付期限に達した。主な遅延箇所は実行によって現役DBまたはカタログの耐久書き出しだった。[検証結果](../kestrel-verification-20261104.md)

復旧時点で既に回収待ちの世代がある場合、`GatewayDatabaseHost.OpenAsync` が要求を受け付けるホストを返す前に、既存の `CheckpointVersioned` で処理する。復旧のロックを抜けてから実行し、廃止世代がない通常の再起動では追加の保存を行わない。通常稼働中に発生した廃止世代の自動回収、受付期限、保存・WAL・共通ファイル公開の順序は既存のままとする。

復旧時のチェックポイント失敗は起動エラーとして返し、途中のストレージは既存の起動失敗処理で閉じる。遅いストレージでは起動完了が遅くなる。ここで検証するのは復旧完了から要求受付までの順序で、稼働中のチェックポイント時間の上限は別に計測する。強制終了の `AfterPublication` では最初の要求前に共通チェックポイントが公開されたことを、`AfterCommonCheckpointPublication` では再起動時に追加で公開されないことを検証する。
