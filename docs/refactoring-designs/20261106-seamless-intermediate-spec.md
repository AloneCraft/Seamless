## 初版の実行方針

- 初版は、メソッド内のクエリと更新を、元の制御フロー・評価順で逐次実行する。FLinq の事前解析・コード生成・インターセプトと、逐次で意味を保持する最適化を適用する。
- FLinq の自動並列化、`ParallelRead`、`Container.Parallel`、並列化目的の `Task`・`async` 化、専用 fork/join 実行器、メソッド内部 DAG の並列ディスパッチは後続検討とする。将来の並列化の詳細は、初版の仕様確定・実装の前提条件にしない。
- 初版の逐次評価では通常の C# の例外処理と `catch`、明示的な取引境界、各更新 API の原子性を維持する。将来の並列区間の失敗規則は、再開時に適用範囲を確定する。
- この逐次実行の決定はメソッド・クエリ内部を対象とする。別接続の同時要求やサーバー全体のスレッド数は、従来の資源管理・ロック・入場制御の対象として扱う。既存の非同期 I/O と低レベルの並列機構は、既存実装の事実として区別する。

## 現在の実装について確認した事実

- `Template/Seamless.Application` には Server・Schema・ServerSchema・ClientSchema の4プロジェクトがある。
- 現在のスキーマ生成器は従来の `Keys`・`Records` の partial 型を補完し、新しい `Tables` の partial 型からキー型と `IRecord<TKey>` 実装を生成する。`get` のみと `get/init` の両方を扱い、getter と init の可視性を宣言から引き継ぐ。通常配置・配置最適化・Collectible の経路で同じアクセサー契約を使う。
- 現在の Container 生成器には、手書きの `Table` プロパティや `View` メソッドの収集に加えて、`CollectDeclaredObjects` により `Tables`・`Views`・`Work` の宣言を集める経路がある。宣言収集の存在と、個別の取引・保存 API の完成度は区別する。
- 従来の `Keys`・`Records` の配置最適化は、一つの private 構造体 `F` の内部を並べ替える。新しい `Tables` の生成では、生成キーと非キー列を private な `C`・`S` へ分け、キー列を `_Key` のみへ保持する。二つの保存領域・WAL への接続は今後必要になる。
- `Auto<T>` は参照を含まない型を生メモリのバイト列で扱い、参照を含む型は MemoryPack を使う。
- `CodecRegistry` はフィールド情報をキャッシュするが、各値の読み書きにはリフレクションを使う経路がある。
- 新しい `RecordValueStrategy<T>` は、正規化・比較・ハッシュ用の型専用 DynamicMethod を初回に作る。private・readonly・継承フィールドを処理し、通常のフィールド処理で FieldInfo.GetValue・SetValue・DynamicInvoke を使わない。型キャッシュの collectible 型の解放も実 GC で検証する。
- 現在のキー付き Set の `Contains(record)`・`Remove(record)` はキーだけで判定する。後述するレコード全体の比較への変更が必要。
- 既存の `...With` は逐次更新を行う。後述する呼び出し単位の原子性への対応が必要。
- 現在の `ParallelDictionary` の代入は RMW を使い、新規追加・削除の増減を操作オブジェクトごとに数える。各オブジェクトの破棄時に増減を集約し、並列区間の終了時に開始時件数へ加算する。
- 現在の件数再集計は、ログを走査し、既存索引で得た最新アドレスと照合して有効な行を数える。後述する計数省略の内部 Upsert 経路は今後の実装対象。
- 通常の Tsavorite 辞書の代入には `SetValue.InPlaceUpdater` があり、条件が合えば既存領域を書き換える。すべての更新で Tail が進むという前提は置けない。
- 履歴保持用の `HistoryStore` は `InPlaceUpdater` で `false` を返し、コピー更新で旧レコードを保持する。旧アドレスや指定版での読み取りの基盤がある。
- `TransactionChangeSet` は小さい変更集合をメモリ上の辞書で保持し、予算を超えると Persisted の一時バイト索引と一時ファイルへ退避する。Graph 形式ではメモリ内も予算付きの符号化キー・行で保持し、入力・取得結果・保存点を独立させる。
- 既存の `DatabaseTransactionAccessAnalysis` は読み取り専用か更新可能かを解析する。後述のコレクション別の事前ロック計画への拡張は実装予定。
- キー取得インタフェースを不変の `IRecord<TKey>` と `Key{get;init;}` に更新した。既存の TPC-E 33 行型、実験用の手書き行型、Set の試験用レコードを新契約に接続した。計算型のキーは `init` で対応するキー列へ値を戻し、既存の列配置を維持する。

関連する実装は `Shared/Database.Generation`、`Seamless.Collections/Serializers`、`Seamless.Collections.Tsavorite/Collections`、`Seamless.Execution/CodecRegistry.cs` にある。

## DB・サーバー・配置

### 用語と配置

- データベースとスキーマは SQL Server の意味で区別する。
- 一つのサーバーで複数の独立した DB を動作させる。各 DB は複数の利用者スキーマを持てる。
- DB プロジェクトごとに独立した DB 定義 DLL を生成する。同一 DB 内の複数スキーマはその DLL に含める。
- DB 間の依存・参照を禁止する。既存定義がこの制約に違反する場合は、対象を明示して拒否する。
- 同じ PC で Seamless サーバーを複数起動することを禁止し、一つのサーバーで資源を管理する。計算処理は子孫プロセスを含め共通の最大8論理CPUのaffinityに制限し、分離が必要な検証DB・成果物・ログは `F:\Seamless\` 配下へ集約する（C/D ドライブを出力先にしない）。
- 一部の DB のオープンが失敗しても、正常な DB の公開は継続する。失敗 DB は `Faulted`（オフライン）として隔離記録し、サーバー全体を再起動することなく、管理 CLI/RPC からのオンデマンド指示により動的再オープンできるようにする（保守競合防止のため自動リトライは行わない）。

### DB の停止・移動

- 対象 DB の新規要求の受け入れを止め、実行中の処理・取引の終了を待って停止する。他 DB は継続する。
- 管理者は待機中の移動を取り消して受け入れを再開できる。
- 停止・永続化完了後、フォルダーをコピーして別ホストで開ける構成にする。停止時は WAL の未反映ログを Tsavorite/Persisted データファイルへ完全フラッシュ（チェックポイント同期）し、静止点データとして即座に別ホストでクリーンオープン可能とする。
- 定義 DLL、データ、必要な復旧情報、DB 内権限、関連する履歴・コード対応情報を移動可能な単位へまとめる。ホスト側のログイン主体との対応は移動先で管理する。
- 移動元のデータは停止した状態で保持する。移動先の失敗だけを理由に自動的に移動元を再開せず、管理者が移動先の停止を確認して再開する。
- 既存 DB の構造・保存形式・永続データを変更する場合は、明示的なバックアップを取得した上で直接変更を適用する。アプリケーション起動時の暗黙的なスキーマ自動バンプ、自動マイグレーション、旧ファイルの自動削除コードには依存しない。

## テンプレート・ビルド・クエリ実行

### 自動生成の目標

- DB テンプレートと処理本体はプログラマーが記述する。
- 今後のテンプレートでは `Tables`・`Views` 名前空間の型定義から、Container の対応コレクションを自動生成する。
- キー抽出、比較・正規化の静的ストラテジ、保存・通信のボイラープレートも generator の生成対象にする。
- ビューの型は列構成を定義する。問い合わせ本体は利用者がビュー型の static メソッド `Query` に記述し、生成した公開 getter へ接続する。`Summary.Query(container)` の形で対応付け、定義用の属性を省く。通常ビューの戻り型は `Seamless.Collections.ISet<ビュー型>` を必須とし、重複のない関係として統一する。呼び出しまたは展開の接続方法等は未決とする。
- 最小3プロジェクトのビルド確認を基礎として、以下の自動生成仕様を実装へ引き継ぐ。
- ビューの宣言を generator が認識できる状態になったら、クエリ本体の編集中でも、生成されるスキーマ・Container の公開プロパティを対象 IDE の補完で利用できることを目標要件とする。未保存の編集内容にも対応し、利用者による保存や明示的なビルドを前提にしない。
- IDE への反映は非同期とし、各キー入力の直後に必ず補完へ反映されるという即時保証は設けない。
- 最終受入で、対象 IDE（VS・VS Code）の実環境を使い、ビュー宣言の追加・変更後に、未保存・未ビルドのまま生成公開プロパティの補完を利用できることを検証する。
- この IDE 補完要件は現在未検証であり、実装・IDE 接続と最終受入の検証を後続作業として扱う。

### 名前空間と Container の対応

DB のルート名前空間を `Sample`、SQL Server 的なスキーマを `dbo` とした場合、以下の対応で生成する。

| 対象 | 名前空間・型 | 定義元 |
|---|---|---|
| テーブルのレコード | `Sample.Tables.dbo.Item` | 利用者 |
| ビューのレコード | `Sample.Views.dbo.Summary` | 利用者 |
| 非トランザクション作業辞書のレコード | `Sample.Work.dbo.ItemCache` | 利用者 |
| テーブルのキー | `Sample.Keys.dbo.Item` | generator |
| 名前付き作業辞書の生成キー | `Sample.Keys.dbo.ItemCache` | generator |
| スキーマ | `Sample.Schemas.dbo` | generator |

- スキーマを定義する場合は、用途を示す `Tables`・`Views`・`Keys`・`Schemas` を先に置き、その下へ SQL スキーマ名を置く。
- スキーマを定義する場合は、Container のスキーマと対応コレクションを自動生成する。スキーマが一つだけでも `container.SchemaName.TableName`・`container.SchemaName.ViewName` の形とし、例えば `container.dbo.Item`・`container.dbo.Summary` で利用する。
- スキーマを定義しない場合は、`container.TableName`・`container.ViewName` の形で直接利用する。アクセス時にスキーマ名を挟むかどうかは、スキーマの個数ではなく定義の有無で決める。
- 利用者が宣言する `Tables`・`Views`・`Work` のスキーマの有無は DB ごとに統一する。同じ DB 内のスキーマあり・なしの混在はビルドエラーとする。スキーマありの DB では複数のスキーマを使える。暗黙の既定スキーマの扱いは未決事項に残す。
- Container に名前付きプロパティとして公開する作業辞書は、専用の `Work` 名前空間の型定義から生成する。`Tables`・`Views` と宣言スタイルを揃え、例えば `Sample.Work.dbo.ItemCache` から `container.dbo.ItemCache` を生成する。生成キーはテーブルと共通の `Keys` にまとめ、`Sample.Keys.dbo.ItemCache` とする。汎用の作業辞書本体はランタイムライブラリ側で提供する。
- ビューの問い合わせ本体は、ビュー型の static メソッド `Query` から生成 getter へ接続する。名前の規約で識別し、`Summary.Query(container)` の形を使う。戻り型は `Seamless.Collections.ISet<Summary>` のように、そのビュー型の関係を表すものとする。現行の `View<TResult>` は `IEnumerable<TResult>` であり、この生成ビューの契約への対応は実装予定。
- 型引数に関する方針は、Tsavorite.Set 等にテーブルのレコード型を渡す既存のコレクション構造を土台にすることを指す。
- 一つの DB 定義 DLL に置く生成対象の Container 型は一つとし、その DB の `Tables`・`Views`・`Work` をそこへ生成する。複数 Container 型への所属を指定する宣言は初版では導入しない。

### 主キーの自動生成

- テーブルのプロパティへ `[Key]` を付けて主キーの構成列を指定する。属性型は `Seamless.Database.KeyAttribute` とし、`using Seamless.Database;` で利用する。利用者へキー列の順序指定は求めない。属性型を追加し、新しい `Tables` 生成器が読み取る。
- 属性が一つ以上ある場合は、指定されたプロパティを含めるキー型を生成する。キーの並び順は generator が決め、参照側・値側の分離や配置の最適化へ合わせられるようにする。
- 属性が一つもない場合は、全データプロパティを含めるキー型を生成する。
- 属性の有無にかかわらず、キー抽出・正規化・比較・ハッシュ・保存通信表現は、generator が決めた列の対応と配置を一貫して使う。利用者が指定する論理的なキー構成列と、生成内部の並び順を分けて管理する。
- キー型に加え、キー抽出・正規化・比較・ハッシュ処理を自動生成する。
- キー列と通常値は利用者がレコード型へ宣言する。例えば `[Key]` 付きの `id0`・`id1` と、通常値の `value0`・`value1` を宣言する。
- 生成レコードはキー列を生成キー型の `Key` にまとめて保持し、レコード側の `id0`・`id1` の getter は `Key` の対応する値を返す。キー列を通常値側のフィールドへ重複保持しない。
- 通常値の参照側を private 構造体 `C` と `_C`、値側を private 構造体 `S` と `_S` に分離する。キー型の列順・配置も generator が決める。保存時の値型領域・参照型領域への分離は、`Key` の内部も含めて扱う。
- レコード全体の一致判定は、主キー指定の有無によらず全データプロパティを対象にする。

以下は新しい生成器に対応させるテンプレート例である。

```csharp
namespace Sample.Tables.dbo;

public partial struct Item{
    [Key]
    public partial int Id{get;init;}

    public partial int Value{get;init;}

    public partial string Name{get;init;}
}
```

この例では `Id` を持つ `Sample.Keys.dbo.Item` を生成する。属性を外した場合は、`Id`・`Value`・`Name` のすべてを含めるキーを生成する。

### レコードのキー取得・初期化契約

- キー取得契約には既存の `Seamless.Collections.IRecord<TKey>` を使い、`Key` に `get` と `init` を持たせる。`Merge`・`Update` の更新ラムダで、新しいキーを持つコピーを構築できるようにする。
- `init` は `TKey` を入力として受け取るため、型パラメーターは不変とし、`out` を付けない。これは C# のインタフェースプロパティの変性規則に従う。[C# 言語仕様](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/interfaces#1944-interface-properties)

```csharp
public interface IRecord<TKey>{
    TKey Key{get;init;}
}
```

- 生成レコードの公開 `Key` は `get/init` プロパティとし、内部の readonly キーフィールドに一度だけ保持する。キー列の getter はこのフィールドの対応する値を返す。
- `Key` の `init` ではキー内の数値・日時を正規化し、参照先の共有を保持する。`init` を宣言した個々のキー列を書き換える場合も、保持する `Key` を整合する値へ更新する。参照先の深い正規化は保存・送信・引数処理の全体境界で行う。
- `row with{Key=newKey}` は新しいレコード値を構築し、保存済みデータへの反映は `Update`・`Merge` 等の明示的な更新で行う。キー変更先の制約と原子性は、それぞれの API の契約に従う。
- 既存のコレクションの `IRecord<TKey>` 制約は新契約へ接続する。手書き実装は `init` を必須とする。旧契約の共変変換を使う利用側と、getter のみの実装はソース修正と再ビルドが必要になる。
- 契約試験では、`IRecord<TKey>` 制約付きの値型を `with{Key=...}` でコピー更新し、元の値と非キー列の保持、Set の保存・取得を確認した。新しい `Tables` 生成器による公開 `Key` の生成と各キー列の同期、数値・日時の正規化へ接続した。参照先を含むキーの深い正規化は、全体の境界処理で行う。

### 作成とコピー更新の生成 API

- キーとレコードに、初期値をまとめて受け取る静的ファクトリー `Create(...)` を生成する。
- partial プロパティは `{get;}` のみと `{get;init;}` の両方を許可し、宣言に対応したアクセサー・内部フィールド・正規化処理を生成する。`get` のみのプロパティは読み取り専用とする。
- `init` を宣言したプロパティの複数列のコピー更新は C# の `with` 式を基本とする。`get; init;` のプロパティは `new` のオブジェクト初期化子からも指定できる。読み取り専用の列を変更した新しい値は、作成 API や生成したコピー更新メソッドで構築する。
- `Withプロパティ名(...)` は、コピーして単一列を変更する補助メソッドとして生成できる。
- 非キー列だけを変更する場合は保持しているキーを引き継ぐ。キー列を変更する場合は対応するキーも更新する。
- 全プロパティがキーになる型では、どのデータプロパティの変更もキー変更になる。
- 構造体のコピーと `with` は浅いコピーとして扱い、参照先の共有は後述の参照構造の契約に従う。保存時にはレコード単位の独立化を行う。

### 生成器への接続の実装順序

- 最初に既存の `Keys`・`Records` 生成器を `get/init` 宣言へ接続する。宣言された getter と init の可視性を維持し、通常配置・配置最適化・Collectible の経路を同じアクセサー契約で扱う。getter のみの列には setter を生成しない。
- コピー更新後の値について、既存 MemoryPack の保存・復元と再生成後のコンパイルを回帰試験で確認する。既存の getter のみの生成、配列、既存 DB スキーマの試験を併せて実行する。
- 続いて `Tables`・`Views` の型定義からのキー・レコード生成、`Key` と各キー列の同期、Container のコレクション生成へ接続する。既存の `Keys`・`Records` のアクセサー対応だけで、新しい生成 API 全体が実装済みとは扱わない。

### Tables 宣言からの生成の実装方針

- `Seamless.Database.KeyAttribute` は引数を持たないプロパティ用属性として追加し、生成器は属性型の完全修飾名でキー列を選ぶ。同じ短い属性名を持つ利用者の別属性とは区別する。
- `Tables` の partial 構造体から、同じ DB ルート・スキーマ・型名の `Keys` 型と `IRecord<TKey>` 実装を生成する。キー型と通常値の格納は private な `C`・`S` へ分ける。レコード側のキー列は `_Key` のみへ格納する。
- 公開 `Create` とコンストラクターの列引数は宣言順へ対応させ、内部の値側フィールドはサイズ等で並べ替える。レコードの作成引数はキーと非キー列とし、全列がキーならキーだけを渡す。引数名は既存生成器の `value0` 等の形式を使用する。
- 生成したキーとレコードの MemoryPack 読み書きを同じ列対応へ接続する。`Key` の変更と、init を宣言したキー列の変更は、同じ保持値を更新する。
- 空の宣言、不正な列、予約した生成名や生成キー型との衝突を診断する。既存の `Keys`・`Records` の生成契約は維持する。
- 新しい生成経路の追加と、複雑な参照グラフを含む正規化・比較・二つの保存領域・取引・Container 生成の完成は分けて検証する。既定の正規化規則を緩める決定は行わない。

### Tables 宣言からの生成の実装検証

- 明示した `[Seamless.Database.Key]` の列をキーにし、属性がなければ全データプロパティをキーにする。別の名前空間にある同名属性はキー指定として扱わない。
- 生成キーは `readonly struct` とする。レコードは通常・readonly の struct と record struct の宣言へ対応し、`IRecord<TKey>` の `Key{get;init;}`、各列のアクセサー、キーと通常列を受け取るコンストラクター・`Create`、MemoryPack 読み書きを生成する。
- 公開の列引数は宣言順とし、キー型では `value0` から、レコード型では `key` と非キー列の `value0` から対応付ける。内部の値側フィールドはサイズ降順等で配置する。空の `C`・`S` は生成しない。
- キー列はレコードの通常列へ重複保持しない。`with{Key=...}` と、init を宣言したキー列の変更は、同じ `_Key` を更新する。入れ子の生成型の参照判定には、生成前の partial 宣言の列も含める。
- 不正な宣言、予約生成名との衝突、既存の生成先キー型との衝突、静的なキー指定を `SDB003` で診断する。同じ DB の `Tables`・`Views`・`Work` のスキーマあり・なしの混在も診断する。複数スキーマと、独立した DB ルートでの異なる選択は許可する。
- 正規化・比較・ハッシュの静的ストラテジを生成し、各走査で参照共有と循環を扱う。参照構造を保持する形式と SharedV2 `RecordGraphV1` の保存境界も接続した。生成 Native の Graph 境界は後述の実装検証に接続し、二つの保存領域と Container の各 API の検証は別工程で引き継ぐ。
- 新しい宣言列を使う参照・サイズ判定は `Tables` 経路へ限定し、従来の配置最適化の推定・並び順を維持する。既存の入れ子 unmanaged 型について `Marshal.OffsetOf` で列位置を実測する回帰試験を追加した。
- 最終候補は Debug 40 件・Release 40 件が合格した。新しい宣言生成 23 件と、既存のアクセサー・Container・集合インポート・実体化ビュー・AdventureWorks2017 スキーマ 17 件を含む。新しい生成コードについて警告がないことも検査した。共有ソースの .NET Standard 2.0 向けビルドを含む。
- 検証証跡は `F:/Seamless/declared-key-20261107-24fd` 配下にある。

### partial プロパティ生成の実装検証

- 既存の `DatabaseSchemaGeneration` は、getter のみの宣言に加えて `get/init` 宣言の実装パーツも生成する。init は既存の保存用フィールドへ値を設定し、getter のみの列に setter を追加しない。
- 通常配置と配置最適化の双方で、コピー更新前の値の保持、値・参照・nullable 列の更新、MemoryPack での保存・復元、同じ入力からの再生成後のコンパイルを検証する。Collectible の経路を含めて `private get`・`private init` の可視性も検証する。
- 変更前は新しい `get/init` 宣言の 4 ケースが `CS9248` 等で失敗した。対応後に追加した `private get` の 2 ケースは `CS8799` で失敗し、両アクセサーの修飾子を引き継ぐように修正した。
- 最終候補の代表回帰は Debug 17 件・Release 17 件が合格した。
- 検証証跡は `F:/Seamless/schema-init-20261106-6ad8` 配下にある。代表回帰の対象は Container 生成、集合インポート、実体化ビュー生成、AdventureWorks2017 の既存スキーマとする。
- この対応は既存の保存フィールドへアクセサーを接続する。`Tables` からのキー生成、二領域への分離、新しい正規化ストラテジ、更新 API の実装状況とは分ける。

### 共通ビルドとクエリの事前生成

- クライアントとサーバーは共通のソリューションでビルドする。必要なクライアント EXE・DLL もサーバーに配置する。
- Native の C# クエリは、コード生成・展開・コンパイルを共通ソリューションのビルド時に行い、すべて事前生成したコードの実行へ統一する。クエリ形状はビルドで用意し、実行時は引数を渡す。
- 受信したクエリから実行時にコードを生成・コンパイルする既存 Native 経路は廃止する方針とする。例えば `NativeLambdaClient<TDatabase>` が送る構造表現を `NativeLambdaCompiler<TDatabase>` が C# 化・コンパイルする経路が対象であり、この経路との併存・後方互換・段階移行を製品要件として要求しない。
- 正式版では事前生成方式へ統一し、既存の実行時コード生成・コンパイル経路を含めない。開発中は、事前生成方式の必要機能と検証結果を確認するため、既存方式を比較用に限って一時保持できる。具体的な除去時期と作業順序は実装・検証状況を踏まえて判断し、正式版の到達点と開発手順を区別する。開発中の比較用の保持は、製品での併存・後方互換を要求するものではない。
- この決定は上記のクエリ実行経路を対象とし、DB データ・永続化や無関係な機能の一括削除を意味しない。DB の構造・保存形式変更時の明示的バックアップと移行、版・契約不一致時の拒否、DB 世代更新の扱いは維持する。既存経路の廃止と事前生成への接続は後続の実装対象であり、対応済みとは扱わない。
- クライアント側の公開メソッド呼び出し境界をインターセプトしてサーバー通信へ接続し、サーバー側で対応する事前生成処理へ引数を渡す。通信単位はメソッド呼び出しとし、内部の LINQ 演算群と中間結果はサーバー内で処理する。
- 元クエリと生成処理の対応をデバッグ・検証に使う。事前生成クエリ ID、引数・戻り型・契約 ID・権限・DB 世代・登録情報の具体的な対応は未決とし、実行時に受信構造から C# を生成・コンパイルする方式へ戻さない。
- 既存 Native 経路が担う契約検査・権限検査を、事前生成方式へ接続して維持する。
- DB 定義・公開契約・関連ビルドの版が異なる場合は実行を拒否する。
- 比較・正規化規則と保存・通信形式の識別情報も互換性確認へ含める。
- クライアント更新は対応する成果物を取得し、実行中の処理を終えてから切り替える。
- DB 世代更新では実行中の旧世代処理の寿命を保持し、新規の旧世代要求は拒否する。保持できない場合は終了を待つ。

### C# の処理メソッドをバッチとする

- 一つの公開 C# メソッドの内部をサーバー内で実行する。中間結果や前の値に依存する後続クエリも、その内部で処理する。
- クライアントに返すのは最終的な戻り値だけとする。
- メソッド全体を自動的に一つの取引にすることは要求しない。必要な取引範囲は明示する。
- 同一接続では実行と結果の完了順を保つ。失敗時は待機中の後続処理を取り消し、取引状態などを確認して接続を再利用する。
- 初版ではメソッド内部を逐次実行し、前の値に依存する処理も元の制御フローどおりに進める。別接続の同時要求はサーバーの資源管理とロック規則に従う。
- クライアントの公開呼び出しは同期的に扱い、まとめたい処理はメソッド内部へ記述する。

### 初版の逐次評価と例外

- 独立した読み取りを含め、元のメソッドの制御フロー・評価順・結果の対応を維持して逐次実行する。FLinq は依存関係・副作用・例外・遅延列挙を解析し、逐次で意味を保持する変形を行う。
- 取引内の読み取りは、先行する自取引の更新を含む既存の可視性規則に従う。メソッド開始時点の最新 DB スナップショットへ一律に読み替えない。`MergeWith` の呼び出し開始時参照は、同 API の契約として区別する。
- 通常の C# の例外伝播・`catch` と、明示的な取引境界を維持する。各更新 API の失敗時の原子性と、取引全体の確定・取消しの範囲を区別する。ライブラリが利用者の処理を自動再実行する仕様は設けない。
- 各結果は元の変数・返却先に対応させ、元コードのタプルの要素位置も維持する。FLinq を使うための専用の並列ブロックや結果の組み替えを初版の利用条件にしない。

### 事前アクセス解析とロック

- 対象の取引方式は、テーブル単位または DB 単位のロックでシリアライザブルを保証する。ストアド処理の LINQ、書き込み操作、呼び出すヘルパーやビュー等から、アクセス対象と読み書きを事前解析する。
- 保証範囲は前後の更新を含む取引全体とする。範囲読み取りと該当行が存在しないことの読み取りも、挿入等との競合を含めて保護する。先行する自取引の更新が見えることを維持する。
- Container が所有する非トランザクション作業辞書も同じ解析・ロック対象に含める。

| 解析結果 | 取得するロック |
|---|---|
| 対象コレクションの読み取りのみ | コレクション単位の共有ロック |
| 対象コレクションへの書き込み | コレクション単位の排他ロック |
| 同じコレクションを読み書きする | 最初から排他ロック |
| アクセス対象を静的に確定できない経路がある | DB 全体の排他ロック |

- 必要なロックを処理開始前にまとめて取得する。複数対象の取得順序を統一し、DB 全体のロックとコレクション単位のロックも相互に調停する。
- 対応する取引がある場合は、その終了まで必要なロックを保持する。ロックの所有と、明示的な取引による確定・取消しの範囲を生成コードで管理する。
- 初版は取得したロックの所有範囲で逐次処理する。将来のワーカー間のロック所有共有や並列用操作オブジェクトの接続は、並列化の再開時に検討する。
- `create`・`update` 等の利用者コードを、競合対策としてライブラリが自動再実行する仕様は設けない。ロック取得後に対象を読み、作成・更新の分岐を決める。保存先の切り替えには計算済み候補を使い、内部コールバックの都合で利用者のラムダを呼び直さない。
- Anchor の有無にかかわらず取引のロックで保護する。Anchor 付きの副作用の回数・評価順序は通常版と FLinq 展開版の両方で守る。外部送信等の実行済み副作用と DB 変更の取消しは区別する。
- 選択したロック、アクセス対象、解析できなかった経路、選択根拠を展開コードのコメントと実行トレースへ残す。
- 現在のコードには DB 全体の書き込みを直列化する経路と、バージョン付き取引の楽観的な競合検査の経路がある。本節は今回合意した目標仕様であり、既存実装全体が対応済みという記述とは分ける。

### DLL の検査

- 同一プロセス内での任意 C# の実行を許容し、DLL を作るプログラマーが責任を持つ設計を選んだ。
- 静的解析で警告・エラーを出す。クライアント側だけに依存せず、サーバーで受信した DLL と依存 DLL を検査する。
- 検査結果は DLL・依存関係・検査規則の識別情報でキャッシュする。
- 登録済みストアド処理は公開・ロード時に検査する。実行ごとの同一検査は省く。
- 検査したバイト列と実際にロードするものを対応させ、差し替え後の未検査 DLL を新規ロードしない。
- CAS 属性をセキュリティ境界として使う方式は採用しない。

## 戻り値・LINQ・集合 API

### ストリームと所有権

- 集合・列の戻り値は所有権を持つストリーム型とし、単一値は直接返す。
- 中間結果はサーバー内で処理する。
- クライアントは拡張メソッドで必要に応じて実体化する。実体化した結果はサーバー DB から独立したコピーとする。
- 所有する結果は `using` で明示的に解放できるようにする。
- メモリ予算に収まらない実体化には、リソースマネージャー管理下の一時ディスクを使う。
- ストリームは一回の列挙、実体化結果は繰り返し列挙を基本とする。
- 途中解放ではサーバーへ取消しを伝え、処理の終了を確認して接続を再利用する。

### 関係代数とシーケンス

- `ISet<T>` として扱う場合は関係代数、`IEnumerable<T>` として扱う場合は通常の LINQ のシーケンス契約に従う。
- キャストとコンパイル時に解決されたメソッドの契約を尊重する。
- 関係代数の射影は結果レコードの重複を除去する。
- 関係演算の公開拡張メソッドは `Seamless.Linq.Set` に整理する。
- シーケンス操作は標準 LINQ を基準にし、既存の FLinq の呼び出しインターセプト境界内で展開する。
- 直接渡したラムダだけをインライン化する。キャスト済みラムダ・デリゲート変数・メソッドグループは、デリゲート呼び出しを維持する。

### レコードとキー

- `Union`・`Intersect`・`Except`・`SymmetricExcept`、集合の等価性・包含関係は、レコード全体で一致を判定する。
- 同じキーでもレコード全体が異なる行は、関係演算の結果では両方保持する。関係演算結果をキー一意の格納型へ暗黙に押し込まない。
- `Contains(record)` はレコード全体を比較する。
- `Remove(record)` はレコード全体が一致した場合に削除する。
- キー指定の操作は `ContainsKey(key)`・`RemoveKey(key)` のように、名前に `Key` を付ける。
- 非破壊の関係演算は拡張メソッドとする。`UnionWith` 等の既存の格納先変更操作はインスタンスメソッドとし、照合・作成・更新を組み合わせる `MergeWith` は `Seamless.Linq.Set` の拡張メソッドとして整理する。
- すべての `...With` は呼び出し単位で全件成功か変更前への復帰とする。例外・キャンセル・リソース不足でも部分更新を残さない。
- `UnionWith` などがキー一意の格納先へ異なるレコードを追加しようとして衝突した場合は、変更を残さず失敗する。
- 移行時のキー衝突は移行を停止し、対象を表示して管理者が解決する。

### 明示的な更新とインデクサー

- 保存時は入力から独立したデータを保存する。取得したレコードとその参照先も、保存済みデータから独立させる。
- 一つの取得レコード内では参照共有・循環を保持する。
- 取得結果を変更した後の DB 更新は、`table[key] = row` 等の更新操作で明示する。
- 更新操作で正規化・制約検査・索引更新を行う。
- 指定キーと新しいレコードのキーを、正規化後の静的ストラテジで比較して経路を決める。

| 指定したキー | 新しいレコードのキー | 動作 |
|---|---|---|
| 存在しない | 指定キーと同じ | 新規追加 |
| 存在する | 指定キーと同じ | 既存行を上書き |
| 存在する | 指定キーと異なる | 旧キーから新キーへ原子的に差し替え |
| 存在しない | 指定キーと異なる | 更新元が存在しないためエラー |

- キー変更先が別の行と衝突する場合は、変更を残さず失敗させる。
- 変更前のキーが配列等を含む場合も、新レコードの変更から独立した状態で旧キーを保持する。
- インデクサーの一回の更新の原子性と、複数操作を含む取引の範囲を区別する。バッチ全体の確定・取消しが必要な場合は明示的な取引に接続する。

### 現在値に依存する Update と展開

- 現在値の取得・計算・反映を一つの原子的な更新として記述する `table.Update(key, updater)` を追加する。
- `Update` の戻り値は `void` とする。失敗は例外で通知する。
- 対象キーが存在しない場合は `KeyNotFoundException` とし、更新コールバックを呼ばない。
- キー不変の処理は一回の RMW へ接続する。キー変更も許容し、旧キーの削除と新キーへの追加を一つの原子的な更新として扱う。変更先が既存行と衝突する場合は元の行を保持して失敗させる。成功したキー変更の件数増減は0とする。
- インデクサーの取得と代入を組み合わせた式は、それぞれの操作の契約を持つ。単一の RMW へまとめる最適化は、元のコードの意味と取引の保証を確認して適用する。
- FLinq は、既存のメソッド呼び出しをインターセプトする境界内で、直接ラムダの `with` 式を解析する。
- 必要な旧値と変更対象を特定し、不要なレコード全体の復元や中間コピーを省く RMW 用コードへの展開を目指す。
- 通常のインデクサー代入でも、キー不変を証明できる場合は値更新経路へ展開し、証明できない場合は生成ストラテジによるキー比較で経路を選ぶ。
- DB テーブルの保存には履歴保持用の経路を使い、開始時参照と取消しに必要な旧レコードを保持する。非トランザクション作業辞書では、条件が合えばインプレース更新を使う。

```csharp
var key=Sample.Keys.dbo.Item.Create(1);
var row=Sample.Tables.dbo.Item.Create(key,10,"初期値");

table[key]=row;

// Update の対象キーが存在し、変更対象は非キー列である場合の例。
table.Update(key,static current=>current with{
    Value=current.Value+1,
    Name="更新済み"
});
```

このコード例は新しい生成 API と更新 API の仕様を示す。既存テンプレートのビルド成功の証拠とは分け、機能の実装時に生成・コンパイル・動作を検証する。

### Merge と MergeWith

- 存在しないキーでは作成し、存在するキーでは現在値から更新する単一キー操作を `table.Merge(key, create, update)` として用意する。公開 API の名称には `Merge` を使い、Tsavorite の Upsert と区別する。
- `Merge` はインスタンスメソッドとし、作成・更新の基本経路に RMW を使う。
- 単一 `Merge` は指定した主キーの行を検索し、そのキーでの作成または既存行の更新を行う。検索と作成は必要なロックで保護する。戻り値は `MergeResult` enum とし、正常時は `Added` または `Updated` を返す。失敗は例外で通知する。
- 複数入力との照合には `outer.MergeWith(inner, outerKeySelector, innerKeySelector, create, update)` を用意する。照合セレクターは両側で指定する。
- 照合値と格納先の主キーを分けて扱う。主キー以外で照合した場合も、対象行の更新には保存上の主キーを使う。
- 追加・更新の判定は `MergeWith` 呼び出し開始時の可視状態で固定する。同じ取引で呼び出しより前に行った変更を含め、今回の途中の追加・更新・キー変更は後続入力の照合へ反映しない。
- `outer` 内と `inner` 内のそれぞれで、正規化後の照合値とレコード全体の一致を判定する。同じ照合値に同一レコードが複数ある場合は重複除去し、異なるレコードがある場合はエラーとする。
- 両側の間で照合値が一致した場合は、レコードの値が異なっていても `update` の対象とする。入力に対応する格納先の行がない場合は `create` を使う。
- `inner` の同一レコードの重複によって更新を繰り返さず、重複除去後の一件として処理する。
- `MergeWith` は呼び出し単位の原子性を持ち、途中の重複エラー・保存先の主キー衝突・例外・キャンセル・リソース不足でも今回の変更を取り消す。
- 更新による主キーの変更を許容する。今回の変更対象外の既存行も含め、最終結果の主キーが一意なら入れ替え・循環移動を許可する。例えば `1 → 2` と `2 → 1` は同じ呼び出しで実行できる。
- 戻り値は名前付き `ValueTuple` の `(long Updated,long Changed,long Added)` とし、この順序で返す。`Updated` は既存行への更新処理数、`Changed` はそのうち正規化後のレコード全体が実際に変わった行数、`Added` は新規追加数とする。入力の同一レコードの重複は除去してから数える。
- 値が同じ既存行を更新した場合は `(1,0,0)`、値が変わった場合と主キー変更は `(1,1,0)`、新規追加は `(0,0,1)` とする。`Merge` の `Updated` には更新後の値が同じ場合も含める。
- 変更判定には生成した正規化・比較ストラテジを使う。FLinq が変更対象を特定でき、意味を維持できる場合は比較範囲も絞る。
- DB 用の `Update`・`Merge`・`MergeWith` の更新先を取引対応の DB テーブル型に限定する。Persisted と非トランザクション Tsavorite 辞書では呼び出せない型・拡張メソッドの受け取り型にする。これらの作業コレクションは `MergeWith` の入力として利用できる。
- 通常実行では入力を列挙して RMW へ作成・更新デリゲートを渡す。FLinq は直接ラムダを生成処理へ埋め込み、同じ取引・正規化・保存・件数管理の基盤へ接続する。照合が主キーと一致することを証明できれば主キー索引を使う。
- `MergeWith` 自体と FLinq の演算認識・展開は実装予定。拡張メソッドにするだけで既存の FLinq が自動的に対応するとは扱わない。会話中の `MergeRuntime`・`IMergeOperation` 等は内部実装案の名称である。

以下は作成・更新ラムダに入力レコードを渡す呼び出し形の設計例である。詳細なジェネリック制約・宣言構文は実装時に確定する。

```csharp
var (updated,changed,added)=outer.MergeWith(
    inner,
    outerKeySelector:static row=>row.Id,
    innerKeySelector:static input=>input.Id,
    create:static(id,input)=>Sample.Tables.dbo.Item.Create(
        Sample.Keys.dbo.Item.Create(id),
        input.Value,
        input.Name),
    update:static(current,input)=>current with{
        Value=current.Value+input.Value
    });
```

```csharp
public enum MergeResult{
    Added,
    Updated
}
```

### 開始時参照と一括キー変更の実行経路

- 開始時データの参照には `HistoryStore` の旧レコード保持・指定版での読み取りを基礎として使う。開始 Tail は参照範囲の境界として利用するが、可視版と旧レコードの保持も管理する。保持中の領域の回収・再利用で参照を失わないようにする。
- 現在の通常の走査は最新アドレスとの照合で古い版を除外するため、開始 Tail を渡すだけで開始時状態を取得できるとは扱わない。履歴読み取りと取引内の開始時ビューを組み合わせる。
- 主キー不変を証明できる場合は、既存の取引の変更集合へ結果を蓄積する簡略化した経路を使う。移動前後のキー配置を管理する専用索引を省ける。照合も主キーであれば既存の主キー索引を直接使い、不要な全件コピー・全件走査を避ける。
- 主キー変更がある一般経路では、開始時の更新元キーの集合と、最終的な主キーから更新結果の保存位置を引く索引を作る。作成・更新結果同士と、変更対象外の既存行との衝突を検査してから、キーごとの最終状態を取引へ反映する。
- 一括のキー配置を確定する経路を追加し、移動先の存在を都度拒否する既存の単一行 `Replace` の逐次呼び出しで代用しない。確定・取消し・復旧は取引の仕組みへ接続する。
- 更新結果の実データは一度蓄積し、作業索引にはキーや保存位置等の管理情報を持たせる。メモリ予算に収まる間はメモリを使い、超える場合はリソースマネージャー管理の一時ディスクへ退避する。
- 順次生成・順次読み取りする結果には Persisted の追記型領域、検索や小さな管理情報の書き換えには非トランザクション Tsavorite 辞書等を候補とする。既存の Persisted 索引も比較対象にし、件数・キーサイズ・予算・ストレージ条件で測定して選ぶ。具体的な最速の構造が確定・実測済みとは扱わない。
- 大規模時のハッシュ分割や外部ソート、まとまった I/O を実装候補とする。初版の照合・計算・比較・検査は逐次実行し、Anchor 付きの回数・評価順序を維持して件数を集計する。ワーカーへの分割は将来の並列化の検討事項とする。
- FLinq は直接ラムダから主キー不変を証明できれば簡略化した経路へ展開し、それ以外はキー変更を扱える一般経路へ接続する。最適化のために利用者のラムダを再実行しない。

### Persisted と非トランザクション作業辞書

- Persisted は作業領域として利用する。DB 用の取引更新 API を公開する対象には含めず、追記データ・一時索引・実体化結果等に利用する。
- 通常の Tsavorite 辞書も、ストレージへ退避できる非トランザクション作業辞書として Container に追加できるようにする。既存の辞書とストア生成の基盤を再利用する。
- 汎用作業辞書の本体と実行時生成の機能はランタイムライブラリ側で提供し、既存の `Store.CreateTsavorite<TKey,TValue>` と操作オブジェクトの生成を再利用する。`MergeWith` 内部等の汎用作業領域はこれを直接使い、DB 固有の `Work` 型や辞書の独自実装を要求しない。
- Container に名前付きプロパティを生成する場合は、利用者が `Work` 名前空間にキーと値の構造を持つ型を定義し、generator が対応するキー型・静的ストラテジ・辞書プロパティ・生成と解放の処理を用意する。この名前付き公開の基本宣言方式を型定義からの生成とする。
- Container の作業辞書は DB を開くたびに空で生成し、開いている間は処理をまたいで保持する。メモリ予算を超えるデータは一時ディスクへ退避し、DB を閉じると辞書と一時領域を解放する。
- 作業辞書の変更は即時反映し、DB 取引を取り消した場合も保持する。共有アクセスの同期には前述の事前ロックを使い、初版のメソッド内では逐次利用する。既存の単一用・並列用操作オブジェクトの実装事実と、初版への接続範囲を区別する。
- `MergeWith` 内部だけで使う一時領域は、その処理が所有して終了時に解放する。初版はその所有範囲で逐次利用する。
- キーと値の正規化・比較・ハッシュ・シリアライズを生成した静的ストラテジへ接続する。generator が辞書型・ストラテジ指定・生成と所有のコードを用意し、型名をまとめるための派生クラスは作らない。
- インプレース更新の許可と旧版保持等の更新方針も静的ストラテジで固定する設計とする。辞書本体の生成時に選び、同じ本体の操作オブジェクト間で整合させる。作業辞書ではインプレース更新を許可し、実際に適用できない場合はコピー更新する。DB テーブルでは取引に必要な履歴を保持する。
- 既存の通常辞書にはインプレース更新経路があり、履歴ストアでは無効化されている。更新方針の静的ストラテジ化、生成コード、Container への作業辞書の接続は実装予定。

### ランタイムの作業 Store API と所有権

- 実行時に作る作業領域の入口は、作業 Store 方式とする。`db.CreateWorkStore()` で DB の親予算・一時領域・寿命管理に接続する作業 Store を作り、その中で既存のコレクション生成・操作オブジェクトの仕組みを使う。
- 作業 Store と、その配下の作業コレクションの生成に、利用者が指定する名前文字列を要求しない。作業辞書は `work.CreateTsavorite<TKey,TValue>()` の形で作る。Store は生成したコレクション本体への参照と解放処理を保持し、所有・破棄を管理する。
- 一時領域の生成・所有・破棄は参照ベースで実装する。一時ファイル・ディレクトリには衝突を避けた配置先を割り当て、所有するファイルハンドルとともに管理する。既存の名前付き登録・保存状態の検索とは用途を分け、作業領域用の生成・登録経路を追加する。
- 一つの作業 Store に複数の辞書・集合・Persisted 領域を所有させられる。各コレクションのネイティブ索引・ログ・バッファはそれぞれが持ち、親予算と作業領域の所有を共有する。
- `using` で操作オブジェクトを先に解放し、その後に作業 Store を解放する。Store は配下のコレクション本体・一時領域を所有し、Store の終了で残る所有資源を解放する。処理全体の終了時にも所有範囲の後始末を行う。
- DB を使わない検証・ベンチマークでも、同じ作業 Store とコレクションのランタイム基盤を使えるようにする。DB 固有の生成型を汎用作業領域の必須条件にしない。

以下は追加する作業 Store 入口と、名前を要求しない生成 API の仕様例である。既存実装がこの呼び出し形に対応済みとは扱わない。

```csharp
using var work=db.CreateWorkStore();

var data=work.CreateTsavorite<int,long>();
using var counts=data.Create();

counts[1]=100;
counts[2]=200;
```

### 初版の RMW と件数管理

- 初版の更新は逐次 RMW を基本とし、確定する新規追加・削除の増減を件数へ反映する。取引の変更集合と各更新 API の原子性に従い、取消し時の件数も整合させる。
- 開始時件数が未確定なら、その状態を引き継ぎ、正確な件数が必要になった時点で安全に再集計する。
- `expectedCount` は容量・索引の見積もりに使い、確定件数として扱わない。

### 将来の並列 RMW とローカル計数

- ワーカー単位のローカル計数を使う並列 RMW と、DB テーブル層への `BeginParallel`・`Create` 等の接続は後続検討とする。初版の更新・件数管理は前節の逐次経路を使う。
- 既存の低レベル `ParallelDictionary` には、同じデータ本体・索引を共有し、ワーカー専用の操作オブジェクトを `using` で管理する仕組みがある。RMW の新規追加・削除を手元で数え、各操作オブジェクトの破棄時に差分を集約する。
- 将来この仕組みを DB 層へ接続する場合は、全操作オブジェクトの終了時に開始時件数と差分を合算する方式を検討する。開始時件数が未確定の場合の扱い、失敗・取消し・取引の確定との整合も再開時に詰める。

### サーバー内部の Upsert 最適化

- Upsert は、サーバー側の最適化で使う `internal` メソッドとして設ける。
- 同じ取引等で存在と件数不変が保証され、旧値を必要としない上書きは、内部 Upsert の対象にできる。
- 正確な件数を必要としない内部作業用データでは、内部 Upsert と計数省略の経路を使えるようにする。
- 重複拒否・旧値依存の計算・制約検査・索引更新・取引の原子性に必要な処理を確認して経路を選ぶ。
- 条件を確認できない場合は RMW を使う。
- Upsert を選んだ根拠、実行時に分岐する場合の条件を展開コードへコメントとして記載し、実行トレースから採用経路を確認できるようにする。
- `DeferredCount` 等の利用者指定モードは会話中の API 案として扱い、合意済みのサーバー内部最適化と区別する。

### 計数省略後の遅延再集計

- 計数省略の経路ではストアの件数を未確定にし、処理区間の終了時もその状態を保持する。
- 件数が初めて必要になった時点で、書き込みと競合しない安全な状態で正確な件数を再集計する。
- 確定できた件数を保持し、以降の通常の件数取得に利用する。
- 現在の再集計はログを走査し、各キーを既存索引で検索して最新アドレスと照合する。現在有効な版だけを数え、削除済みの行を除外する。
- 重複排除用に同じ規模の別ストアを作る必要はない。走査と検索のバッファ等を使う。
- コストは現在の行数だけでなくログの履歴量・索引検索・ディスク I/O に左右される。
- Tail の増分はログ領域の増加を表す。インプレース更新、既存キーの末尾への書き直し、削除済み領域の再利用があるため、Tail 差だけを正確な行数の根拠にしない。
- Tail で区切る差分再集計には、開始時点の生存判定と領域再利用への対応等が必要であり、採用済みの仕様とは分けて扱う。
- RMW と Upsert の性能比較では、書き込み時間と、必要な件数が確定するまでの合計時間を確認する。

## 比較・正規化・静的ストラテジ

### 型に固定する契約

- 後続で独自比較を扱う場合は、比較の意味が異なる値を「値＋静的ストラテジ」を持つ別の値型として表現する。初版は合意済みの既定規則を使う。
- 比較、ハッシュ、正規化、保存・通信表現、契約の識別情報を一貫させる。
- 操作ごとに比較器を渡したり省略したりして、永続データの扱いが変わる設計を避ける。
- 既定ストラテジは generator が自動生成する。初版では、本書で合意済みの既定の比較・正規化規則を一貫して使用し、操作箇所ごとに比較方式を変更できる仕組みを増やさない。
- 独自比較の新たな宣言機能は初版では追加せず保留する。後続で扱う場合も定義は型に固定し、利用者には意味の選択を求め、実装の手書きを最小化する。
- 後続でストラテジが異なる値型間の変換を扱う場合は明示的な変換とし、失われる情報は変換前に判断する。
- 保存後に比較規則を変更する場合は、契約の照合と明示的な移行を必要とする。
- 既定以外の比較意味を指定する具体的なテンプレート構文は、後続検討事項とする。独自比較の宣言機能を保留しても、合意済みの比較・正規化規則と、保存後の規則変更に必要な契約照合・明示的移行の方針は維持する。

### 正規化・比較の実装接続

- 数値・日時の共通正規化は下位の `Seamless.Collections.ScalarNormalization` に置き、DB・実行基盤・送信処理で同じ処理を再利用できるようにする。float・double・Half のゼロと NaN、decimal の符号・スケール、DateTime・DateTimeOffset と各 nullable 形式を対象とする。
- 生成器の作成・列 init・キー代入を共通のスカラー正規化へ接続する。既存の `Keys`・`Records` の保存形式を、この追加だけで変更しない。
- 参照共有を維持する全体処理、private フィールドの型専用処理、比較・ハッシュの静的ストラテジを共通基盤へ接続した。参照を含む値の深い正規化は境界でレコード全体へ適用し、元の入力から独立したコピーを作る。Create・with・個々の init は渡された参照共有を維持し、数値・日時の列はその場で正規化する。
- キー列と通常列が同じ参照先を持つ場合も、レコード全体で一つの参照対応表を使う。正規化後もその共有を保持し、内容が等しくても別々だった参照先は別々のままコピーする。文字列の等価性は既定どおり内容で判定する。

### レコード全体の処理の実装方針

- `Seamless.Execution.RecordValueStrategy<T>` を全体の正規化・等価性・ハッシュの既定入口とし、生成した型の静的ストラテジへ接続する。深い正規化の一回ごとに、入力参照からコピー先への対応表を作る。
- 型解析は初回に行い、private・readonly フィールドを読む・正規化する・書く型専用の DynamicMethod をキャッシュする。通常のフィールド走査で FieldInfo.GetValue・SetValue・DynamicInvoke を繰り返さない。参照を含む型のキャッシュは collectible 型の寿命を保持しない方式とする。
- 比較では左右の参照対応を照合し、ハッシュでは走査順の参照 ID を使う。文字列は内容で比較する。値型のフィールドと object 等に格納された boxed 値は、その参照としての扱いを区別する。
- ワーク領域は ResourceBudget で制限し、失敗・取消しでも予約を解放する。既定入口の上限を用意し、DB・要求が持つ親予算を渡せる経路も用意する。Graph 形式の復元値には後述の `OwnedValue<T>` を用意し、保持寿命の予算を所有側へ引き継ぐ。

### 正規化・比較・ハッシュの実装検証

- `ScalarNormalization` をキーと通常値の作成・init・キー代入へ接続した。NaN は float が `0x7fc00000`、double が `0x7ff8000000000000`、Half が `0x7e00` の正の quiet NaN とし、ゼロは正のゼロへ統一する。
- 生成型は `IRecordStrategy<T>` を実装する nested `Strategy` を持つ。`Strategy.Normalize`・`Equals`・`GetHashCode`、規則・型・列対応を含む `ContractId` を生成し、型の `IEquatable<T>`・既定の Equals・GetHashCode へ接続する。
- スカラー列だけの型には直接処理を生成する。共通入口も初回にその型固定の処理へ結び付け、ハッシュを一致させる。`IsGraphFree` はこの生成経路の識別情報であり、操作ごとに比較の意味を変える指定には使わない。
- 全体正規化は一回ごとに独立した参照対応を作り、共有・循環・配列の次元と下限・boxed 値の共有を維持する。元の入力を変更しない。文字列の共有は等価性に含めない。
- ワーク予算の既定上限は全型共通の 64 MiB とし、親 ResourceBudget と取消しを渡せる。明示レイアウトの宣言サイズを含めて見積もり、大きな値型の boxing 前にも予約する。通常の Normalize が返すコピーは呼び出し元が所有し、Graph 形式で保持分も計上する場合は後述の所有付き復元を使う。
- 重複している明示フィールド、ポインター・byref-like フィールド、デリゲート・メタデータ・SafeHandle・finalizer を持つ型などのランタイム所有状態は自動処理で例外にする。専用アダプターの接続は後続実装とする。
- 複雑な型の private フィールドは現在 DynamicMethod の型専用処理で扱う。UnsafeAccessor の事前生成、余白のない連続範囲のバイト比較・ハッシュは引き続き実装対象とする。生成 Native の送信・引数境界は後述の共通コーデックへ接続した。
- 最終候補の通常入口は Debug 81 件・Release 81 件が合格した。共通スカラー 21 件、レコード全体 17 件、新しい宣言生成 26 件、既存のアクセサー・Container・インポート・ビュー・AdventureWorks2017 スキーマ 17 件を含む。代表的な int・decimal・string の生成型で、ウォームアップ後の正規化・比較・ハッシュの追加割り当てが 0 bytes であることを検査した。
- 検証証跡は `F:/Seamless/record-strategy-20261107-9c1e` 配下にある。通常入口が一時的に FLinq の構文エラーで停止した工程は分離し、実行基盤の試験で継続した後、通常入口で生成型を含む回帰を再確認する。
- レコード全体での正規化を指定した追加確認では、生成レコードのキー列と通常列をまたぐ共有・循環、内容が等しい別インスタンスの維持、呼び出しごとのコピーの独立性を既存の生成器試験へ追加した。共通の正規化実装を使い、関連する正規化・参照形式・宣言生成の回帰は Debug・Release 各92件が合格した。失敗・スキップは0件。証跡は `F:/Seamless/normalization-boundary-20261107-2b29/verification.json` にある。

### 参照構造を保持する保存・通信への接続方針

- 保存・通信の境界で値の正規化と符号化を一緒に行うコーデックを実装する。一回のデータ全体で参照 ID を共有し、読み取りでは生成直後に ID を登録してからフィールドを復元する。
- 型専用のフィールド処理をキャッシュし、private・readonly フィールド、共有配列、循環、boxed 値を扱う。文字列は内容として扱う。利用者のコンストラクター・プロパティ getter を復元時に呼ばない。
- 新形式には形式版と型契約を含め、実行時型は既に読み込まれた同じモジュール版だけから解決する。既存 CanonicalV1 の形式を引き継ぐ経路と分け、永続ストアへ接続する際は形式の識別と明示的な移行を必要とする。
- 符号化・復元のワークと出力構築を ResourceBudget で制限し、取消し・失敗時にも予約を解放する。出力の保持寿命は呼び出し元の所有管理へ接続する。
- 共有と循環の往復、数値・日時の正規化、異なる版と不正データの拒否、入力の非変更、予算と取消しを先に契約試験へ追加する。DB・送信の自動接続の進捗はコーデック単体の検証と分けて記録する。

### 参照構造の保存・復元の実装検証

- `Seamless.Execution.Codecs.RecordGraphSerializer<T>` を追加した。符号化時にスカラーを正規化し、一つの参照 ID 表で共有と循環を保持する。private・readonly・継承フィールドを型専用 DynamicMethod で扱い、復元時に利用者のコンストラクターやプロパティ getter を呼ばない。
- 文字列は UTF-16 の内容を保持し、共有の仕方を比較へ含めない。boxed 値、配列の次元・下限、`InlineArray` の全要素を扱う。`FixedText<TBuffer>` の往復も検証した。従来のフィールド走査では `InlineArray` の後続要素を処理できない欠陥を再現し、正規化・比較・ハッシュも全要素の処理へ修正した。fixed buffer は専用アダプターを必要とする型として拒否する。
- 形式版、正規化規則、宣言型・フィールド・モジュール版からの契約を照合する。実行時型の解決は root の読み込み文脈と共有ランタイムの既存モジュールに限定する。不明なモジュール版、型契約の不一致、不正な参照・長さ・末尾データを拒否する。実際の collectible AssemblyLoadContext で往復し、型キャッシュがアンロードを妨げないことを GC で確認した。
- `CodecRegistry.UseRecordGraphSerialization` を最初の型解決前に指定し、`RecordGraphCodec<T>` を ExecutionScope の所有バッファ・予算・取消しへ接続する。子スコープには子の予算を渡す。変更集合のメモリ内キー比較と退避索引のバイト比較を同じ契約へ揃え、保存したキーを入力から独立させる。異なる比較器の追加指定を拒否する。
- 新規の型付き SharedV2 領域では `DatabaseRecordSerialization.RecordGraphV1` を明示指定する。通常テーブル・実体化ビュー、同期の取引オーバーレイと非同期取引、版付きテーブルの保存・読み取り・WAL へ接続した。チェックポイント版 7 に形式と各テーブルの契約を記録し、形式の切り替え・行型変更・表集合の不一致を読み取り前に拒否する。
- 管理対象ストアでは、低層の `RecordGraphSerializer<T>` も所有 Store の予算へ束縛する。ExecutionScope 経由の adapter は DB・要求の親予算を使う。単独の静的 API の既定枠は共通 64 MiB とする。保持分の会計には後述の `DeserializeOwned`・`DecodeOwned` を使う。通常の Deserialize・Decode が返す値は呼び出し元が所有する。
- 最終の通常入口で Debug・Release 各 93 件と DB 関連各 22 件が合格した。前者には共通スカラー 21 件、全体処理 17 件、参照形式 12 件、宣言生成 26 件、既存生成・インポート・ビュー・AdventureWorks 17 件を含む。DB は参照形式の 15 件と既存の銀行・読み取り専用取引 7 件を含む。途中で対象外の FLinq 生成エラーがあった工程は独立ハーネスで継続し、最終候補では通常の両入口へ戻して確認した。
- 証跡は `F:/Seamless/record-graph-20261107-b571/verification.json` と同ディレクトリ内の receipt・TRX に記録する。生成 Native の自動適用は後述の実装検証へ接続し、C/S の物理分離は後続実装へ引き継ぐ。

### 低層の保存処理への予算接続方針

- 管理対象の Tsavorite ストアでは、所有する Store の ResourceBudget を操作オブジェクト・走査オブジェクト・セッション関数へ明示的に渡す。I/O 完了の実行スレッドに依存しない形にする。
- 既存の静的 serializer 契約を引き継ぎ、予算付きコーデックを作る追加契約を用意する。初回の型判定と生成処理をキャッシュし、各レコードの読み書きでリフレクションを繰り返さない。
- キーの符号化バッファは Pending 完了まで、値の符号化バッファはログへのコピー完了まで予約を保持する。長さを求める処理は予算付きコーデックの計測を使い、符号化失敗・復元失敗でも操作の予約を解放する。
- 読み取り、追加・上書き、削除結果の復元、キー・値・ペアの走査、並列操作を同じ予算へ接続する。予算不足の拒否、解除後の再実行、件数・既存データの維持を契約試験で検証する。
- 通常の取得結果を呼び出し元が保持する寿命と、生成 Native の境界に設ける所有付き引数・送信バイト列は、低層処理中のワーク予算と区別する。追加の所有契約は後述の実装検証へ接続する。

### 低層の予算接続の実装検証

- `IResourceSerializer<T>.CreateCodec(ResourceBudget)` を実行基盤へ追加し、`RecordGraphSerializer<T>` から予算に束縛した adapter を生成する。`StoreSerializer<T,TStrategy>` は型ごとの生成 delegate をキャッシュする。管理対象ストアの操作オブジェクト、キー・値・ペアの通常走査とメモリ限定走査、Read・RMW・削除のセッション関数へ所有予算を渡す。
- 符号化は `SerializedStoreValue` が一時バッファの予約を所有し、コピー・Pending の必要な区間を `using` で囲む。長さの計測では不要な符号化バッファの生成を省く。追加契約を持たない serializer は既存の静的呼び出しを使う。
- `DictionaryStore.BeginParallel<TKeySerializer,TValueSerializer>(expectedCount)` を追加した。同じ serializer を全ワーカーへ引き継ぎ、各ワーカーの RMW と Dispose による件数合成を所有 Store の予算内で実行する。
- 修正前には、読み取り・走査・削除結果の復元が所有予算を迂回する 3 件の失敗を確認した。修正後の 16 件では、予算不足の拒否と解除後の再実行、符号化中の例外、キー・値の予約解放、既存行・件数の維持、複数ストアの独立した上限、並列ワーカーを検証した。実際に FlushAndEvict してディスク経由の Read・Remove の完了処理も確認した。
- collectible 型の検証に管理対象ストアでの保存・復元を追加し、新しい型生成 delegate のキャッシュも DLL の解放を妨げないことを実 GC で確認した。
- 通常入口のコレクション関連は Debug 31 件・Release 30 件が合格した。両構成の新規 16 件と既存の件数 13 件を含み、同時走査の検出試験は Debug が 2 件、Release が 1 件である。正規化・比較・参照形式は両構成各 50 件、DB 関連は各 22 件が合格した。変更対象外の既存テスト 4 箇所に `xUnit1031` の警告がある。
- 証跡は `F:/Seamless/serializer-budget-20261107-8d91/verification.json` と同ディレクトリ内の receipt・TRX に記録する。保持寿命と生成 Native の境界は後述の所有・通信の検証へ接続し、C/S の物理分離は後続実装へ引き継ぐ。

### 保持中の参照構造の所有・予算管理

- 復元用ワークと、復元後に保持するオブジェクトの予約を分ける。`OwnedValue<T>` を `using` で所有し、Dispose まで保持分の予約を残す。ExecutionScope へ接続した所有値は scope の終了でも解放する。
- 参照 ID と同じ走査で復元後の大きさを見積もり、参照共有・循環は一回分を数える。文字列・配列・boxed 値・宣言サイズを持つ型も対象にする。所有値から取得した参照を使う区間は、その所有寿命内とする。
- Graph 形式の変更集合は、メモリ内でも予算付きの符号化キー・行を保持する。読み取り時に独立した値を復元し、上書き・退避・破棄時に旧バッファの所有を解放する。メモリ索引の比較も符号化キーの内容へ揃える。
- 変更集合の列挙では現在の復元値を所有し、次要素への移動・列挙終了・例外で予約を解放する。保存点の独立性、失敗後の再試行、件数と既存データを維持する。
- LINQ の結果バッファは入力参照を保持し、参照の一致を保つ。Graph 形式では符号化長の倍率を、復元後の大きさを反映する保守的な見積もりへ置き換える。配列・リスト・辞書を呼び出し元へ渡す時点で構築側の予約を解放する。

### 保持中の参照構造の実装検証

- `RecordGraphSerializer<T>.DeserializeOwned` と `ExecutionScope.DecodeOwned<T>` を追加した。`OwnedValue<T>` が復元後の予約を保持し、Dispose または所有 scope の終了時に解放する。破棄後の Value 取得を拒否し、所有オブジェクト自体はレコードの保存対象として拒否する。

- Graph 形式の変更集合は、メモリ内と退避後の両方で入力・取得結果・保存点を独立させる。現在の列挙値には所有付き復元を使い、列挙を中断した場合も予約を解放する。通常の TryGetValue・Deserialize・Decode が返す値は呼び出し元が所有する。

### Graph 形式の通信境界への接続方針

- Native の引数・結果に Graph 形式を接続する前に、値の復元前の受信検査を同形式へ対応させる。共通の reader と型契約を使い、値オブジェクト・文字列・配列の生成や利用者の getter・コンストラクターの呼び出しを検査に使わない。
- フィールドを読み飛ばす型専用処理を初回に作り、通常の検査でフィールドのリフレクションを繰り返さない。参照先の型を登録して共有・循環・参照 ID の妥当性を照合する。
- 本文長、文字数・配列要素数の合計、値・型記述を合わせた走査ノード数、値と型記述の深さを制限し、ワークと復元時の必要量を ResourceBudget で検査する。形式・型契約・版の照合と、取消し・失敗時の予約解放を維持する。
- 既存 Native の MemoryPack 用検査を Graph 形式へ流用せず、通信経路への適用と実接続の検証は共通検査の契約試験後に行う。正式な Native クエリを事前生成へ統一する方針は維持する。

### Graph 形式の復元前検査の実装

- `RecordGraphSerializer<T>.Validate` を追加した。復元と同じヘッダー・スカラー・型記述・配列境界の reader を使い、型専用の読み飛ばし処理をキャッシュする。通常のフィールド検査で `FieldInfo.GetValue`・SetValue・DynamicInvoke を呼ばない。
- 検査中の参照表には型を保持し、共有・循環と代入可能性を検査する。利用者の値オブジェクト・文字列・配列を復元せず、コンストラクター・getter を呼ばない。参照表・型表等の検査用ワークは ResourceBudget へ計上し、復元に必要な大きさも検査する。
- `RecordGraphValidationLimits` で上限を指定する。既定は本文 16 MiB 未満、文字数合計 65,536、配列要素数合計 65,536、値・型記述を合わせた走査ノード数 1,000,000、値と型記述それぞれの深さ 64 とする。文字列・配列はレコード全体で合算し、参照 ID による共有先の配列を重ねて数えない。
- 正常な共有・循環、private・readonly、nullable、InlineArray、多次元と下限付き配列、各スカラー、全位置での切り詰め・余剰、不正な版・型・参照・長さ、予算不足・取消しを確認する。型記述だけが深くなるケースも深さ上限の対象にする。
- 宣言サイズが 4 MiB の参照型について、ウォームアップ後の検査の割り当てを 64 KiB 以下として検査した。利用者のコンストラクターと getter の呼び出し回数も検査する。種を固定した 300 件のバイト改変では、検査を通った入力が同じ reader で復元できることを確認する。
- 配列要素数の合計が long 上限を越える場合の OverflowException を再現し、加算前に残り上限と照合して InvalidDataException で拒否する形へ修正した。失敗時の予約解放も検査する。
- 通常入口の選択回帰は Debug・Release 各 129 件が合格した。正規化・参照形式・宣言生成が各 91 件、DB の保存・銀行取引が各 22 件、低層 serializer の予算接続が各 16 件である。新しい復元前検査の契約 7 件を含む。検査・生成側の最終ビルドに警告はなく、変更対象外の保存関連試験コードに `xUnit1031`・`xUnit2017` がある。

### 型別の正規化規則

| 型・値 | 保存・送信・引数処理での規則 |
|---|---|
| 浮動小数点の `-0` | `+0` に正規化する |
| 浮動小数点の `NaN` | 型ごとの一つのビット表現へ統一する |
| `decimal` | 不要な末尾ゼロを除き、ゼロの符号・スケールを統一する |
| `DateTimeOffset` | UTC、オフセット `+00:00` に統一する |
| `DateTime` の `Utc` | そのまま使用する |
| `DateTime` の `Unspecified` | `Ticks` を保持し `Utc` とみなす |
| `DateTime` の `Local` | 送信前に送信元マシンのローカル時刻から UTC へ変換する |

- 正規化はキーと通常の値フィールドの両方に適用する。「通常の値フィールドは入力表現を保持する」という以前の方針は、この合意で更新された。
- サーバー内で新たに作った値にも、保存・比較用表現を作る際に同じ規則を適用する。サーバー生成の `Local` はサーバーのタイムゾーンを使う。
- 後続で別の日時ストラテジによる比較を扱う場合は、オフセットや地域に必要な情報を保持する。地域を表すタイムゾーン ID は UTC オフセットと区別する。
- クライアントの送信ライブラリで、シリアライズに組み込んで正規化する。呼び出し元のオブジェクトの変更を必須にしない。
- 正規化規則を含む通信契約が一致する経路では、サーバー側の同じ正規化走査を省く。

## レコード配置・二つの保存領域・コード生成

### 二つの保存領域の確定・取消し・復旧

- 値型領域と参照型領域の両方の更新内容を、共通 WAL へ同じ取引として記録する方式を採用する。既存の取引基盤を再利用し、同じ行・同じ取引に属する両領域の対応を保持する。
- WAL の確定記録の永続化を待ち、両領域の新しい状態がそろった段階で同じ取引として公開する。片方だけ更新された状態を読み取りへ公開しない。
- 未確定の変更を取り消す場合は旧状態を維持する。障害後は共通 WAL の確定済み取引から必要な両領域の更新を再適用する。
- WAL の確定記録が永続化された後に反映が失敗した場合の結果判定・復旧も、共通の取引基盤へ接続する。確定・取消し・結果不明の状態を区別する。
- 二領域用の WAL 符号化、行・版の対応付け、大きい変更の分割記録、再適用と回収の詳細は実装判断として残す。この二分離が既存実装で対応済みとは扱わない。

### 利用者定義の構造体

- 通常の `struct` と partial プロパティ形式の両方を許容する。`record struct` は通常の構造体の一種として扱う。
- partial プロパティ形式では、値側と参照側をそれぞれ private 構造体へ集める。値側のフィールドを詰めて配置する。
- 保存先も値側と参照側の二つに分ける設計を採用する。
- 入れ子の構造体の内部まで分離する。プロパティ取得で元の型が必要な場合は復元する。
- FLinq で内部の値フィールドだけを利用する場合は、元の構造体全体の復元を省ける展開を目指す。
- 通常の構造体も、途中にパディングがない配置は分離対象とする。参照と値の前後関係に制限を設けない。
- 末尾のパディングは有効長から除外する。

| 通常の構造体の配置例 | 扱い |
|---|---|
| `long, 参照` | 分離対象 |
| `参照, long` | 分離対象 |
| `byte, 参照` | 途中のパディングにより対象外 |
| `参照, 参照, long, int, short, byte` | 分離対象。末尾の余白は除外 |
| `参照, 参照, long, int, byte, short` | 途中のパディングにより対象外 |

- 宣言順だけで最終配置を断定せず、実際の配置を確認する。型ごとに確定した処理を利用する。
- analyzer は、余白を減らすフィールド順、または partial プロパティ形式への変更を警告する。
- generator にフィールド生成を任せる形式の必須条件はエラーで検査する。通常の構造体を許容する仕様と区別する。
- 余白のない連続範囲はバイト比較を使い、それ以外は生成した比較処理で余白を除外する。ハッシュも同じ有効データを対象にする。

### private フィールドと BCL 型

- private フィールドも自動対応する。BCL 型も、内部の型情報や既知の公開 API を利用して対応する。
- 生成器所有フィールドには直接アクセスする。
- ビルド時に特定できる非公開フィールドには、`UnsafeAccessor` を用いるアクセス処理を生成する方針。
- 実行時に具体型が確定するなどの経路では、初回に `DynamicMethod` 等で型専用処理を作り、型付きデリゲートとしてキャッシュする方針。
- 通常処理で毎回 `FieldInfo.GetValue`・`SetValue` や `DynamicInvoke` を使う方式を高速経路にしない。
- 読み取り・正規化・書き出しを型単位でまとめ、不要な boxing・全体コピー・再構築を減らす。
- 独自形式のバイト列内部は、その形式を知る処理との接続が必要になる。

### 参照共有

- 一回の送信データ、または一つの保存レコード内で、同じインスタンスを指す複数の参照は復元後も共有させる。
- 例として二つのプロパティが同じ配列を指す場合、復元後も片方からの変更をもう片方から観測できるようにする。
- 自分自身や親を指す循環参照も、保存・送信・比較・ハッシュの対象にする。
- 等価性は、正規化後の値と参照のつながり方で判定する。異なるインスタンス同士でも内容と共有・循環構造が同じなら同一と扱う。
- 同内容の二つの配列を別々に持つ構造と、一つの配列を二つのプロパティで共有する構造は区別する。一つのノードが自分へ戻る循環と、二つのノードが互いを指す循環も区別する。
- 文字列は内容を ordinal 比較し、同じ内容を持つ別インスタンスと共有インスタンスを区別しない。配列など変更可能な参照型は共有・循環構造も比較へ含める。
- メモリアドレスやインスタンス固有のハッシュへ依存せず、定まった走査順で参照 ID を割り当て、比較・ハッシュ・シリアライズを一貫させる。
- 訪問済みの参照は再展開せず、循環があっても走査を終了する。処理量とメモリ使用量はリソースマネージャーの上限で管理する。
- 型の解析も再帰的な定義を扱えるようにし、型の解析と実データの走査を分けて管理する。
- 保存はレコードごとに独立させ、保存時の参照 ID の範囲もレコード単位にする。異なる保存レコードへ同じ配列を渡しても、復元後の配列はレコードごとに独立する。
- レコード全体の比較・ハッシュは、そのレコード内の値と参照構造だけで決まるようにする。一回の送信データ内の参照共有は、その送信データの範囲で保持する。

## 初版のリソース管理

- 初版はメソッド・クエリ内部を逐次実行し、DB 間・要求間の資源予算、入場制御、待機、取消し、所有寿命を管理する。
- 使用可能な論理コアは利用者が明示指定する。NUMA・物理ドライブ・I/O コントローラーの独立性を考慮する。
- 不明なトポロジーは観測値や利用者設定を使う。
- 全 DB で資源予算を共有する。固定の DB 別予算を基本にしない。待機と aging による公平性を考慮する。
- メモリ上限と最低空きメモリ、保存先ごとの使用上限と最低空き容量、一時ディスクをリソースマネージャーで管理する。
- 予算を下げた場合は新規獲得を抑え、安全に縮小・解放する。
- 圧迫時は新規処理の入場を抑え、既存の重い処理の進行、縮小、一時ディスクへの退避などを行う。
- 資源獲得等の取消し・再試行・ロールバックは、その内部処理が安全に再実行・取消し可能な場合に行う。利用者のクエリ・更新ラムダの自動再実行を避け、外部副作用や既に送った結果の取消しを仮定しない。
- 単独でも資源上限に収まらないクエリは明示的な資源不足として失敗する。
- サーバーなし検証とサーバー動作を同時実行しない。切り替えでは新規受け入れを止めて既存処理を待つ。
- サーバーなし検証同士は共有予算内で並行できる。性能測定は競合する測定・検証と調整して実行する。
- Windows を先行し、Linux へ展開する。

## 将来の並列化・DAG 実行

- 独立読取の自動並列化、`ParallelRead`、`Container.Parallel`、並列化目的の `Task`・`async` 化、専用 fork/join 実行器の選択は後続検討とする。初版は逐次実行を使う。
- クエリを依存関係付きサブタスクへ分け、CPU・メモリ・ストレージ・NIC 等へ非同期ディスパッチし、別リソースの待ち時間に実行レーンを解放する DAG スケジューラは将来案とする。
- 並列度、ワーカー、分割粒度、専用実行器の比較と性能測定、ワーカー間の所有・ロック共有、結果の固定と遅延列挙、先行自取引更新の共有方法は、並列化を再開する時点で具体化する。
- 並列区間の失敗・取消しの伝播と Join の中止、`catch` と取引全体の取消しの関係は、再開時に適用範囲を確定する。初版は通常の逐次 C# 例外処理と明示的な取引境界に従う。

## 最適化・副作用

- 通常は副作用なしとして扱う。網羅検証で副作用ケースを追加する場合は UI で指定する。
- `Anchor` は副作用があり、最適化を制約する指定。評価順と評価回数を保証する。
- 副作用ありでは、基準クエリの副作用の値・発生順序も比較する。
- 展開を行った上で最適化を無効にする比較経路を設ける。
- 安全な書き換えを行う根拠、実行しない根拠、実行時選択の条件を展開コードのコメントへ記載する。
- 多段 Join、ブーリアン演算、集合演算の並べ替えは、意味と副作用の契約を保てる範囲で行う。
- 一回の Join でも要素数が取得できる場合は、実行時に構築側を選択できる。要素数を知るための余分な列挙を前提にしない。
- メモリ超過は明示的な予約・上限検査で制御し、通常の容量制御をアクセス違反の捕捉に依存させない。

## 検証・ベンチマーク

- ランダム探索とは別に、有限の入力・式・構造の集合を順序立てて生成する網羅モードを設ける。
- 直列はペアと3段を基本とし、通常の4段以上を対象に広げない。共有 source・共有中間チェイン・fork は式の構造として検証し、初版はこれらも逐次評価する。
- 有限の代表入力、式の種類、境界定数、キャスト・デリゲートの渡し方等を組み合わせる。具体的な全コーパスは今後確定する。
- 同じインスタンスと同内容の別インスタンスで動作差が出るケースは両方含める。
- 比較対象は System.Linq、ZLinq、FLinq 最適化あり、FLinq 最適化なしを固定で用意する。
- 生成器・展開器が未対応の有効クエリを、黙って除外して成功扱いにしない。
- エラーは記録して続行し、種類別の一覧・フィルターから確認できるようにする。
- 副作用なし、短時間の代表ケース、性能計測なしを初期設定とし、広い網羅・副作用・性能計測等はドロップダウンから選ぶ。
- 手動停止・異常終了から再開できるようにし、未完了ケースは再実行する。
- コード・設定の世代が違う結果を混在させない。
- 改善の判定は履歴・計測値を提示して利用者が判断する。自動的に改善完了と決めない。
- 既知ケースはインプロセスで初版の逐次実行基盤を使い、未知の生成ケース等は別プロセスの選択肢を持つ。ケース間・検証間の同時実行は共有資源の既存規則に従う。
- 初版の受入では、逐次の正しさ、既定比較・正規化、保存・復元、取引全体の Serializable、先行自取引更新、例外と `catch`、各更新 API の原子性、対象 IDE の生成プロパティ補完を検証する。将来の並列機能の検証は後続工程へ分ける。

## FLinq GroupBy 最適化と汎用集約の設計知見 (2026-11-07)

### 1. 実装済み: 小範囲整数キーの Dense stackalloc 集約
- 対象: キー式が静的に限定（0〜255）される場合（例: `x & 15` → 0〜15, `Math.Abs(x) % 8` → 0〜7, `byte` キー → 0〜255）。
- 実装: `stackalloc` による直結テーブル＋出現順管理（`seen`/`order`）。
- 成果:
  - `chain-08`: 7,404.5 ns (6,208 B) -> **378.0 ns (120 B)** (vs System.Linq **8.98x 圧勝**)
  - `chain-20`: 8,787.5 ns (6,872 B) -> **1,010.4 ns (408 B)** (vs System.Linq **4.30x 圧勝**)
- 理由: ハッシュ計算、バケット検索、衝突チェーン、ヒープ割当を完全排除。

### 2. ZLinq 比較調査から得られた知見と汎用 GroupBy 集約の設計指針
- **旧汎用ハッシュ (DictionarySlim) のボトルネック**:
  - LINQ の GroupBy 規約である「出現順（Insertion Order）」の維持のため、ハッシュテーブルと出現順配列の二重管理が発生し、System.Linq に敗北していた（0.46x〜0.49x）。
- **ZLinq (LookupBuilder) の優位性**:
  - `ArrayPool<T>.Shared.Rent(16)` によるバケット管理（ヒープ割当 0 B）。
  - `Grouping` 自体がハッシュ衝突チェーンと出現順循環リストを保持する侵入型（Intrusive）構造により、追加配列を排除。
  - 2の累乗サイズバケットと高速ビット積 `hashCode & (len - 1)` による探索。
- **FLinq の汎用パス（キー範囲不明時）への拡張方針**:
  - FLinq では後続パイプラインが集約（Sum / Count 等）であることがコンパイル時に判明しているため、全要素を保持する配列を一切作らず集約値のみを更新できる。
  - `ArrayPool.Shared.Rent` を利用した単一バッファ上の開放番地法（Open Addressing）プールテーブルを展開することで、キー範囲不明時でもヒープ割当 0 B を達成し、ZLinq を超える集約速度を実現可能。

30. **Seamless Manager クロスプラットフォーム UI 候補比較試作（6要素プロトタイプ実機検証）規約**:
   - 共通管理 UI 選定に向けて、Avalonia、Uno Platform、Blazor / Razor コンポーネントの各候補において、6 つの主要操作要素（DB ツリー、タブ、キーボード操作、C# エディタ、結果グリッド、静的計画ビュー）を含む最小統合プロトタイプ画面を構築・実機動作させる。

31. **監査 WAL 保持上限到達時における Fail-Closed（監査整合性優先）運用規約**:
   - 業務テーブル更新と同一 WAL でアトミックに確定される監査ログ（`AuditEvent`）の管理 DB 転記が障害や長期停止で滞留し、未転記 WAL の保持量がストレージ予算上限に達した場合、Fail-Closed 方式を採用する。
   - 新規の更新トランザクションを `AuditRetentionBudgetExceededException` で安全に拒否・一時停止し、監査ログの改ざん・欠落なき完全性（コンプライアンス要件）を 100% 保証する。管理者のディスク拡張または転記滞留解消をもって自動再開する。
32. **WAL 要求前フレーム超過時における個別取引中止（Aborted）と DB 健全性維持境界**:
   - 変更行のエンコード段階で WAL フレーム上限（既定 4 MiB）を超過した場合、WAL への append 要求前かつ永続適用開始前であれば、共通 Coordinator や WAL Writer を故障停止（Faulted）させず、当該トランザクションのみを `Aborted` として安全にロールバック・スコープ解放する。
   - DB インスタンスは健全なオンライン稼働状態を維持し、同一接続で後続の通常サイズトランザクションを継続可能とする。WAL への append 呼出後または永続適用開始後の失敗のみを厳格に DB 停止・リカバリ対象とする。
33. **組織主体の緊急無効化（即時リース取消）と認可ポリシー破損時の安全拒絶（Fail-Secure）規約**:
   - サーバー管理者が特定主体（ユーザー/組織）を緊急無効化した際、確定と同時に対象主体の既存アクティブリース（実行中セッション・未コミット取引）に対して即時取消（Cancel）を発行し、以降の操作を完全に遮断する（再有効化しても過去に取り消されたリースは復活しない）。
   - システム DB に保存された認可ポリシー文書にハッシュ不一致や破損が検出された場合、旧権限への暗黙フォールバックや推測許可を行わず、安全に拒絶（Fail-Secure）して管理者へのアラートを発報する。
34. **高負荷時におけるトランザクション確定・取消（COMMIT / ROLLBACK）の優先バイパス枠保証規約**:
   - Kestrel 通信基盤においてサーバーの同時要求処理枠（Concurrency Quota）が満杯に達し、新規クエリや新規トランザクションが待機または 503 制限されている状態であっても、既存の開始済みトランザクションに対する `COMMIT` および `ROLLBACK` 要求は一般枠の制限を受けずに即座に実行できる専用優先枠（バイパス枠）を保証する。
   - ロックを保持するトランザクションが確実に完了・ロールバックして資源を解放できるようにし、同時実行枠枯渇に伴うシステム全体の連鎖デッドロックを原理的に排除する。
35. **公開契約指紋（SchemaFingerprint）一致によるバイナリ後方互換性保証規約**:
   - サーバー側の内部実装、非公開カラム、配置最適化、インデックス等の内部改修が行われた場合でも、クライアントに公開されているインターフェース・引数型・戻り値型の「公開契約指紋（SchemaFingerprint）」が一致している限り、配置済みのクライアント成果物は再ビルド・再配布なしにそのまま 100% 継続動作することを保証する。
   - 破壊的スキーマ変更により契約指紋が不一致となった場合のみ、サーバー側で安全に契約不一致エラー（`RecoverableError`）を返却して不整合な実行を確実に拒絶する。
36. **入れ子トランザクションにおける確定投票（Voted）と連鎖ロールバック規約**:
   - 入れ子（階層化）された子トランザクションスコープの `Commit` は即座の WAL 確定を行わず、親への確定投票（`Voted`）として扱い、最上位の親トランザクションのコミット時に全体を一括アトミックに確定する。
   - 未コミットの子が存在する状態での親のコミットは拒否し、子スコープが 1 つでも `Rollback`（または未コミットで破棄）された場合は、親を含むトランザクションツリー全体を `Aborted` として連鎖ロールバックし、不整合な部分確定を原理的に排除する。
37. **遅延更新 MVCC における履歴圧迫（History Pressure）時の古い読取取引中止規約**:
   - 遅延更新＋MVCC（Serializable）において、過去バージョン履歴の保持量がストレージ／メモリ予算上限に達した場合（History Pressure）、履歴回収（GC）を妨げている最も古い読み取り専用取引を `HistoryPressureException` で明示的に安全中止・ロールバックする。
   - 履歴蓄積による OOM や更新トランザクションの全面停止・無期限ブロックを防ぎ、データベースシステム全体の継続稼働性と書き込みスループットを最優先する。
38. **WAL 耐久化完了後の本体反映失敗時における Committed 保持・Crash-Stop 規約**:
   - WAL への物理同期（`Sync`）が完了した時点でトランザクションは不可逆的に確定（Durability 成立）するため、その後のメモリ／ストレージ本体への反映処理（Apply）や後処理中に例外・障害が発生した場合でも、`Aborted` へ巻き戻すことはせず状態を `Committed` として厳格に保持する。
   - 不整合な状態での動作継続を排してプロセスを安全に障害停止（Crash-Stop）させ、再起動時にチェックポイント以降の未反映 WAL ログを末尾まで自動リプレイして確定状態へと完全復旧させる。これによりコミット済みデータの喪失を 100% 防止する。
39. **階層的リソース予算（ResourceBudget）における親子アトミック予約・デッドロック防止規約**:
   - データベースストア、クエリ実行スコープ、一時作業領域のメモリ・ディスク消費を管理する `ResourceBudget` は親子階層を持ち、子予算の増分予約は親予算と子予算の両方で成功した場合にのみ確定する。
   - いずれかが上限超過（Quota Exceeded）した場合は両者とも予約前の状態を不変に維持（完全ロールバック）し、階層昇順の固定ロック順序を厳守してリソース競合デッドロックを原理的に排除する。予約会計とプロセス実メモリ（Working Set）は混同せず別指標として管理する。
40. **FLinq 最適化コード生成における C# 標準セマンティクス厳格維持規約**:
   - `Where` や `Select`、集約・結合内の複合式において、短絡評価（`&&` / `||`）、例外発生順序、および `checked` 算術演算の挙動を、元の C# 式と 100% 同一に保持する。
   - ループ融合を行う場合でも、元の式で評価されないパスで例外が発生するような先行投機評価や、副作用を伴う計算の勝手な削除・順序変更を厳格に禁止し、LINQ 標準との完全な意味の同一性（Semantic Equivalence）を保証する。
41. **正常読み取り監査における非同期有界バッファ集計・Non-Blocking 継続規約**:
   - 正常読み取りクエリの監査集計は、クエリ実行完了後に有界なインメモリ集計バッファ（1分ウィンドウ・5秒保存周期）へ非同期に加算し、クエリのレスポンス返却を一切ブロック（待機）させない。
   - バッファ上限到達時や監査保存ストアの障害時であっても読み取りクエリをエラー停止させず、「既知の欠落（Known Drops）」として管理メトリクスへ明示記録した上で読み取りを継続する。更新監査（WAL 直結・完全性優先・Fail-Closed）と正常読み取り監査（非同期集計・スループット優先・Non-Blocking）の責務を厳格に分離する。
42. **スキーマ構造変更（DDL）と行データ変更（DML）の厳格分離・未確定データ保護規約**:
   - スキーマ構造の保存・適用（コード生成・検証・データ移行・新世代公開）と、行データの追加・更新・削除は別個の明示操作・取引として完全に分離する（構造変更に未確定の行編集を混入させず、行確定でスキーマを暗黙移行しない）。
   - 構造変更が画面内の未確定な行データ編集に影響を与える場合（カラム削除や互換性のない型変更等）、構造の保存を自動停止して警告を発し、利用者が先に行データを確定または破棄するまで構造変更を中断して未確定編集のサイレントな破棄やデータ破壊を防止する。
43. **外部 C# 編集と Manager 編集の変更追跡・未適用表示および安全な個別取消規約**:
   - 外部エディタ（VS Code / Visual Studio）と Manager 間で作業ソース（.cs）を共有し、三者比較（3-way）により変更を追跡する。タブの `*` 印は「稼働版 DB に未適用」を意味し、ファイル保存・下書き保存状態と区別して明示表示する。
   - 取り消し操作は「タブを閉じる（表示のみ閉じる）」、「Manager 編集のみの取り消し（外部変更は保持）」、「対象オブジェクトを稼働版へ戻す（明示的合意の上で両方リセット）」の 3 つの粒度を厳格に区別し、ユーザーが外部エディタで書いたソースコードが勝手に巻き込まれて消失する事故を原理的に防止する。
44. **外部キー（参照整合性）における最外取引確定時・全表移行完了時の最終状態一括検証規約**:
   - 1 行ごとの即時外部キー照合（逐次検査）を行わず、複合キー・自己参照・循環参照（テーブル相互参照）を含め、通常トランザクションは最外トランザクションのコミット直前の最終状態で、スキーマ一括移行時は全表の変換・投入完了後の最終状態で一括検証する。
   - レコード投入の物理順序による不当な外部キー制約違反を排除し、制約違反が発生した場合でも当該トランザクションのみを安全にロールバックして DB 全体を故障状態にしない。外部キー検証の読み取りは競合検出へ参加し、WAL 確定前に確実に遮断する。
45. **Collectible ALC による動的 DB・クエリ DLL の完全アンロード規約**:
   - 生成される DB 定義アセンブリや Native クエリ DLL は、世代ごとに独立した `AssemblyLoadContext(isCollectible: true)` にロードする。
   - スキーマ変更やクエリ再ビルド後、旧世代を参照しているすべてのアクティブな実行スコープが終了した時点で、static 参照・キャッシュ参照を完全に遮断して ALC を破棄し、サーバープロセスを再起動することなく GC による 100% のアセンブリ解放・メモリ回収を保証する。
46. **再起動・復旧時におけるクエリ受付開始前の廃止世代チェックポイント先行完了規約**:
   - サーバー再起動やクラッシュ復旧時に既に未回収の廃止世代が存在する場合、`GatewayDatabaseHost.OpenAsync` でクエリ要求の受付を開始する前に、廃止世代のチェックポイント・整合性確定を同期的に先行完了させる。
   - サービス再開直後に届いた初回クエリや読み取りトランザクションが重いチェックポイント保守に巻き込まれて受付期限（5 秒タイムアウト）に達するスパイクを防止し、クリーンな状態でリクエスト処理を開始する。
47. **Gateway HTTP API におけるトークン完全束縛と SQL 認可迂回防止規約**:
   - Bearer 資格情報には HTTPS を必須とし、OIDC 検証を通過した API アクセストークンの認証元・主体 ID に HTTP セッションおよび明示取引（`BEGIN TRANSACTION`）を不可逆的に束縛する（取引途中の資格情報すり替えや他主体のセッション利用を拒絶）。
   - SQL 実行時においては、`USE` コマンド、DB 修飾名（`db.schema.table`）、ビューや関数のインライン展開による認可迂回を防止するため、バインド時に解決されたすべての物理テーブル・ビュー等のリソース ID に対して共通認可（`AuthorizationManager`）による権限検査を必須とする。
48. **FLinq DemandAnalysis におけるパイプライン除去の厳格安全判定規約**:
   - `OrderBy`、`Reverse`、`Distinct` などのパイプライン中間処理を消去・バイパスできるのは、①「結果が要素順序や重複に依存しない終端であること」、②「下流が全要素を消費するか、または早期終了するまでに評価される中間述語（`Where` 等）が存在しないこと」の 2 条件を両方満たす場合に限定する。
   - 間に `Where` 述語が介在する場合に安易に `OrderBy` を消去して System.Linq と異なる要素が先に評価され例外が発生するリスク（意味的不一致）を原理的に排除する。
49. **静的実行計画の ExecutionPlanAttribute メタデータ埋め込み・PE 直接読取規約**:
   - クエリのコード生成・コンパイル時、採用された物理走査経路、融合パイプライン、メモリ構造の計画を不変な構造化データとして `[ExecutionPlan(...)]` 属性へ版付き JSON で直接アセンブリ内に埋め込む。
   - Seamless Manager は、生成コードのコメント文字列を逆解析（正規表現パース）する手法を完全に排除し、コンパイル成果物（DLL）の PE メタデータから属性を直接読み取って DOT グラフや計画ビューへ正確に描画する。
50. **SQL DDL・オブジェクト管理における Object ID の単調増加・非再利用厳格規約**:
   - テーブルやビューが `DROP` された後、同一スキーマ内に同名で再作成された場合であっても、過去の Object ID を絶対に再利用（リサイクル）せず、常に新規の単調増加 ID（または一意な UUID）を採番する。
   - これにより、WAL リプレイや過去のインメモリキャッシュ、残留ストレージブロックにおける旧世代の行データや古いアクセス権限が、新しく作られた同名テーブルへ誤って復活・混入するデータ破壊やセキュリティ侵害を原理的に排除する。
51. **FLinq における既定副作用なし・`expr.Anchor` による局所最適化抑止規約**:
   - 既定ではすべてのラムダ式を純粋（副作用なし）として扱い、連続 `DistinctBy` / `Distinct` の畳み込み削減やパイプライン融合などのアグレッシブな最適化を最大限適用する。
   - 外部副作用を持ち評価順序や回数を厳格に保ちたい式に対して `expr.Anchor`（拡張プロパティ）が指定された場合に限り、該当式の削除・複製・並べ替えをそのステージ単位で局所的に抑止する（インライン展開やアロケーション削減は継続し、生成コード上は identity として透過除去される）。
52. **ストレージテストにおける媒体別隔離・GUID 短短パス・メモリ安全ガードレール規約**:
   - ストレージテストのデータ配置は媒体別に厳格分離（SSD: `D:\SeamlessTestData`、HDD: `F:\SeamlessTestData`）し、C/G ドライブへの出力を禁止する（不在時のフォールバックも禁止）。
   - Tsavorite チェックポイント階層による Windows の `MAX_PATH`（260 文字）超過エラーを防ぐため、データディレクトリ名は 32 文字の GUID のみとし、テスト名や日時はメタデータ JSON 側で追跡・照合する。
   - 物理メモリ 85% 以上では重いテストの開始を抑止し、実行中に 88% に達した場合は子プロセスを安全終了させてホスト全体の OOM を防止する。
53. **Benchmark UI グリッドにおける隣接ペア比較・シェアゲージ表示規約**:
   - 3 列タブ（左: FLinq、中央: ZLinq/ValueLinq、右: System.Linq）において、最右列との一律比較ではなく「左 vs 中央」「中央 vs 右」という隣接ペア比率をプロジェクトヘッダー内列（`日時 → 時間 → 時間シェア → メモリ → メモリシェア`）として表示する（基準の最右列はシェア列不保持）。
   - シェア値は合計比率（例: `"0.35:0.65"`）と色付き視覚バーで表示し、相手側より 3% 超遅延したセルには `" ⚠"` 警告を付与する（旧「x倍」テキスト表示は廃止）。
54. **Tsavorite ストレージ走査と FLinq の UnsafeAccessor・関数ポインタ直結ネイティブスキャン規約**:
   - `Tsavorite` 具象型コレクションを起点とする FLinq クエリでは、コード生成器が `[UnsafeAccessor]` を介してストレージ内部の `Scan<TState>` プリミティブを `delegate* managed<ref TState, TKey, bool>` 関数ポインタで直接駆動する。
   - `IEnumerable` / `IEnumerator` の生成、インターフェース仮想呼び出し、ボクシングを完全に排除し、ストレージのネイティブページ走査と FLinq 述語・集約処理を完全ゼロアロケーション・完全インラインで直結する。
55. **BENCH_AS_TEST によるベンチマークコードの単体テスト兼用実行と実測環境の物理分離規約**:
   - 共通のベンチマークシナリオコード（LINQ / Tsavorite 走査等の実測コード）は `Shared/Common/Benchmarks/` 配下の共有プロジェクト（`.projitems` / `.shproj`）として一元保持し、テストとベンチマークでの二重管理を排除する。
   - 回帰テスト（`tests/`）側では `DefineConstants` に `BENCH_AS_TEST` を付与し、短時間の単一反復実行で機能と結果のアサーション検証（単体テスト）として実行する。
   - 反復測定を伴う本番 BenchmarkDotNet 実測プロジェクトは `sandbox/` 配下に配置し、CI 回帰テストの自動実行対象から物理的に分離する。
56. **DataGrip 必須対象・独自 JDBC / バイナリ RPC 一本化と TDS/SSMS 偽装互換層の段階的廃止**:
   - 外部汎用 DB 管理ツール連携において、Microsoft TDS プロトコルや SSMS / SMO / システムカタログの偽装互換性は必須とせず、JetBrains DataGrip を必須対象とする。
   - DataGrip 向けには「Seamless JDBC ドライバー」および「バージョン付き独自操作 API（RPC）」を提供し、カタログ参照・構造化 CRUD・DDL スキーマ変更等は SQL 文字列を介さず型付きバイナリ RPC でダイレクトに通信する（SQL コンソール等のクエリのみ SQL フロントエンド／共通 IR で処理する）。
   - DataGrip 独自接続・RPC 経路の受入完了後、既存の SSMS 固有偽装コードは段階的に削除・完全廃止する。
57. **一括スキーママイグレーションにおける非公開 Snapshot 構築と業務 WAL 負荷隔離規約**:
   - 大規模なテーブル構成変更・列の型変換・全表データ移行において、移行先データは非公開の一時 Snapshot 領域に全件変換・投入し、通常の業務 WAL（先行書き込みログ）へ大量の移行レコードを流さない。
   - 全表の変換投入完了後に外部キー参照整合性や各種制約を全体検査し、永続化が 100% 成功した候補（Candidate）のみをアトミックに現行世代ポインタとして昇格・公開する。
   - 変換や制約検証に失敗した候補は即座に破棄し、稼働中の旧世代を無傷・無停止のまま維持する。
58. **.NET ネイティブ優先型定義と SQL 往復変換境界の責務分離規約**:
   - Seamless の手書き C# DB 定義・クエリ・ルーチンは、.NET 標準型（`decimal`, `DateTime`, `DateOnly`, `float` 等）とその実行セマンティクスを唯一の正本基準とし、SQL の物理精度に合わせた専用ラッパー型（`Decimal18_4` 等）の強制を禁止する。
   - SQL Server や MySQL 等の DBMS 向け再構築・SQL 出力に必要な型マッピング・精度指定・照合順序は「SQL 出力プロファイル／変換器」の責務として解決し、DBMS 側で表現できない不整合（精度落ちや丸め等）は暗黙に隠蔽せず Roslyn 診断（Diagnostics）として明示報告する。
59. **管理 GUI インライン下書き確定と二段階適用・未適用表示の規約**:
   - Seamless Manager や管理 GUI 上での F2 キーや右クリックによる名前変更・構造定義編集はノード上でのインライン編集とし、モーダルダイアログへ退避させない。
   - Enter キーは「ローカル下書き（Draft）への仮確定」に留め、サーバー上の稼働 DB には即時反映せず、UI ツリー上には「旧名 → 新名・未適用」として明示的に区別表示する。
   - 「変更を適用」の明示操作時に初めてサーバーへ一括送信し、競合・権限・名前衝突を再検証してアトミックに適用する（名前変更のみの場合は行データの物理移行を発生させない）。
60. **ロック取得局所待機と AsyncLocal 注入・実行計画分離規約**:
   - 接続単位のロック待機タイムアウト（`SET LOCK_TIMEOUT` や接続プロパティ）は「DB / テーブルの排他ロック・読取ロック取得待機」のみに局所適用し、ロック取得完了後はタイマーを破棄する（クエリ実行全体の制限時間や取引寿命の打ち切りには流用しない）。
   - ロック待機期限超過時はエラー 1222（Lock request time out）を返し、クライアントからの明示的キャンセル（CancellationToken）を最優先する。
   - 接続ごとのタイムアウト値は `AsyncLocal` 実行コンテキストで安全に動的注入し、コンパイル・キャッシュされた実行計画（Plan）に特定接続の待機時間を焼き込まず、他接続との安全な計画再利用を保証する。
61. **ワーカー停止・Dispose の単一 Task 共有と完全 Join 待機規約**:
   - バックグラウンド計算ワーカーや子プロセスのライフタイム管理において、`Cancel`、`Shutdown`、`Dispose` の重複呼び出しは初回生成の単一 Task（`TaskCompletionSource`）を共有し、同一の成功完了または同一の例外を全呼び出し側へ伝播させる（完全なべき等性）。
   - 単なる OS プロセス終了のみで即座にハンドルを破棄せず、stdout EOF / stderr ドレインおよび永続化タスクの完全完了（Join）を待機してからリソースを解放する。
   - 停止確認が取れないプロセスは正常完了（合格 Receipt）とみなさず、所有権を保持したまま障害追跡対象として隔離する。
62. **マルチエージェント協調における統括一元所有権と多段メモリ安全ガードレール規約**:
   - 共有プロジェクト（`Shared/`）、ソリューション構造（`Seamless.slnx`）、DB 永続スキーマ、全体仕様書の最終更新権限は統括エージェント（親セッション）が一元所有し、子サブエージェントによる共有ファイルの直接競合編集を禁止する。
   - 大規模テストや実測ベンチマークなどの重い計算処理は、ホスト全体の物理メモリ使用率が 80% 未満であることを確認できた場合のみ起動を許可し、実行中に 88% を超えた場合は直ちに所有処理を安全中断（Abort）して OS や共存プロセスの安定性を死守する。
   - 実行結果はソース / バイナリの SHA256 ハッシュおよび TRX / 結果 JSON の完全な証跡をもって判定する。
63. **正常読取監査の 1 分集計・5 秒フラッシュと旧形式非破壊運用規約**:
   - 正常読み取りクエリの監査集約は「利用者・DB・問い合わせ・コード版・権限版」のタプルごとにメモリ上で 1 分単位のウィンドウにまとめ、5 秒間隔の非同期バッチでストレージへフラッシュする。
   - 管理者が明示的に監査を停止できる `--no-read-audit` を公式に提供し、期間・間隔オプションとの矛盾した指定は起動時に即座に拒否する。
   - 既存の旧形式（形式3/4）のデータ領域は、サーバー起動時に暗黙マイグレーション・自動上書きを行わず、明示的な移行指示があるまで旧データを保護する。
64. **期待例外（ExpectExceptions）の同型一致合否判定および結果記録規約**:
   - FLinq、通常 LINQ、ストレージ実行経路の動作検証において、オーバーフローやゼロ除算等の意図的な境界値テスト（`ExpectExceptions`）では、全実行経路でスローされた例外の型が完全に一致する場合のみ `Succeeded` かつ `isMatch`（合格）とする。
   - スローされた例外型が異なる場合（例: 一方が `OverflowException` で他方が `ArgumentOutOfRangeException`）や、一方のみ例外となった場合は `SemanticMismatch`（意味論不一致）として検出・不合格とする。
   - 例外一致ケースでは架空の所要時間を捏造せず、「時間測定なし」として正確に診断ログ・画面に記録する。
65. **検証ワーカーの 1,000 件上限バッチ分割と決定論的シード・オフセット継続規約**:
   - ワーカー通信プロトコルの 1 要求あたり最大処理件数を 1,000 件の固定定数とし、これを超える大規模探索は件数を勝手に削減せず、1,000 件以内の連続バッチへ自動分割して送出する。
   - 後続バッチは直前の `QueryIndexOffset` と疑似乱数 `Seed` を厳格に引き継ぎ、直前の終端から決定論的に検証を継続する。
   - ワーカーが完了通知なしに突然終了した場合は標準エラー出力（stderr）を収集して診断へ記録し、決して正常終了とみなさない。
66. **要素型 13 種拡張とフォールバックゼロ・展開未完了厳格検査規約**:
   - ランダムチェーン動的検証基盤を `Benchmark.Dynamic` に一本化し、検証対象の要素型を `int` だけでなく 13 種類（`long`, `float`, `double`, `decimal`, `string`, `Int256(struct/class)`, `Quadruple(struct/class)`, `int?`, record `Order`, `CollidingKey` 等）へ拡張する。
   - 合否判定において、結果・例外型・評価回数の一致に加え、「`EnumerableFallback == 0`（暗黙フォールバックの発生ゼロ）」、「生成コード内の未展開目印文字列なし」、「コンパイラ警告（FLINQ002 等）ゼロ」を必須合格条件とする。
   - 性能および検証合否判定の正本は `Verification.Core.VerificationComparison` に一元化し、各ツール独自の局所的な合否判定を排除する。
67. **MVCC 履歴保存における現行 Tsavorite 基盤維持と専用履歴ストアのプロトタイプ保持規約**:
   - 通常業務トランザクションで支配的な「最新版（1版）常駐条件」での追加・読取性能、および共通 WAL との整合性・チェックポイント復旧実績を最優先し、製品の MVCC 行履歴保存バックエンドとしては現行の Tsavorite を標準採用として維持する。
   - 小さいキャッシュかつ多数の世代を保持する条件で圧縮率に優れる専用履歴ストア（HistoryStore prototype）は、将来の研究・比較検証用プロトタイプとしてコードベースに保全し、現段階での製品テーブルへの一律置換は行わない。
68. **認可ポリシーの system DB アトミック確定・WAL 同期後公開と Fail-Secure 規約**:
   - 認可ポリシー、不変の過去版、変更索引、および PermissionChange 監査レコードは、`system` DB へ単一トランザクションで一括確定し、WAL の永続化完了を待って初めてメモリ上のポリシー版を公開する（準備中・未確定版の公開禁止）。
   - 確定後・メモリ公開前の失敗や、保存文書の破損・未知状態を検出した場合は旧権限への暗黙フォールバックを固く禁止し、保存ストアからの再同期が完了するまで新規操作を遮断する（Fail-Secure）。
   - 通常のポリシー変更は既に開始しているセッション（実行中リース）を強制中断せず、次回の操作から適用する。
69. **大規模ネイティブ接続における待機・実行資源分離と未完了状態返却拒否型プール規約**:
   - 待機中の物理接続に対して常駐スレッドや個別バッファを固定割り当てせず、非同期 I/O（Kestrel / Pipelines）により少数の実行資源を多数の接続で多重化する。
   - クライアント接続プールは「接続先・TLS 信頼設定・認証主体」ごとに厳格に分離し、未確定トランザクションや未読結果ストリームが残存しているクライアントのプール返却を固く拒否（例外送出）して物理接続のクリーンさを保証する。
   - 明示トランザクションの最大継続時間を既定 30 分とし、5 分ごとの所属・権限再確認に失敗した場合は新規操作を即座に停止する。
70. **階層的認可モデルにおける明示的拒否（DENY）最優先と公開定義の最小委任実行規約**:
   - 権限は「DB → スキーマ → オブジェクト（表・ビュー・関数・公開クエリ）」の順で階層継承されるが、同一操作・対象に対する明示的な拒否（DENY）はいかなる許可（ALLOW）や継承よりも常に最優先される。
   - 元テーブルへの直接アクセス権限を持たない利用者に対しても、管理者が明示的に許可した公開定義（ビュー・関数・公開クエリ）経由で必要な集計結果を安全に提供できる。委任実行時も定義が必要とする最小限のアクセス範囲に限定して評価し、定義自体の実行拒否や接続拒否の迂回を固く禁止する。
   - DB 管理者は担当 DB 内の権限割り当てのみを委任管理でき、サーバー全体や他 DB の管理権限を持たない。
71. **クエリ外エスケープ時の Group 具体化（Materializer 共有・読取専用 ICollection・事前要素数確保）規約**:
   - `GroupBy` の結果をクエリ・トランザクション外へ返却（エスケープ）する際、クエリローカルな `QueryGrouping.Materializer` を共有し、private コーデック解決およびリソース予算予約をクエリ単位で集約処理する。
   - 生成される各 `OwnedGrouping` は自身の Key と所有配列のみを保持し、Materializer への逆参照を持たない（利用者が 1 つのグループを保持したことによる全体バッファのリークを防止）。
   - 内部 Lookup の要素数から一発で正確なサイズの配列を確保して拡張リサイズを排除し、読取専用 `ICollection<T>` を実装して後続の `Count()` や `ToArray()` を O(1) に最適化する（変異 API は例外送出）。
72. **外部 IDE 下書き同期における 3-way 比較・状態 3 軸表示と変更由来別選択的取り消し規約**:
   - 外部プロジェクト管理の `.cs` を唯一の作業正本とし、ファイル保存検知時は「直前同期内容・Manager下書き・外部ファイル」の三者比較（3-way diff）を行い、Manager 自身の書き込み再検知による循環同期ループを原理的に防止する。
   - タブの `*` は「稼働 DB 未適用」を意味し、UI 上で「ファイル保存済み／下書き保存済み／稼働版未適用」の 3 軸状態を正確に可視化する。
   - 取り消し操作は、外部 VS Code の編集を保護して Manager の操作分だけを戻す「Manager 由来編集の取消」と、明示的な確認を経て外部変更も含めて戻す「対象テーブルを稼働版へ復帰」を厳格に分離する（一律の全破棄ボタンを廃止）。
73. **読み取り監査ログのメソッド情報検索・権限連動型情報隠蔽・1Mi文字上限規約**:
   - 検索監査ログにおいて、C# メソッド名・完全修飾名・シグネチャは通常の管理閲覧権限で照会・検索可能とするが、クエリ本文（テンプレート）の閲覧およびテンプレート文字列への検索一致は「対象 DB の編集権限」を必須とし、権限のない利用者への検索ヒット漏洩を固く遮断する。
   - 監査照会時はアセンブリのロード・実行やソース再解析を一切行わず、ビルド時に保存された静的メタデータ（JSON）との照合のみで行う。
   - 検索結果は 1 ページあたり約 1Mi 文字・最大 100 行（4,096 レコード）に制限し、途中ページは `HasMore` とカーソルで表現する（メタデータキャッシュは 1 要求あたり最大 64 成果物に制限）。
74. **テストプロジェクト統廃合における完全ケース照合・TFM 分離・DynamicFallbackCapture 必須化規約**:
