# Managerのコンテキスト依存操作基盤

## 背景

利用者の2026年11月7日の要求により、対象付近の操作ハンドル、検索できるコンテキストメニュー、直接操作、段階的開示を共通の操作体系として実装する。Windows・Linuxデスクトップ・Webを今回の対象とする。スマホの配布・受入は将来の可能性として残す。

## 現状の観察

| 画面・機能 | 実装の入口 | 引き継ぐ操作 |
|---|---|---|
| 接続・サーバー・Gateway | `管理ウィンドウ.cs`、`管理ウィンドウ.起動.cs`、Gateway各Window | IPC、TCP/TLS、接続設定、起動、権限・公開版の管理 |
| 稼働DB・スキーマ・オブジェクト | `管理ウィンドウ.カタログ.cs`、`.ブラウザー.cs`、`.対象操作.cs` | 開く、作成、設計、削除予定、下書きの復元 |
| C#・表・文書タブ | `管理ウィンドウ.オブジェクトタブ.cs`、`テーブル設計.cs` | 編集、比較、行表示、保存、閉じた下書きの再開 |
| 下書きと適用 | `管理ウィンドウ.設計.cs`、`.操作.cs` | 保管、検証、プレビュー、明示適用、操作ID照会 |
| 外部ソースとの同期 | `.ソース連携.cs`、`.ソース競合.cs`、`.ソース取消.cs`、SourceWorkspace | 外部変更保持、競合、Manager編集の取消、下書きの復元 |
| 結果・計画・監査 | 主ウィンドウと監査各partial | 結果グリッド、静的計画、履歴、監査検索・状態 |

WPFには対象別の右クリックメニューと権限判定がある。対象操作と全体操作の表示が別々に構築され、検索付きの共通コマンド登録、ハンドルからの文書移動、共通のポップオーバー状態は見つからなかった。表タブには複数の常時表示ボタンがあり、閉じるボタンも常時表示される。

共通Razor試作では同じ画面から実DB一覧・空DB作成が動く。共通APIは `IManagementOperations` で、既存の管理・下書き・検証・適用処理へ接続する。

## 過去設計から引き継ぐ仕様

空DB作成のインライン名入力、Enter確定、Esc取消、結果不明時の操作ID照会を維持する。既存DBへの変更は下書きと検証を経て明示適用する。SourceWorkspaceの競合・取消、ソースのUndo、閉じた文書の作業保持を引き継ぐ。各ホストから同じ管理処理と認証済み権限を使う。

## 目的

対象、選択、フォーカス、メニュー、ドラッグの状態を共通の操作体系にまとめる。必要な機能を対象付近と検索から発見できるようにし、操作コマンドの可否判定と実行処理を共用する。

## 提案設計

### 共通コマンド

コマンドの安定ID、表示名、検索語、階層、ショートカット、破壊的操作の表示、表示条件、実行条件、実行処理を宣言する。検索とメニューは同じ登録を参照し、実行直前にも対象と実行条件を検査する。サーバー側の認可を実行境界として使う。

### 共通UI部品

共有Razor画面の候補実装に、対象操作ホスト、検索付き操作メニュー、ポップオーバー配置、ツールチップ、文書タブとドラッグハンドルをまとめる。画面と操作状態のコードをWindows・LinuxのデスクトップホストとWebで使う。UI技術の正式選定は、引き続き3環境の実行結果に基づく。

操作の余白は先に確保し、ホバー・選択・キーボードフォーカス・メニュー表示中にハンドルを示す。メニューへのポインター移動中も操作対象を保持する。メニューは一度に一つを開き、対象と戻り先フォーカスを保持する。外側クリックでは移動先のフォーカスを保ち、Escapeでは起点へ戻す。

メニューには検索、上下移動、Enter、Escape、サブメニューの往復を用意する。スクロール・画面端・サイズ変更に合わせて配置し、イベント購読は共通の画面・表示中メニューに集約する。

### 直接操作

代表画面では、文書タブの表示順をハンドルからドラッグで編集する。挿入位置を表示し、Escape・ポインター取消では元の順序を保持する。キーボードからの移動コマンドも同じ並べ替え処理へ接続する。DB構造の編集には既存の下書き・適用APIを使う。

### 入力と環境の境界

ホバー、フォーカス、選択、ポインターを入力として扱う。将来のタッチ操作を同じ状態とコマンドへ接続できる構造にする。ファイル選択、外部IDE、ローカルIPCなどの環境操作はホストの入口へ接続する。

## 影響範囲

共通の操作モデルと共有UI部品、Razor試作ホスト、ソリューション登録、代表画面の操作試験。既存WPFとサーバー処理を参照し、機能ごとに共有画面へ移行する。

## サーバー側プロジェクトと開発時の基本形

利用者の追加選択により、Managerで開く `.slnx`・フォルダー・`.csproj` は、Seamlessサーバー側のファイルとする。ブラウザーを操作しているPCのローカルファイルとは区別する。最初の開発・テストでは開発者PCでSeamlessサーバーも動かし、ManagerとVS／VS Codeが同じソースを編集する。DLLは開発者PCの通常のビルドで生成する。

現行生成器の目印は `DatabaseGenerator` という型であり、その型が属する名前空間を生成ルートとして扱っている。プロジェクトを開いた場合はプロジェクトと検出したルート名前空間を対応付けて表示し、そのソースを編集・同期する。生成器には共有契約・サーバー実装・クライアント側それぞれの目印があるため、目印の発見だけで稼働DBとして公開できると判定しない。Container・公開契約・生成成果物は別途照合する。

ファイルへの保存、個人下書きの保管、開発者によるビルド、稼働DBへの明示適用は、それぞれ別の状態として表示する。IDEでビルドしただけで稼働DBを切り替えない。非競合変更の三者比較、競合時の内容保全、Manager編集だけの取消、保存直前の照合は既存SourceWorkspaceの規則を引き継ぐ。

従来の `SourceWorkspace.Create/Open` は、自分で作った `Schema.csproj` と `.seamless` 同期記録を前提とする。既存プロジェクトには `ImportProject` を追加し、MSBuildのCompile対象と実ファイルの対応を保存して、同じ三者比較・書き込みジャーナルへ接続した。既存プロジェクトのCompile設定は書き換えない。共通UIからの開く・編集・同期を所有者専用APIへ接続している。現行ManagerのBuild等にはサーバーでのコンパイル経路が残っており、開発者ビルドの成果物を正式版へ取り込む経路とは区別する。

新規DBは既存のインライン作成を維持する。専用C#プロジェクトの保存タイミングは「DB作成直後」に確定した（空DB作成時に保存先フォルダーを指定させ、即座に標準パッケージ参照を含む専用C#プロジェクトを生成してVS Code外部連携を有効化する）。既存の一つのDB定義DLLに一つのContainerという契約を守り、既存の別DBのプロジェクトへ新DBの宣言を混在させない。新規プロジェクトのSeamless依存は、既に合意したパッケージ参照を基本とする。

### 既存プロジェクトを開く入口の実装方針

場所を開く操作は、ソリューションまたはフォルダー内のプロジェクト一覧を返す。プロジェクトを選んだ時にSDKでCompile対象と条件定義を評価し、`DatabaseGenerator`の所属名前空間を取得する。大きいソリューションの全プロジェクトを開く時点で一斉ビルド・評価しない。複数ターゲットがある場合はターゲットを選んで評価する。

既存ソースの同期はSourceWorkspaceの三者比較・競合記録・書き込みジャーナルを再利用する。取り込み時には実ファイルと編集用パスの対応を保存し、既存csprojのCompile設定を変更しない。同期対象は評価済みCompileファイルに限定する。ファイル集合や条件が外部で変わった場合は再評価を要求し、表示中の編集を保持する。プロジェクトを開く・同期する操作ではDBの作成・ビルド・公開を実行しない。

共通のソース操作APIを、同一所有者をOSで確認したIPCとインプロセスへ接続する。ブラウザーは既存の所有者セッション検査を通る。通常のTCP接続や旧ローカル認証の利用者には、この所有者専用ファイル操作を許可しない。SDK子プロセスは時間・出力量・並行数を制限し、取消時には所有する子プロセスの終了を確認する。UIには場所、プロジェクト、ルート名前空間、ファイル保存状態を表示する。

### 現在の接続と受入範囲

`SourceProjectService`、`IManagementSourceOperations` と共有コンポーネント `プロジェクト作業領域` を追加した。場所の列挙とSDK評価はDB操作から独立した作業として処理する。OS所有者IPCとインプロセスのInfoだけが `OwnerSourceProjectsV1` を返し、共通UIはその能力がある接続でソース入口とコマンドを表示する。ブラウザーの各操作では所有者セッションを再検査する。

現在の編集用スナップショットは既存基盤に合わせてnet10.0・C#14を対象とする。既定Compile、Compile Remove、リンクされた実ソースと条件付き宣言を扱う。SDKが暗黙に追加するフレームワーク定義は、SDKの評価済み版一覧とBeforeCommon.targetsの規則から復元し、Buildターゲットを実行しない。プロジェクトを再評価する際は同期対象だけを更新し、Compileから外れた実ファイルを削除しない。UIに未保存編集がある場合は三者比較で保持し、同じ箇所の競合では自動上書きしない。

Windowsブラウザーの隔離試作で、.slnx・フォルダー・.csprojを開く入口、名前空間・ファイルの表示、Managerの列名変更が実ファイルへ保存されること、外部保存を模擬した別の列名変更の自動取り込み、DB画面からコマンド検索で戻った時の編集保持を確認した。実際のVS／VS Codeの画面による保存、Linux／ネイティブWebViewでの今回のソース操作、稼働DBの下書き・ビルド成果物と開いたプロジェクトとの対応付け、新規DBの専用プロジェクト保存は後続受入である。現在はソースの編集・ファイル同期までを提供し、プロジェクトを開いたことをDB公開の完了とは扱わない。
