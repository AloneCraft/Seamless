# Managerのコンテキスト依存操作基盤

## 現在の配布方針

利用者の追加指示により、Managerはブラウザー版へ統一する。Windows・LinuxのネイティブManagerとWebView試作は移行・整理の対象に変更した。以下の既存デスクトップ試作の記録は移行元の確認範囲を示す。現在の構成と完成条件は [Managerのブラウザー統一](20261107-manager-browser-hosting.md) を優先する。

## 背景

利用者の2026年11月7日の要求により、対象付近の操作ハンドル、検索できるコンテキストメニュー、直接操作、段階的開示を共通の操作体系として実装する。Windows・Linux上のホストと、そのホストが配信するブラウザー画面を今回の対象とする。スマホの配布・受入は将来の可能性として残す。

## 現状の観察

| 画面・機能 | 実装の入口 | 引き継ぐ操作 |
|---|---|---|
| 接続・サーバー・Gateway | `管理ウィンドウ.cs`、`管理ウィンドウ.起動.cs`、Gateway各Window | IPC、TCP/TLS、接続設定、起動、権限・公開版の管理 |
| 稼働DB・スキーマ・オブジェクト | `管理ウィンドウ.カタログ.cs`、`.ブラウザー.cs`、`.対象操作.cs` | 開く、作成、設計、削除予定、下書きの復元 |
| C#・表・文書タブ | `管理ウィンドウ.オブジェクトタブ.cs`、`テーブル設計.cs` | 編集、比較、行表示、保存、閉じた下書きの再開 |
| 下書きと適用 | `管理ウィンドウ.設計.cs`、`.操作.cs` | 保管、検証、プレビュー、明示適用、操作ID照会 |
| 外部ソースとの同期 | `.ソース連携.cs`、`.ソース競合.cs`、`.ソース取消.cs`、SourceWorkspace | 外部変更保持、競合、Manager編集の取消、下書きの復元 |
| 結果・計画・監査 | 主ウィンドウと監査各partial | 結果グリッド、静的計画、履歴、監査検索・状態 |

WPFには対象別の右クリックメニューと権限判定がある。対象操作と全体操作の表示が別々に構築され、検索付きの共通コマンド登録、ハンドルからの文書移動、共通のポップオーバー状態は見つからなかった。表タブには複数の常時表示ボタンがあり、閉じるボタンも常時表示される。

共通Razor試作では同じ画面から実DB一覧・空DB作成が動く。共通APIは `IManagementOperations` で、既存の管理・下書き・検証・適用処理へ接続する。

## 過去設計から引き継ぐ仕様

空DB作成のインライン名入力、Enter確定、Esc取消、結果不明時の操作ID照会を維持する。既存DBへの変更は下書きと検証を経て明示適用する。SourceWorkspaceの競合・取消、ソースのUndo、閉じた文書の作業保持を引き継ぐ。各ホストから同じ管理処理と認証済み権限を使う。

## 目的

対象、選択、フォーカス、メニュー、ドラッグの状態を共通の操作体系にまとめる。必要な機能を対象付近と検索から発見できるようにし、操作コマンドの可否判定と実行処理を共用する。

## 提案設計

### 共通コマンド

コマンドの安定ID、表示名、検索語、階層、ショートカット、破壊的操作の表示、表示条件、実行条件、実行処理を宣言する。検索とメニューは同じ登録を参照し、実行直前にも対象と実行条件を検査する。サーバー側の認可を実行境界として使う。

### 共通UI部品

共有Razor画面に、対象操作ホスト、検索付き操作メニュー、ポップオーバー配置、ツールチップ、文書タブとドラッグハンドルをまとめる。画面と操作状態のコードは、Windows・Linuxのホストが配信する共通画面で使う。ブラウザー統一の合意に従い、共有Razorの正常操作を各ホストで受け入れる。

操作の余白は先に確保し、ホバー・選択・キーボードフォーカス・メニュー表示中にハンドルを示す。メニューへのポインター移動中も操作対象を保持する。メニューは一度に一つを開き、対象と戻り先フォーカスを保持する。外側クリックでは移動先のフォーカスを保ち、Escapeでは起点へ戻す。

メニューには検索、上下移動、Enter、Escape、サブメニューの往復を用意する。スクロール・画面端・サイズ変更に合わせて配置し、イベント購読は共通の画面・表示中メニューに集約する。

### 直接操作

代表画面では、文書タブの表示順をハンドルからドラッグで編集する。挿入位置を表示し、Escape・ポインター取消では元の順序を保持する。キーボードからの移動コマンドも同じ並べ替え処理へ接続する。DB構造の編集には既存の下書き・適用APIを使う。

### 入力と環境の境界

ホバー、フォーカス、選択、ポインターを入力として扱う。将来のタッチ操作を同じ状態とコマンドへ接続できる構造にする。ファイル選択、外部IDE、ローカルIPCなどの環境操作はホストの入口へ接続する。

## 影響範囲

共通の操作モデルと共有UI部品、Razor試作ホスト、ソリューション登録、代表画面の操作試験。既存WPFとサーバー処理を参照し、機能ごとに共有画面へ移行する。

## サーバー側プロジェクトと開発時の基本形

### 作成元DBの同期記録の継承

新規プロジェクトは、作成時に保持したDB定義ID・基準版と同じSourceWorkspaceを使って編集・再開する。SDKのCompile評価と定義条件の変更は既存の取り込み処理で確認する。作成元のProjectBindingと開くcsprojが一致する場合、ルートの同期記録を正本にする。別プロジェクトを開く場合は既存のプロジェクト別同期記録を使う。

以前の実装で作成元と一般取り込みの二つの同期記録ができている場合、作成元が初期状態を保持し、取り込み側の競合・未完了操作がないことを確認してから、取り込み側の編集・取消基準を作成元のDB定義へ引き継ぐ。以前の記録は保全し、そのハッシュを正本へ記録する。両方の編集や未解決の競合がある場合は内容を保持してConflictを返す。取り込み後に旧記録が変更された場合も照合して停止する。この継承は同期メタデータに適用し、後続のDB下書き・明示適用では既存の版照合を使う。

利用者が指示した「稼働DBの下書きとの継続的な対応」へ接続するための修正として実装する。既存のファイル同期・三者比較・取消・書き込みジャーナルを再利用する。新規作成後の同期とサービス再開、旧二重記録からの編集・取消基準の引き継ぎ、両側の変更と競合記録の保全を検証する。

IDEの外部保存監視では、待機時間が完了した後でも処理開始前に新しい保存が届いた場合、以前の取消トークンをロック内で確認して新しい待機分を取り出さない。公開コンストラクターは従来の時計を使い、内部コンストラクターのTimeProviderで完了順を制御した試験を行う。実ファイル監視と、待機完了・新しい保存・古い処理開始という順序の試験を組み合わせる。

同期記録の継承と監視の関連試験はDebug／Release各44件が成功した。作成元の記録が更新されない症状と、古い待機による早い通知は、それぞれ修正前の試験で失敗を確認した。実ファイル側は最後の保存内容が通知・同期されること、時計を制御した側は一つの待機期間の集約と次の待機期間の再通知を確認する。証跡は `F:\Seamless\manager-cross-platform-20261107\source-sync-debug3-results` と `source-sync-release2-results` にある。

### プロジェクトからDB下書きへの反映

作成元DBの同期記録を持つプロジェクトには、DB名と同期基準版、明示的な「DB下書きへ反映」を表示する。SourceProjectDocumentに作成元の定義ID・DB名・基準版・下書きリビジョンを持つSourceProjectDatabaseを任意の追加プロパティとして返し、既存のコンストラクターを維持する。一般のソースプロジェクトはファイル編集・同期の入口を使う。

反映は所有者専用の共通ソース操作へ追加する。OS所有者IPC、組み込みホスト、同居ホスト、所有者ブラウザーの各入口が同じSourceProjectServiceの調整処理を呼ぶ。実行前に評価済みCompile対象と条件を照合し、ディスクと編集内容を同期する。DBの公開版・個人下書きと版を確認し、前回保管した定義または公開版を基準にSourceWorkspace.MergeDefinitionsで三者比較する。参照・条件・ファイル構成の違い、公開版の進行、同じ部分の変更は内容を保持して確認を求める。対応するプロジェクトのファイル構成の変更は、SDK再評価と明示的な整理へ接続する。

DB画面に未保管の編集がある場合は既存の下書き保管処理を先に通し、反映結果を同じ文書へ取り込む。処理中の追加入力は基準スナップショットから再比較する。保管内容がすでに一致する再要求は同じ下書きを返す。DB保管後に同期記録への反映が中断した場合も、再要求時に保管済み内容を照合する。ファイル保存、個人下書き、公開版の状態を区別して表示する。

この操作は下書きの保管までを担う。開発者ビルド成果物の取り込み・検証・明示適用は続く工程として実装する。検証では、組み込みと所有者IPCの反映・再要求・再開、独立した編集の統合、競合・公開版進行・Compile変更の保全、ブラウザーセッション失効とTCPからの拒否、共通画面への接続を確認する。

プロジェクト生成前に、表示中の設計を個人下書きへ保管する。保管中に追加入力があれば編集を保持し、生成前に確認を求める。組み込み・同居・所有者IPCは下書きの版・基準版・定義ハッシュを確認してからファイルを生成し、その応答を同期の比較基準へ記録する。これにより追加直後のテーブルも初回編集から反映できる。未確認の版・内容は保存先を作る前に拒否する。SDKのCompile評価が返さないDB定義の参照DLL一覧は、通常の再オープンと旧同期記録の引き継ぎで保持する。

旧記録に比較基準がない場合、Manager編集を除いた全ファイルと現在のDB下書きが一致することを確認できる場合に基準を復元する。別々に変更されている場合は両内容を保持して競合を返す。公開直後に旧基準版の個人下書きが残る場合、直前保管内容と公開内容の一致を照合して次の版へ進む。下書き反映の成功・失敗はプロジェクトごとに表示し、定期ファイル同期の通知で消さない。

### 既存プロジェクトを開く入口の実装方針
