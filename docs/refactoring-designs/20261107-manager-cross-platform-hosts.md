# Seamless Managerの共通画面と実行形態

## 背景

2026年11月7日の利用者要求に基づき、Windowsデスクトップ・Linuxデスクトップ・ブラウザーの管理画面と、組み込み・サーバー同居・別プロセス接続の実行形態を実装する。最小の接続・表示を先に通し、その結果を使ってUI技術を選定する。

## 現状の観察

- `Seamless.Management.UI/SeamlessManager.csproj` はnet10.0-windowsのWPFで、AvalonEditとMsagl.WpfGraphControlを参照する。操作コードはManagementClientへ接続する。
- `Seamless.Management` はnet10.0で管理契約、TLS・Named Pipeクライアント、C#編集モデル、下書きモデル、静的計画を持つ。
- `Seamless.Management.Server/WindowsServer.csproj` は名前と異なりnet10.0を対象とし、ManagementService・ManagementStore・NativeRuntime・Kestrel管理RPCを持つ。名前からWindows専用と判断せず、Linuxで必要な依存を実行確認する。
- ManagementServiceには同期の一覧・下書き・ビルド・検証・プレビュー・明示適用がある。行編集には非同期のゲート取得があり、組み込み型の一つのDB実行スレッドへ接続する際に実処理のスレッドを検証する必要がある。
- 現在のIPCは双方にCurrentUserOnlyを指定するNamed Pipeで、サーバー設定のSeamless利用者へ対応付ける。今回合意したOS所有者の全操作権限との違いを明示して移行する。
- NativeRuntimeとGatewayDatabaseHostは別のホスト入口を持つ。同じDBを別エンジンとして開く構成を避けるため、DBの所有・世代・実行境界を最初に照合する。

## 過去設計から引き継ぐ仕様

`20261102-native-management.md`、`20261103-management-usability-local-ipc.md`、`20261104-external-source-draft-state.md`、`20261106-seamless-intermediate-spec.md`を引き継ぐ。空DB作成の名前確定と公開、既存DBの下書き・検証・明示適用、操作IDによる結果照会、最終状態での参照整合性検査、失敗時の旧世代保持を維持する。

## 目的

- 同じ画面と操作モデルを3環境で共有する。
- 共通の管理・DB操作に、同期直接呼び出し、IPC、TCP/TLS、Webから接続する。
- 組み込み型では管理・業務・WebのDB操作を一つの専用実行スレッドへ集約する。
- サーバー同居型では既存の取引・ロック・取消・認可・資源管理へ複数接続を参加させる。
- 所有プロセス、操作スレッド、接続主体、対象DB、公開世代を実行証跡から確認できるようにする。

## 非目的

一つの問い合わせ内部の並列化は、中間仕様書の初版方針に従う。運用DBと保存形式の変更は、既存のバックアップと明示移行の手順に従う。

## 提案設計

### 共通の操作とDB所有

既存ManagementServiceとNativeRuntimeの管理・下書き・公開機能を共用する。DBの所有・世代・実行境界は `GatewayDatabaseHost` を唯一のストレージ・WAL・取引調整器の排他所有者として一元統合し、`ManagementService` や `NativeRuntime` は別個にDBをオープンせず、`GatewayDatabaseHost` からデータベース参照（`InProcessDatabaseAdapter`）を取得して下書き・検証・公開・管理操作を行う。これにより多重オープンやファイルロック競合を原理的に排除する。通信配送、認証済み主体、操作の実行方針、画面を分離する。新しい表示方式のためにDBを追加起動せず、稼働DBの所有者を共通にする。

組み込み型の業務APIは同期メソッドとする。生成クライアントDLLへの依存を持たせず、同じプロセス内の共通DB操作へ接続する。待機中の通信と描画をDB実行スレッドから分ける。UIスレッドやWeb/IPC通信スレッドからの要求は非同期キュー駆動型ディスパッチャー（専用DBワーカースレッドが逐次実行しTaskCompletionSourceで完了復帰）を介して接続し、UIフリーズとデッドロックを防止しつつ完全なスレッドセーフティと逐次性を保証する。行結果の列挙・取引の確定と取消・停止時の処理まで、実行スレッドの保証対象を明示して検証する。

### 主体と権限

- 利用者の追加回答により、パスワードなしのローカルIPCはサーバー所有者と同じOSアカウントに限定する。WindowsとLinuxの両方でOSの接続元確認を使う。
- インプロセスの所有者と、確認済みIPCの所有者には対象ローカルインスタンスの全DB操作を許可する。既存Seamlessアカウントの権限へ暗黙に依存する経路との差分を検証する。
- TCP/TLSは既存の証明書・ホスト名検証と利用者の認証・認可を使う。
- Webの初期設定はループバック待受けとする。デスクトップからのブラウザー起動は、確認済みOS所有者に結び付いた短命のワンタイムトークン引き渡しから、有界で失効可能なブラウザーセッション（HttpOnly Cookie）を確立する。すべての状態変更操作（DB作成、スキーマ変更、クエリ実行等）にはセッション検証およびCSRF対策を必須とする。
- 外部公開は明示設定・HTTPS・利用者ごとの認証と権限を要求する。画面の可否表示とサーバー側の実行時検査を対応付ける。

### UI候補と選定の条件

Avalonia、Uno、共有Razorコンポーネントとデスクトップホストを候補として調べる。MAUIについても公式の対象環境と必要な追加実装を確認する。試作にはDBツリー、タブ、キーボード、C#エディター、結果グリッド、静的計画を含め、実行・配布・依存導入・デバッグの条件を記録する。

UIの最終選定は試作後とする。選定の最優先判定軸は「コード共通化率と3環境（Windows / Linux / Web）での単一コードベース描画・操作の一致度」とし、DBツリー、C#エディタ、結果グリッド、静的計画ビューの共通コード範囲を最大化し、OS固有の分岐・再実装を最小化する。ブラウザーの静的ファイル、デスクトップの描画、管理APIの接続がそれぞれ実際に動くことを判定条件にする。

## 影響範囲

管理ホスト、共通操作契約と配送、IPCの主体、Kestrel Webホスト、共通UIとデスクトップ起動、VS・VS Codeの起動設定、既存WPFからの段階移行、配布・回帰試験。

## テスト計画

専用の隔離管理領域と検証DBを使用する。同期直接呼び出し、Manager、Webが同じDBへ接続することをDB識別子・PID・スレッドIDで確認する。単一スレッドの逐次性、再入、例外、待機中取消、終了時の排出、所有ファイルの排他を検査する。

サーバー同居型では複数接続と切断時の未確定取引を確認する。IPCではOS所有者の成功と異なるOS利用者の拒否を確認する。TCP/TLS、ブラウザーの所有者引き渡し、未認証・権限不足・外部認証利用者は別のケースとして確認する。

3環境の実行、ビルド、内部操作、描画、実OS入力、IDEデバッグを分けて記録する。未実行環境は未検証とする。

## リスクと対策

既存WPFの操作コードには配送と表示の結合があり、移行する機能ごとに操作契約を共用へ寄せる。DBを開く既存入口が複数あるため、所有者と公開世代の共有を画面移行前に確認する。非同期処理の継続先がDB専用スレッドを離れる箇所は、直接呼び出しの試験で検出する。

## 未決事項

- UI技術は、Avalonia・Uno・Blazor/Razorの各候補で6要素（DBツリー、タブ、キーボード操作、C#エディタ、結果グリッド、静的計画）を含む最小統合プロトタイプ画面を構築・実機実行し、描画性能・起動速度・配布フットプリントを横断比較して最終選定を行う。
- Linux検証環境は利用者の回答によりWSL2＋WSLgを第一候補とする。テスト実行および成果物・ログ収集はWindows側スクリプト（Invoke-Checks.ps1）からWSL2（wslコマンド）を透過的に呼び出し、結果ログを `F:\Seamless\` 配下へ統合集約する自動化方針で合意完了。WSL2ディストリビューションの導入とWSLg GUI起動確認を後続ステップで実施する。
- 共通DB所有者と既存Gatewayの接続方法は、GatewayDatabaseHostを唯一の排他ストレージ所有者とし、ManagementService/NativeRuntimeがそのInProcessDatabaseAdapterを参照共有する一元統合方式として合意完了。
