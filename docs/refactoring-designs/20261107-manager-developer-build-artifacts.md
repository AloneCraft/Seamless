# Managerの開発者ビルド成果物と明示適用

## 背景

開発者PC上のSeamlessとIDEが同じプロジェクトを扱い、DLLは開発者側の通常ビルドで生成する。ブラウザーManagerのソースから個人下書きへの反映は実装済みであり、続く成果物の検査・取り込み・明示適用を接続する。

## 現状の観察

- `SourceProjectService` はCompile対象・条件・物理パスと、DBの下書きの比較基準を保持する。
- `ManagementService` のBuild・検証DB作成は、BundleHashを指定すると保管バイナリを使う。選択なしの既存経路とPreview・Applyにはソース再コンパイルが残る。`TypedMigration` にも移行処理をコンパイルする経路がある。
- `NativePrebuiltPackage` は事前生成RPCモジュールと依存DBのパッケージを扱う。Managerの任意のDB定義DLLと下書きを結び付ける入口はない。
- 通常のSDKビルドのPortable PDBには元のCompileファイルのチェックサムと、生成ソースの文書が記録される。DLLのCodeViewとPDBのIDを照合できる。

## 過去設計から引き継ぐ仕様

サーバー側のプロジェクトを開く。版が違う成果物は実行前に拒否する。個人下書きと公開版を区別し、明示適用する。旧世代の維持、取引、参照整合性、WAL、監査、移行の規則を引き継ぐ。正式版の事前生成方針は中間仕様書の「共通ビルドとクエリの事前生成」に従う。

## 目的

ソース・下書き・開発者ビルドDLLの対応を検査し、検査済みの同じバイト列を検証・変更確認・明示適用へ渡す。

## 実装順序

1. 所有者専用の共通ソース操作へ成果物検査を追加する。開いているプロジェクト、保管済み下書き、実ファイル、DLL・PDBの対応を、DLLを実行せずに検査する。
2. 検査したバイト列を管理領域へ保存し、成果物ハッシュを下書き・検証・プレビュー・操作IDの要求へ束縛する。検査後のファイル差し替えを再読込で持ち込まない。
3. NativeRuntimeの検証・差分・公開を選択済み成果物へ接続する。依存クエリと移行処理も事前ビルド成果物に対応付け、サーバーでのソース再コンパイルを順次除去する。
4. 共通画面から選択・検査・取り込み・確認・明示適用を操作し、同じ公開DLL契約の既存クライアント互換を受け入れる。

第1段階の検査結果は実行許可や公開完了を表さない。後続の取り込みでは、検査と保存を一つの所有期間で行う内部結果を使用する。

## 検査契約

- OS所有者IPC、組み込み、同居、所有者ブラウザーから同じ検査処理を使う。TCPと一般ブラウザーにはサーバー上のファイル参照権限を与えない。
- 評価済みCompile対象・条件と、要求元が表示しているSourceHashを照合する。変更を同期した結果が未保管ならDB下書きへの反映を求める。サーバー下書きのID・版・基準版・定義ハッシュも確認する。
- DLLとPortable PDBのID、全元ソースの実ファイルとPDBチェックサム、入口型をPEメタデータで照合する。未確認のソースやDebug情報不足は成功へ含めない。
- Seamless共有ライブラリはサーバーとビルド出力のバイト列を照合する。非共有依存も参照の閉包を検査し、依存ファイルの名前・版・ハッシュを結果へ含める。
- 件数・ファイルサイズ・全体の予約予算に上限を設け、取消・例外時に返却する。リンク経由の読み取りを拒否する。

## 条件定数の由来と新規project保存の判断境界

`SourceSnapshot.Defines`はSDK評価済みの凍結コンパイル入力として、解析・同期競合・PDB照合に使う。`SourceWorkspace.Create`と`CreatePackageProject`は現在その全定数を新規csprojへ転記する。既存projectの同期は元のcsproj・Import構造を変更しない。新規専用projectの再生成とは保存契約を区別する。

11月11日にWindows SDK10.0.403の同梱MSBuildLocatorと評価APIを使い、Build targetを実行せず`AllEvaluatedProperties`・`Predecessor`・`Xml`からDefineConstantsの代入元file/line・未評価式・前後評価値を取得した。相対Importの未評価式と解決先も取得でき、通常dotnet msbuildの評価3対照と一致した。独立probeはReleaseビルド警告0・エラー0、9checks成功。通常の構成定数はDebugのDEBUGからReleaseのRELEASEへ変化し、ユーザーが明示指定したDEBUGとNET10_0はReleaseでも保持された。

履歴からSDKの代入操作だけを除き、残るuser定数の評価済み値を再出力する案には反例がある。SDKがDEBUGを追加した後のuser targetsが、その値を条件にDERIVED_FROM_DEBUGを追加すると、元のReleaseではDERIVEDが無い。Debug履歴から得たuser値を新projectへ固定するとReleaseにもDERIVEDが残る。定数名だけの差引きや、SDK暗黙定数を無効化した別評価も、後続user条件式の意味を保つ証明にはならない。

同じ入力の未評価csprojと相対props/targetsをそのまま保持したコピーでは、Releaseの評価値が元と一致した。ただし任意のImport閉包・非選択構成・外部依存まで保持できることは未検証であり、未評価Importの無条件全copyは採用しない。

新規専用project保存では、凍結したコンパイル契約を保持するか、元project/Import構造の構成追従を保持するか、製品として追加判断が必要である。由来定数配列からの再構成案は採用保留とする。旧snapshotに由来を推測で補わず、ユーザーのDEBUG等を自動除去しない。現行コードにCompilationContext型は無く、この調査では製品コード・共有wire/hashを変更していない。新しいSDK build・PDB照合・#if実行回帰は未実行。証拠は`F:/Seamless/config-provenance-probe-20261111/proof-r2.json`、`run-r2/receipt.json`、`summary.json`に保存する。

## 第2段階の保管と下書き束縛

検査結果へDLL・PDB・解決済み依存DLLから決定するBundleHashを追加する。取り込み要求は表示済みのBundleHashを指定する。取り込みでは検査と保管を一つのバッファ所有期間で実行し、検査後に元ファイルを読み直さない。内容が変わった場合はConflictとして再検査を求める。

管理領域の `source-builds/<BundleHash>` へ、固定名のDLL・PDB・依存DLLとマニフェストを保管する。生成した一時ディレクトリで全ファイルを確定してから名前を切り替える。同じBundleHashの再要求では保管済みの内容を検査し、同じ下書きへの束縛を再利用する。保管領域には件数と合計サイズの上限を設ける。

個人下書きの所有者・定義ID・版・基準公開版・定義ハッシュを確認し、既存の管理取引で束縛を記録する。保管後に下書きや公開版が変わっていたら束縛を拒否する。ファイルの準備だけが終わった場合は未公開の保管物として残り、再要求で確認して利用できる。再起動時の自動公開や保存形式変更は行わない。

保管済み成果物の読み出し・実行ではマニフェストとファイルのハッシュを再照合する。欠損・改変は実行を拒否し、元の稼働DBを維持する。検査・保管と、検証・プレビュー・移行・適用への接続は段階を分けて実装する。

## 影響範囲

`Seamless.Management` のソース契約・サービス、`Seamless.Management.Server` の所有者アダプター・IPC・検査処理、共通Razor画面、Management.Tests、正式ソース検証入口を対象とする。公開APIへの追加は既存のコンストラクターと呼び出しを維持する。

## テスト計画

通常のSDKで作ったDLL・PDBを使い、下書きとの一致、DLL/PDB取り違え、ソース変更、依存版違い、未保管・古い表示・古い下書き、上限・取消、所有者IPCとブラウザー失効を短い試験から確認する。取り込み以降は再起動、差し替え、操作再要求、移行失敗時の旧世代維持まで追加する。各段階の成功を後続の合格へ広げない。

## リスクと対策

固定版NuGetと現在のサーバーが違う場合は共有DLLの照合で拒否する。同じ版番号だけで同じビルドとは判断しない。プロジェクトの評価とビルドを分け、検査からビルドを起動しない。PDBに元ソースが不足する構成は、ビルド出力側の証明情報を整備してから許可する。

## 未決事項

実装から回答できる生成成果物・移行処理の接続方式は現行コードで照合して具体化する。新しい製品上の選択が必要になった場合は、その一点を確認する。

## 合意状態

利用者の開発者ビルド・版違い拒否・明示適用の実装指示に基づく作業設計である。第3段階のバイナリ読み出し・計画取得・検証DB作成から、DB全体のプレビュー・明示適用へ接続した。全体の完了条件は4段階を通した実行確認とする。

### バイナリ読み出しと実行接続の順序

保管物の読出しでは上限付きでバッファを所有し、マニフェスト・全ファイル・現在ホストの共有依存を照合する。private依存は同じ捕捉済みバッファからCollectibleな読み込みコンテキストへ渡す。生成物のビルド結果取得と空の検証DB作成へ先に接続し、読み込み失敗・破棄時の所有予約を確認する。

成果物の世代保存にはDLL・PDB・依存DLL・バンドル情報を含め、検証DBの後続操作と再起動でも元のプロジェクト出力へ依存しない。成果物全体の識別にはBundleHashを使い、PE本体のSHA-256は別に照合する。既存の世代マニフェストの識別・監査先検査を引き継ぐ。

現在のTypedMigrationにはC#の移行ヘルパーをコンパイルする処理がある。既存行の移行・依存クエリの準備・プレビュー・適用の接続まで追い、事前ビルドへ統一する。DLLの読み出しや検証DBの成功だけで明示適用までを完了にしない。

### 選択済みDB本体のプレビュー・適用への接続順序

プレビューのトークンと適用操作の要求ハッシュへBundleHashを含める。プレビューは公開中の実バイナリと選択済みDB本体を使い、型・移行・依存クエリを確認する。適用は同じ成果物を再照合してから、既存の移行・制約検査・非公開世代・公開取引へ渡す。保管バッファを共有する所有リースを用意し、準備中のロードコンテキスト破棄と公開後のDBキャッシュの寿命を分離する。

この接続では既存の移行ヘルパー生成・依存クエリコンパイルを引き継ぎ、その事前ビルド化を後続で除去する。DB本体の選択と公開の一致を先に検証し、旧新DLLの識別や移行の問題が判明したら同じ経路で修正する。部分表だけの適用ではDLL全体の定義と候補が異なるため、選択済み成果物を指定した部分表の適用はUnsupportedを返す。

実SDK成果物を使った組み込み・所有者IPCで、元出力の退避後のプレビュー、既存行を保持した公開、同じ操作IDの再照会、異なるBundleHashの拒否、公開後の行追加・更新を確認した。生成コンストラクターの `value0` 等を列名として誤解していたため、`GeneratedRecordConstructorAttribute` へ対応列名を生成し、型付き移行とJSON行復元で使用する。捕捉バッファの参照カウントにより、準備用インスタンスの破棄後も公開中インスタンスが同じ捕捉済み依存物を利用できる。

WindowsブラウザーでSDK成果物の検査・取り込み・再読込後の選択復元・プレビュー・公開版v2への適用を確認した。行保存では、セッション期限による拒否とコンストラクター列名の不一致を観測した。後者の修正後に同DBを別候補で再開すると、共有依存 `Seamless.Database` のハッシュ不一致を拒否した。最終候補によるブラウザー行保存の成功には含めない。同じビルドの新しいフィクスチャで再開し、共有DLL照合を維持する。

近接13件と、起動例外修正を含む正式Debugソース連携94件が成功した。途中の正式Debug再確認では92件中2件がRoslynのMetadataReference読み込み中のOutOfMemoryExceptionで失敗した。後の94件成功と両方の証跡を保持し、原因未確定の失敗として全件・配布受入へ引き継ぐ。通常NuGet配布、SDK同一アセンブリ名間の反復移行、事前生成依存クエリ、強制終了境界、デバッガー到達は残る。
