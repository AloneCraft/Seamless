# 組み込み同期の業務実行入口

## 背景と既存契約

W07-BUSINESS・W07-SERIALの実経路を接続する。既存InProcessManagementHostは管理操作を専用DBスレッドへ配送する。公開クエリのManagementService.ExecuteはNativeRuntime.Executeの結果を最後まで列挙してから取引を確定する。結果を返した時点では確定していない場合がある。

## 実装設計

公開済みクエリの単一値を返すExecuteScalar<TResult>を、組み込みホストの同期APIとして追加する。入力のJSONは受付前に所有コピーを作り、実行・型変換・単一値の件数検査を専用DBスレッドで行う。実行本体は既存の認可・取引・参照整合性・WAL・監査へ接続する。

NativeRuntimeの確定直前に結果検査を呼べる内部境界を設ける。空の列、複数要素、型変換失敗では確定に到達せず取引を取り消す。既存の通信による結果列挙は従来の呼び出し契約を使う。

行の参照・更新とビュー／関数実行にも同期入口を追加し、対応する既存管理処理へ配送する。Manager・業務呼び出しが競合した場合は専用DBキューで順番に実行する。

## 検証と継続範囲

公開入口からの追加・読取・失敗時取消、同時投入、実行スレッド、取消後の再実行、再起動後の値と監査を確認する。スカラーの空・複数結果と型変換失敗も書込取消を確認する。集合の管理公開クエリ経路を下記の所有型・予算・退避へ接続し、正式RPC・グラフ表現と大規模受入はW17・W18へ引き継ぐ。

## 集合の同期取得と所有

合意済みの独立した結果コピー・所有型ストリームをExecuteStream<T>へ接続する。公開クエリの列挙・型検査・結果コピーの構築は専用DBスレッド上で完了し、取引確定後にQueryResultStream<T>を返す。読取中にDBのゲート・取引を持ち続けない。結果構築中の型不一致・例外・取消・予算超過では、書込と結果コピーを破棄する。

結果コピーは既存の管理用JSON行表現を長さ付きで保持する。共通ResourceBudgetの子予算へメモリ容量と読取用領域を計上し、保持メモリが不足したら既存TemporaryFileへ一度退避する。一時ディスクの上限も親予算と共有する。単一行の読取枠を確保できない場合は取引確定前に失敗する。JSON投影・復元内部の全割当ての会計と参照グラフ形式への移行はW11・W15・W18で継続する。

結果は一度だけ列挙でき、通常のLINQで必要に応じて実体化する。列挙の完了、列挙子のDispose、結果のDispose、取消後の次の読取、ホスト停止で所有領域を解放する。ホストは未破棄の結果も回収する。要素の取得後に呼出元が保持する値は呼出元の所有とし、結果の破棄で変更しない。

```csharp
using var rows=application.Embedded!.ExecuteStream<Item>(
    new ExecuteRequest("list-items",null,ManagementJson.Element(new{})),
    memoryLimitBytes:16L<<20,temporaryStorageLimitBytes:1L<<30);
foreach(var row in rows){
    Process(row);
}
```

公開済み問い合わせの最終結果を同期で取得する。メソッドが戻る時点でコピーの構築と取引確定が終了している。途中で列挙をやめても既に確定した更新を取り消さない。`ToArray()`などで取得した要素は呼出元が所有する。現行のExecuteRequest.MaximumRowsと管理用JSONの型契約を引き継ぐ。事前生成の通常業務RPCとグラフ形式の戻り値はW18で接続する。

近接試験ではメモリ保持と退避、部分読取後の次クエリ、型不一致と列挙途中の失敗による取消、上限超過、入力コピー、ホスト停止時の回収を確認する。既存の同期スカラー・キュー・監査試験を回帰対象とし、UIの全件操作は再実行しない。

## 合意状態

生成クライアントDLLを使わない同期直接呼び出し、単一値は直接返す契約、一つのDB実行スレッドへ集約する合意に基づく実装設計。

## 呼び出しと確定の境界

```csharp
await using var application=await ManagementApplicationHost.OpenAsync(
    new ManagementHostOptions(root,ManagementExecutionMode.Embedded));
var count=application.Embedded!.ExecuteScalar<int>(
    new ExecuteRequest("count",null,ManagementJson.Element(new{})));
```

公開済み問い合わせIDと引数を渡し、同期メソッドが最終戻り値を返す。呼出元の生成クライアントDLLを使わず、ホストが所有する公開定義を認可・実行する。行の参照・確定と公開ビュー／関数にもReadRows・CommitRows・ExecuteObjectの同期入口を設ける。

スカラーは内部で2件まで読み、2件目を検出した時点でResultShapeを返す。入力のMaximumRowsが1でも複数結果を見逃さない。0件、型変換失敗、本体例外の場合も書込取引を確定しない。nullの単一値はnullableな戻り型で受け取れる。結果の検査が成功し、列挙の終了・取引確定が完了してから呼出元へ戻る。

## キューと入力の所有

待機中の取消と実行開始をCASで競合させ、取消が先なら本体を実行せず呼出元の待機を終了する。実行開始後は本体による取引の確定・取消結果を待つ。容量に達した受付は既存の有界チャネルで待機し、取消済み項目の枠はDBスレッドが取り出した時点で返す。

行・関数の同期／非同期入口は受付前にJSON要素と配列をコピーする。呼出元がJsonDocumentを破棄し、元の配列を書き換えても、受理した入力の値を保持する。

## WAL監査の組み込み配送

組み込みでは共通ホストのタイマーが250ms単位で有界な転記作業をDBキューへ配送する。参照集計は設定された保存間隔で配送する。WAL転記のロック待ち・対象監査の確定・ACKと転記元状態の保存は同期経路を使い、専用DBスレッドで処理する。サーバー型の既存非同期ワーカーは同じバッチ処理を使用する。

参照集計を無効にしてもWAL監査を転記する。再起動後は保存した転記元を走査し、追加の業務クエリを待たずに未転記の確定済みWALを回収する。終了時には受付済み操作の後で参照集計とWAL監査の最終転記を同じDBスレッドで行う。転記失敗は既存の転記元状態へ記録し、確定済み業務更新と未転記監査を保存する。

### 集合の追加検証

ExecuteStream<TResult>・QueryResultStream<T>とホスト終了時の回収を実装した。新規3件と既存の業務・キュー・停止・再入9件が最終候補のDebug・Release各12件で成功した。両構成のサーバービルドは警告・エラー0件。

- 部分読取中にも次の同期参照・更新が実行できた。型不一致、列挙途中の例外、2行目生成直後の取消、結果上限、予算不足では書込みを取り消し、次の問い合わせへ継続した。
