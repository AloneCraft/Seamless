# IPC受信バッファの親予算会計

## 背景と既存仕様

W11-LIMIT-IPCを実装する。IPCのPipeTransportは4096バイト単位で受信し、65536／32768バイトの閾値で先読みを制限する。現在は既定のメモリープールを使用し、管理DBのResourceBudgetへ計上していない。LengthPrefixedPipeの分割フレーム復元もArrayPoolから借り、通信フレームの共有上限と管理DBの親予算は別の会計になっている。

## 実装設計

管理DBの既存ExecutionScopeのResourceBudgetを親として、サーバーがIPC専用のExecutionScopeとMemoryPool<byte>アダプターを所有する。アダプターは既存OwnedBufferを使い、バッファ容量と管理費64バイトを確保前に予約する。入力Pipeと分割フレームの復元に同じプールを渡し、個別接続と管理DB全体の使用量を対応付ける。

LengthPrefixedPipeには受信プールを指定するオーバーロードを追加し、既存のコンストラクターと既定のArrayPool経路を維持する。独自プールのバッファも解析成功・失敗・取消で返し、共有フレーム予算と親予算を両方解放する。完成した入力を借用して解析する経路も維持する。

予算不足はバッファ確保前に拒否し、接続失敗として通知する。未完了フレームの接続終了・解析失敗・サーバー停止では、Pipeと復元バッファを閉じてからIPC資源スコープを閉じる。保存形式、OS所有者確認、共通要求枠、TLSと既存の通信フレーム上限を引き継ぐ。

## 検証計画

保持中のIPC接続が親予算に計上されていないことを修正前に再現する。修正後はアイドル接続、分割フレーム、親予算の枯渇と再接続、解析失敗、切断、停止で現在値が基準へ戻ることを確認する。既存の接続再利用・共有受信予算・共有実行枠を変更境界の回帰として選ぶ。

## 継続範囲と合意

利用者が合意した親予算・資源上限・取消と解放の実装に基づく。今回はIPCの入力・フレーム復元バッファを接続し、TCPのKestrel内部バッファ、JSON復元、コンパイル、業務DB全体の予算と既知のRoslynメモリ不足はW11の別の枝へ続ける。

## 実装した所有関係

ManagementService.CreateTransportResourcesは管理DBのResourceBudgetを親とし、同じメモリ上限・一時領域上限0のIPC専用ExecutionScopeを作る。ManagementServerがスコープとプールを所有し、各接続と全読取の終了後に閉じる。プールは既存OwnedBufferで要求容量と64バイトを予約し、返却時にバッファへの参照と予約を解放する。

管理用の要求・応答上限と親予算は別の制約として維持する。分割フレームの完成・解析失敗・取消・途中終了では復元バッファを清掃して返し、フレームの共有予約も返す。親予算の不足は確保前にResourceLimitExceptionとなり、未完了要求の実行を開始せず接続失敗として通知する。

LengthPrefixedPipeの既存3〜7引数のコンストラクターは維持し、8引数のオーバーロードでMemoryPool<byte>を指定する。指定したプールは読取中に利用可能である必要があり、読取結果へ持ち出す値は解析コールバック内でコピーする。指定しない呼出元は従来のArrayPool経路を使用する。

## 実行結果と証跡

修正前の代表1件で、保持中のIPC受信バッファが親予算へ計上されない失敗を再現した。修正後の近接11件が成功し、6接続の共有予算不足・復帰を追加した最終候補はDebug・Release各24件が成功した。内訳は新規12ケースと既存回帰12ケース。変更した通信・サーバー・試験のビルドは警告・エラー0件。

- アイドルの再利用IPC接続が親予算へ計上され、切断後に戻ることを確認した。
- 親予算を使い切った状態で新しいバッファの確保を拒否し、予約が増えず、予算を返した後に再接続できることを確認した。
- 分割フレームの成功・JSON解析失敗、未完了フレームの切断・サーバー停止で、入力・復元・フレーム共有予約の返却を確認した。
- 独自受信プールの成功・解析例外・取消・途中EOF・予算不足で、親予算とフレーム予約の両方が0へ戻ることを確認した。予算不足では親予算のピーク増分も0だった。
- 6接続が32768バイトの不完全フレームを保持した状態で、両構成ともIPC予約221952バイトを観測した。管理DBの親上限は268435456バイト、開始時使用量は76432576バイト。追加の1MiBフレームを残量不足で拒否し、全接続の終了後は親使用量76432576バイト、IPC・フレーム予約0へ戻った。再接続も成功した。
- 共通要求枠の両方向待機・待機取消・停止、接続再利用、TLS／IPCの共有受信上限、分割JSONの完全検証、同居ホストと失敗後処理の既存試験を確認した。

証跡は `F:\Seamless\ipc-memory-20261108` のbefore-results、debug-results、final-Debug-tests・final-Release-testsのTRXとreceipt.json、ビルドログ、verification.json。数値は `F:\Seamless\ipc-final-1108` 配下のipc-memory-evidence.jsonに保存した。候補ソースと試験で使ったDLLをハッシュで対応付ける。
