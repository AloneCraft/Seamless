# Browser Managerの監査と実クエリの静的計画

## 今回の接続

実施順5の静的計画、6の監査画面を共通管理APIへ接続した。監査イベント・参照集計・転記状態・記録バッファのサービスとRPCは既存実装を使う。IManagementOperationsに既存ManagementClientと同じ4操作を追加し、同居、専用DBスレッドの組み込み、所有者ブラウザー、認証済み利用者ブラウザーへ配送する。既存の認証・認可を各操作の受付時に通す。

監査画面は対応する接続のシステム区分と共通コマンド検索から開く。入口は全DBに対するManage権限で表示し、サーバーも権限を検査する。検索・表示は既存の監査用テーブルを参照し、稼働DBと同じホストを使う。

## 監査の操作

- イベント、参照集計、WAL転記状態を切り替える。
- 検索語、DB、利用者、開始・終了UTC、操作、結果で検索する。
- イベントの詳細は対象行内で展開する。イベント・操作・取引のID、コード版、権限版、メソッド、許可された問い合わせ情報を表示する。
- 各ページは最大100件を置き換えて表示する。続き取得には検索時の条件と上限を保持し、全件を画面へ蓄積しない。走査上限により0件の途中ページでも、続きがあれば次へ進める。
- 参照集計には記録の有効状態、受付・保存・未確認・欠落・失敗の数も表示する。
- 転記状態は世代、永続・転記済LSN、最終更新、エラーを表示する。
- 表示切替・破棄時は前の読み込みを取り消し、古い応答を適用しない。失敗時は案内を表示する。

ブラウザーの確認で検索入力が絞り込みへ反映されないケースを観測し、検索語・DB・利用者の値をoninputで更新するよう修正した。最終候補で検索語変更と検索結果の一致を確認した。

## 静的計画で修正した不一致

IPCのplansはBuildResultを返すが、ManagementClient.PlansAsyncは配列として読んでいた。既存のRPC応答を維持し、クライアントでBuildResult.Plansを返す。

RuntimeCompilerはDBコードを生成したschemaCompilationをFLinqへ渡していた。FLinqの解析はDatabaseAnalysisCompilationでDBコードを内部生成するため、DB型の生成メンバーが解析上で重複していた。DB型内のSumValuesを呼ぶ実クエリでは計画が空になり、同じ演算を独立した型へ置いた比較入力では生成できた。FLinqへ生成前のcompilationを渡し、元のDB生成物を最終出力へ一度だけ合流させて修正した。管理入口のブリッジは両方のコンパイル文脈へ同じ構文木を追加する。

画面は公開済み計画の取得と下書き計画の表示を区別する。公開済み計画の取得結果が下書き配列に隠れる問題を修正した。対象切替・破棄時の旧応答を除外し、ノードに元ファイルと開始位置・長さを表示する。ノードカードとDOTテキストプレビューを切り替えられる。

## 取得中の画面切替・権限失効・破棄

監査のイベント・参照集計・WAL転記と公開計画について、取得失敗時に直前の結果を保持する処理がAuthentication／Permissionにも適用されていた。制御した操作アダプターを共通Razor画面へ接続し、権限・認証失効後も以前の結果が描画される8ケースを再現した。加えて監査画面の反復DisposeでCancellationTokenSourceのObjectDisposedExceptionを再現した。修正前13ケースは9件失敗・4件成功だった。

現在の取得要求が認証・権限エラーになったときは、監査の結果・参照状態・転記状態・続き取得情報と、取得済みの公開計画を消去する。通信失敗では既存結果を保持して案内し、再取得を可能にする。下書きの入力は別の所有データとして保持する。両画面の破棄は保持するCancellationTokenSourceを切り離してから取り消し・解放し、繰り返し実行できる。

既存の読込世代による応答除外を使い、同じ定義IDで別DBへ切り替えたときの旧成功・失敗、監査表示切替後の旧失敗、破棄後の計画の成功・失敗が画面へ反映されないことを確認した。前要求への取消通知と、権限回復後の再取得も確認した。

最終候補は新規15ケースと既存BrowserComponentDisposalの6ケースがDebug・Release各21件成功し、両構成のUIビルドと試験ビルドの警告・エラーは0件だった。試験は共通画面の実描画へ制御した成功・例外・未完了Taskを返す方式で、実回線断の受入と区別する。今回変更した層は画面の取得状態と破棄であり、共通管理API・認可・保存・実計画生成の既存証拠は上節を再利用する。
