# Browser Managerの共通ロール管理

## 背景と現状

W06-USERS-ROLESを、既存のStoredAuthorizationとManagementAuthorizationApiへ接続する。現行の共通認可RPCはOIDCトークンを検査し、DB別のロール・許可と拒否・主体への割り当て・操作結果を扱う。Browser Managerの管理用アカウントはUserAccountのManage権限を使う。

## 引き継ぐ契約と設計

OSで確認済みの同一所有者は対象ローカルインスタンスの全管理操作を行える。管理用アカウントからの編集には現在の全DBのManage権限を要求する。この管理権限を確認した入口で、共通認可マネージャーに属する一操作だけの管理用リースを作る。監査主体にはインスタンスを認証元としてos-ownerまたはmanagement-userの接頭辞を付ける。リースの使用先は共通認可の管理APIとする。

既存のOIDC入口は本人確認後に同じ操作本体を呼び出す。共通ポリシーの保存、版照合、資源範囲検査、操作ID照会、監査は既存実装を使う。初期ポリシーの登録は既存の明示登録を引き継ぎ、未登録なら画面へ初期登録が必要な状態を返す。

共通画面はDB選択、版を固定したメタデータの取得、ロール名・資源別許可と拒否、利用者またはグループへの割り当て、保存・取消を提供する。競合と通信失敗では編集内容と操作IDを保持し、結果照会で確定状態を確認できるようにする。

## 影響と実装順

認証処理と認可操作本体の境界をManagementAuthorizationApiで分離する。管理サービスと各操作アダプターへ型付きAPIを接続し、共通Razor画面へ展開する。既存の管理用DB権限画面はその保存契約を使う。共通ポリシーの資源IDとDB名は既存メタデータから取得する。

## 検証

共通APIで保存・競合・権限変更・再オープン後の保持、既存OIDC経路の拒否と許可を確認する。共通画面で編集・取消・入力保持を確認し、隔離したポリシーの通常ブラウザー操作と再起動を確認する。Windowsで実行し、Linuxと外部HTTPSの画面受入は各環境の枝へ接続する。

## 実装と確認結果

共通APIへAuthorizationDatabasesAsync・DatabaseAuthorizationAsync・ChangeDatabaseAuthorizationAsync・AuthorizationChangeResultAsyncを追加し、同居・所有者IPC・所有者ブラウザー・管理用アカウントのブラウザー・組み込みへ接続した。ServerInfoのDatabaseAuthorizationV1を画面の対応判定に使う。要求の配列は実行キューへ渡す前にコピーし、保存・結果照会は管理入口で確認した主体へ対応付ける。

ロール管理ビューはシステム区分と共通コマンド検索から開く。既存APIが返すDB内ロールを一覧表示し、名前、資源ごとの11権限の許可・拒否、利用者／グループへの割り当て、作成・更新・削除を提供する。ロール一覧の描画は100件ごとに切り替える。競合後も入力を保持し、結果不明時は編集を保護して保存結果の照会または同じ操作の再送を行う。確定済み要求の再送がConflictとなった場合は本人の操作結果を照会する。

## 継続する範囲

管理用アカウントのDatabaseGrantと共通ポリシーの資源ID・主体IDは別の保存契約を持つ。今回の画面は共通ポリシーを編集し、既存の管理用DB権限画面はDatabaseGrantを編集する。実際の業務DB・C#クライアント・SQL・Managerを通した許可／拒否の対応付けはW09・W18・W19の統合受入へ接続する。今回のブラウザー確認は共通認可のメタデータ用DB資源を使用し、稼働中の業務表への権限適用を合格に含めない。

DBをまたぐロールとサーバー全体のロールは次節のスコープAPIと共通画面へ接続した。DB別編集APIは従来の対象範囲を維持する。現在は選択スコープのメタデータを同じ版で全ページ取得して編集内容を構成する。巨大ポリシーでの読み込み・メモリ予算・描画、実回線断と再送、外部HTTPS・Linuxの画面受入は継続する。

## サーバー全体のロール管理への接続設計

W06-USERS-ROLES-GLOBALでは、DB内に限定した既存APIの範囲検査を保持し、資源スコープを明示する照会・変更APIを追加する。スコープは同じインスタンスのServerまたはDatabaseを対象とし、Serverの変更にはManageServerを要求する。サーバー全体の取得ではサーバー資源と全DBの資源、複数DBにまたがるロール、規則を持たないロールも扱う。DB別の取得と変更は従来の範囲へ限定する。

AuthorizationManagerの既存ロール変更処理を共用し、StoredAuthorizationの管理WAL・版照合・操作ID照会・確定後の公開と復旧を使う。資源の作成・変更はこの入口の対象へ含めない。所有者と管理用アカウントの管理入口には、既存の全DBのManage検査を引き継ぐ。OIDC入口は実際の認可リースのManageServerを検査する。

共通画面の対象選択へ「サーバー全体」を追加し、既存の規則・割り当て・保存・取消・結果不明からの照会を共用する。機能対応はServerInfoの追加能力で判定する。DB別の既存接続にも同じ画面を利用できるようにする。

実装後は単一DB契約の回帰と、サーバー／複数DBの作成・更新・削除・割り当て、権限不足、版競合、再オープン、共通描画を短い試験で確認する。その候補を隔離ホストへ接続し、ブラウザーの対象切替・保存を確認する。既存のDB内ロールの通常操作証拠は、変更が影響する範囲を照合して再利用する。

## サーバー全体の実装と確認結果

AuthorizationRoleChangeとAuthorizationManager.ApplyRoleChangeを追加し、既存のDB内変更と同じ変更集合の検査・版照合・確定処理を使う。ApplyDatabaseChangeはDB資源に限定する。サーバースコープの変更にはManageServerを要求し、権限規則がないロールも扱う。資源一覧自体の変更は公開しない。StoredAuthorizationは同じ管理WALへ保存し、サーバー全体の保存結果はDatabaseIdをnullとする。

共通管理APIのAuthorizationScopeAsync・ChangeAuthorizationScopeAsyncを同居、組み込み同期、所有者ブラウザー、管理用アカウントのブラウザー、既存IPC／TCP管理RPC、OIDC管理RPCへ接続した。AuthorizationScopesV1で対応を通知する。画面の対象選択へ「サーバー全体」を追加し、資源は親を含む名前で区別する。ManageServerはサーバー資源を選択した規則で編集する。新規のサーバー全体ロールの初期規則は許可なしとし、保存・取消・割り当て・結果照会はDB内ロールと共用する。

新規4ケースと既存11ケースを両構成で確認した。Debugは既存候補の14件成功を再利用し、OIDCの新規1件を追加実行した。Releaseは15件を一括実行して成功した。その後、複数DBロールと操作結果を残したまま閉じて再オープンする検査を共通入口試験へ追加し、その1件だけを両構成で再実行して成功した。変更4プロジェクトと試験ビルドの警告・エラーは0件。

- サーバー全体からの複数DBロールの追加・サーバー規則への変更・削除、グループ割り当てと解除、版競合、保存結果照会を共通5入口で確認した。
- DB内APIから範囲外のロールを変更できず、サーバー資源をDB指定として扱えないことを確認した。サーバー管理権限のないOIDC利用者は、TLS管理RPCで全体照会・変更の両方を拒否された。
- 管理用アカウントの全DBのManageを外すと全体照会・変更を拒否し、所有者ブラウザーのセッション失効も拒否した。
- 複数DBの許可・拒否規則と名前を保存した後、同じDBを組み込みホストから再度開いて版・規則・本人の操作結果を照合した。
- 共通描画で対象切替、複数資源の規則、割り当て、保存・削除、サーバー管理のチェック項目、未保存状態からの対象切替拒否と取消を確認した。
