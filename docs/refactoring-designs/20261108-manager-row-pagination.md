# Managerの行ページングとキー編集

## 修正した不一致

画面は最後の行のKeyを続き取得へ渡していたが、TableRowsRequest.Keyは単一行の検索だった。そのため2ページ目には最後の行だけが再表示されていた。列メタデータがある場合は全列を非キーとして表示しており、空テーブルでも主キーを識別できなかった。

## 共通APIと画面

- Keyは既存の単一行検索を維持する。Cursorを追加し、応答のNextCursorで続きへ進む。位置と既読行の照合値をJSONで往復する。続き取得はExpectedVersionを必須とする。
- KeyMembersを追加し、0行でも実際のキー型から列情報を返す。見出しにPKを表示する。キー列も編集でき、保存は取得時のKey・Stampと変更後のValuesを渡す既存の原子的な行変更を使う。
- 各読み込みはDBの読み取りセッション内で実行する。ページ間にロック・列挙子・全件コピーを保持しない。既読部分を再走査し、行識別値を照合する。既読部分の変更・削除やカーソルの不一致はRowConflictとして返す。
- まだ読んでいない範囲の変更は次の読み込みに反映される。ページ全体を開始時点へ固定する契約は持たない。
- 1ページは既存の1000行・4MiB上限を使い、キャンセルを走査中にも確認する。UIの1回の取得は100行とする。
- 画面は取得したカーソルを送り、Keyへ代用しない。続き取得の失敗時も編集中の値を保持する。
- DB名とテーブル名の両方で表示対象を識別する。再読込・対象切替・破棄時は読み込みを取消し、古い応答は現在の行へ適用しない。保存中・読込中はセル入力と変更操作を抑止する。
- 空テーブルからの行追加、キー変更、保存後の再読込に対応し、保存件数の確認メッセージを表示する。

## 確認した範囲

変更前の近接試験で空テーブルのキーメタデータ欠落を再現した。修正後はDebug・Release各16件が成功した。DebugではHTMLエスケープを復号する表示判定の修正後、該当1件を再実行した。製品側の修正は追加していない。

- 実データ205行を100・100・5行で読み、全205キーが一度ずつ揃うことを確認した。
- カーソルのJSON往復、終端、既存の単一行検索、既読行の変更拒否、不正カーソルを確認した。
- 共通画面の描画試験で空表への追加、キー変更、保存確認、同名表の別DB切替、旧応答の除外、読み込み失敗後の編集保持と再試行を確認した。
- 既存の行競合・世代変更・外部キー・認可とJSONセル9件を合わせて確認した。

WindowsのRelease配布候補を隔離保存先で起動し、ブラウザーの通常操作とDOM値で次を確認した。

- Rowsの100→200→205行、205キーの重複・欠落なし、終端で続きボタンがなくなる。
- Emptyは0行から列とPKを表示し、Id=301・Value=71を追加する。
- その行をId=302・Value=72へ変更し、再読込後も1行と値302・72が一致する。

証跡は `F:\Seamless\manager-rows-20261108` のred-results、debug-results、ui-debug-results、release-results、server-run、row-browser-20261108.jsonに保管した。ブラウザー用DBは停止済み試験DBから正式なbackupコマンドで複製し、検証後は所有サーバーを正常停止した。画面は `Work/row-pagination-20261108.png`、`Work/row-empty-key-20261108.png`。

## 残る範囲

既読部分の再走査は読み進めるほどコストが増える。ネイティブな走査再開位置への接続と大規模結果の予算・I/O測定はW05-PAGING-SCALEとW11で継続する。大量結果を保持する画面の仮想化、Linuxと正式配布物の全体受入も継続する。
