# Browser Managerの管理用アカウント

## 対象と共通経路

実施順6の管理用アカウント作成・編集をBrowser Managerへ接続した。UserAccount、DatabaseGrant、ManagementService.ChangeUser、既存のパスワード処理と保存取引を使う。組織向けのStoredAuthorizationのロール・割り当ては、その既存APIへ接続する後続範囲とする。

IManagementOperationsへUserProfilesAsyncとEditUserProfileAsyncを追加し、同居・所有者IPC・所有者ブラウザー・認証済み利用者ブラウザー・組み込みの専用DBスレッドから同じサービスを呼ぶ。UserProfilesV1で接続先の対応を判断し、全DBに対するManage権限を入口とサーバーで確認する。

## 編集契約

- 一覧はUserProfileとしてUserInfoと変更検出値Stampを返す。パスワードハッシュは返さない。Stampは保存済みアカウント全体のSHA-256であり、パスワード本体を含む情報は送信しない。
- 作成はCreateOnlyを明示する。既存の正規化名と一致する場合はConflictとし、既存アカウントを上書きしない。
- 編集は取得時のExpectedStampを必須とする。アカウントの現在値、呼出元の現在の権限、更新を同じ管理ストアの排他内で確認する。別の更新が先に確定していた場合はConflictとし、保存済みの変更を保持する。
- パスワードの省略は現在値を保持する。新規作成は12文字以上のパスワードを必要とし、変更・無効化は既存規則で接続セッションを失効させる。
- 自分自身を無効化する操作と、自分の全DB管理権限を外す操作は既存規則で拒否する。
- 更新の監査は既存のUserChanged履歴・AccountChange監査を使う。UserAccountの保存形式を変更しない。
- 従来のusers・changeUser RPCは既存契約を維持する。新しいuserProfiles・editUserProfile RPCで条件付き編集を提供する。

## 画面

システム区分と共通コマンド検索の利用者から開く。ページは最大100アカウントを置き換えて表示し、選択した利用者のフォームを右側で編集する。

新規作成、DBごとの8操作権限、有効・無効、パスワード変更、保存・取消を提供する。パスワード変更欄は詳細を開いたときに表示する。DB名は現在の候補と全DBの*を補完し、既存・将来のDB指定を入力できる。

未保存の編集はワークスペースの未保管状態へ接続する。別の利用者や一覧ページへ切り替える前に保存・取消を案内する。DBや監査など別画面へ移っても、編集フォームの状態を保持する。保存失敗では入力を保持し、保存成功ではパスワード欄と未保存状態を消す。

## 確認結果

Debugの近接3件、Releaseの関連6件が成功した。Releaseでは同じ3件に、共通画面起動2件と監査・計画接続1件を合わせた。最終ビルド・試験に新規の警告・エラーはない。

- 作成、編集、正規化名の重複拒否、不正な編集条件を確認した。
- 同じStampからの同時保存は1件成功・1件Conflictとなり、勝った更新を保持した。
- 同居、IPC、所有者セッション、利用者セッション、組み込みで同じ編集を確認した。
- パスワード変更後の旧パスワード・旧セッション拒否、新パスワードによる接続、自己無効化の拒否、Manage権限変更後の一覧・編集拒否を確認した。
- 206アカウントの100件・100件・6件取得で重複・欠落がないことを確認した。
- 共通画面の描画試験で新規作成、競合後の入力保持、画面を隠して戻す操作、取消・最新取得、未保存通知、保存後のパスワード欄のクリアを確認した。
- 管理ストアを閉じ、組み込みホストから再度開いて設定の保持を確認した。

WindowsのRelease配布候補を正式バックアップした隔離DBで起動し、ブラウザーの通常操作とDOM値で次を確認した。

- operatorの行更新権限を外し、保存成功を表示する。
- 無効化を未保存のままDB画面へ移り、利用者画面へ戻ってもチェックと未保存状態を保持する。
- 編集取消で元の有効状態へ戻り、保存済みの行更新権限の解除を保持する。
- アカウントを無効化して保存する。
- 正常停止後に別PIDのサーバーで同じDBを再開し、operatorが無効、行参照が有効、行更新が無効であることを確認する。

利用者作成とパスワード変更はAPI・共通画面描画試験の確認範囲であり、ブラウザーからのパスワード入力は未検証とする。
