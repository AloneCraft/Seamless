# DLL世代間の列値移行

## 背景と現状の観察

実施順4のDB定義DLL固有列型を対象にする。改修前のTypedMigration.Shared.csは同名DLLの行をobject配列で渡すが、SharedTypeNameがcollectible型を拒否していた。別のALCの同名型は直接キャストできない。既存の正規化・保存はprivateフィールドと参照共有・循環を扱い、移行もそれらを保持する必要がある。

## 過去設計から引き継ぐ仕様

20261108-same-name-sdk-migration.mdの逐次読み取り、非公開世代、既存の取引・制約検査・取消・確定を使う。全行のメモリ蓄積を避け、一行内の参照対応を保持する。移行失敗時は稼働中の旧世代を維持する。

## 目的と提案設計

旧側の読み出しヘルパーは旧世代へ束縛した引数型で式を評価する。新側の構築前に、型の所属・名前・フィールド契約を照合した変換器で列値を新しい型へ複製する。列間の共有を含め、一行ごとに同じ参照対応を使う。配列・nullable・列挙・ジェネリック・private/readonlyフィールドと循環を扱う。型とフィールドの調査・アクセスデリゲート生成は変換器の準備時に行い、行ごとのメタデータ探索を避ける。

## 影響範囲と移行手順

TypedMigrationの同名DLL経路と近接試験を更新する。型の構造が変わって自動対応できない場合はMigrationRequiredで明示変換を要求する。共有される数値列などの既存のキャスト・値変換を保つ。列変換用の一時メモリは移行先DBの実行資源予算から予約して行単位で返す。変換器の型cacheは移行の寿命内に閉じ、collectibleなDLLを大域cacheへ保持しない。

## テスト計画

同名DLLのprivate値、enum、nullable、配列・ジェネリック、循環と列間共有を通常取引とcanonical非公開スナップショットで確認する。構造不一致、取消、予算超過で旧データの維持と予約返却を確認する。既存の同名移行8件を回帰に使う。生成SDKの通常の成果物取り込み・適用へ代表入力を通す。

## リスクと対策

型名の一致だけでコピーすると値を失うため、すべての保存フィールドの対応を確認する。ランタイム所有型、ポインター、特殊レイアウトは既存保存処理の制約に合わせて拒否する。配列の形状と下限を保持する。変換器の準備だけで未使用の動的派生型をすべて検査することはできないため、実値の型も初回に照合する。

## 合意状態と未決事項

利用者が指定した型・依存関係を含む取り込み・適用の実装範囲として進める。カスタム型内部の任意の構造変更を表す移行宣言の拡張は別途必要になる。既存の列の明示変換式を引き継ぐ。

## 実装と確認結果

MigrationValueConverterを追加した。同名DLLに加え、DB定義DLL固有の列を持つ異名DLLでも読み出し・変換・構築の経路を選ぶ。主DLLの名前変更とprivate依存DLLの版変更を区別して対応付ける。旧側ヘルパーは取り込み済みの旧依存DLLのバイト列を参照し、実行も旧側のロード文脈へ束縛する。新しい値型の追加列は既定値で初期化する。共有の組み込みスカラー列では既存の値配列をそのまま使う。

型・フィールドを準備時に照合し、private/readonlyフィールドの読み書きはDynamicMethodで生成する。変換用予約は列値を構築して移行先へ書き込む間まで保持し、次の行へ進むか列挙を破棄した時点で返す。型cacheは移行の寿命内に閉じる。

Debug・Releaseで移行22件が成功した。CanonicalV1の非公開スナップショットとRecordGraphV1の通常取引、異なる主DLL名、private値、enum、nullable、入れ子のジェネリック、配列、非ゼロ下限の多次元配列、参照共有・循環、構造不一致の拒否、予算超過と取消後の予約返却を含む。循環を含む試験にはRecordGraphV1を明示指定した。CanonicalV1での循環保存を合格には含めない。

SDK取り込みの追加1件もDebug・Releaseで成功した。初期の動的生成DLLからSDK DLLへ移行し、private依存DLLの列を追加して既定値を確認後、行を更新した。private依存DLLを1.0から2.0へ変更して再ビルドし、検査・取り込み・プレビュー・明示適用を通して値7・13を保持した。ホストを停止して開き直した後も値が一致した。

SDKの構成による条件定義の差は厳密に検査する。改修前にはReleaseで自動追加されるRELEASEと、ManagerのDebug評価との不一致による取り込み拒否を観測した。初回の列値移行試験は条件定義を固定して実行した。現在は構成選択をSDK評価へ接続し、通常のDebug・Release設定で取り込み・明示適用・再起動を確認した。現在の仕様と追加の実行結果は [開発ソースのビルド構成選択](20261108-source-build-configuration.md) に記載する。

証跡は `F:\Seamless\manager-types-20261108\results-Debug\custom-final.trx`、`results-Release\custom-final.trx` の移行22件と、`sdk-fixed-Debug\sdk-fixed-defines.trx`、`sdk-fixed-Release\sdk-fixed-defines.trx`。Releaseの最初の全23件には条件定義不一致のSDK1件の失敗があり、成功した22件と固定条件の再試験を分けて扱う。

## Browser ManagerのJSONセル

SDKで公開したDBのコピーで、カスタム列ValueとPriceの表示を確認した。編集時には既存のグリッドが未編集のオブジェクトをGetStringで取り出し、保存前にInvalidOperationExceptionとなる不具合を再現した。

結果グリッドは未編集のJsonElementを保持し、編集・新規入力は列型と元のJSON種類に従ってJSONへ変換する。文字列は文字列のまま扱い、構造値・配列・数値・真偽値・nullを保持する。巨大な数値も途中でdecimalへ変換しない。再現2件と入力種別7件の計9件がDebug・Releaseで成功した。証跡は同領域の `grid-results-Debug\grid-green.trx` と `grid-results-Release\grid-green.trx`。

Windowsブラウザーで既存Priceを13から14へ更新し、Value=7の保持、新規行Value=21・Price=34の追加、再読込を確認した。同じ候補のサーバーを正常停止・再起動し、ブラウザーで両行の値7・14と21・34が一致した。画面は `Work/custom-columns-edited-20261108.png`、再起動後は `Work/custom-columns-restarted-20261108.png`。検証用DBはオフラインバックアップした隔離領域を使った。
