# 業務行ストリームの途中終了と接続再利用

## 背景と引き継ぐ契約

集合結果は所有型ストリームとして提供し、途中解放でサーバーへ取消しを伝え、処理終了を確認して接続を再利用する。W18-STREAMの基盤として、既存IAsyncEnumerableの列挙子の破棄からこの取消経路を接続する。

## 変更前の観察

NativeQueryClient.QueryProjectedAsyncは未完了時に接続を閉じる。NativeQueryServerは独立した受信ループと容量1のチャネルを持つ。接続終了ではlifetimeを取り消し、実行と取引を回収する。更新問い合わせは結果コピーの構築と確定後に行を送信する。

## 実装設計

接続ごとの通常要求の通番を内部で共有し、Cancelフレームに対象の通番を入れる。通常要求の既存ペイロードを引き継ぐ。認証・接続ポリシーの専用フレームは通番へ含めない。受信済みの要求だけを取消対象にできる。

Cancelは種別12、Cancelledは種別13とする。ペイロードは8バイトのlittle-endian符号付き整数で、接続ごとの1から始まる通番を格納する。通常要求には取引のbegin・commit等も含め、接続を閉じた時点で通番をリセットする。

受信ループは取消しを要求キューの外で実行し、その後に完了確認用の制御項目をキューへ入れる。実行中の要求は接続寿命と結合した専用CancellationTokenを使う。実行・取消・保存点の後始末を終え、制御項目へ進んだ時点でCancelled応答を返す。既に完了した要求への取消しも同じ応答で確定する。通番で後続要求への誤伝播を防ぐ。

クライアントは途中終了時、取消フレームを送り、残った行や終端を読み流して対応するCancelledを待つ。その間は接続枠を保持する。後始末には利用者が取り消したトークンを使わず、15秒の上限を設ける。応答を確認できない通信・プロトコル障害では接続を破棄する。明示取引は取消完了を確認できた場合、既存の保存点規則に従って次の操作へ継続する。

実行中の要求の取消トークンと、送信中フレームの接続寿命を分ける。フレームは接続寿命のトークンで完結させ、次のフレームへ進む前に要求の取消を確認する。クライアントは残りの行を4KiBの固定領域で読み流す。型復元の失敗や不正なフレームでは、既存の接続破棄を引き継ぐ。取消送信の非同期タスクも、期限・接続の後始末を終える前に回収する。

## 影響範囲と検証

NativeProtocol、NativeQueryClientとNativeQueryServerの受信・要求取消を変更する。通常要求、認証、要求枠、既存の確定済み更新の扱いを維持する。所有型公開APIと生成戻り型の接続はこの基盤の後に進める。

既存のNativeTransportフィクスチャで、途中列挙、実行中取消、完了済みとの競合、同一ソケットの再利用、明示取引、取消フレームの上限・不正通番を確認する。生成済みグラフRPCの正常系・失敗時取消を回帰対象とする。Debug・Releaseの対象試験を実行し、TLS・IPC・配布物の統合受入は対応する枝で追跡する。

## 合意状態

合意済みの途中解放・終了確認・接続再利用を、既存の逐次要求プロトコルへ実装する設計。保存形式の変更はない。

## 実行結果

取消プロトコル導入時の候補のDebug・Releaseで、新規15件と既存53件の計68件ずつが成功した。クライアント・Gatewayと既存の結果実体化ライブラリの両構成ビルドは警告・エラー0件。通常のループバックTCP、生成済みグラフRPC、更新・保存点、接続ポリシー、プール、不正フレームを対象とした。

- 20回の途中列挙で同じNetworkStreamを保持し、後続の値99を毎回受信した。実行中の待機を取り消したケースでは、列挙の後始末終了後に同じ接続で値3を受信した。
- 8MiBの有効な行を受信し、2行目の送信開始後に破棄した。列挙の後始末が終わり、同じ接続で値7を受信した。
- 生成済みのWriteを途中で読み終えた場合、明示取引が継続し、件数1を参照して確定できた。共有・循環参照、数値・日時の正規化も既存RPC試験で確認した。
- 実行中に行を追加して待つモジュールを取り消した。Gatewayの有無と明示取引の有無の4組で、取消した文の行を除去し、明示取引に先行する行1件を保持した。同じ接続で参照・確定へ進んだ。
- 未受信の通番、0、過大な制御フレームを拒否した。通常の切断では、サーバーを停止せず再接続し、未確定行が見えず、同じキーへ書き直して確定できた。
- 応答の通番不一致、長さ不正、確認前の切断の3組では元の接続を破棄し、新しい接続で値9を受信した。取消送信タスクの回収を含む後始末の後に次の実行枠へ進んだ。

変更前DLLへ新しい2試験を通し、途中終了と実行中取消で接続が破棄される失敗を再現した。最初の回帰では完了済み問い合わせの取消トークンを接続終了の通知として保持した1試験が両構成で失敗した。要求単位になったトークンの寿命を文書化し、この試験は稼働サーバーへの再接続・未確定行の取消・同一キーの再取得を外部から確認するよう更新した。元の失敗結果も保持する。

## 取消確認の期限と途中切断

所有型の最初の行を受け取ってから、制御応答を再現するループバックTCPの試験で4ケースを追加した。製品の実装変更は不要で、Debug・Releaseとも4件が成功した。期限には実際の15秒を使った。

| 条件 | Debugの解放待ち | Releaseの解放待ち |
| --- | --- | --- |
| 確認応答なし | 15.014秒 | 15.013秒 |
| 確認ヘッダーの3バイトで切断 | 0.001秒 | 0.002秒 |
| 確認本文の3バイトで切断 | 0.001秒未満 | 0.001秒未満 |
| 確認本文の3バイトで停止 | 15.006秒 | 15.008秒 |

全ケースで、反復DisposeAsyncが同じ終了処理を待ち、元の接続が破棄され、同じクライアントの次要求が新しい接続で値9を受信した。レコード用のメモリ予約は0へ戻り、終了後の再列挙を拒否した。合格範囲はクライアント側の接続・列挙・レコード予算の回収とし、サーバー側のDB処理終了はW18-STREAM-ENVへ引き継ぐ。

製品ソース・依存DLLを照合して、所有型の既存RPC試験と生成器試験を再利用した。証跡は `F:\Seamless\native-ack-boundary-20261108` のDebug-tests・Release-testsのTRXとreceipt.json、verification.json。Consoleの実測値はTRXの全体StdOutへ保存される。

## TLSと別PIDの生成クライアント

Windowsの正式NativeQueryServer／NativeQueryClientをTLSで接続し、生成済みRecordQueriesClientの所有型を確認した。Gatewayの有無と明示取引の有無の4組で、生成集合の部分読取、処理中の所有型解放、反復Dispose、要求取消、同じSslStreamの継続使用が成功した。中止した文の追加を取り消し、先行する1行を保持して確定した。共有・循環参照と正規化を通常の生成行でも照合し、クライアントとサーバーのレコード予算が0へ戻った。

信頼する証明書の指定がない接続とホスト名不一致の接続を拒否し、拒否した書込みではモジュールを呼び出さず、正常なTLS接続から件数0を確認した。試験用の秘密鍵は既存HTTPS試験と同じSchannel互換の読み込み方法を使い、各試験後の削除も検査する。

別PIDのC#実行入口は、同じテストアセンブリに生成した正式クライアントを利用する。Gatewayの有無の2組で、親側が実行中の追加を観測した後、子へ所有型解放を指示した。子では自動取引の1行と明示取引の1行を残し、例外を起こした文と実行中に取り消した文の追加を除外した。同じ暗号化接続で件数2を参照・確定し、子の終了後に親の別接続でも2行を確認した。双方のPID、子の作成時刻、CPU affinity 0xFF、レコード予算0を保存する。

新規8ケースと既存36ケースの計44件がDebug・Releaseで成功した。その後、CPU affinity取得を対応OSの分岐内へ置き、CA1416警告を解消して、影響する別PIDの2件を両構成で再確認した。他42件と変更のない製品DLL・生成器の証拠を再利用する。

最初の試験はinit専用RecordBudgetへの代入でコンパイルに失敗したため、公開ファクトリーが使用する既定予算の観測へ修正した。次の試験は一時秘密鍵をSchannelから参照できずTLSハンドシェイクで失敗した。鍵の読み込み方法を既存試験へ揃えた後の成功と区別し、初回の記録も保存する。製品実装の変更は行っていない。

## TLSクライアントのレコード資源指定

TLSの公開ファクトリーは既存の署名を保持し、host・port・trustedRoot・recordBudget・任意のrecordLimitsを受けるオーバーロードを追加する。認証付きTLSも同じ指定を受ける。接続プールの既存OptionsにもRecordBudgetとRecordLimitsを追加し、貸出しごとにクライアントへ引き継ぐ。既定値は従来の共有予算と型制限とする。

指定した予算は呼出し元が所有し、既存の引数構築・送受信・復元の会計へ接続する。制限値の検査は既存CheckForNativeを使い、明示したnull予算と不正な制限は接続前に拒否する。init専用プロパティによる既存の直接構築も引き継ぐ。認証プロトコルとwire形式は同じものを使う。

```csharp
var budget=parentBudget.CreateChild(16L<<20,0);
var limits=new RecordGraphValidationLimits{MaximumDepth=32};
await using var connection=NativeQueryClient.ForTls("localhost",14335,certificate,budget,limits);

using var pool=NativeConnectionPool.ForTls("localhost",14335,new(){
    MaximumConnections=4,
    RecordBudget=budget,
    RecordLimits=limits
},certificate);
```

追加する確認は旧署名の存在、TLS・認証付きTLS・両プールでの設定保持、親予算不足時の未送信と返却・再試行、型制限違反とプール再貸出しとする。Windowsの実TLSを近接入口とし、認証付き実通信は既存の認証試験へ接続する。

新規3ケースの近接試験がDebug・Releaseで成功し、既存グラフRPC、所有型、TLS・別PID、接続プールと接続方針を含む各64件が成功した。新旧の認証付きTLSファクトリーでも、実接続、認証済み主体の保持、権限変更による拒否と再許可の各2件が成功した。Clientの両構成ビルドと最終テストビルドは警告・エラー0件。実装前の署名・プロパティ不足のコンパイル失敗を保存し、テストの同名型には明示的なエイリアスを付けた。

生成クライアントの所有型と既存NativeResultによる実体化は [結果所有](20261108-native-result-ownership.md) へ接続した。認証付きTLS・正式業務RPCのIPC、共通ホスト・Linux・配布物、サーバー側の停止・資源上限を含む統合はW09・W11・W18の対応枝で確認する。現在、正式NativeQueryClient／NativeQueryServerはTCP／TLSを持ち、OS所有者のIPC入口は管理RPCに実装されている。管理IPCの合格範囲と正式業務RPCのIPC実装を区別する。
