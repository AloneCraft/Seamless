# 管理コンパイラーの参照メタデータ共有

## 背景と現状の観察

W11のメモリ不足を切り分ける。SourceEditor.PlatformReferencesは呼び出すたびにTPAの各DLLへMetadataReferenceを生成する。RuntimeCompilerはその結果からパスを取り出し、同じDLLの参照をさらに生成している。Benchmark.Dynamic.WorkerのMetadataReferenceProviderでは、不変スナップショットを保持して再利用する実装がある。

この重複と、既知のWSLでのメモリ不足との因果関係は測定対象とする。共有化の成立と、DB作成・コンパイル時の資源使用量を別々に確認する。

## 引き継ぐ契約と目的

ホストは同じビルドの共通DLLで動作し、ホスト更新時に再起動する。DB固有の依存DLLは取り込んだイメージからコンパイラーへ渡す。SourceEditorの既定参照と、呼出し元が明示した参照の二経路を使う。公開APIが返す配列は呼出し元が所有する。

目的は、実行中ホストの不変なTPAメタデータを一組に集約して、反復コンパイル時の重複確保を抑えることとする。

## 設計

SourceEditor内でTPA参照配列をプロセス単位に保持する。初回生成は排他し、生成中の例外では次回の生成を可能にする。PlatformReferencesは毎回配列のコピーを返し、配列の中にある不変のMetadataReferenceを共有する。

RuntimeCompilerはこの参照を直接リストへ取り込み、追加のホストアセンブリだけをパスで重複判定して追加する。ソースが宣言した参照のSHA照合と、DB固有の依存イメージによる参照解決を通す。

## 影響範囲と移行

SourceEditorの既定参照作成、RuntimeCompilerの参照リスト作成、対応する近接試験を対象にする。ビルドしたホストで切り替える。配列の所有と参照の不変性を回帰条件にする。

## 確認方法

反復取得で同じメタデータを共有し、片方の配列の書換えが他方へ影響しないことを修正前後で照合する。既存のC#解析・生成・実行・禁止API検査を回帰対象とする。メモリ上限付きの隔離環境で通常のDB作成と反復コンパイルを実行し、使用量・失敗・再試行を記録する。メタデータ共有の試験だけでW11全体の解消を判定しない。

## 合意状態

利用者が指定したW01〜W21の全残件実装と、W11の資源・メモリ不足対応に基づく内部の具体化。TPAは実行中ホストの参照として共有し、DB固有DLLは依存イメージの経路で扱う。

## 確認した範囲

配列の所有・参照共有の追加試験は修正前に失敗した。修正後はDebugのソース解析・破棄17件、実コンパイルと子プロセスを含むNative関連2件が成功した。Linux管理・IPC・認証付きTLSの101件全体がDebugで成功し、Releaseではこの101件とソース解析・破棄17件の合計118件が成功した。

別々の新規プロセスで、177個の同じTPA参照と同じソースの20回コンパイルを比較した。参照を毎回生成した場合は約3365ms、割当141778160バイト、専有メモリの観測ピーク628215808バイトだった。共有した場合は約1136ms、割当23903888バイト、専有メモリの観測ピーク220868608バイトだった。プローブは`F:/Seamless/linux-desktop-recovery-20261109/metadata-probe`、実行記録は`metadata-measure`に置く。

同じ4GBのUbuntuで、専用Linux Chromeから新規DBを作り、SDK成果物の検査・適用・行保存を行った。試験用サーバーのcgroup観測ピークは425316352バイト、スワップ使用は0で、観測時のUbuntu利用可能メモリは約2GBだった。DB追加、サーバー再起動、継続編集後の再適用でも行を保持した。[GUIの確認範囲](20261109-linux-manager-acceptance.md)

この測定は元のOOMとブラウザー数・並行試験条件が異なる。参照の重複削減、コンパイルの測定、今回のGUI正常系の成功を分け、W11の総予算・全障害条件・元の並行条件の受入を継続する。
