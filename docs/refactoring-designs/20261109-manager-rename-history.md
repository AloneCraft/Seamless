# DB名変更時の履歴走査

## 現在の契約

DBの内部IDを持つ履歴は名前変更後も同じDBへ結び付く。旧形式の履歴で内部IDがないものは、名前変更の管理取引内で内部IDを付ける。表示用の旧DB名と履歴の順序・内容を保持する。

ManagementStore.Historyはカーソルから順に読み進める。名前変更の処理は100件ずつ更新し、次のカーソルへ進む。取消対応は既存の3引数の公開署名を保持し、内部の4引数経路で各行の走査前と結果返却前に取消を検査する。名前変更はこの内部経路を使う。

## 観測した上限

内部IDのない履歴1万件を100件ずつの取引で準備すると、準備は成功し、実際の名前変更取引が4MiBのWALフレーム上限で失敗した。予算不足とフレーム上限を区別する。走査はカーソルを進める線形処理であり、繰り返し先頭から走査する原因ではない。

旧形式5での失敗証跡は`F:/Seamless/linux-desktop-recovery-20261109/rename-history-observe4`。利用者が既存の分割WAL基盤の利用を選択し、管理形式6とバックアップ付き明示移行を接続した。`DatabaseRenameHistory.RenameRetainsTenThousandLegacyHistoryEntriesAcrossRestart`は形式5で準備した1万件を形式6へ実移行してから名前変更を実行する回帰試験となった。Windows Debugでは成功し、名前変更本体は約586ms、割当て約83.4MB、資源会計のピーク約122.1MBだった。移行を含む当該試験全体は約59秒。証跡は`prepared-wal-management-debug/Debug/manager.trx`。Windows Releaseでも約355msで名前変更が成功し、管理50件を確認した。Linux Debugでも履歴1万件の移行・名前変更・再送・再起動が成功した。Linux Releaseの確認を継続する。[分割WALの境界](20261109-management-prepared-wal.md)

## 確認と実装順

隔離した管理領域に内部IDのない履歴1万件を作り、名前変更、履歴の所属と内容、同じ操作IDの再送、再起動後の保持を確認する。経過時間・割り当て量・既存予算の測定値を記録する。測定結果と資源予算の上限到達試験を分ける。

履歴走査へ取消トークンを渡し、行を探している途中でも取消を観測できるようにした。既存の3引数Historyの公開署名を保持し、名前変更から追加の取消対応経路へ接続した。

取消対応の近接試験はLinux Debug・Release各14件成功した。該当行がない走査の10件目で取消し、それ以上述語を呼び出さないこと、既存の3引数経路で全履歴を引き続き取得できること、終端カーソルでも事前取消を拒否することを確認した。既存の名前変更・権限・取引取消・再起動の試験を含む。証跡は`rename-history-cancellation2/Debug/rename.trx`と`Release/rename.trx`。1万件のWAL上限の失敗はこの成功へ含めない。

W01〜W21の全残件を進める指示と、W01-HISTORY・W11の受入条件を適用する。
