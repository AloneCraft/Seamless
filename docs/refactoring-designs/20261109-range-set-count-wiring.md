# Range集合の件数計算の接続

## 観察

既存の範囲差集合・積集合には区間から件数を計算する生成メンバーがあるが、Countの通常入口から呼ばれていない。和集合の専用入口は右入力が一つのケースを候補から除外している。既存の回帰試験では生成メンバーの呼び出しが欠け、最大件数の和集合で列挙が続いていた。

## 修正

Count・LongCountの直接展開から、既存の区間件数式を選ぶ。入力範囲は既存の処理で左から順に一度ずつ評価・検証する。Countのintへの変換はcheckedとし、LongCountの結果型を維持する。Anchorを含む経路の従来の評価契約を保持する。和集合専用入口は一つ以上の右入力を扱う。

最適化後の空パイプラインへ戻す経路も、述語なしの件数取得では既存のCount断片へ接続する。既存のテストで固定していた和集合の実装名は、採用した直接区間計算のメンバーと生成番号を許容する照合へ揃える。結果、checkedの型、入力検証順の確認を維持する。

前段の正規化は連続Unionを、右入力のConcatと外側Unionへ変換する。最上位がUnionであることを確認してから、内側のUnion・Concatを左から順に収集する。最上位がConcatの場合は重複を含む列の件数を維持する。拡張形式・静的形式を扱い、objectへ返すCountでもintとしての結果型を保持する。

## 検証と合意

W01〜W21の全残件実装指示と既存の最適化契約を適用する。CoreCarrierOptimizationTestsの範囲の差・積・和、最大件数・桁あふれ、例外時の後続引数の未評価、引数順序の既存試験を使用する。修正前の固定旧生成器と現候補の両方の失敗を証拠とする。

Windows Debugの既存4件と新規4件が成功した。新規入力はUnion内部のConcat、Union外のConcatの重複、静的なCount・Union、objectへ返すintを扱う。静的形式は対象検出と文・式本体の候補選択にも同じ判定を接続した。range-count-wiring-boundary3へTRXと生成C#を保存した。

共有する生成・ランタイムの52契約はWindows Debug・Release各52件で成功した。同じAnyCPU候補をUbuntuでも実行し、両構成各52件が成功した。証拠はrange-count-regressionとrange-count-linux-regressionへ保存した。Linux用配布物のビルド・全コーパスと残る既存最適化は別の受入として継続する。
