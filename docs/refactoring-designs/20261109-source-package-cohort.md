# サーバーと専用C#プロジェクトのパッケージ対応

## 背景

W04・W13の通常配置から、専用C#プロジェクトの保存・SDKビルド・成果物の取り込みへ接続する。利用者のパッケージ参照と同一ビルド要求、1〜21の残項目実装の承認範囲で進める。

## 現状の観察

- 固定Linux配置のsourceCreateを未使用の出力先で呼ぶとPackageFeedで失敗した。出力先は未作成だった。証跡はsource-feed-default-repro.jsonとsource-feed-default-repro-run。
- Publish.ps1はサーバーとWeb資産を作るが、専用プロジェクト用のpackagesを作らない。
- SourceWorkspace.CreatePackageProjectは既定0.0.0を参照する。過去の実SDK確認は専用フィードと別キャッシュを使用していた。
- 依存DLLの照合・取り込み・既存DBへの明示適用は既存の共通機能を使用できる。

## 過去設計から引き継ぐ仕様

[フィード解決](20261109-source-package-feed.md)の探索順とXMLエスケープを維持する。DB保存、プロジェクト保存、SDKビルド、成果物の検査と明示適用を独立した操作として扱う。既存プロジェクトの編集は現在のソース同期へ接続する。

## 目的

配布物の通常起動から新規専用プロジェクトを保存し、既存のNuGetキャッシュがある環境でも、サーバーに対応するDLLでビルド・検査・取り込みできるようにする。

## 非目的

既存DBの保存契約、既存プロジェクトの参照設定、SDKビルドと明示適用の境界を維持する。

## 提案設計

1. サーバーの配布処理で、専用プロジェクトが使う12パッケージを同じ構成のビルド出力から作る。既存Pack-Products.ps1へ再ビルドを省く指定を追加して再利用する。
2. パッケージのコード・プロファイル等の内容と依存メタデータから識別を作り、0.0.0-build.hに32桁のハッシュを付けた開発版を使う。全SHA-256はマニフェストへ残す。この版形式は実装判断とする。
3. パッケージ内のSeamless依存と新規プロジェクトの参照を同じ版へ固定する。旧0.0.0キャッシュが推移依存の最小版を満たすことも防ぐ。
4. packages/source-packages.jsonへ形式1、版、一式の識別、DLLとパッケージのSHA-256を記録する。作成と照合を終えてからpackagesを公開する。
5. SourceWorkspaceは版の省略時にマニフェストを読み、サーバー側にある対応DLLのハッシュを確認してからプロジェクトを書き出す。無効・不一致は出力先作成前にPackageFeedで拒否する。
6. 明示したpackageVersionと、マニフェストを持たない既存フィードの0.0.0は既存の呼出し契約を維持する。既存バイナリのメソッド署名も保持する。

## 影響範囲

SourceWorkspaceの新規生成、管理サーバーのpublish、既存のパッケージ作成スクリプト、専用プロジェクトの検証へ限定する。新しいプロジェクトのパッケージ版はマニフェストに従う。

## 移行手順

新しい配布物へ対応フィードを同梱する。現在の稼働配置は固定したまま別の出力を作り、近接試験と実SDKの照合後に切り替える。既存の専用プロジェクトは現在の明示編集の契約を使用する。

## テスト計画

- 自動版選択、4参照の固定版、明示版と旧フィードの互換を確認する。
- DLL不一致・不正マニフェスト・不正な版で、出力先が作られないことを確認する。
- パッケージ内の依存閉包・固定版・DLLハッシュを検査する。
- 旧0.0.0を持つキャッシュを使い、新版のSDKビルドと成果物照合を確認する。
- 通常配置のGUIから新規保存・ビルド成果物の取り込み・明示適用へ進み、再起動後の定義と行を確認する。

## リスクと対策

ビルド出力とパッケージの対応はDLLハッシュで検査する。未完成の一式は公開前の別ディレクトリに作る。既存DLL検査を実行境界として維持する。SDKやOSの違いは実行条件と証跡へ対応付ける。

## 未決事項

正式リリースの公開版番号は今回の開発版識別と分けて扱う。

## 合意状態

パッケージ参照、同一ビルド、通常配布の動作確認と全残項目実装の既存承認に従う。実装状況と試験結果を同文書へ追記する。
