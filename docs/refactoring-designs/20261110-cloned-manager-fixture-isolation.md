# Linuxの管理DBコピーを使う検証の分離条件

## 必須の境界

DBコピーは保存されたInstanceIdも保持する。Linuxの所有者IPC名はInstanceIdから決まり、実ソケットの場所は`LocalServerConnection.PipeEndpointFor`が`Path.GetTempPath()`と`CoreFxPipe_<pipeName>`から生成する。DB・HTTPポート・systemd scopeだけを分けても、同じInstanceIdとTMPDIRを使う同時起動は分離されない。DBごとのファイルロックでは、このIPC名前空間の衝突を防げない。

コピー検証では、次の条件を起動前に満たす。

- クローンごとに新しい所有者専用TMPDIRを作り、権限を0700にする。検証サーバー、owner CLI、子プロセスへ同じTMPDIRを明示する。利用中サーバーや別のクローンのTMPDIRを再利用しない。
- Unixソケットのパス長も検査する。例えば`/home/kazuh/.cache/Seamless/t/<8桁のnonce>`のような短い専用ディレクトリを使用し、生成したendpointのUTF-8長がOS上限内にあることを確認する。
- ソケットの予定絶対パスを取得し、利用中ホストの実`UnixPipePath`と異なること、予定先が既存ソケットでないことを確認する。PIDが不変という確認に加え、IPC endpointの所在と所有者も保護対象にする。
- 所有者接続ではコピー先の接続ファイルのPID・生成時刻・InstanceId・UnixPipePathを照合する。起動後はそのサーバーの公開メタデータとHTTP起点がコピー先に対応することも確認する。
- 停止時は自分のstop-fileと実終了シグナルだけを使う。別ホストのソケット、接続ファイル、プロセスを削除・停止しない。終了後にも保護対象のIPC接続が利用できることを確認する。

共有TMPDIRで実行した既存のコピー検証を再開してはならない。新しい専用TMPDIRと新しい実行記録を用意してから起動する。通常利用中のサーバーのTMPDIRやInstanceIdを変更して分離を後付けしない。

## 確認された欠陥と受入証拠の範囲

2026年11月10日の列ドラッグ受入では、固定Managerと隔離DBコピーのInstanceId・pipeName・TMPDIRが同じだった。隔離ホスト終了後、固定ManagerのPIDは生存したままIPCのpathnameが失われていることを確認した。稼働PIDの一致だけを根拠に非干渉とした検証条件が不十分だった。列ドラッグのDOM順・未保管状態の確認は成功しているが、その検証をIPC非干渉の合格としては扱わない。

記録は`F:/Seamless/manager-plan-demo-20261110/candidate04/endpoint-collision-readonly.json`と`process-instance-audit.json`にある。監査時点では同じInstanceIdの生存ホストは固定Manager一件のみで、隔離した全ホストの実終了を確認した。固定Managerの復旧は利用者の保存確認と再起動承認に従って行う。

現行サーバーに、同じInstanceIdとソケットパスを使う別DBホストの起動を事前拒否する保証は確認できていない。この製品側の重複起動防護と、専用TMPDIRによる検証ハーネスの分離は別の条件として扱う。
