# ソース宣言に固定する表示用ID

## 合意と境界

2026年11月10日にCore単位の実装を承認された。スキーマ・テーブル・列の同一性を名前から推測せず、宣言に付く明示UUIDを正本とする。既存定義にはIDを自動追加しない。付与は下書きソースを返す明示操作とし、既存の検証・ビルド・明示適用を通った公開定義だけが公開カタログのIDとなる。通常起動でDBやソースを移行しない。

マーカーは宣言の直前のC#コメント`/* seamless-id:<UUIDのN形式> */`とする。スキーマは手書きのschema propertyまたは生成元namespace、テーブルは手書きのtable propertyまたは生成元record、列はrow型のpropertyまたはpositional parameterへ付ける。同じ宣言の名前変更ではコメントを保持する。コピーしたUUIDの重複は拒否する。削除・再作成は新UUIDであり、マーカー喪失を名前や型の一致で補完しない。

カタログの既存`Id`・名前・SQL参照は保持し、optionalな`StableId`を追加する。IDは表示用であり、物理表の保存キーやデータ移行の対応へ流用しない。既存の明示Migration契約がデータ移行の正本である。ソースコメントは既存SourceSnapshotの一部としてWAL・成果物対応・競合検査へ入るため、管理保存形式6/7の変更は行わない。

## 今回の実装単位

まず、明示ID付与・マーカー検証・宣言からカタログへの伝搬を実装し、生成元宣言と手書きContainerの双方を確認する。旧定義は`StableId=null`で従来どおり扱う。ブラウザーの旧Format5は同じ定義版・成果物に限定した復元を維持する。

GUIにはDBメニューの「その他」から「表示用IDを下書きへ付与」を追加する。コマンド実行で現在の下書きへ直接付与し、既存の保管・変更確認・明示適用へ進む。対象DBと下書き状態、宣言の自己申告性、別版への復元が未接続であることを画面に表示する。

スキーマ改名のC#参照リファクタ、別版への文書復元、マーカーを扱えない外部宣言と名前変更・所属移動のUI受入は後段である。これらが接続されるまで、名前変更をまたぐ文書復元を実装済みとして表示しない。稼働中の固定URLサービス・デモ・利用者DBは変更しない。

## 検証条件

- 旧定義を読んでもソースもIDも変わらない。
- 明示付与後の再付与が同じUUIDを保持し、C#がコンパイルできる。
- 明示した宣言の名前変更・コメント保持と、コピーによる重複拒否を確認する。
- マーカー喪失・不正形式・不適切な配置を黙って補完しない。
- 現行DB生成器による生成・C#コンパイル後のNativeカタログで、表・列のIDが元宣言と一致する。
- 同じ宣言を複数scopeで使う場合は曖昧と判定する。親schemaと合成したIDへ置き換えず、明示付与をUnsupportedで拒否する。既存マーカーの読取では該当IDを提供せず、`AmbiguousDeclaration`を返す。

## 成功したデータコピーに結び付く別版の対応

2026年11月10日に次の限定単位を承認された。以下は実装準備中の設計であり、現在のブラウザーFormat5に跨版復元を許可するものではない。

実装上、`TypedMigration.Plan`が実行する表・列対応を決め、`TypedMigration.Copy`が移行先世代へコピーする。`NativeRuntime.Publish`はコピー後に移行先を閉じて再度開き、依存問い合わせを準備してから管理サービスの確定コールバックへ進む。管理サービスは既存の一つの`store.Write`内で`version`・`active`・成功した`operation`を確定する。この境界を利用する。

- コピーを生成する同じPlanから移行元・先の表と直接代入列を採取し、コピー成功後だけ結果として返す。移行定義の名前やUUIDだけから、後から成功したコピーを推定しない。列の対応は行コンストラクターへ実際に渡す値に限定し、式変換・既定値・新規列には提供しない。
- 前後両方の宣言に同じ有効なIDがあり、実際のコピー元・先と一致するTableだけを証明候補とする。列もその表の直接コピー対応と一致する場合に限定する。共有宣言・不正マーカー・片側の欠落は対応を提供しない。`NewTables`で新規と宣言した表も除外する。
- `DefinitionVersion`へ省略可能なコピー受領証を追加する。前後の定義ID・版・Definition hash・成果物hash、同じ確定取引のOperationId、証明対象の表と列を結び付ける。Definition本体と成果物manifestのhash対象は変更しない。既存の管理保存形式6/7とWALを利用し、起動時移行を追加しない。
- コピー成功だけでは受領証を公開しない。公開版と同じ取引で保存されて初めて有効とする。コピー・制約・取消・再開放・公開競合・管理取引に失敗した場合は、新しい公開版と受領証の両方を確定しない。
- メタデータ専用の解決APIは現在の利用者を再取得し、View権限と要求した現在版・成果物を検査する。要求元の保存版・成果物・元ObjectId・元StableIdから隣接する受領証を上限付きでたどり、現在カタログの対象と照合する。生ソースや受領証中の自由文は返さない。最初の単位はキャッシュを用いない。
- 旧版の受領証欠落、監査導入の別経路、定義の削除・再作成、途中版の欠落、失敗したOperation、ID転用、スキーマ・ビュー・関数・式変換列は未証明とする。未知形式や容量上限に達した証明を黙って部分採用しない。表や列に同じUUIDがあるだけの復元は許可しない。

近接試験は、明示Migrationによる表／列改名と実行後の既存行保持、無変更版、式変換列の除外、ID転用・欠落・重複、途中削除、新規指定、コピー例外／取消、公開CAS失敗、管理取引取消、再起動後の証明、権限失効、要求版／成果物不一致、旧JSONの同形往復と管理形式6/7を対象とする。新規の隔離DBだけを利用する。サーバー契約と各アダプターの確認後にブラウザーの保存・復元へ接続する。
