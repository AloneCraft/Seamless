# 並行トランザクションと FLinq の接続設計案

## 背景

2026-11-02 の利用者要求。読み取りと更新、および複数の更新トランザクションを並行実行する。競合制御には楽観的ロックを採用する。FLinq の既存の高速化を活用する。利用者から、Tsavorite の前レコードへのリンクを利用し、必要に応じてその情報をコレクションから公開する案が提示された。

## 現状の観察

- `Seamless.Transactions/TransactionCoordinator.cs` は既定のExclusiveで取引全体を調停し、明示したOptimisticでは版付きdomainへ接続する。独立した取引の読取り・変更収集を並行して進め、共通層が検証・WAL・公開を管理する。実装範囲と検証結果は [実装設計書](DeferredMvccImplementation.md) を参照する。
- `Seamless.Collections.Tsavorite/SessionFunctions/SetValue.cs` は `InPlaceUpdater` による上書きを許す。その場で更新した値の旧版は、前レコードのリンクだけでは復元できない。
- `Seamless.Collections.Tsavorite/Stores/CollectionStore.cs` は `RevivificationSettings.InChainOnly` を使用する。これは領域の再利用を全面的に無効にする設定ではない。
- `Seamless.Collections.Tsavorite/SessionFunctions/ContainsDelete.cs` は RMW の expire を使用する。既存の削除をそのまま MVCC の削除版として扱う設計にはしない。
- `Seamless.Collections.Tsavorite/Collections/Collection.cs` の読み取りは値を返し、FLinq 用の走査は `IterateValuesCore` / `IterateValuesAdapter` を通る。現在の走査はエンジンの tombstone を除外する。
- 現在の参照パッケージは `Microsoft.Garnet` 2.2.5。初期調査の2.2.1の `Tsavorite.core.xml` で `ReadAtAddress`、`RecordMetadata.Address`、`ISourceLogRecord.Info`、`RMWInfo.PreserveCopyUpdaterSourceRecord`、`RevivificationSettings.None` の存在と説明を確認した。更新時の確認は[実装設計書](DeferredMvccImplementation.md)のGarnet更新欄を参照する。
- 同 XML による `ReadInfo.Version` は Tsavorite の実行コンテキスト版であり、Seamless のトランザクション確定番号として扱わない。
- `RecordInfo.PreviousAddress` はハッシュ連鎖のリンクであり、同一キーの直前版だけを指す契約ではない。Microsoft の公式資料 https://microsoft.github.io/garnet/docs/dev/tsavorite/readcache を参照。
- 初期調査のローカルGarnetソースはcommit `8fe430922bea7f8a5106ff7578bb515f563cbbfe`で、当時の2.2.1のnuspecは `b0255a31de95b1e903ee187feb59ceb04819a639`を示した。現在の2.2.5は `8d007138208ce030eb10a50c80e636b1678b83e4`。既存ローカルcheckoutは更新せず、対応する公式ソースを隔離取得した。履歴読み取りの実動作は採用パッケージによる試験が必要。

## 過去設計から引き継ぐ仕様

`20261029-generic-transactions-tpc-c12.md` と同受入台帳を参照した。Serializable、型付き明示ビュー、親子スコープの契約、WAL 永続化前の成功応答禁止、取引 ID による結果照会、Unknown を中止とみなさない契約を維持する。WAL 永続化後の反映失敗は Committed を保持し、復旧を必要とする。要求の自動再実行と既存データの自動変換は行わない。

本案は、初版の「汎用 DB 全体排他」を将来置き換える提案である。既存設計の実装・受入結果を、本案の並行実行や MVCC の合格証拠へ読み替えない。

## 目的

- 独立した取引の読み取り・計算・変更収集を並行して進める。
- 読み取り中の版を保持し、複数行・複数表を一貫した時点で読めるようにする。
- 楽観的検証で Serializable を守る。書き込み競合だけでなく、読み取り依存、存在しなかったキー、検索範囲への挿入も扱う。
- FLinq の具体型、ネイティブ走査、演算融合、早期終了を活用する。
- 取引結果と障害の判定を共通層へ集約する。

## 非目的

分散 DB 化、既存領域の自動変換、全クエリの無変更・無負荷での並列化、業務処理の自動再実行は対象にしない。長期間の履歴照会 API と運転中のスナップショット保持は別の契約とする。

## 提案設計

### 責務と所有権

| 層 | 責務 |
|---|---|
| `Seamless.Transactions` | 取引 ID、読み取り版、依存関係、競合検証、確定順序、WAL、確定結果、共通の障害状態、履歴保持の下限 |
| `Seamless.Transactions.Collections` | 型付き変更集合、版の可視性、主表と二次索引の整合、保存先の履歴機能との接続 |
| `Seamless.Collections.Tsavorite` | 保持されたレコードの読み取り、ヘッダー情報の一貫した取得、論理アドレス、履歴保持中の再利用・切り詰め制御、ネイティブ走査 |
| Persisted の私有作業領域 | セッション・取引・クエリ専用の退避を管理する。DB 本体の保存先・共有業務表の MVCC 参加先には追加しない |
| FLinq 生成器 | 取引に見える行を供給する具体型に対する演算融合。取引の確定や WAL の管理はしない |
| Gateway / TPC / アプリ | 共通取引への接続、業務判断、外部通知。独自のコミット判定や無条件の再実行を追加しない |

WAL と確定チェックポイントは再起動時の正本とする。運転中の可視性は、全参加表・索引へ設置済みの確定状態から公開する。論理アドレスは保存先内部の場所であり、取引 ID や論理的な版そのものにはしない。

### Tsavorite の連鎖の利用候補

第一候補は、履歴を保持する専用経路で `PreviousAddress` の連鎖を利用する案。キーが異なるレコードは読み飛ばし、同一キーの可視な版を探す。リンク自体を MVCC 専用ポインタへ書き換えない。

履歴保持経路では、必要な旧値をその場で上書きしない。RMW のコピー更新で `PreserveCopyUpdaterSourceRecord` を使う案を採用パッケージで検証する。初期試作では再利用を無効にする保守的な設定を用い、保持中のレコードを通常のコンパクションで失わないようにする。設定一つで履歴保証が完成したとはみなさない。

削除は、旧版と分離した論理的な削除版として表現する。古いスナップショットから必要な行と、その行へ到達するための探索起点を残す。削除済みキーが通常の最新値走査から消える問題を、走査設計で明示的に扱う。

別案は、同一キーの旧版への独自リンクを保存する方式、および別の履歴ストアへ旧値を保存する方式。前者は探索の衝突コストを減らせるが保存形式と回収が増え、後者は保存先を共通化しやすいがコピーと二重管理を増やす。第一候補の試作結果で比較する。

### 更新方式を選ぶ判断基準

利用者との合意により、並行方式の製品実装は遅延更新＋MVCCに絞り、即時更新＋MVCCは比較実験として残す。以下は方式を比較した観点であり、両方式を製品として実装する計画ではない。

共有ログへ未確定版を先に追記する即時更新方式と、取引固有の変更集合へ保持する遅延更新方式を、履歴リンクの利用可否と走査コストを含めて比較した。楽観的ロックは両方へ適用可能であり、履歴リンクも両方の MVCC に利用できる。製品実装は合意した遅延方式に絞り、リンクの利用可能性だけを即時方式の採用理由にはしない。

| 観測結果 | 方式選択への意味 |
|---|---|
| 旧版を保持して低コストで参照でき、取引対応のネイティブ走査も効率的 | 即時方式が私有変更集合との走査合成を減らせる可能性を、比較実験で検証する。製品の採用方式とは区別する |
| 点検索の履歴だけ読めるが、走査の版解決が高コスト | 遅延更新との実測比較を継続する。既存の FLinq 走査をそのまま MVCC とみなさない |
| 保持・削除・回収により履歴参照を保証できない | 既存リンクに依存する即時更新案は採用しない。遅延更新でも並行読み取り用の旧版保持は別途必要 |

即時更新案は、現在の TPC の「本体を変更し、Action の undo で書き戻す」処理の流用とは区別する。旧値を壊さず、取引 ID と可視性情報を持つ未確定版を共有ログへ追記し、検証・WAL 永続化・公開を共通層で制御する。正常中止の未確定版は不可視とし、必要な寿命を満たしてから回収する設計候補である。

2026-11-02 の下記最小試験では履歴リンクの利用が成立した。その後の [更新方式比較試験](TransactionModesAcceptance.md) と利用者の判断により、製品実装の方式は遅延更新＋MVCCに絞った。性能の未完了条件と製品への接続後の安全性は引き続き検証する。

### 採用パッケージによる最小試験の結果

`Work/Experiments/TsavoriteHistoryProbe/` の独立した診断プログラムを D の新規領域へ複製し、Microsoft.Garnet 2.2.1 を参照して Debug / Release 各3ケースを実行した。最終実行はすべて合格、両構成のビルドは警告0・エラー0。これは製品トランザクションの実装試験や性能試験ではない。

| 試験 | 観測結果 |
|---|---|
| 通常の上書き | 値100と値200が同じ論理アドレス64を使い、旧アドレスを読み直しても200だった。旧値を保持しない対照条件を確認 |
| コピー更新と元レコード保持 | アドレス64の値100を残し、値200を160へ配置。意図的に同じハッシュを返す別キーは112に入り、160→112→64の連鎖を確認 |
| 論理削除版と再挿入 | 値の中の削除フラグで別版を追記し、再挿入後も同一キーの版4→3（削除）→2→1を取得。既存の Delete / expire の履歴保証を確認したものではない |
| ディスク退避後 | ファイルデバイスで FlushAndEvict 後、アドレス指定の Pending 完了を含め、キーと各版の内容が退避前と一致 |
| 通常のネイティブ走査 | 最新のキーA版4とキーB版1のみを取得。版1以下で絞るとキーAが欠落することを検査。過去版へ解決する専用走査の必要性を確認 |

最終試験の作業領域: `D:\CodexTemp\Seamless\HistoryProbe\20261102-0145-final`。証跡: `F:\CodexTemp\Seamless\HistoryProbe\20261102-0145-final\launch-01` の stdout / stderr / receipt。receipt の affinity は `0xFF`。`TestSeamless/Invoke-LocalProcess.ps1` を使用した。メモリ監視の作業登録・状態確認・更新・終了もこの試験では成功した。

試験の全ケースで read cache と revivification を無効にした。エンジンの削除 API、read cache 有効時、コンパクション、再起動、並行実行、WAL と複数表の原子性は未検証。SDK は .NET 11 preview、ターゲットと実行は net10.0。初回 SDK 実行のログには HTTPS 開発証明書のインストール通知があり、信頼設定は実行していない。最終試験では `DOTNET_GENERATE_ASPNET_CERTIFICATE=false` を指定した。

### コレクションから見せる情報

高度な読み取り API は、利用者との合意により当面トランザクション接続層向けに限定する。値と同じ読み取りで取得したヘッダーのコピー、ストアと世代に結び付いた論理アドレス、履歴読み取り結果を、有効な保持期間とともに扱う。一般利用者向けの任意の過去版の照会・長期保持は別機能として検討する。生のメモリポインタや書き換え可能なヘッダー参照を公開する契約にはしない。

- 現行の型は`HistoryAddress`と`HistoryRecord`、物理的な前リンクは`HistoryRecord.PreviousAddress`。これはハッシュ衝突を含む連鎖であり、同一キーの前版を保証しない。`ReadVisibleRecord`がキーを照合して可視版を解決する。
- 履歴読み取りには保持 lease を必要とし、その有効期間中の履歴とアドレスの利用範囲を定義する。
- 保持 lease は履歴の論理寿命を守る。エンジンの短期間の epoch 保護を、長時間の取引全体にそのまま保持する設計にはしない。
- 履歴切れ、別ストア・別世代のアドレス、ストアの障害を「キー不存在」と区別する。
- アドレスで読んだレコードについてもキーを検証し、別キーの値を返さない。
- `ReadInfo.Version`、レコードアドレス、エンジンの Valid / Sealed は、アプリケーションの Committed を代用しない。
- 通常の `TryGetValue` と通常走査は、取引の履歴機能を使わない利用者のために維持する。

### FLinq の接続

取引対応の具体型を走査起点に追加し、ネイティブ走査の内側で可視な版を解決してから、利用者のラムダと融合済み処理へ渡す。全件の配列化、汎用列挙への強制変換、行ごとの取引ロックは導入しない。

現在の保存先の列に `CommitVersion <= ReadVersion` の Where を付けるだけでは実現できない。更新前の値、削除された行、同一キーの重複、自己の未確定変更を解決する専用の列供給が必要。

`Count`、`Contains`、点検索、二次索引、Join の全入力、実体化ビューも同じ読み取り版を使う。現在値の Count や Contains をそのまま最適化に使用しない。正しいスナップショット件数が得られない場合は KnownCount を宣言しない。

古い版が必要ない行・安全性が証明されたチャンクでは高速経路を使うことを目標とする。履歴の検査による追加コストは存在するため、性能維持は測定によって判定する。

### 確定と失敗モデル

1. 公開済みの版を取得し、取引固有の変更集合と読み取り依存関係を管理する。
2. 確定順序を決める短い同期区間で依存関係を検証する。検証済み・WAL 待ちの先行取引との競合も管理し、検証から公開までの競合見落としを防ぐ。
3. 競合した取引は WAL の確定受付前に中止し、専用の競合エラーを返す。正常な競合を共通の永続化障害としてラッチしない。
4. 非競合の確定要求を共通 WAL へ渡し、複数要求をまとめた Sync を利用できるようにする。DB 全体を fsync 待ちの間排他しない。
5. WAL 永続化後、全参加表・索引へ版を設置する。設置途中の行が他の取引に見えない可視性の境界を持つ。
6. 設置が完了した確定状態だけを公開し、成功応答する。単に最大の LSN を公開して未設置の穴を飛び越えない。
7. WAL 永続化後の設置失敗は Committed を維持する。共通 WAL と公開状態を共有する範囲の新規受付・成功応答・チェックポイントを停止し、確定チェックポイントと WAL から復旧する。

チェックポイントには設置・公開済みで永続化された状態のみを含める。必要な旧版は、活動中の最古のスナップショットから見える版とそれ以降を保持する。履歴回収、コピー、削除版、read cache、再オープンに伴うアドレスの寿命を保存先ごとに定義する。

## 影響範囲

共通コーディネーター、変更集合と保存先接続、Tsavorite のセッション関数とログ回収、Persisted の私有作業領域、型付きビュー生成、FLinq のソース能力、Gateway と TPC の参加境界、関連テスト。保存先・生成器への変更が必要なため、コーディネーターの全体排他の削除だけで実現したとは扱わない。

## 移行手順

- 採用パッケージを使った最小試作で、同一キーの複数版、衝突、削除と再挿入、メモリ外の読み取りを検証する。
- Tsavorite の高度な履歴読み取りと保持契約を、通常 API の意味を変えずに追加する。
- 一つの表の点検索と走査で MVCC と楽観的検証を接続し、別行の更新並行性を確認する。
- 複数表・二次索引・範囲読み取り・FLinq の最適化を接続し、Serializable の不変条件を検証する。
- 共通 WAL のグループ確定・公開・回収・復旧を検証してから Gateway と TPC を接続する。
- 既存の保存領域はそのままの形式で開く。MVCC メタデータを追加する領域は別の形式として識別し、必要な移行は別途設計する。

## テスト計画

- 同じキーを同じサイズで繰り返し更新し、全ての保持対象版を読める。
- ハッシュ連鎖に別キーを挟んでも、別キーの値を誤返却しない。
- 削除・再挿入・存在しないキーの読み取り・挿入の競合を扱う。
- 読み取りと複数更新を同期障壁で重ね、実際の並行区間を確認する。同一キーの競合で lost update を許さない。
- 別行への更新で発生する write skew、範囲検索への挿入、全件集計の依存関係を検出する。
- メモリ外の履歴読み取り、read cache のコピー、再利用、コンパクション、再オープンで保持契約を守る。
- FLinq の点検索・Contains・Count・Join・GroupBy・早期終了と、複数表の可視性を同じスナップショットの参照結果と照合する。
- WAL 前・Sync 中・永続化後・複数表の設置途中・公開直前・応答喪失の障害で、取引 ID の結果と復旧結果が一致する。
- ネスト、保存点、資源上限、長い読み取り、mutable な参照値、外部通知の既存契約を検証する。
- 履歴なし／履歴あり、点検索／走査、低競合／高競合で FLinq と通常 LINQ を比較する。速度・割り当て・競合率・履歴容量を記録し、無条件に速度維持を主張しない。

## リスクと対策

- ハッシュ連鎖を同一キーの版連鎖と誤解しない。キー比較と保持試験を必須とする。
- 長い読み取りで履歴容量が増える。共通予算に計上し、履歴不足を誤った結果で隠さず明示的に扱う。
- 現行の最新値走査・削除・回収を流用すると古いスナップショットの行が欠落する。MVCC 専用の経路と試験を設ける。
- 索引を最新値だけで管理すると古い読み取りが不整合になる。主表と同じ可視性・公開境界へ参加させる。
- 依存関係の管理に全行単位の大量の記録を強制すると FLinq の利点を損なう。全走査には保守的な表・区画単位の検証を検討し、不要な競合による中止率と比較する。任意の Where を正確なキー範囲に変換できるとは仮定しない。

## 実装状況と残る検証

- 独立試作の比較は [比較試験の結果](TransactionModesResults.md)、製品接続後の履歴圧迫・読取取消・静止回収・checkpoint/WAL復旧の実装と試験は [実装設計書](DeferredMvccImplementation.md) を参照する。小規模試験の成功を長期運転や全体性能の受入完了とは扱わない。
- 高度APIは`HistoryStore`/`HistoryAccessor`と世代付きアドレスを使い、接続層が取引の保持・operationと結び付ける。一般向けの任意過去版照会は対象外。
- 履歴を専用化した場合の性能・実メモリ・ストレージの同条件比較は [履歴保存の評価](20261103-mvcc-history-store-assessment.md) に記載する。専用版は未実装・未採用。
- 分割Lookupはworker専用のscope・予算付き格納・Persisted退避・終了時の排出を実装した。対応するクエリ形状と残る検証は実装設計書を参照する。PersistedをDB本体の共有保存先にはしない。
- 履歴予算・排出期限は有限の設定として扱う。実資源と予約会計の差、長期保持と結果台帳の運用、性能の受入基準は残る検証である。予算不足時に古い読取専用取引を中止して更新を優先する方針は合意済み。

## 合意状態

新規 DB も取引全体排他を既定とし、並行方式は有限の資源予算とともに明示して有効にする。Join / GroupBy を含むクエリ内並列化とホスト共通の CPU 配分は初版に含める。同じ取引の公開操作は順番に呼び出し、安全性が不明な処理を自動並列化しない。NUMA・I/O 構成および CPU と作業メモリの統合制御は後の段階へ回す。取引境界はソースに明示し、アクセスは展開時に解析する。不明な呼出しは更新可能な共通取引経路で実行する。詳細と今後の受入条件は [実装設計書](DeferredMvccImplementation.md) を参照する。これらの合意を試作の実測済み機能へ読み替えない。

初版の履歴回収は案 A とし、新規取引を待たせ、既存の処理・参照の終了後にまとめて整理することで合意した。履歴圧迫時は古い読取り専用取引を中止する既定方針を使い、既存の更新は完了に必要な予算を確認して確定・中止まで進められるようにする。回収用の一時受付停止と終了用の永久停止を分け、全参加先の準備が整ってから再開する。具体的な契約と受入条件は [遅延 MVCC の実装設計案](DeferredMvccImplementation.md) に記載する。

利用者と合意済みなのは、読み書き・複数更新の並行実行、楽観的ロック、FLinq の高速化を活かす要求である。前レコードへのリンクの利用とコレクションからの情報公開は検討対象として提示されている。別途、[更新方式比較試験](TransactionModesAcceptance.md) の実装・実行は承認済み。

集計と更新の同時進行は、利用者の追加回答により必須条件ではない。集計走査中は同じ表への物理追記を待たせる方式も採用候補とする。重なった場合も一貫性と終了時の待機解除を守る。通常の読み取り・更新と複数更新取引の並行性は維持する。更新を待たせない集計走査は将来の最適化候補であり、製品化前の必須条件には置かない。

並行方式の製品実装を遅延更新＋MVCCに絞り、即時方式は比較実験として残す開発方針は利用者と合意済み。具体的な保存形式、公開 API、移行、性能・資源予算、製品の受入条件は引き続き確定する。独立した実験プロジェクト `Benchmark/Experiments/TransactionModes` に比較実装と受入試験を置く。製品への実装・受入が完了したことを意味しない。

性能は並行実行時の全体性能を優先することで合意した。FLinq のネイティブ走査・演算融合を活かしながら、版の確認などによる単独実行の追加費用を許容する。評価では成功処理量に加えて応答時間の分布、競合率、資源使用量を確認し、正確性や耐久化の保証を弱めない。数値的な許容幅は同条件の基準測定後に定める。

履歴予算が不足した場合は、履歴保持を妨げる古い読み取り専用取引を中止し、更新を優先する。呼び出し側へ理由を明示し、自動再実行はしない。中止決定後の新たな読み取りと正常終了を拒否し、実行中の履歴アクセスが終了してから保持を解放する。取消要求だけを根拠に参照中のレコードを回収せず、待機中も予算を超えて書き進めない。この合意は、現在の試作に中止・運転中回収が実装済みであることを意味しない。

TPC-E・Gateway を含め、取引の開始・確定・競合・中止を共通トランザクション層で扱う方針は合意済み。共通層が楽観的検証・WAL・確定結果・履歴保持の調整を管理し、保存先の接続層が Tsavorite の保存表現と古い版の操作を担う。Persisted は私有作業領域として扱う。調整状態は同じ WAL と一括公開を共有する commit domain の範囲で管理する。単独 DB はその DB、Gateway は既存の複数 DB 一括確定を維持する。具体的な接続実装、互換性、導入順序、既存データの移行は [実装設計案](DeferredMvccImplementation.md) に具体化する。
