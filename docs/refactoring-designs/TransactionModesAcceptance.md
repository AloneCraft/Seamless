# Tsavorite 更新方式の採用判断試験

## 合意と範囲

2026-11-02、利用者が会話内の比較試験計画の実装を指示した。Tsavorite のメモリ／ディスク構成を対象に、シングル高速・遅延更新 MVCC・即時更新 MVCC を比較する。並行方式は楽観的検証と Serializable を用いる。起動時に方式を選択し、自動切替えは対象外。性能の数値閾値は事前に固定せず、実測結果と損益分岐点を判断材料とする。

利用者の追加回答により、集計と更新が待たずに同時進行することは必須条件にしない。集計走査中に同じ表への物理追記を待たせる方式も採用候補に含める。重なった場合の一貫性、走査終了・失敗・取消時の待機解除は維持する。点検索を含む通常の読み取りと更新、別行を変更する複数取引の並行実行は引き続き必要。集計に伴う待機時間の上限・取消方針は未決とする。

利用者は、並行方式の製品実装を遅延更新＋MVCCに絞り、即時更新＋MVCCは比較実験として残す方針に合意した。直列モードは起動時に選ぶ独立した方式として維持する。三方式の比較結果は保存し、製品化に向けた実装・検証は遅延方式を中心に進める。この合意は性能の全条件検証や製品の受入完了を意味しない。

性能の優先順位は、利用者の回答により並行実行時の全体性能を優先する。単独の問い合わせに版の確認などの追加費用がかかることは許容し、成功処理量と応答時間の分布、競合率、資源使用量を合わせて評価する。FLinq のネイティブ走査・演算融合を活かす要求と Serializable・耐久化の契約は維持する。単独実行の追加費用も同条件の基準と比較して報告し、数値的な許容幅は測定後に定める。

履歴予算が不足した場合は、履歴の保持を妨げる古い読み取り専用取引を中止し、更新を優先する方針で合意した。中止理由を呼び出し側へ明示し、自動再実行はしない。中止決定後はその取引で新たな読み取りや正常終了を認めず、実行中の履歴アクセスの終了を確認してから保持を解放し、回収する。中止を要求しただけで参照中の領域を再利用しない。対象がない場合や安全な解放を待つ間も履歴予算は守る。具体的な予算値、待機上限、エラーの型は未決とする。

TPC-E・Gateway を含め、取引の開始・確定・競合・中止を同じ共通トランザクション層で扱う方針に合意した。共通層は楽観的検証、WAL、確定結果、履歴保持の調整を担い、DB 本体の保存形式と古い版の操作は Tsavorite の接続層で扱う。Persisted はセッション・取引・クエリの私有作業領域で使い、DB 本体の保存先には追加しない。共通化するのは実装と契約であり、調整状態は同じ WAL と一括公開を共有する commit domain の範囲で管理する。単独 DB はその DB、Gateway は既存の複数 DB 一括確定を維持する。既存 API との互換性、接続の詳細と導入順序、保存領域の移行は引き続き確定する。

前レコード情報の API は、当面トランザクション接続層向けの高度な API に限定することで合意した。値と同じ読み取りで取得したレコード情報、ストアと世代に結び付いた論理アドレス、有効な保持期間を扱う。一般利用者向けの任意の過去版の照会・長期保持は別機能として検討する。通常のコレクション操作の契約を維持し、具体的な API の型名と接続方法は実装設計で確定する。

## 継承する契約

用語として、Serializable（取引の結果の保証）、複数取引の同時実行、複数クエリの同時実行、一つのクエリ内部のワーカー並列化を区別する。ここでいう直列モードは取引全体排他を意味し、クエリ内部の計算を単一スレッドに限定する意味ではない。今回の比較試作では、一つのクエリを複数ワーカーへ分割する実装・性能は検証していない。詳細は [実装設計案の用語](DeferredMvccImplementation.md) を参照する。

`ConcurrentTransactions.md` と `20261029-generic-transactions-tpc-c12.md` を参照した。旧データの自動変換、業務の自動再実行、既存製品 API の変更は行わない。WAL 永続化後の反映失敗は確定済みとして復旧し、正常な競合は障害停止と区別する。前の履歴読み取り6ケースを今回の採用試験の合格へ流用しない。

## 比較設計

実験プロジェクトは `Benchmark/Experiments/TransactionModes` に独立配置する。既存製品の公開 API や保存形式を変更しない。試験用 API と保存領域だけで三方式を実装する。FLinq 生成器と Tsavorite コレクションの既存のネイティブ走査を実際に参照する。

並行方式は、共有の取引状態表、確定順序、WAL、依存関係の検証を用いる。即時方式は書込み時、遅延方式は WAL 確定後に版を追記する。確定状態の公開までは他取引へ新しい版を見せない。キー単位の読み取りと、全走査時の表単位の依存関係を検証する。二次索引を含む複数表も一つの状態で公開する。

実験では、コレクションの公開 API にヘッダー付き走査がない制約を明示する。必要なネイティブ前リンクを値の封筒へ格納する場合、その追加バイト数を計上し、製品の最終実装と同一コストであるとは主張しない。FLinq の生成コードがネイティブ走査へ接続されたことを検査する。

実装時の観測により、次の接続条件を追加した。コピー更新の保持処理はコールバック後に前リンクを復元するため、値に入れる走査用の最初のリンクは `RMWInfo.SourceAddress`（同一キーの更新元）を使う。以後は実際のヘッダーの連鎖を読み、キーを検証する。通常行16バイトに対し版管理行40バイトで、所有者・走査用リンク・論理削除に各8バイトを要する。

並行追記中の通常の最新値走査ではキーの欠落を再現した。実験では問い合わせの間だけ表の構造を安定化し、同じ表への物理追記を待たせる。書込みの短い物理追記区間も表内で直列化する。従って、この比較から「走査と物理更新が無待機で並行する」「別行への物理追記が完全に並列になる」とは判断しない。取引の計算・点検索・WAL 待ちは並行可能であり、接続層の待機費用を含めて測る。

FLinq の最適化対象の本体に置いた `using var` が生成コードで通常の変数宣言になるケースを観測した。試験では、スコープの取得・解放を通常の C# メソッドに置き、純粋な問い合わせを含む内部メソッドだけを最適化対象にする。製品の生成器の変更は今回に混ぜない。

現在の試作の履歴回収は活動中取引がない場合に限る。中止版が物理的な最新位置に残る場合は通常の Compact が旧確定版を捨てるため、さらに回収を拒否する。即時方式の中止後の回収には MVCC 対応が必要であり、この制約は採用判断へ含める。24 MiB の予算はネイティブログの使用量で、取引状態表などの管理メタデータを含む総予算ではない。製品化では、合意した読み取り専用取引の中止と安全な保持解放、必要な旧版の保持を満たす回収、およびメタデータの回収を実装・検証する。

## 試験順序

1. 正確性: Debug / Release。更新履歴、ハッシュ衝突、論理削除と再挿入、退避、並行読取り・更新、lost update、write skew、存在しないキーと範囲挿入、複数表公開、FLinq 結果、保持・回収、予算超過、WAL 各境界の失敗と復旧を検査する。故意に保証を外す対照条件で検出能力を確認する。
2. 性能: Release のみ。利用者の追加指示により規模を1万／10万件に縮小する。ストアの常駐ログ上限32 MiB、版の使用量上限24 MiBとし、履歴8版などの条件は1万件側で測る。メモリ／ディスク、同時実行1/2/4/8、読取100%/95%/50%、一様／1%集中を比較する。履歴のある読取り、反復更新、中止の負荷も測る。
3. 各条件はウォームアップ後5回測定し、方式の順序を交代する。成功処理量、中央値/p95/p99、競合率、割当量、ピークメモリ、ログ容量、回収量、復旧時間を報告する。

## 実行と証跡

.NET 10 SDK、Garnet 2.2.5 を固定する。2.2.1での過去の性能値は再測定と区別する。独立したソーススナップショットと SHA256 を D に配置し、ビルド・実データも D、ログ・キャッシュは F に置く。`TestSeamless/Invoke-LocalProcess.ps1` で共通8論理CPUを使用し、共有 BGO は使用しない。メモリ85%以上では新しい重い処理を開始しない。

途中終了したセルは合格・性能値へ含めず、再開時は未完了セルだけ実行する。未コミットの製品変更を上書きしない。比較の正確性が成立しない候補は性能上の採用候補から除外する。

## 製品化で優先する検証

具体的な API・状態遷移・保存先と Gateway への接続・受入条件は [遅延 MVCC の実装設計案](DeferredMvccImplementation.md) に記載する。初版の履歴回収は案 A とし、新規取引を待たせて既存の処理・参照の終了を確認してから整理する方式を利用者と合意済み。既存の更新の終了を妨げず、終了・障害停止を解除して受付を再開しない。

- 履歴予算不足による読み取り専用取引の中止、新規アクセスの拒否、実行中アクセスの終了、安全な保持解放と回収を一つの試験で確認する。対象取引がない場合も予算を超えない。
- 回収中の新規受付待ち、既存取引の確定・中止、回収要求の集約、待機者の取消、排出期限切れ、回収・保存・再取得の失敗を検証する。回収を必要とした更新自身が参照を保持したまま待たないこと、全参加先の準備後に受付が再開することを確認する。
- 遅延更新の自己変更を含む Count / Sum / Join / GroupBy、複数表・索引の可視性を検証し、同条件の基準と比較して FLinq の追加費用と並行実行時の全体性能を測る。
- 共通層への接続後、競合と資源不足を障害停止と区別し、WAL 永続化・全参加先の設置・公開・復旧の境界を検証する。
- TPC-E・Gateway と保存先の接続実装は、既存の取引契約とデータ形式との互換性を確認する。試作の合格を接続後の受入結果へ流用しない。

## 合意状態

新規 DB も取引全体排他を既定とし、並行方式は有限の資源予算とともに明示して有効にする。Join / GroupBy を含むクエリ内並列化とホスト共通の CPU 配分は初版に含める。同じ取引の公開操作は順番に呼び出し、安全性が不明な処理を自動並列化しない。NUMA・I/O 構成および CPU と作業メモリの統合制御は後の段階へ回す。取引境界はソースに明示し、アクセスは展開時に解析する。不明な呼出しは更新可能な共通取引経路で実行する。詳細と今後の受入条件は [実装設計書](DeferredMvccImplementation.md) を参照する。これらの合意を試作の実測済み機能へ読み替えない。

比較試験の実装・実行、並行方式の製品実装を遅延更新＋MVCCに絞る方針、TPC-E・Gateway を含む共通トランザクション層への統一、前レコード情報の API を当面トランザクション接続層向けに限定する範囲、初版の履歴回収中に新規取引を待たせる案 A は合意済み。具体的な API と互換性、性能・資源予算、製品の受入、私有作業領域の管理、既存領域の移行は引き続き個別に確定する。
