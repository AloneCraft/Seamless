## 試験条件

本試験の `Single` / 直列は取引全体の排他、`Deferred` / `Immediate` は複数取引の同時実行の比較条件である。Serializable は結果の分離保証であり、一つのクエリを何ワーカーで処理するかの指定ではない。本試験は複数クエリを異なる取引で実行する条件を含むが、一つのクエリ内部のワーカー並列化の実装・測定には使っていない。

- Intel Core i7-14700F、Windows のバージョン表示 `10.0.26300.0`。起動した計算プロセスと子孫は共通8論理CPU、affinity `0xFF`。
- SDK 10.0.401、Microsoft.Garnet 2.2.1、net10.0、Release で性能計測。
- 主表1万 / 10万行、副表64行。テーブルのログメモリ32 MiB、並行方式のネイティブログ使用量予算24 MiB。プロセス全体の上限ではない。
- 成功処理量・成功した取引のレイテンシを各セル0.5秒、5反復で記録。方式の順序を交代。下表は条件ごとの5反復の中央値。
- メモリ構成も WAL は共通のファイルへ書き、`Flush(true)` を待つ。全走査の1標本は8回の問い合わせで、表示時間は1回分に換算した中央値。
- 完了セルの中にメモリ圧迫中の測定が含まれ得る。同居処理、OSのキャッシュ、JIT、スケジューリングを排除した計測ではない。

## 正確性で確認できたこと — Fact

遅延・即時の両方式をメモリ／ファイルの各構成で検査した。

| 項目 | 結果 |
|---|---|
| 自己の変更、古いスナップショット、中止、論理削除、再挿入 | 他取引の未確定値や新しい値が古い取引へ漏れない |
| 同じ行の更新、write skew、存在しないキーと phantom | 楽観的検証が競合を検出する |
| 4更新スレッドと古いスナップショットの同時走査 | 更新完了値と、旧時点の件数・合計が一致する |
| Count / Any / First / Sum / Join / GroupBy | 期待値と一致し、自己挿入した未確定行も集計・結合に含まれる |
| 複数表の公開、WAL Sync 中の遮断 | 耐久化前に成功や新しい版を公開せず、片方の表だけが見えない |
| ハッシュ衝突、退避後のアドレス読取り | 別キーを挟む連鎖と旧値を読み戻せる |
| 活動中の履歴保持、静止時の通常回収、予算超過 | 必要な履歴を保護し、予算不足をエラーにする |
| 中止版が物理的な最新値として残る場合の回収 | 通常の Compact を拒否し、旧確定値を保護する |
| WAL 前・永続化後・反映途中・公開直前の注入失敗 | 確定前後を区別し、耐久化済み取引を新規領域へ再生できる |
| WAL 前・永続化後・公開直前の実プロセス強制終了 | 再起動側が WAL を読み、二表の取引を全体として再生できる |
| 検証を故意に外した対照条件 | lost update を検出する試験が失敗することを確認 |

Release の小さな二表のプロセス終了後再生は、耐久化済みケースで約7.3～25.0 msだった。大規模な再起動時間や、チェックポイント・世代管理・破損復旧の性能を示すものではない。

## 設計上の判断 — Decision

**前レコードへの情報は利用できるが、それだけで即時方式を採用する理由にはならない。両方式の旧版解決に利用できる。** この結論は、履歴読み取り・衝突・退避と、二方式の可視性試験に基づく。

利用者の追加回答により、集計と更新が待たずに同時進行することは必須条件にしない。全走査の構造安定化によって同じ表の物理更新を待たせる方式も採用候補に含める。更新を待たせない集計走査の実装を、製品化前の必須課題には置かない。混在時の一貫性と走査終了時の待機解除は引き続き必要である。

利用者は、**並行方式の製品実装を遅延更新＋MVCCに絞り、即時更新＋MVCCは比較実験として残す方針**に合意した。遅延方式は、同じ行への反復変更を変更集合内でまとめ、中止時に共有ログへ未確定版を残さない。即時方式には中止版を含む回収の専用設計が必要になる。今回の選択はこの構造と保守範囲に基づく開発方針であり、全性能試験による速度の優位や製品の受入完了を主張するものではない。集計中に更新を待たせること自体は不採用の理由にしない。

利用者は、単独の問い合わせへの追加費用を許容し、並行実行時の全体性能を優先する方針を選択した。FLinq の既存の高速化を活かし、成功処理量と応答時間の分布、競合率、資源使用量を合わせて評価する。正確性と耐久化の保証は維持する。単独実行の追加費用も報告し、数値的な許容幅は同条件の基準との比較後に決める。

履歴予算が不足した場合は、古い読み取り専用取引を明示的なエラーで中止し、更新を優先する方針で合意した。中止後に新しい読み取りや正常終了を認めず、実行中の履歴アクセスの終了を確認してから保持を解放・回収する。自動再実行はしない。これは製品化に向けた契約であり、今回の59件の試作試験で実装・受入済みの機能ではない。

TPC-E・Gateway を含め、取引の開始・確定・競合・中止を同じ共通トランザクション層で扱う方針に合意した。一貫性の意味と楽観的検証・WAL・確定状態・履歴保持の調整は `Seamless.Transactions` に集約し、型付き変更集合と可視性を `Seamless.Transactions.Collections`、DB 本体の保存形式と古い版の操作を Tsavorite の接続層へ置く。Persisted は私有作業領域に限定し、DB 本体の保存先には追加しない。調整状態は同じ WAL と一括公開を共有する commit domain の範囲で管理し、Gateway の既存の複数 DB 一括確定を維持する。FLinq は可視な行の具体型を入力として高速化し、業務の確定判断を持たない。直列モードは、起動時に選ぶ独立した方式として比較・維持する。この合意は、今回の比較試験が TPC-E・Gateway・Persisted の受入まで完了したことを意味しない。

前レコード情報の API は、当面トランザクション接続層向けの高度な API に限定することで合意した。値と同時に取得したレコード情報、ストアと世代に結び付いた論理アドレス、有効な保持期間を扱う。一般利用者向けの任意の過去版の照会・長期保持は別機能として検討する。この範囲の合意と、製品 API の実装・受入完了は区別する。

初版の履歴回収は、新規取引を待たせて既存の処理・参照の終了後にまとめて回収する案 A とする。回収中に新しい取引を待たせることは利用者と合意済み。通常時の複数取引の並行実行は維持し、実行中の更新を一律に強制中止して回収しない。受付停止・排出・回収・再開と障害時の扱いは製品化で検証する。

新規 DB も取引全体排他を既定とし、並行方式は有限の資源予算とともに明示して有効にする。Join / GroupBy を含むクエリ内並列化とホスト共通の CPU 配分は初版に含める。同じ取引の公開操作は順番に呼び出し、安全性が不明な処理を自動並列化しない。NUMA・I/O 構成および CPU と作業メモリの統合制御は後の段階へ回す。取引境界はソースに明示し、アクセスは展開時に解析する。不明な呼出しは更新可能な共通取引経路で実行する。詳細と今後の受入条件は [実装設計書](DeferredMvccImplementation.md) を参照する。これらの合意を試作の実測済み機能へ読み替えない。

製品接続の具体化は [遅延 MVCC の実装設計案](DeferredMvccImplementation.md) を参照する。新しい API・回収方式・公開手順は設計案であり、この試験結果の実装済み機能には数えない。

## 製品採用前の制約 — Guardrail

- この試験では、全走査の間は同じ表の物理追記を待たせる。独立した更新の短い物理追記区間も表内で直列化する。無待機の並行走査・追記を証明したものではない。
- 値だけの走査に最初の履歴リンクを渡すため、版管理行40バイトのうち8バイトを追加している。点検索は実際のヘッダー、走査の最初の遡及は `RMWInfo.SourceAddress`、以後はネイティブの連鎖を使う。公開 API を追加した製品の最終費用と同一ではない。
- コピー更新の保持処理はコールバック後にヘッダーのリンクを復元する。コールバック中の新レコードのヘッダーを最終値として保存しない。
- 最適化対象に置いた `using var` が通常の変数宣言になるケースを観測した。スコープの取得・解放は通常の C# メソッドへ置いた。製品の FLinq 生成器は今回変更していない。
- 活動中取引と並行して行う回収、中止版を含む MVCC 回収、管理メタデータの到達性に基づく回収と総予算は、長期運転へ進む前の課題。予算を単に増やして解決した扱いにしない。
- 製品の二次索引維持、制約、Gateway、TPC 業務、Persisted、可変参照値、ネスト・保存点、結果照会は今回の受入範囲外。
