共通 `Seamless.Execution.Store` が保存先、予算、寿命を所有する。作成は `Store → CreatePersisted... → コレクション操作` の順。新しい型は `Seamless.Collections.Persisted.Work` に置き、従来 API のバイト等価性とレコードのシリアライズを維持する。ファイル上のハッシュ索引は、2026-09-26の利用者の決定により旧形式との読込互換を維持せず、新形式へ変更する。

## API と選択基準

| 用途 | 型 / Store 拡張 | 検索可能な時点 |
|---|---|---|
| 一括追加後の集合、重複除去、範囲検索 | `Work.SortedSet<T>` / `CreatePersistedSortedSet<T>` | `CompleteAdding()` 成功後 |
| 一括追加後の辞書、同値キーの最後の値 | `Work.SortedDictionary<TKey,TValue>` / `CreatePersistedSortedDictionary<TKey,TValue>` | `CompleteAdding()` 成功後 |
| JOIN の重複行、ORDER BY、GROUP BY の入力 | `Work.SortedList<T>` / `CreatePersistedSortedList<T>` | キー検索は `CompleteAdding()` 成功後 |
| 追加と存在確認の反復、DISTINCT | `Work.HashSet<T>` / `CreatePersistedHashSet<T>` | 作成直後から |
| 追加と検索・更新の反復、集計 | `Work.HashDictionary<TKey,TValue>` / `CreatePersistedHashDictionary<TKey,TValue>` | 作成直後から |

すべて単一スレッドで操作する。内部並列処理や並行更新の保証はない。`Store.CreateMemory()` は対象外。共通 Store の破棄は子コレクションも破棄し、一時 Store のフォルダも削除する。

既存 `Persisted.Set<T>` / `Dictionary<TKey,TValue>` は既に `.hindex` による即時検索を提供する型であり、今回それらを未確定型へ変更していない。旧 `Compact()` は既存の最適化・保存処理のまま、新型の明示確定とは別の契約である。

## ソート方式の状態

作成直後および `Add` 後は `IsReady=false`。この間の列挙は追加順で重複を含み、`Count` / `LongCount` は追加された行数になる。`SortedList` の位置 indexer はこの追加順の行を読む。

`CompleteAdding()` は入力ファイルを変更せず、行位置だけをソートした索引を作る。ソート、重複処理、Flush、作業ファイルの解放が成功してから完成索引を公開する。失敗時は未確定のまま、入力を再利用して再実行できる。確定済みに対する再呼出は何もしない。

確定後は比較順で列挙する。set / dictionary は同値キーを1件にまとめ、最後の Add の行を採用する。dictionary の「後勝ち」は入力位置で決め、sort の安定性に依存しない。list は重複をすべて保持し、同値行は追加順になる。`AddedCount` は常に入力行数、`Count` / `LongCount` は確定後の論理件数となる。

確定後に `Add` すると未確定へ戻り、入力全体を対象に再確定する。未確定時の `Contains`、`IndexOf`、`ContainsKey`、`TryGetValue`、dictionary のキー indexer、`Range` は `InvalidOperationException`。検索から暗黙にソートしない。確定後の検索は完成位置索引に対する二分探索で、`Range(lower,upper)` は半開区間 `[lower,upper)` を返す。`SortedList.IndexOf` は比較で同値となる最初の行の位置を返す。

列挙中の追加・復元による変更は次の MoveNext で例外として検出する。hash set の重複 Add は内容が変わらないため列挙を継続できる。どちらの方式も操作を順序付ける。

## ハッシュ方式と比較規則

hash set は同値要素を再追加しても増やさず、最初の代表値を保持する。hash dictionary の `Add` と indexer の setter は最後の値で上書きする。どちらも衝突時に実際のキーを comparer で比較する。dictionary は追記式に古い値も保存するが、列挙は最新の行だけを返す。列挙は全件をメモリに蓄えない。

sort は `IComparer<T>` / `IComparer<TKey>`、hash は `IEqualityComparer<T>` / `IEqualityComparer<TKey>` を受け取る。sort の文字列既定比較は `StringComparer.Ordinal`、それ以外は `Comparer<T>.Default`。hash は `EqualityComparer<T>.Default`。注入する等価比較器にも、等しいキーの hash 値が等しいという `IEqualityComparer<T>` の契約を求める。同じ結果を必要とするクエリでは、`Compare(a,b)==0` と `Equals(a,b)` が一致する規則を与える。例えば文字列では両方に `StringComparer.OrdinalIgnoreCase` を渡す。comparer が認める null 要素は set/list で扱えるが、dictionary の null key は拒否する。

set の代表値は sort が最後、hash が最初であり、同値でも表現が異なる文字列の保持表現まで一致する契約ではない。dictionary のキー表現と値は両方式とも最後の Add から採用する。hash の列挙順はソート順ではない。

永続 Store でカスタム比較を使う場合は安定した `comparisonId`（sort）または `comparerId`（hash）が必須。比較器の型と ID を保存し、再オープン時の不一致は拒否する。stateful comparer の設定を変えたら ID も変える。hash のプロセス固有 seed は保存せず、open / Load 時に索引を再構築する。旧バイト等価コレクションからの自動移行は行わない。

## ハッシュ索引の保存形式

2026-09-26に利用者が「過去は読み込めなくてもよい」と決定したため、`.hindex` は新形式だけを受け付ける。既存のSet/Dictionaryと新しいwork hash型が共有する索引基盤に適用する。旧形式や未知版は `InvalidDataException` で拒否し、その拒否を理由に自動変換・自動削除は行わない。保存状態がない component の未確定ファイルを破棄する既存の Store 契約は維持する。旧 `.hindex` を含むデータが必要な場合は旧実装で取り出し、新しい保存先へ明示的に作成する必要がある。work hash 型の snapshot はレコード本体と位置索引だけを保存し、Load 時に派生ハッシュ索引を新規作成するため、`.hindex` を含まない既存 snapshot まで一律に拒否する変更ではない。

新形式は32バイトのヘッダーに負数で符号化した容量、項目数、flush時の行数、形式版1を保存する。旧実装も負の容量を不正として拒否する。キーの64ビットhash自体は変更せず、検索・追加・索引成長の開始スロットを決めるときに64ビット全体を混ぜる。これにより、下位bitが同じキー群の集中を抑える。ソート型のデータと完成位置索引、およびレコード本体の形式はこの変更の対象外。

## メモリ・ディスクと保存

sort は `sortMemoryBytes` で上限を決めた `long` の行位置配列だけをメモリに持つ。run をディスクへ出し、二方向 merge を繰り返す。run 管理は固定64枠、位置配列は最大1,048,576要素。全データを `ToArray`、`List`、`Dictionary` に変換しない。実装は性能より境界と予測可能な使用量を優先する。

共通 `ResourceBudget` に、位置配列、比較時のレコードバッファ、固定コピー領域、データ・索引・merge の中間ファイル・保存世代を予約する。ファイル拡張は容量を予約してから行い、hash 索引の拡張時も旧ファイルと作業ファイルの同時存在分を含める。`sortMemoryBytes` とは別にメタデータと比較する数行分の余裕が必要。予算不足は例外で処理を止める。通常は `ResourceLimitException` で、配列sort内部の比較で発生した例外は .NET の `InvalidOperationException.InnerException` に保持される。

この予約はプロセス全体のヒープや OS ページキャッシュを制限するものではない。既存 serializer は1要素のバイト列を生成してから長さを返すため、その初回確保を先行制限できない。ユーザー comparer / serializer 自身の確保も厳密には管理しない。巨大な単一要素を扱う場合は、要素サイズも入力側で制限する。

`Store.Save()` は入力ファイルと完成位置索引を不変な世代へコピーし、状態・型・比較規則を保存する。`Load()` / `Load(token)` は別の作業世代へコピーして復元する。古い checkpoint に戻って追加しても、別の保存済み checkpoint のデータを上書きしない。未確定で保存したものは未確定へ、確定済みで保存したものは確定済みへ戻る。

コピーは固定4 KiB。保存世代と現在の作業世代、Load 中の新旧世代が同時に存在する容量を必要とする。保存世代の自動削除や圧縮はない。既存 Store の checkpoint 寿命に従う。プロセス強制終了や OS I/O 障害での操作全体の原子性、孤立作業ファイルの自動回収は保証しない。

## 利用例

```csharp
using Seamless.Collections.Persisted;
using CommonStore=Seamless.Execution.Store;

using var store=CommonStore.CreateTemporary(new(){MemoryBytes=1<<20,DiskBytes=64L<<20});
using var distinct=store.CreatePersistedSortedSet<string>("distinct",StringComparer.OrdinalIgnoreCase,sortMemoryBytes:4096);
foreach(var value in source){distinct.Add(value);}
distinct.CompleteAdding();
var found=distinct.Contains("alpha");

using var aggregate=store.CreatePersistedHashDictionary<string,long>("aggregate",StringComparer.OrdinalIgnoreCase);
foreach(var row in sourceRows){
    aggregate.TryGetValue(row.Key,out var total);
    aggregate.Add(row.Key,total+row.Amount);

```

JOIN の同一キー行には `SortedSet` を使わず、キーだけ比較する `SortedList<(Key,Payload)>` を使う。比較順の走査による GROUP BY と `Range` から重複行を消費する例は `Test.Persisted.Collections/Work/SortedList.cs` で実行する。集合・辞書の両方式一致例は `Work/SortedDictionary.cs` のテストで検証する。

FLinq の provider 判定は namespace と generic metadata 名の一致を調べる。新 namespace `Seamless.Collections.Persisted.Work` を従来の `Persisted.Set<T>` や `PersistedList<T>` として登録しない。通常の `IEnumerable<T>` 経路から列挙でき、存在判定を二分探索/ハッシュ探索で行う場合はコレクション自身の `Contains` / `ContainsKey` を呼ぶ。`IEnumerable<T>` に変換した後の LINQ Contains は別の走査・比較契約である。

既存の `Seamless.Linq` の scoped query、disk lookup、external sort はそのまま利用できる。今回の追加 API は内部作業コレクションの選択肢であり、クエリプランの全演算を自動置換するものではない。

## 既存呼び出し側と移行

既存 API は追加変更のため移行不要。追加中に検索する既存 Set / Dictionary の呼出をソート型へ自動置換しない。新しいクエリ作業では、従来の `CreatePersistedSet` / `CreatePersistedDictionary` を同じ Store 上の `CreatePersistedHashSet` / `CreatePersistedHashDictionary` に明示変更すれば等価規則を指定できる。永続データは別の component 名を作り、旧型から列挙して新型へ Add し、検証して保存する。旧ファイルをそのまま新型として開く方法は提供しない。

一括処理へ変更する場合は Sorted factory を選び、すべての Add と最初の検索の間へ `CompleteAdding()` を置く。単なる追記・再列挙は既存 `CreatePersistedList` / `AppendOnlyList` を使い、不要な索引を作らない。

既存クエリ実装は `ScopedLookup` / `DiskLookup` が等価規則付きのグループ行を保持し、`ScopedOrderedQuery` / `ExternalSort` が `IComparer<TKey>` を使う。入力途中の検索・group の重複保持・scope の寿命という既存契約を変更する必要はなく、その実装は維持した。`ScopedOrderedQuery` の既定比較は従来の `Comparer<TKey>.Default` のままであり、新 work 型の文字列 Ordinal とは独立する。

FLinq の調査対象は `FLinqIncrementalGenerator.ProviderFacts.cs`、`FragmentBuilder.cs`、`UnorderedSourceSafety.cs`。名前だけの一致でなく namespace と generic 型を比較する既存条件を維持した。呼出側で追加したものは work 型の利用例・回帰テストと生成コードの誤分類検証であり、生成器の provider 登録は変更していない。
