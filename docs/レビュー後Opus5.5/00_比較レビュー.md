# 00 比較レビュー

Atras 版（`docs/AtrasReverseEnginnering/`、6文書）と Opus 5.5 版（`docs/Opus5.5ReverseEnginnering/`、14文書）を比べた結果と、この文書群で採った方針です。

## 総評

| 観点 | Atras 版 | Opus 5.5 版 | この文書群 |
|---|---|---|---|
| 構成 | 横断型。機能・契約・Phase・受け入れ・課題を ID で結ぶ | 機能別。機能群ごとに10項目を書く | **ID で結ぶ横断型を骨格にし**、機能別の10項目は短くして ID を参照する |
| 追跡性 | F / INV / NG / AC / GAP / Q の ID が一貫 | ID は未実装（U-）と判断（D-/Q-）だけ | Atras の ID 体系を採用し、Opus 版の項目を割り当て直した |
| 根拠 | ファイル単位が中心。行番号は一部 | ほぼすべてに `パス:行番号` | 行番号つきの根拠を残す |
| 事実の新しさ | 静的調査のみ。BUG-0005〜0008 を「再現待ち」とした | 静的調査。バグは記録として扱った | **同日の修正で確かめた事実に更新**（BUG-0005〜0008 は解決済み、BUG-0010〜0013 を追加） |
| 検証の設計 | 受け入れ表、判定区分、証跡のきまり、UI の確認表、移行・ロールバック表が充実 | 機能ごとの検証表 | Atras の検証設計を採用し、実際に使えた手順（生成器の検証方法、性能の前後比較）を加えた |
| 未実装の粒度 | 大きな単位（GAP-01〜11） | 細かい単位（U-01〜18） | 中くらいの単位（G-01〜20）にまとめ直した |
| 判断事項 | Q-01 は回答済み（正しさ優先）、Q-02 は回答待ち | Q-002〜Q-006、D-06〜D-10 | 1つの表（Q-01〜Q-12）にまとめ、重なりを除いた |

## Atras 版から採ったもの

- ID の体系（F・INV・NG・AC・Q）。課題は G- とした。
- 「混同してはいけない境界」：Store の上限と ExecutionScope の予算の区別、等値性の2系統、Registry の Excluded の意味、旧ゲートと新しい比較の区別、SQL の能力の区別。
- **Dynamic の能力除外に現れている FLinq の不具合**（`SelectManyXor` の CS1673、Range の `ElementAt` の CS0103、最適化なし `UnionBy` の不完全な和集合）。Opus 版は見落としていた。今回コードで確認した（`Benchmark/Benchmark.Dynamic.Core/CapabilityProfile.cs:139`、`:159`、`:165`）。→ G-06
- **Dynamic UI の Worker コピーが、BUG-0009 で Benchmark.UI から外した方式のまま**であること（`Benchmark/Benchmark.Dynamic.UI/Benchmark.Dynamic.UI.csproj:48`）。→ G-08
- SQL の制約・トリガー・ビューの鮮度が、メタデータとして読まれるだけで執行されないこと。→ G-11
- SQL 取り込みの分離レベル（メモリ最適化テーブルがあれば ReadCommitted、なければ Snapshot：`Seamless.Database.SqlServer/SqlServerImportSource.cs:86-87`）。
- 取り込みの受け入れが件数中心で、値の比較が足りないこと。→ G-12
- 判定区分（PASS / FAIL / BLOCKED / NOT_RUN / 人の確認待ち / 比較不能）、証跡のきまり、UI の確認表、移行・ロールバック表。
- Q-01 の回答「正しさ・データ保全・検証の再現性を最優先」を計画の順序に反映した。

## Opus 5.5 版から採ったもの

- 機能ごとの `パス:行番号` の根拠。
- 細かい未実装：`IReadOnlySet<T>` の未実装、`TryAdd` の戻り値、辞書の型引数、比較子、辞書生成のリフレクション、Persisted の `Rewrite` の全件実体化、保存番号が増え続けること、キーつきレコードの Codec。
- **スコープ付きクエリで一覧外の演算子が、黙って全件メモリ処理になりうること**（Atras 版にはない）。→ G-05
- 並行使用の検出を「作成スレッドとの一致」で実装すると DB の使い方を壊すこと。→ Q-11
- リポジトリの整理候補。特に、ライセンスキーと思われるファイルが Git で追跡されていること。→ Q-09
- Dynamic の演算子の網羅（46種、未収載20種）。→ G-07

## 同日の修正で新しく分かったこと

- BUG-0007（FLinq の集計のあと DB を閉じられない）と BUG-0005（DB テストが終わらない）の原因：集計関数 `Compute` への値渡しで、列挙子が破棄されていなかった。修正済み（`6ac6c388`）。→ INV-01 に「列挙子は必ず1回破棄する」を加えた。
- BUG-0006（StoreCheckpoint の不安定）の原因：テスト基盤 `BenchmarkTiming` が async のテストを待たずに事前実行し、同じテストが並行に走っていた。修正済み（`f905f118`）。→ F-20 と INV-20 を新設した。
- BUG-0008・0010・0011・0012・0013 はテストやテスト基盤の不具合で、すべて修正済み。
- `Test.csproj` は生成器を固定パスから読むため、`--artifacts-path` の隔離ビルドでは古い生成器でテストされる（OBS-0002）。→ NG-14、06 の検証手順。
- 生成器の変更による性能の前後比較の方法（`Benchmark.Headless` の対測定を、修正前の作業ツリーと交互に回す）。→ 06
- `TestPath` が `[BenchFact]` をテストメソッドと認識しないため、同じクラスのテストがフォルダを共有していること（BUG-0006 の調査で確認。原因ではなかったが、別の不具合）。→ G-19

## 食い違いの決着

| 論点 | Atras 版 | Opus 5.5 版 | 決着 |
|---|---|---|---|
| 旧 API の扱い | Q-02「残すか、移行後に削除か、両方を正式サポートか」を回答待ち | 承認済み計画の決定11「一括で置き換え、旧 API は削除」を前提 | **未決着**。決定11（2026-09-19 承認）と Q-02 の再質問が両立しないので、Q-01 として最初に確認する。それまでは削除しない（NG-12） |
| 操作用オブジェクトのスレッド検査 | 「Release でも自動で防ぐとは宣言しない」 | 承認済み計画は「Release でも安価に検出して例外」。ただし作成スレッドとの一致では DB を壊す | **不変条件は「同時に2つの操作を入れない」**（INV-07）。検出の方式と Release で例外にするかは Q-11 |
| BUG-0005〜0008 | 再現待ち（歴史的観測） | 記録として扱い、Phase 1〜2 で修正予定 | **解決済み**（2026-09-25、検証済み）。04 の不具合表を参照 |
| 優先順位 | 正しさ・データ保全 → 検証の再現性 → 明確な機能不足 → 性能と保守性 → 配布 | 正しさ → 回帰判定 → 再設計の完了 → 暗黙フォールバック → 網羅・性能 → 新機能 → 整理 | ユーザーの Q-01 回答に合わせて Atras 版の順序を正とし、Opus 版の具体的な作業を当てはめた（05） |
| 作業範囲の書き方 | この文書作成ではコードを変えない、と明記 | 未記載 | 05 の各 Phase に変更範囲と非対象を書く |

## この文書群で採らなかったもの

- Atras 版の「これまでの QA 記録は歴史的観測なので、現行の失敗とは扱わない」という一律の方針。今回すでに再現と修正をしたものは、確かめた事実として扱う。
- Opus 版の、機能群ごとの長い10項目の本文。共通の内容は 02 に集め、03 は機能固有の差分だけを書く。
