# 01 機能と現状

## このシステムが行うべきこと

メモリに載り切らない件数のデータを、.NET の普通のコレクション・LINQ・宣言的 DB の書き方のまま、ストレージへ分散して扱えるようにする。保存場所・寿命・資源の上限を利用者が指定でき、上限を超えたときや対応できないときは、理由がわかる失敗にする。LINQ はコンパイル時に展開して速くし、その正しさ・性能・容量を同じ条件で測り続ける。

## 混同してはいけない境界

- **2つの上限**：共通ストア（`StoreLimits`）の上限と、実行スコープ（`ExecutionOptions`）の予算は、使う場所も設定の口も違う。どちらもプロセス全体のメモリ上限ではない。
- **2つの等値性**：スコープ付きクエリとストアの既定は、シリアライズ後のバイト列の一致。スコープの外で FLinq が `System.Linq` を展開するときは .NET の既定の等値性。同じ正解データで比べない（`+0.0f` と `-0.0f` など）。
- **順序**：Tsavorite・Persisted の列は順序なし。位置に依存する演算は、明示的に順序を受け入れたとき（`AsEnumerable()` など）だけ許す。
- **Registry の Excluded**：FLinq の登録表で「除外」とされた分類は、同じ名前の API のすべての経路が未実装という意味ではない。経路ごとに確かめる。
- **Persisted の件数**：Set の `Count` は `Compact()` 前は重複を含む追記件数。正確な件数の責任は呼び出し側にある（`Set.cs:20-24`）。
- **比較の基準**：Benchmark UI の旧履歴と、検証基盤の新しい比較（`VerificationComparison`）は別物。旧い固定 run ID や比率の目標を新しい基準に持ち込まない（旧性能ゲートは 2026-10-22 に削除済み）。
- **SQL の能力**：カタログの取得、型の生成、データの取り込み、ルーチンの実行、制約の執行は、それぞれ別の能力。1つができても他ができるとは言わない。
- **取り込みの一貫性**：通常は Snapshot で読むが、メモリ最適化テーブルがあると ReadCommitted になる。全表が同じ時点の内容だとは保証しない（`SqlServerImportSource.cs:86-87`）。
- **テストがあることと通ること**：テストの存在や過去の成功件数を、現在の受け入れに使わない。
