# 02 不変条件・禁止事項・前提

全機能に共通する契約です。機能ごとの差分は [03](03_機能別の契約.md) に書きます。「確かめる手段」は [06](06_検証と受け入れ.md) の AC-ID です。ここに書いた契約を、現在のコードがすべて満たしているとは限りません。満たしていない箇所は [04](04_未実装と既知の問題.md) の G-ID に結びつけています。

## 不変条件（INV）

| ID | 変更後も成り立ち続けること | 根拠 | 確かめる手段 |

| INV-03 | 大規模データの経路は共有予算から予約し、全件がメモリに載る前提にしない。退避できない・上限を超えるときは理由つきで失敗し、**別の意味の処理へ黙って切り替えない** | `ResourceBudget.cs:54-56`、`ExecutionOptions.cs:93-98` | AC-RESOURCE。違反：G-04（Compact）、G-05（一覧外演算子） |

## 禁止事項（NG）

| ID | やってはいけないこと |
|---|---|
| NG-01 | 例外を握りつぶす、固定値を返す、待ち時間や再試行だけを増やす、診断を隠す、失敗するテストを外す、を修正とみなす |
| NG-02 | 全件を `List`・`Dictionary`・配列に集めて予算を迂回する。入力を黙って小さくして成功に見せる |
| NG-03 | 型・SQL・Codec・順序が未対応のとき、別の意味へ黙って変換する。FLinq の展開できない呼び出しを `System.Linq` へ黙って戻す |
| NG-04 | アプリの起動処理、スキーマ版の増加、自動削除・自動移行で既存のローカル DB を変える。変えるときは明示バックアップを取り、対象 DB へ直接行う |
| NG-05 | 未保存のストアの状態、未 commit の DB 操作、checkpoint 前の WAL を、確定したり捨てたりする |
| NG-06 | 古い Worker・DLL・生成コードの結果を、現在の変更の証拠にする |
| NG-07 | baseline を自動で更新する。入力ハッシュや意味論の違いを無視して比べる。旧い固定 run ID を新しい基準に持ち込む |
| NG-08 | 所有の分からない変更を reset・clean・checkout で戻す。関係のない未コミット変更をまとめてコミットする。ほかのプロセスをまとめて止める |
| NG-09 | 生成されたファイル（`.g.cs`）だけを直して生成器を放置する。共有ソースをソリューションの単独ファイルとしてだけ見せる |
| NG-10 | SQL の解析や取り込みができたことを、ルーチン・トリガー・制約の実行ができると報告する。一部のテストの成功を全体の合格と報告する |
| NG-11 | 不具合の修正に、関係のない改名・構造の作り直し・大量の整形・保存形式の変更を混ぜる |
| NG-12 | 回答のない互換性・製品範囲の判断を、承認済みとして扱う（例：旧 API の削除。Q-01） |
| NG-13 | 性能の良し悪しを、自作の簡易計測で判断する。判断は Worker の実測（`Work/UI/Benchmark.db`、`Benchmark.Headless`、検証基盤）で行う |
| NG-14 | FLinq 生成器を変えたとき、`--artifacts-path` の隔離ビルドで検証する（`Test.csproj` が古い生成器を読む。OBS-0002） |
| NG-15 | 操作用オブジェクトが2つ以上生きている間に、Tsavorite の `GrowIndexAsync` を呼ぶ（Tsavorite の 2.0.1-beta.5 と 2.1.8 で停止する。EXP-0004） |
| NG-16 | 並行使用の誤りを「作成スレッドと違えば例外」で検出する（DB の順次利用を壊す） |
| NG-17 | 却下済みの最適化候補を、同じ仮説のまま名前を変えて再び試す（`FLinq-Optimization-Candidate-Backlog.md` の規約） |

## 前提条件

- 対象はローカルの `G:\GitHub\Seamless`。比較用の作業ツリー（`Work/qa/wt-head` など）を現在の正本にしない。
- SDK は `global.json`（`10.0.100`、`latestFeature`）。実行するときは `dotnet --info` を記録する。FLinq 生成器は `netstandard2.0`、ランタイムの多くは `net10.0`、Windows の UI は `net10.0-windows10.0.19041`。
- Windows での開発を前提にする。UI の検証には MAUI のワークロードと、実際のデスクトップ操作が必要。
- インターセプター（C# preview 機能）を使う。利用側は `InterceptorsPreviewNamespaces` に `Intercept` を含める。
- 参照を含む型を保存する利用者は、`[MemoryPackable]` を付けて MemoryPack を参照に加える。
- C# の書き方は `AI_SYNTAX_RULES.md`。既存ファイルに局所的な書き方があれば、それに合わせる。
- SQL Server の統合試験は、接続先・専用の試験データ・権限が用意できたときに行う。接続情報を文書・ログ・manifest に残さない。
- 機能の試験は隔離した一時 DB・ストアを使う。`Work/UI`・`Work/Verification`・`Test/Work` を試験の失敗時に自動で消さない。
- 同じソリューション・同じ `bin`/`obj` に対するビルドとテストを並行させない。Visual Studio や MSBuild が常駐しているときは、競合しないことを確かめてから始める。
