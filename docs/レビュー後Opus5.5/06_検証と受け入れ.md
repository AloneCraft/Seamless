# 06 検証・受け入れ・移行・ロールバック

## 判定の区分

| 区分 | 扱い |
|---|---|
| PASS | 指定した条件と対象で終わり、期待どおりの挙動と証跡を確かめた |
| FAIL | 正しさ・資源・回帰・画面などの受け入れ違反を確かめた |
| BLOCKED | 必要な環境・接続先・入力がなく、実行できない |
| NOT_RUN / SKIPPED | 実施していない、または条件つきで外した。PASS に数えない |
| 人の確認待ち | VS からの F5 など、必須の操作や製品判断が残る。その関門は未完了 |
| 比較不能 | 比較条件の不一致・未完了・測定不足。「速い」「遅い」に変換しない |

この表は計画の管理用です。検証基盤のコード上の状態（`Passed`・`Regressed`・`Incompatible` など）はそのまま保存します。テスト0件、skip だけ、途中停止、プロセスが終わらない、ファイル名に PASS とあるだけ、は合格の証拠になりません。

## 証跡として残すもの

日時、対象の絶対パス、コミット、未コミット差分のハッシュ、SDK・ランタイム・OS・CPU、構成と TFM、入力と Seed、コマンド、終了コード、テスト結果ファイル（trx）、標準出力と標準エラー、実行したバイナリ・依存 DLL・生成コードのハッシュ、対象の DB・ストア。性能では測定方法と生の測定値、画面ではアプリのプロセスと exe、画面サイズと DPI、操作、前後の画像、表示値と保存値の対応を加えます。保存先は `Work/qa/artifacts/<ID>/`、検証基盤の run は `Work/Verification/Artifacts/<run-id>/`。

## 受け入れ条件（AC）

| ID | 何を確かめるか | 入口（既存）と追加すべき証拠 |
|---|---|---|
| AC-BASELINE | 正本のコミット・未コミット差分・SDK・成果物・テスト・作業記録が一致する。前からある失敗と新しい失敗を分けられる | `git status`/`diff`、成果物のハッシュ、`Work/qa/state.json`、現在の trx。2026-09-25 時点で HEAD からの失敗はない |
| AC-RESOURCE | 同じ予算へ予約と解放を計上し、上限の直前と超過・巨大な単一値・大量のキー・巨大なグループで、完了するか理由つきで失敗する | `Execution.Tests`、`ScopedQuery`、Persisted の共有テスト。Compact の入力を増やしたときの予約量・ピークメモリ・一時領域 |
| AC-LIFETIME | 空列、全消費、`First`/`Any`、途中の break、例外、取消、破棄後のアクセスで、列挙子・読み取りセッション・予算・ファイルロックが契約どおりになる | `Execution.Tests`、DB のトランザクションテスト、**`ScalarTerminalDisposeSemantics.cs`**（取得と破棄の回数を System.Linq と比べる）、**`DatabaseScalarQueryDisposeTests.cs`**（別コンテキストの破棄が止まらない） |
| AC-CODEC | 形式・型・版の不一致、ハッシュの衝突、匿名型と構造体、明示 Codec、登録の固定、一般クラスの拒否 | `Execution.Tests/CodecRegistry.cs`。登録の固定のテストは追加が必要（G-20） |
| AC-COLLECTION | 空・重複・上書き・削除・再追加、件数の不明から走査、差分の反映、同時の操作用オブジェクト、保存と開き直し、`int` の桁あふれ | `Test.Persisted.Collections`、`Test.Tsavorite.Collections`、`Test/Seamless/Stores/StoreExtensions.cs`、`StoreCheckpoint`、標準コレクションとの差分テスト（G-02 で追加） |
| AC-DB | 読み書きの排他、昇格の拒否、内側 Rollback、未 commit の破棄、キーの重複、退避、commit 異常後の拒否、終了後の資源解放 | `DatabaseTransactionTests`、`DatabaseStoragePersistenceTests`、`DatabaseScalarQueryDisposeTests`。結果だけでなく、待ちの解除とプロセスの終了を見る |
| AC-RECOVERY | 保存番号での復元、未保存、WAL の commit 前後、checkpoint 前後、まだ開いていないテーブル、壊れた末尾、archive の内容不一致、繰り返しの開き直し | ストアのテスト、DB の保存テスト、隔離したプロセスを強制終了させる試験（EXP-0005）。電源断は別の実験 |
| AC-LINQ | 結果・順序・安定ソート・重複・null・比較子・例外の種類と時点・評価回数・遅延性・早期終了・列挙子の破棄 | `Test/System/Linq`、各 `Test.*.Linq.Enumerable.*`（8フレーバー）。.NET の基準とスコープの基準を分ける |
| AC-GENERATOR | 実際に届く生成コードがコンパイル・実行できる。登録表・能力・網羅・診断、増分キャッシュ、再生成の決定性 | `LinqFragmentCoverageTests`、`IncrementalCacheTests`、`RenderContractTests`、`GenerationServicesTests`、`FallbackDiagnostics`、`OptimizationFixedPointTests`、`PerformanceShapeTests`、`UnorderedEnumerableAnalyzerTests` |
| AC-DYNAMIC | Seed・IR・ソース・経路・診断・結果・trace が対応し、全経路を正しく評価する。除外を外すのは実経路の成功と一致するときだけ | `DynamicRouteShapeTests`、`DynamicEndToEndTests`、`DynamicWorkerRestartTests`。縮小は同じ失敗の署名を保つ |
| AC-IMPORT | 生成 → ビルド → staging 取り込み → 破棄 → 開き直し → manifest → 公開。スキーマ・件数・値、取消と失敗、backup からの復旧 | `DatabaseToolImportIntegrationTests`、`DatabaseToolIntegrationTests`、`SqlServerImportSourceTests`、`SqlServerImportSizerTests`。分離レベルを記録する |
| AC-SQL | 選んだ範囲の解析・生成・実行が対応表と一致し、SQL Server と値・NULL・順序・副作用・失敗が一致する | `SqlServerRoutineAnalyzerTests`、`RdbmsSourceGeneratorTests`、`RdbmsViewSourceGeneratorTests` に実行の基準を追加 |
| AC-WORKER | クリーンなビルド、Worker だけの変更、Debug/Release、VS からの F5 で、意図した Worker がコピーされて起動する | 実際の exe のパスと、Worker の exe・dll・deps.json・runtimeconfig.json の SHA-256 |
| AC-COMPARE | 条件が一致するものだけを比べる。結果のダイジェストが違えば `CorrectnessFailure`。無効・欠けた測定を成功にしない | `VerificationComparison` と `Verification.Tests`。性能は有効な測定5回以上、既定の5%境界。容量は最大成功件数と失敗種別 |
| AC-VERIFY | `init` は明示で既存を拒否、baseline は全成功の run へ明示で設定、同じソースでの再開、違うソースでの再現、改ざん・範囲外の成果物の拒否、中断からの復旧 | `Verification.Tests` と隔離した workspace での CLI。本番の履歴で破壊的な試験をしない |
| AC-UI | 計画の理由・実行状態・結果・詳細・履歴・比較が CLI と DB に一致する。開始・停止・取消・再開・再実行・再起動が成り立つ | 下の UI 確認表、`Benchmark.UI.UITests`、`Benchmark.Dynamic.UITests` |
| AC-API | 共通ストアの寿命と保存を保ち、選んだ互換性と未対応の拒否を確かめる | ストア拡張のテスト、旧 API と新 API の利用例、AppendOnlyList の新しい契約のテスト |
| AC-PROJECT | `.csproj`・`.shproj` の全登録、共有プロジェクトの GUID と import 名、軽量ソリューションの再生成が一致する | XML の突き合わせ、`Update-FocusedSolutions.ps1`。生成されたソリューションを手で直さない |
| AC-PACKAGE | アナライザー・ランタイム・ツールの TFM・依存・生成物・版が正しく、リポジトリ外の小さな利用プロジェクトで restore・ビルド・実行できる | Release の pack、nupkg の中身、FLinq と Database の生成器の生成と実行 |
| AC-ROLLBACK | コードとバイナリ、DB・スキーマ・Codec・manifest を組で戻し、開き直しと代表操作を再現できる | 隔離コピーでの復元演習、戻す前後の件数・値・代表クエリ・履歴の比較 |

## 生成器を変えたときの検証手順（重要）

`Test/Test.csproj` は FLinq 生成器を `..\Seamless.FLinq.Generator\bin\$(Configuration)\netstandard2.0\Seamless.FLinq.Generator.dll` という固定パスから読みます（OBS-0002）。そのため次の手順を守ります（NG-14）。

1. Visual Studio・MSBuild が同じソリューションをビルドしていないことを確かめる。
2. `--artifacts-path` を**使わず**、通常の出力先でビルドする。コンパイラサーバーが古い生成器を使い回さないよう、`-p:UseSharedCompilation=false` を付ける。
   `dotnet build Test/Test.csproj -c Debug -f net10.0 -p:UseSharedCompilation=false`
3. 生成コード（`Test/obj/Debug/net10.0/generated/Seamless.FLinq.Generator/...`）を開き、変更が反映されたことを確かめる。
4. 生成器を使う全プロジェクトを流す：`Test`（net10.0）、`Execution.Tests`、Linq の8フレーバー（`Test.{System,Tsavorite,Persisted}.Linq.Enumerable.*`）。

## 性能の前後比較の手順

検証基盤の性能スイートは代表5件だけで、特定の演算子の経路を測れません。生成コードの形を変えたときは、次の方法で前後を比べます（2026-09-25 の BUG-0007 で使用。`Work/qa/artifacts/BUG-0007/perf/`）。

1. 変更前の版を別の作業ツリーに用意する：`git worktree add --detach Work/qa/wt-<名前> <基準コミット>`。利用者の未コミット差分があれば、それだけを `git apply` でそろえる。
2. 両方のツリーで `Benchmark/Benchmark.Headless` を Release でビルドする（Headless と Worker がベンチ本体を参照するので、各ツリーの生成器で展開される）。
3. 1件ずつ対測定する（約1秒で JSON を返す）。作業用のフォルダをカレントにして実行する。
   `dotnet exec <tree>/Benchmark/Benchmark.Headless/bin/Release/net10.0-windows10.0.19041/win-x64/Benchmark.Headless.dll --run-tab "<タブID>" --type Int32 --method <メソッド> --operator-harness`
4. 修正前と修正後を交互に3巡以上測り、巡ごとに先に測る側を入れ替える。
5. 各回の「FLinq ÷ 比較対象（ZLinq）」の中央値を前後で比べる。比較対象は変更の影響を受けないので、環境の揺れを打ち消せる。1行の再測定の揺れは ±21% 程度ある。
6. 作業ツリーを片付ける。`git worktree remove` はパスが長すぎて失敗することがあるので、その場合は登録を外したあと PowerShell で `\\?\` を付けたパスを削除する。

タブ ID は `Shared/UI.Core/BenchmarkSourceTabs.cs`（例：`System.Array`、`System.Collections.Generic.IEnumerable<>`）、メソッド名は `Shared/Linq.Enumerable/Base.cs` の `[BenchFact]` の名前です。

## よく使うコマンド

実行の前に、TFM・対象のテスト数・ほかのプロセスとの出力先の競合を確かめ、順番に実行します。`--no-build` は、ソースと成果物が一致しているときだけ使います。

```powershell
dotnet --info
git status --short
git rev-parse HEAD

dotnet test .\Execution.Tests\Execution.Tests.csproj
dotnet test .\Test\Test.csproj -f net10.0 --blame-hang-timeout 600s
dotnet test .\Test.Persisted.Collections\Test.Persisted.Collections.csproj
dotnet test .\Test.Tsavorite.Collections\Test.Tsavorite.Collections.csproj
dotnet test .\Verification.Tests\Verification.Tests.csproj
dotnet test .\Benchmark.Dynamic.Tests\Benchmark.Dynamic.Tests.csproj
dotnet test .\Test.Tsavorite.ParameterSweep\Test.Tsavorite.ParameterSweep.csproj

# 検証基盤。既存の Verification.db を init し直さない。run は履歴に書き込む操作
dotnet run --project .\Verification.Cli -- plan --root G:\GitHub\Seamless --suite changed --profile quick --output Work\Verification\plan.json
dotnet run --project .\Verification.Cli -- run --root G:\GitHub\Seamless --plan Work\Verification\plan.json
```

## 移行の条件と手順

| 対象 | 段階 | 切り替えてよい条件 |
|---|---|---|
| コレクションの API | 利用箇所の列挙 → 共通ストアの口 → 1つの利用側 → 1つのライブラリ群 → 旧 API の整理 | 各段で所有・件数・保存・開き直しの契約が合格。旧 API の削除は Q-01 の回答と利用側の検証が前提 |
| 生成器の内部 | 現在の Fragment → 描画の契約 → 責務ごとの移設 → 仲介の解消 | 生成コードのコンパイル・意味・診断・trace・キャッシュ・性能に説明のない回帰がない |
| 検証の UI とゲート | 旧 UI と履歴を保持 → 検証基盤の比較を正本に → 導線の移行 | 同じ規則で表示・保存される。旧 UI の廃止は Q-07 の回答後 |
| SQL の取り込み先 | 旧宛先を保持 → 別の staging に生成・取り込み → 開き直して検証 → 旧宛先を backup → 新宛先を公開 | スキーマ指紋・件数・値・代表クエリ・分離レベル・再起動の検証が成立 |
| ローカル SQLite のスキーマ | 書き手とアプリを止める → 整合したバックアップ → 対象 DB へ明示変更 → 整合の検査 → 再起動 | バックアップと手順が記録済み。起動時の自動移行は使わない |

WAL モードの SQLite は、使用中の DB ファイルだけをコピーしても整合したバックアップになりません。接続を止めてからコピーするか、適切なバックアップ手段を使います。DB が参照する成果物も一緒に保全します。

## ロールバックの条件と戻し先

| 問題 | すぐに行うこと | 戻す先 |
|---|---|---|
| 結果・件数・SQL の意味の不一致、commit 境界の違反、データ損失 | 対象の書き手を止め、失敗した入力・新しいデータ・ログを保全 | Phase の直前に受け入れたコードとバイナリ、対応するスキーマ・Codec・DB のバックアップ（AC-RECOVERY、AC-ROLLBACK） |
| 資源の上限超過・解放漏れ・終了の停止 | 所有するプロセスを特定し、タイムアウトと trace を保存 | 直前の資源・列挙の実装と隔離データ |
| 古い Worker・DLL の不一致 | その数値を採用しない。起動した実体とハッシュを保存 | 同じ構成の UI・Worker・依存の一式とビルドの構成 |
| 比較条件・履歴・画面の不整合 | baseline の更新を止め、候補の run を保全 | 直前の比較の実装と、整合した履歴のバックアップ |
| 性能の最適化が基準に届かない・悪化する | 候補の前後の生成コード・生の測定・原因の候補を保存 | 自分の候補の差分だけを戻す |
| 利用プロジェクトでのパッケージの失敗 | 候補の採用・公開を止める | 直前に受け入れたパッケージ一式 |

戻し先は「最新のバックアップ」のような曖昧な指定にせず、作業 ID・コミットまたは差分・バイナリのハッシュ・保存形式と Codec の版・バックアップの絶対パスで示します。`git reset --hard` や `git clean` を一般の手順にしません。切り替えのあとに利用者の新しい書き込みがあれば、旧バックアップへ戻すだけではそれを失うので、先に退避して損失のない戻し方を決めます。
