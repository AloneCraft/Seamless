## 1. 目的

容量探索（`Benchmark/Benchmark.Tsavorite.ParameterSweep`）と Scalable ベンチ（`Shared/Scalable.Tsavorite.Collections`）で、次の3つを測れるようにする。

- 実際のハッシュ分散：索引の大きさを固定したとき、どれだけ溢れるか
- 索引の挙動：実際のバケット数、使用中の枠の数
- ストレージの速度：ログのうちメモリとディスクにある量、読み書き方式による差

現在の実装：

- 共通ストアから作る `store.CreateTsavorite*` に、公開した `TsavoriteTuning` を渡せる。
- 計測コードは索引を `AutoGrowIndex=false` で固定し、ストレージの方式を `StorageTuning` で指定する。
- `GetStatistics()` と `DumpIndexDistribution()` により、索引のバケット数、使用中の枠、溢れ、ログの配置を観測できる。
- Persisted の設定伝達と Windows の Unbuffered 入出力を実装した。容量探索と Scalable は新 API を使い、容量探索は観測4項目を結果・DB・UI・Headless へ渡す。
- コードの接続、関連テスト、DBとHeadlessの実行による確認は済んでいる。追加workを含む回帰の結果と残る確認事項は10章・11章に記録する。

## 4. 現在の実装と契約（2026-09-25）

### Tsavorite コレクション（`Seamless.Collections.Tsavorite`）

- `Stores/TsavoriteTuning.cs` は `public sealed record`。`IndexSize`、`PageSize`、`SegmentSize`、`LogMemorySize`、`MutableFraction`、`AutoGrowIndex`、`Storage` を持つ。省略時のサイズ自動決定と索引自動拡張は維持する。
- `Stores/StoreExtensions.cs` の `CreateTsavorite<K,V>`・`CreateTsavoriteHashSet<T>`・`CreateTsavoriteSet<K,R>` は `(store,name,TsavoriteTuning tuning,long expectedCount=0)` を公開する。設定を省略する既存の多重定義も維持する。
- `Stores/TsavoriteLayout.cs` は2の累乗、ページとセグメント、可変割合、メモリストアへのストレージ設定を検証する。ログメモリが2ページ未満なら `ResourceLimitException(Memory)`。固定索引と保存済み索引サイズが異なる場合は拒否する。
- メモリストアは `NullDevice`。ストレージでは `Storage` 指定時に既存の `TsavoriteStorageDevices.Create` へ渡し、省略時のデバイス選択は維持する。反映する項目は `AccessPattern` と `BufferingMode`。
- `CollectionStore.EnsureCapacity` はページ単位で予算を予約する。メモリストアは索引＋ログ全体、ストレージはメモリに索引＋min(ログ,ログメモリ)、ディスクにログ全体を予約する。
- `GrowIndexIfCrowded` は `AutoGrowIndex=false` なら拡張しない。複数 accessor の既存ガードも維持する。
- 新 API は型から保存方式を決める。Scalable の既存12種（辞書7・集合5）は移行前と同じ保存方式になる。旧 API の正しさテストは今回移行しない。

### 観測値

- `TsavoriteStatistics.IndexSize` は64バイトの索引バケット数、`IndexBytes` はその64倍。設定の `TsavoriteTuning.IndexSize` はバイト数なので単位を区別する。
- `EntryCount` は索引の使用中の枠の数。衝突によりコレクションの件数とは一致しない。
- `OverflowBucketCount` は初期予約を含む溢れバケット数。`OverflowBucketAllocations` は初期予約を除く割当数。混雑は追加前からの増加で確認する。
- ログの4アドレスと、`MemoryLogBytes=TailAddress-HeadAddress`、`DiskLogBytes=HeadAddress-BeginAddress`、`HighWaterAllocatedPageCount` を取得できる。ログバイト数は物理ファイルやオブジェクトログを含めた総確保量ではない。
- `DumpIndexDistribution()` は Tsavorite の `DumpDistribution()` が返す `string` を公開する。これと `GetStatistics()` の `EntryCount` は索引全体を走査する。並行書込中の項目間整合性は保証しない。

### 共通ストアと Persisted

- 共通ストアの作成は `Store.CreateMemory(limits)` と `Store.CreateTemporary(limits,temporaryDirectory)`。`StoreLimits` の既定はメモリ256MB、ディスク16GB。メモリストアは保存できない。
- `ResourceLimitException.Kind` は `Memory`・`TemporaryStorage`・`SingleElement`。プロセス全体の資源上限とは異なる。
- `CreatePersistedSet/List/Dictionary` は末尾の `StorageTuning? tuning=null` をコレクションへ渡す。
- Persisted の Buffered は既存のメモリマップ方式。Unbuffered は Windows の `FILE_FLAG_NO_BUFFERING` と整列バッファを使い、データ・位置索引・ハッシュ索引・AppendOnly を同じ経路で開く。非Windowsでは `PlatformNotSupportedException` とし、方式を黙って切り替えない。
- Buffered / Unbuffered 間で保存形式を共通にする。`.hindex` は2章の追加決定により新形式へ変更した。未整列末尾の部分更新は既存セクターを読み戻して保持し、既存範囲を十分読めなければ上書き前に拒否する。構築失敗時には取得済みファイルと accessor を解放する。

### 容量探索と Scalable

- 共通ストア → 新 API のデータ本体 → accessor の順で作り、索引を固定する。予算はメモリを `checked(Index+Memory+2*Page)`、容量探索のディスクを正の指定値または既定値にする。
- 容量探索の accessor は各ワーカースレッド内で作成・使用・破棄し、全 `Join` 後に統計を1回取得する。共通ストアがデータ本体と一時フォルダを所有する。
- 構築時と操作時は同じ失敗分類を使い、enum 末尾の `メモリ上限超過`（6）と `ディスク上限超過`（7）へ振り分ける。Headless と Verification はこの2種を容量探索の境界結果として扱う。
- Scalable は新しい `CreateTunedSet/CreateTunedStore` を使い、旧 factory を維持する。検索用キャッシュはインスタンス所有の `ThreadLocal` で、全スレッドの操作終了後に accessor → Store の順で破棄する。
- 新旧 API の結果は直接比較しない。測定方式識別子だけでは移行前後を自動区別しないため、移行後の結果で基準を作り直す。

### 容量探索の DB と表示

- DB は `Work/UI/Benchmark.ParameterSweep.db`。2026-09-25 の再確認時点でも存在しないため、既存DBへの変更は不要。
- 容量探索のスキーマ版は21。通常ベンチマーク26、Scalable20を維持する。
- 結果と `UIパラメータスイープ結果` の末尾に、`索引バケット数`・`溢れバケット数`・`メモリログバイト数`・`ディスクログバイト数` を追加した。型は `long?`、既定は null。
- `UiRunStore` は4つの nullable INTEGER 列を保存・読込し、形状検査の対象は15列。既存DBの自動移行は行わない。
- UI は4列を表示し、null は `-`。Headless は JSON に4項目を出力する。Verification は値のある項目を対応する観測メトリクスへ渡す。Headlessの実出力とDBの往復テストは確認済み。UI実画面の確認は残る。

## 5. 実装の手順

以下は実装した内容の契約と確認条件。各段の確認済み範囲は10章、残る確認事項は11章に記録する。全5段のコード実装と10章に示す範囲の自動検証は済んでいるが、受入全体は完了していない。

### 段1：設定オブジェクトを公開する

1. `TsavoriteTuning` を `public sealed record` にし、次の2項目を足す。
   - `bool AutoGrowIndex`（既定 true）：false なら索引を拡張しない。
   - `StorageTuning? Storage`（既定 null）：ログのファイルの読み書き方式。
   - 先頭の説明コメントを、今の仕様に書き換える（「利用者には公開せず」を消す）。
2. 設定の検証を足し、`Resolve` の最初で呼ぶ。違反したら `ArgumentException` にする。
   - `IndexSize`・`PageSize`・`SegmentSize`・`LogMemorySize` が2の累乗でない
   - `SegmentSize` が `PageSize` より小さい
   - `MutableFraction` が「0より大きく1以下」の範囲の外
   - メモリストアで `Storage` を指定した
   - ログのメモリがページ2つ分より小さい場合は、今までどおり `ResourceLimitException` のままにする（予算の問題として扱う）。
3. `StoreExtensions`：設定を受け取る多重定義を public にし、引数を `(store,name,TsavoriteTuning tuning,long expectedCount=0)` の順にする。3種類とも同じにする。
   - 既存の public 版は、これに処理を任せる。
   - 呼び出し側（`Test/Seamless/Stores/StoreExtensions.cs`、`Seamless.Database` など）を直す。
4. `GrowIndexIfCrowded`：`AutoGrowIndex` が false なら、最初に戻る。
   - データ本体からこの設定が見えるよう、`TsavoriteLayout` に `AutoGrowIndex` を持たせる。
   - 既存のガード（操作用オブジェクトが2つ以上なら拡張しない）は残す。
5. `Resolve`
   - `Storage` があれば、`TsavoriteStorageDevices.Create(path,storage)` で hlog と obj を作る。なければ今のデバイスのままにする。
   - `AutoGrowIndex` が false で、指定した `IndexSize` と保存済みの値が違うときは、黙って変えずに `InvalidOperationException` にする。指定と違う大きさで測ってしまうのを防ぐため。

### 段2：観測の統計を出す

1. 新しいファイル `Seamless.Collections.Tsavorite/Stores/TsavoriteStatistics.cs` に、public の record を作る。項目：
   - 索引のバケット数（`IndexSize`）と、索引のバイト数（バケット数×64）
   - 索引の使用中の枠の数（`EntryCount`）
   - 溢れバケットの数（`OverflowBucketCount`）と、確保した回数（`OverflowBucketAllocations`）
   - ログのアドレス4つ
   - メモリ上のログのバイト数（Tail−Head）と、ディスク上のログのバイト数（Head−Begin）
   - メモリ上で確保したページ数の最大値（`HighWaterAllocatedPageCount`）
2. `CollectionStore` に `GetStatistics()` と `DumpIndexDistribution()` を足す。後者は `Store.DumpDistribution()` の結果を返す。
3. XML コメントと docs に次を書く。
   - 取得した時点の値で、並行して書き込んでいる間は、項目どうしが整合しない。
   - 使用中の枠の数は、件数ではない。
   - 分布の出力は索引全体を走査するので重い。

### 段3：Persisted に設定を渡す

- 追加承認（2026-09-25、ユーザー回答「2」）：Unbuffered 自体も実装する。Windows では FILE_FLAG_NO_BUFFERING と整列バッファによる直接 I/O を使用し、データ・要素位置索引・ハッシュ索引・AppendOnly を同じ方式に揃える。Buffered は既存のメモリマップ方式を維持する。未対応 OS では PlatformNotSupportedException を返し、Buffered へ黙って切り替えない。
- Buffered / Unbuffered 間で同じ保存形式を用い、セクター境界に合わない末尾でも論理長と物理ファイル長を維持する。Buffered と Unbuffered の切替、索引成長、保存・復元・再オープン、末尾の部分更新を検証する。
- `CreatePersistedSet/List/Dictionary` の最後に `StorageTuning? tuning=null` を足し、そのままコンストラクタへ渡す。

### 段4：容量探索と Scalable を新 API へ移す

#### 容量探索

`ParameterSweepRunner.cs` のワークロード基底と各ワークロードを共通ストア経由にする。旧 `ストアを作成` とデバイスの独自所有は除去済み。

- 共通ストアを作る。
  - バックエンドが「メモリ」なら `Store.CreateMemory(上限)`。
  - 「ストレージ」なら `Store.CreateTemporary(上限, ストレージディレクトリ)`。
- データ本体は、`CreateTsavoriteHashSet`・`CreateTsavoriteSet`・`CreateTsavorite` に `TsavoriteTuning` を渡して作る。
  - `IndexSize`・`PageSize`・`SegmentSize`・`MutableFraction` は、探索の設定をそのまま使う。
  - `LogMemorySize` は `Memoryサイズ`。
  - `AutoGrowIndex=false`。
  - ストレージのときは `Storage=new StorageTuning(FileAccess.ReadWrite,StorageAccessPattern.Sequential,StorageBufferingMode.Buffered)`（今と同じ）。
- 上限
  - `MemoryBytes` は「索引＋ログのメモリ＋ページ2つ」以上にする。予算より先にログの満杯が起きるようにして、これまでの「ログ満杯」と同じ意味を保つ。
  - `DiskBytes` は、`オプション.ストレージデバイス容量` が正の値ならその値、そうでなければ既定値。
  - デバイスの容量はもう指定しない。ディスクの上限は予算で掛かるので、超えたときは「ディスク上限超過」になる。
- 共通ストアを破棄すると、データ本体とフォルダも片付く。今の独自の後始末（`Dispose` でのフォルダ削除など）と重ならないよう整理する。
- `パラメータスイープ失敗種別` の**末尾**に、`メモリ上限超過` と `ディスク上限超過` を足す。
  - `失敗を分類` で `ResourceLimitException` を `Kind` によって振り分ける：`Memory` → メモリ上限超過、`TemporaryStorage` → ディスク上限超過、それ以外 → 例外。
  - この分岐は、最後の `_ => 例外` より前に置く。
- 結果の `エントリCount` は、段2の統計から取るように変える（値の意味は同じ）。

#### Scalable

- **既存の `CreateMemorySet`・`CreateMemoryStore` と、それを使う正しさのテストは変えない。**
  - 旧 API のテストの移行は、旧 API をどうするかの判断（`docs/レビュー後Opus5.5/07_判断事項.md` の Q-01）と一緒に行う。
- `IHashSetTestStrategy<T>` と `IDictTestStrategy<K,V>` に、新 API で作る静的メソッドを足す。例：`CreateTunedSet(TsavoriteTuning tuning,StoreLimits limits)`。
  - 中身：`Store.CreateMemory(limits)` → `CreateTsavoriteHashSet<T>(名前,tuning)` → `Create()`。
  - 保存形式は型で自動的に決まり、今の組み合わせと同じになる（4章）。そのため、どの戦略でも中身は同じになる。インターフェイスの既定の実装（static virtual）にしてもよい。
  - 戻り値は、Scalable が使うもの（`Set` または `NewDict()`、`Dispose`）だけを持つ新しい型にする。この型が共通ストアの破棄まで受け持つ。
- `Shared/Scalable.Tsavorite.Collections/Bases.cs` を、新しいメソッドを使うように切り替える。
  - ベンチの引数は変えない。
  - 上限は、容量探索と同じ決め方にする。
- 使い回している Contains 用の集合と TryGetValue 用の辞書が、複数のスレッドから同時に使われないことを確かめる。操作用オブジェクトは1スレッドに1つが決まり。
- 旧 API で測った値とは、そのままは比べられない（メモリストアの方式と予算の掛かり方が変わるため）。このことを `docs/verification.md` かベンチの説明に書く。

内部の実装ではなく、外から見える振る舞いを確かめる。主に `Test` プロジェクトに足す。

| 確かめること | 方法 |
|---|---|
| 索引を固定できる | `AutoGrowIndex=false` と小さい `IndexSize` で多く入れる → 索引のバケット数が変わらず、溢れバケットの数が追加前から増える。同じ条件で既定の設定なら、索引が拡張される（対照） |
| ログの置き場所が見える | 一時ストアで `LogMemorySize` を小さくして入れる → ディスク上のバイト数が0より大きい。メモリストアでは常に0 |
| 読み書き方式が効く | 一時ストアで `Storage` に Random と Unbuffered をそれぞれ指定する → 追加・保存・開き直しができ、内容が一致する |
| 誤った設定を拒む | 2の累乗でない、Segment が Page より小さい、Fraction が範囲外、メモリストアで `Storage` を指定 → `ArgumentException`。保存済みと違う固定索引で開く → `InvalidOperationException` |
| 分布を出せる | `DumpIndexDistribution()` の結果が空でない |
| Persisted に設定が届く | リストは `PersistedList<T>.Tuning` が指定と一致する。集合と辞書は、Random と Unbuffered を指定して追加・保存・読み込みが通る |
| 既定の動作が変わらない | 既存のコレクションとストアのテストがすべて通る |
| 失敗の分類 | `Test.Tsavorite.ParameterSweep` に、`ResourceLimitException` の2種類が新しい失敗種別になることを確かめるテストを足す |
| 保存の形 | `Test/Benchmark/UiRunStore.cs` のパラメータスイープのテストで、新しい4列を保存して読み込めることを確かめる |
