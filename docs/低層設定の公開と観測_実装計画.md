# 低い層の設定の公開と観測：実装計画

- 状態：未着手（2026-09-25 作成）。範囲と方式はユーザーが決定済み。
- 想定読者：この計画を実装するエージェント。会話の経緯を知らなくても実装できるように書いている。
- 事実は 2026-09-25 のコードで確かめた。着手時に行番号がずれていたら、名前で探し直すこと。

## 1. 目的

容量探索（`Benchmark/Benchmark.Tsavorite.ParameterSweep`）と Scalable ベンチ（`Shared/Scalable.Tsavorite.Collections`）で、次の3つを測れるようにする。

- 実際のハッシュ分散：索引の大きさを固定したとき、どれだけ溢れるか
- 索引の挙動：実際のバケット数、使用中の枠の数
- ストレージの速度：ログのうちメモリとディスクにある量、読み書き方式による差

いまの問題：

- 共通ストアから作る新しい API（`store.CreateTsavorite*`）では、索引・ページ・セグメント・ログのメモリ量・可変割合を外から渡せない。渡す口（`TsavoriteTuning`）が internal だから。
- 索引の自動拡張を止められないので、指定した大きさのままで測れない。
- ストレージの読み書き方式（`StorageTuning`）が Tsavorite 側に渡らない。
- そのため、計測コードは旧 API（`Seamless.Collections.Tsavorite.Store.Create(...)`）を使い続けている。
- 測ったあとも、索引の実際のバケット数、溢れの量、ログの置き場所が見えない。

## 2. 決まっていること

2026-09-25 にユーザーが決めた。`docs/レビュー後Opus5.5/07_判断事項.md` の「確定済みの判断」にも記録した。

| 項目 | 決定 |
|---|---|
| 設定の渡し方 | 設定オブジェクトを公開し、作成時の引数で渡す。`HashSet`・`Dictionary` を継承した計測用の型は作らない。FLinq の生成器は型名で照合しているので、継承すると最適化が外れる |
| 範囲 | 次の4つすべて。(1) 観測の統計を出す (2) Persisted にも同じストレージ設定を渡せるようにする (3) 容量探索と Scalable を新 API へ移す (4) 観測値を容量探索の結果（DB）に保存する |

これで変わる承認済みの決定（2026-09-19 承認の計画。リポジトリ外の `C:\Users\kazuh\.claude\plans\qa-workflow-md-validated-stream.md`）：

- 決定3の一部「ページ、セグメント、MutableFraction などは内部で決め、公開しない」→ 公開する。ただし、省略したときは今までどおり自動で決める。
- 決定6「ページや索引などの詳細設定は internal にする」→ public にする。決定6の目的だった「最小サイズでテストを書ける」は引き続き満たす。

変わらない決定：

- 決定2「デバイスはストアが内部で作り、利用者には見せない」：公開するのは読み書き方式の設定だけで、デバイスそのものは見せない。
- 決定3「索引は件数に応じて自動で拡張する」：既定のまま。計測のときだけ止められるようにする。

## 3. 壊してはいけないこと

- 設定を渡さないときの動作は今と同じ。索引とメモリ量の自動決定、索引の自動拡張、デバイスのどれも変えない。
- 操作用オブジェクトが2つ以上あるときは索引を拡張しない、という既存のガードを外さない。Tsavorite 2.0.1-beta.5 の `GrowIndexAsync` は、並行して実行すると壊れる（EXP-0004）。
- メモリストアはディスクを使わない。
- DB の自動移行は作らない。変更はバックアップしてから直接当てる。
- 既存の正しさのテストを弱めない。

## 4. 確認済みの事実（2026-09-25）

### Tsavorite コレクション（`Seamless.Collections.Tsavorite`）

- `Stores/TsavoriteTuning.cs`：internal の record。
  - 項目：`IndexSize`（バイト、省略可）、`PageSize=1<<16`、`SegmentSize=1<<30`、`LogMemorySize`（省略可）、`MutableFraction=1.0`、既定値 `Default`。
  - internal が見えるのは `Test` と `Seamless.Database` だけ（`AssemblyInfo.cs`）。
- `Stores/StoreExtensions.cs`
  - public の `CreateTsavorite<K,V>`・`CreateTsavoriteHashSet<T>`・`CreateTsavoriteSet<K,R>` は `(store,name,expectedCount=0)` だけ。
  - 設定を受け取る多重定義 `(store,name,expectedCount,TsavoriteTuning)` は internal。
  - 戻り値はデータ本体の `DictionaryStore<K,V>`・`HashSetStore<T>`・`SetStore<K,R>`。
- `Stores/TsavoriteLayout.cs` の `Resolve`
  - 索引：指定があればその値。なければ件数から計算する（最小 1<<16）。保存済みの値のほうが大きければ、保存済みを使う。
  - ログのメモリ：指定があればその値。なければ次のとおり。
    - メモリストア：`StoreLimits.MemoryBytes` 以下の最大の2の累乗
    - それ以外：`min(64MB, MemoryBytes/2 以下の最大の2の累乗)`
  - ログのメモリがページ2つ分より小さいときは `ResourceLimitException(Memory)`。
  - デバイス：メモリストアは `NullDevice`。それ以外は `Tsavorite.core.Devices.CreateLogDevice` の既定設定で、データ本体のフォルダに `hlog` と `obj` を作る。
- `Stores/CollectionStore.cs`
  - 公開フィールド `Store`（`TsavoriteKV<...>`）と、プロパティ `Address`（Begin/Head/ReadOnly/Tail）がある。
  - `EnsureCapacity` → `GrowReservationCore`：ログが伸びるたびに、ページ単位で予算を予約する。上限を超えると `ResourceLimitException`。
    - メモリストア：メモリに「索引＋ログ全体」
    - それ以外：メモリに「索引＋min(ログ, ログのメモリ)」、ディスクに「ログ全体」
  - `GrowIndexIfCrowded`：推定件数が「バケット数×4」を超えると、索引を倍にする。操作用オブジェクトが2つ以上あるときは何もしない。
- ログが満杯になったとき：`Collections/Collection.cs` の `ThrowLogFull()` が `OutOfMemoryException("Tsavorite mutable log is full. ...")` を投げる。
- 保存形式の選び方
  - 新 API は型で決める。参照を含む型は MemoryPack、それ以外はそのまま保存する。
  - 旧 API の集合（`Store.Create<T>(MemoryPackSerializerStrategy)`）は、引数を無視して同じものを作る。
  - 旧 API の辞書は引数で選ぶ。ただし、Scalable の12種（辞書7・集合5）はどれも、新 API が自動で選ぶ組み合わせと同じ。
  - **そのため、移行しても保存形式は変わらない。**

### Tsavorite 本体

NuGet の `microsoft.garnet` 2.0.1-beta.5 に含まれる `Tsavorite.core.xml` で確かめた。`TsavoriteKV<...>` に次がある。

- `IndexSize`：索引の大きさ（64バイトのバケットの数）
- `EntryCount`：索引の使用中の枠の数。衝突があるので、件数とは一致しない
- `OverflowBucketCount`：使用中の溢れバケットの数（1つ64バイト）
- `OverflowBucketAllocations`：溢れバケットを確保した回数
- `HighWaterAllocatedPageCount`：メモリ上で確保したページ数の最大値
- `DumpDistribution()`：空でないバケットの分布を出す。戻り値の型は実装時に確かめる

### 共通ストア（`Seamless.Execution`）

- 作り方：`Store.CreateMemory(limits)` と `Store.CreateTemporary(limits,temporaryDirectory)`。
- `StoreLimits` は `MemoryBytes`（既定 256MB）と `DiskBytes`（既定 16GB）を持つ。
- メモリストアの `Save()` は `NotSupportedException`。
- `ResourceLimitException` は `InvalidOperationException` の派生。`Kind`（`Memory`・`TemporaryStorage`・`SingleElement`）、`RequestedBytes`、`LimitBytes` を持つ。

### ストレージ設定

- `StorageTuning`（`Seamless.Collections/Persisted/PersistedList.cs`）は public の record struct。読み書き方式（Sequential/Random）やバッファの有無（Buffered/Unbuffered）などを持つ。
- `Seamless.Collections.Tsavorite/Devices/TsavoriteStorageDevices.cs` の `Create(path,tuning,...)` が、この設定から Tsavorite のデバイスを作る（Random→RandomAccess、Unbuffered→Native）。
- Persisted を共通ストアから作る `Seamless.Collections.Persisted/StoreExtensions.cs` の `CreatePersistedSet/List/Dictionary` は、設定を受け取らない。
  - ただし、中で呼ぶ `new Set<T>(...)`、`new Dictionary<K,V>(...)`、`Store.CreateList<T>(...)` は、どれも最後の引数に `StorageTuning?` を受け取れる。
- 設定を外から読めるのは `PersistedList<T>.Tuning` と `AppendOnlyList<T>.Tuning` だけ。集合と辞書には読む手段がない。

## 5. 実装の手順

段ごとにビルドとテストを通してから、次の段へ進む。

### 段1：設定オブジェクトを公開する

1. `TsavoriteTuning` を `public sealed record` にし、次の2項目を足す。
   - `bool AutoGrowIndex`（既定 true）：false なら索引を拡張しない。
   - `StorageTuning? Storage`（既定 null）：ログのファイルの読み書き方式。
   - 先頭の説明コメントを、今の仕様に書き換える（「利用者には公開せず」を消す）。
2. 設定の検証を足し、`Resolve` の最初で呼ぶ。違反したら `ArgumentException` にする。
   - `IndexSize`・`PageSize`・`SegmentSize`・`LogMemorySize` が2の累乗でない
   - `SegmentSize` が `PageSize` より小さい
   - `MutableFraction` が「0より大きく1以下」の範囲の外
   - メモリストアで `Storage` を指定した
   - ログのメモリがページ2つ分より小さい場合は、今までどおり `ResourceLimitException` のままにする（予算の問題として扱う）。
3. `StoreExtensions`：設定を受け取る多重定義を public にし、引数を `(store,name,TsavoriteTuning tuning,long expectedCount=0)` の順にする。3種類とも同じにする。
   - 既存の public 版は、これに処理を任せる。
   - 呼び出し側（`Test/Seamless/Stores/StoreExtensions.cs`、`Seamless.Database` など）を直す。
4. `GrowIndexIfCrowded`：`AutoGrowIndex` が false なら、最初に戻る。
   - データ本体からこの設定が見えるよう、`TsavoriteLayout` に `AutoGrowIndex` を持たせる。
   - 既存のガード（操作用オブジェクトが2つ以上なら拡張しない）は残す。
5. `Resolve`
   - `Storage` があれば、`TsavoriteStorageDevices.Create(path,storage)` で hlog と obj を作る。なければ今のデバイスのままにする。
   - `AutoGrowIndex` が false で、指定した `IndexSize` と保存済みの値が違うときは、黙って変えずに `InvalidOperationException` にする。指定と違う大きさで測ってしまうのを防ぐため。

### 段2：観測の統計を出す

1. 新しいファイル `Seamless.Collections.Tsavorite/Stores/TsavoriteStatistics.cs` に、public の record を作る。項目：
   - 索引のバケット数（`IndexSize`）と、索引のバイト数（バケット数×64）
   - 索引の使用中の枠の数（`EntryCount`）
   - 溢れバケットの数（`OverflowBucketCount`）と、確保した回数（`OverflowBucketAllocations`）
   - ログのアドレス4つ
   - メモリ上のログのバイト数（Tail−Head）と、ディスク上のログのバイト数（Head−Begin）
   - メモリ上で確保したページ数の最大値（`HighWaterAllocatedPageCount`）
2. `CollectionStore` に `GetStatistics()` と `DumpIndexDistribution()` を足す。後者は `Store.DumpDistribution()` の結果を返す。
3. XML コメントと docs に次を書く。
   - 取得した時点の値で、並行して書き込んでいる間は、項目どうしが整合しない。
   - 使用中の枠の数は、件数ではない。
   - 分布の出力は索引全体を走査するので重い。

### 段3：Persisted に設定を渡す

- `CreatePersistedSet/List/Dictionary` の最後に `StorageTuning? tuning=null` を足し、そのままコンストラクタへ渡す。

### 段4：容量探索と Scalable を新 API へ移す

#### 容量探索

`ParameterSweepRunner.cs` の `ストアを作成` と、各ワークロードを直す。

- 共通ストアを作る。
  - バックエンドが「メモリ」なら `Store.CreateMemory(上限)`。
  - 「ストレージ」なら `Store.CreateTemporary(上限, ストレージディレクトリ)`。
- データ本体は、`CreateTsavoriteHashSet`・`CreateTsavoriteSet`・`CreateTsavorite` に `TsavoriteTuning` を渡して作る。
  - `IndexSize`・`PageSize`・`SegmentSize`・`MutableFraction` は、探索の設定をそのまま使う。
  - `LogMemorySize` は `Memoryサイズ`。
  - `AutoGrowIndex=false`。
  - ストレージのときは `Storage=new StorageTuning(FileAccess.ReadWrite,StorageAccessPattern.Sequential,StorageBufferingMode.Buffered)`（今と同じ）。
- 上限
  - `MemoryBytes` は「索引＋ログのメモリ＋ページ2つ」以上にする。予算より先にログの満杯が起きるようにして、これまでの「ログ満杯」と同じ意味を保つ。
  - `DiskBytes` は、`オプション.ストレージデバイス容量` が正の値ならその値、そうでなければ既定値。
  - デバイスの容量はもう指定しない。ディスクの上限は予算で掛かるので、超えたときは「ディスク上限超過」になる。
- 共通ストアを破棄すると、データ本体とフォルダも片付く。今の独自の後始末（`Dispose` でのフォルダ削除など）と重ならないよう整理する。
- `パラメータスイープ失敗種別` の**末尾**に、`メモリ上限超過` と `ディスク上限超過` を足す。
  - `失敗を分類` で `ResourceLimitException` を `Kind` によって振り分ける：`Memory` → メモリ上限超過、`TemporaryStorage` → ディスク上限超過、それ以外 → 例外。
  - この分岐は、最後の `_ => 例外` より前に置く。
- 結果の `エントリCount` は、段2の統計から取るように変える（値の意味は同じ）。

#### Scalable

- **既存の `CreateMemorySet`・`CreateMemoryStore` と、それを使う正しさのテストは変えない。**
  - 旧 API のテストの移行は、旧 API をどうするかの判断（`docs/レビュー後Opus5.5/07_判断事項.md` の Q-01）と一緒に行う。
- `IHashSetTestStrategy<T>` と `IDictTestStrategy<K,V>` に、新 API で作る静的メソッドを足す。例：`CreateTunedSet(TsavoriteTuning tuning,StoreLimits limits)`。
  - 中身：`Store.CreateMemory(limits)` → `CreateTsavoriteHashSet<T>(名前,tuning)` → `Create()`。
  - 保存形式は型で自動的に決まり、今の組み合わせと同じになる（4章）。そのため、どの戦略でも中身は同じになる。インターフェイスの既定の実装（static virtual）にしてもよい。
  - 戻り値は、Scalable が使うもの（`Set` または `NewDict()`、`Dispose`）だけを持つ新しい型にする。この型が共通ストアの破棄まで受け持つ。
- `Shared/Scalable.Tsavorite.Collections/Bases.cs` を、新しいメソッドを使うように切り替える。
  - ベンチの引数は変えない。
  - 上限は、容量探索と同じ決め方にする。
- 使い回している Contains 用の集合と TryGetValue 用の辞書が、複数のスレッドから同時に使われないことを確かめる。操作用オブジェクトは1スレッドに1つが決まり。
- 旧 API で測った値とは、そのままは比べられない（メモリストアの方式と予算の掛かり方が変わるため）。このことを `docs/verification.md` かベンチの説明に書く。

### 段5：観測値を容量探索の結果に保存する

  - 索引のバケット数
  - 溢れバケットの数
  - メモリ上のログのバイト数
  - ディスク上のログのバイト数
  - 値は、計測の最後に `GetStatistics()` で取る。
  - 使用中の枠の数は既存の `エントリCount` があるので、足さない。
- `UiRunStore.cs`
  - 表の定義、保存、読み込みに4列を足す。
  - 形の検査は、4列を加えた15列を数える。
  - スキーマ版を種類ごとに分ける：ベンチマーク 26、スケーラブル 20、パラメータスイープ 21。書き方はファイルの既存の書き方に合わせる。
- 既存の DB
  - `Work/UI/Benchmark.ParameterSweep.db` が無ければ、何もしない。次に起動したときに新しい形で作られる。
  - ある場合は、同じフォルダに日時つきの名前でコピーしてから、次を直接当てる。当てた SQL とバックアップの場所を報告する。
    - `ALTER TABLE "ベンチマーク" ADD COLUMN ...` を4回
    - `PRAGMA user_version=21;`

## 6. 追加するテスト

内部の実装ではなく、外から見える振る舞いを確かめる。主に `Test` プロジェクトに足す。

| 確かめること | 方法 |
|---|---|
| 索引を固定できる | `AutoGrowIndex=false` と小さい `IndexSize` で多く入れる → 索引のバケット数が変わらず、溢れバケットの数が0より大きい。同じ条件で既定の設定なら、索引が拡張される（対照） |
| ログの置き場所が見える | 一時ストアで `LogMemorySize` を小さくして入れる → ディスク上のバイト数が0より大きい。メモリストアでは常に0 |
| 読み書き方式が効く | 一時ストアで `Storage` に Random と Unbuffered をそれぞれ指定する → 追加・保存・開き直しができ、内容が一致する |
| 誤った設定を拒む | 2の累乗でない、Segment が Page より小さい、Fraction が範囲外、メモリストアで `Storage` を指定 → `ArgumentException`。保存済みと違う固定索引で開く → `InvalidOperationException` |
| 分布を出せる | `DumpIndexDistribution()` の結果が空でない |
| Persisted に設定が届く | リストは `PersistedList<T>.Tuning` が指定と一致する。集合と辞書は、Random と Unbuffered を指定して追加・保存・読み込みが通る |
| 既定の動作が変わらない | 既存のコレクションとストアのテストがすべて通る |
| 失敗の分類 | `Test.Tsavorite.ParameterSweep` に、`ResourceLimitException` の2種類が新しい失敗種別になることを確かめるテストを足す |
| 保存の形 | `Test/Benchmark/UiRunStore.cs` のパラメータスイープのテストで、新しい4列を保存して読み込めることを確かめる |
