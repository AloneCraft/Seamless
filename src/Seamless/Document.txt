    ScanLookup（IterateLookup の内部実装）のこの箇所が問題です：
    // numPending == count - acceptedCount  ← count=long.MaxValue のとき実質 ∞ で発動しない
    // numPending > 256                     ← 256件溜まって初めて drain
    if (numPending == count - scanCursorState.acceptedCount || numPending > 256)
    {
        bContext.CompletePending(wait: true);
        numPending = 0;
    }
    IterateLookup は count: long.MaxValue で ScanCursor を呼ぶため、最大256件の Pending I/O が同時に溜まってから一括 drain されます。
    問題は drain 後の cursor 更新処理です：
    // Update the cursor to point to the next record.
    if (scanCursorState.retryLastRecord)
        cursor = iter.CurrentAddress;
    else
        cursor = iter.NextAddress;
    drain される 256件の CompletePending が完了するとき、その完了コールバック（SingleReader(ref int, ref int, ref int, ref int, ref ReadInfo)）の中で endBatch や retryLastRecord がセットされます。しかし cursor の更新は CompletePending より後ではなく、if(status.IsPending) の外側ループで行われています。つまり：
    1.	レコードAを処理 → IsPending → numPending++ → cursor = A.NextAddress
    2.	レコードB,C,...,257を処理 → 次々 IsPending → cursor は最後のレコードの NextAddress に更新される
    3.	numPending > 256 で CompletePending(wait:true) 実行
    4.	レコードAのコールバックで endBatch=true にセットされていても、cursor はすでに257件分進んでしまっている
    結果として、Pending I/O の結果（endBatch/retryLastRecord）が正しく cursor に反映されず、cursor が飛びすぎ、その後の Count が0のまま IterateLookup が false を返します。これで if(!Completed && Count==0) の条件が成立し Done=true → 途中で列挙終了。
    これは Tsavorite の設計上の制約であり、count=long.MaxValue で ScanCursor を使う際に Pending が発生するディスクスキャンでは正しく動作しないのです。
    修正方針
    IterateLookup に戻しつつ、正しく動かすには maxAddress を使って Pending の発生を防ぐ か、あるいは IterateLookup の maxAddress パラメータに HeadAddress を渡すことでメモリ内のレコードのみを Conditional に使う ことができます。

    構造的な分析をすると、lock は実は不要です。理由を説明し、2つのアプローチを提案します。

    分析
    ManagedIntersectWith.cs:103 に既にこう書いてあります:

    IterateLookup でスキャンしたキー（= 必ずメモリ上、HeadAddress以上）に対して RMW を呼ぶ。一方 ConvertOutputToHeap が呼ばれる条件は「RMW が IsPending になった時」だけ（= レコードがディスク上、HeadAddress未満）。この2条件は同一レコードに対して同時に成立できないため、IntersectWith 経由では構造的に到達不可能。

    つまり:

    IterateLookup は HeadAddress～TailAddress（メモリ上）のレコードだけをスキャンする
    各レコードのコールバックはスキャンスレッドで同期的・順次に呼ばれる
    スキャン対象がすべてメモリ上なので、スキャン起因の pending IO は発生しない
    メモリ上のキーに対する RMW も IsPending にならない
    ScanIteratorFunctions の Interlocked コメント（「Pending非同期がConcurrentで呼ばれるため」）は列挙の一般的な安全策ですが、IntersectWith/SymmetricExceptWith では上記の構造的保証により並列コールバックは発生しません。

SymmetricExceptWith では OTHER のスキャン中に THIS の RMW が IsPending になりうる（THIS 側のキーがディスク上の場合）が、Pending() は同じスレッドで inline 解決するため、スキャンコールバックの並列化は起きません。

提案A（推奨）: lock を除去する

結論だけ言うと、1.1.1 系の IterateLookup/ScanCursor 経路では ConcurrentReader + SingleReader の並列は起こりえます。

整理:

SingleReader + SingleReader 並列
起こりにくい（通常はない）という理解で合っています。

ConcurrentReader + ConcurrentReader 並列
同一スキャン文脈では基本想定しにくいです（主スレッド側の進行で呼ばれるため）。
ただし別セッション/別スキャンを同時実行すればアプリ全体では並列になりえます。

ConcurrentReader + SingleReader 並列
ここが要注意で、起こりえます。
理由は、mutable 側の処理進行中に pending I/O 完了側から read-only 側コールバックが返ってくる経路があるためです。
そのため、同じ状態（同じ session や同じ可変フィールド）を触るなら排他が必要になります。

2.0でconcurrentreaderが無くなった理由

理由を正確に言語化するため、まず 1.x と 2.0 のスキャン関数インターフェース差分（Single/Concurrent の有無）をコードで再確認します。

理由は、2.0 でスキャン API 自体が整理されて「呼び分けが不要になった」からです。

1.x 系はスキャン側に 2 つの入口がありました
ScanIteratorFunctions.cs:8 に SingleReader、ScanIteratorFunctions.cs:25 に ConcurrentReader があります。

2.0 系は入口を 1 本化しています
ScanIteratorFunctions.cs:8 は Reader だけです。
同様にセッション関数群も Reader 1 本で統一されています（例: ManagedRead.cs:13, UnmanagedRead.cs:16）。

つまり「mutable だから ConcurrentReader、immutable だから SingleReader」という分岐モデルを 2.0 で廃止した
これにより、ConcurrentReader という概念そのものが不要になって削除されています。
設計意図としては、コールバック面を単純化して実装と利用側の分岐を減らすためです。

要するに、2.0 は「並行読み専用の別コールバック」を残す設計ではなく、「Reader 1 本に統合して内部で処理する設計」に変わった、が直接の理由です。
