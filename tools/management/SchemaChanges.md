# DB作成とスキーマ変更

## 空のDBを作る

接続後に左の「通常のデータベース」の「＋」を押すか、右クリックして「新しいデータベース…」を選ぶ。ツリー内の追加行にフォーカスが移り、DB名を入力できる。編集中はEnterで作成、Escで取り消す。通常表示に戻った追加行は、クリックまたは選択中のF2・Enterで再び編集できる。定義生成・検証・公開が成功すると、新しいDBが選択される。名前が無効な場合は、同じ行で修正して再試行できる。サンプルテーブルは作らない。

`system`は利用者・定義・履歴を保存するシステムDB。管理権限がある場合に構造を参照できる。通常DBのシステムメタデータは一覧で既定非表示とし、「システムオブジェクトを表示」で切り替える。スキーマを持たない表には架空のスキーマを付けない。

## テーブルを設計してまとめて適用する

1. 新規の場合は対象のDB・スキーマ・「テーブル」分類を右クリックし、「新しいテーブル…」を選ぶ。既存の場合は対象テーブルを右クリックして「設計を編集」を選ぶ。
2. テーブル名、スキーマ、列名、C#型、主キー、必要な外部キーを入力する。新しいスキーマは名前から定義を作成する。
3. 右側のプレビューで実際に保存するC#を確認する。コピーできる。「C#で編集」は同じ内容をエディターへ引き継ぐ。
4. 「下書きへ反映」で個人の下書きを保存する。複数の表・列・関係を続けて変更してよい。編集・保存・解析・ビルドでは稼働データを移行しない。
5. 「未適用の変更」で変更内容を確認し、「変更を検証」で定義・移行コード・依存問い合わせを確認する。これは稼働データ全件での事前移行を意味しない。
6. 「変更を適用」で差分と影響を確認して公開する。DB内の変更を最終形へまとめて一度に移行し、制約検査が成功してから切り替える。

既存の個人下書きがあれば設計操作はその内容を引き継ぐ。稼働版を開く操作では、下書きの内容へ黙って置き換えない。共有版が進んでいれば競合を解消してから適用する。

名前変更は移行元の表・列へ対応付ける。型変更や既存行への値の補充では「初期値・変換式」を指定する。式の`row`は移行前の行で、例えば`checked((long)row.Value)`と書ける。追加した値型列は、初期値を指定しなければC#の既定値になる。参照型列には明示的な初期値が必要。

表を削除する場合は「テーブルを削除…」で下書きから削除する。列の削除は設計表の行を削除する。稼働DBのデータを削除するのは後の適用時で、削除を含む適用には確認とバックアップが必要。

「移行定義を編集」では版1のJSONを編集できる。`tables`の`target`と`source`が新旧の表、`columns`が新旧の列と`expression`、`droppedColumns`と`droppedTables`が明示削除を示す。直接C#を変更した場合も、名前変更を推測せず、この対応付けを確認する。移行定義はC#と同じ下書き・版・エクスポートに含まれる。

計算を含むキーやカスタム実装など、GUIで解釈できない宣言はC#で編集する。他の表と共有する行・キー型の構造をGUIから黙って変更しない。依存する公開済み問い合わせが新しい定義でコンパイルできない場合、適用を拒否する。問い合わせの別の下書きを自動採用しない。

## 自己参照と循環参照

ネイティブの関係は表のプロパティに宣言する。参照先は同じDB内の主キーで、スキーマ配下は`Sales.Customers`のようなC#上の表の経路を使う。複合キーでは対応する列をすべて指定する。行の型は`Tables`に宣言し、主キーの列に`[Key]`を付ける。キーの型`Keys.<名前>`はDBの生成器が作る。

```csharp
[ForeignKey("FK_Node_Parent","Nodes",new[]{"ParentId"},new[]{"Id"})]
public Table<Keys.Node,Tables.Node> Nodes=>this.Table<Keys.Node,Tables.Node>(row=>row.Key);

namespace Tables{public partial struct Node{[Key] public partial int Id{get;}public partial int? ParentId{get;}}}
```

外部キーは行ごとに確定しない。同じ取引に含まれる全変更の最終状態で検査する。例えば次の相互参照は、一つの取引にまとめれば登録できる。

```csharp
using(var transaction=db.BeginTransaction()){
    db.Nodes.Add(new Tables.Node(new(1),2));
    db.Nodes.Add(new Tables.Node(new(2),1));
    transaction.Commit();
}
```

同期取引は最外スコープの終了時、生成された非同期取引は最外の`CommitAsync`で確定する。親子をまとめて削除・キー変更する場合も最終状態で判定する。参照先が欠ける単独操作は拒否する。自動連鎖削除・更新は行わない。nullableな外部キーでは、構成列にnullを含む行を参照なしとして扱う。

「検証データ」は、単一表の行配列のほか、複数表のJSONを一つの取引で投入できる。自己参照・循環参照を別々の確定操作へ分けない。

```json
{"As":[{"Id":1,"Other":2}],"Bs":[{"Id":2,"Other":1}]}
```

## 移行と失敗時の扱い

canonical SharedV2の移行先は、新しい非公開の保存領域へ逐次構築する。全件の変更集合や巨大な単一WALフレームを作らず、全表がそろってから関係を検査する。行の投入順で循環参照を回避する方式にはしない。通常の更新では、検査の読み取りも競合検出に参加させる。

変換失敗、キー衝突、外部キー違反、取消、容量不足では候補を公開せず、旧世代を維持する。失敗した候補を再利用しない。切断・応答喪失は失敗確定とせず、操作IDで結果を照会する。

削除を含む適用の自動退避先は`<サーバーの保存先>/backups/<操作ID>`。旧DB世代のDLL・マニフェスト・データと`definition-version.json`を保存し、コピー成功後に移行を開始する。操作結果の`BackupPath`で場所を確認できる。退避先作成やコピーが失敗した場合は公開しない。

この退避はDB世代の保全用で、管理領域全体を復元するCLIの入力とは異なる。停止・復元を行う運用では、適用前に管理領域全体のバックアップも取得する。

```powershell
# 対象サーバーを停止してから実行する。退避先・復元先は未使用の場所を指定する。
Seamless.Management.Server backup --root D:\Seamless\Instance1 --destination D:\Seamless\Backups\BeforeChange
Seamless.Management.Server restore --backup D:\Seamless\Backups\BeforeChange --destination D:\Seamless\RestoredInstance
```

復元した領域を別の接続先として起動し、定義・データ・利用者を確認してから運用先を切り替える。適用成功後のコード切替とデータ復元は別の操作であり、その後の更新を残す逆移行は新しい移行として扱う。DB世代だけを自動で戻すCLIは提供しない。

## 移行システムのデバッグ

`MigrationDebugSession`は運用RPCには公開しない開発用の実行器。新旧の`Definition`、保存方式、空の専用ディレクトリを指定し、`Before`へテストデータを投入して`Run`する。本番と同じ型付き変換・非公開構築・関係検査を通す。`GeneratedSource`で実際の変換コードを確認でき、動的DLLにはPortable PDBと埋め込みソースを付ける。

`checkpoint`では`BeforeCopy`、表の経路と累積行数、`BeforeConstraints`、`AfterConstraints`を受け取れる。例外・取消・資源予算不足をこの経路で再現できる。失敗後は新しいセッションと専用領域で再実行する。

テストは少量という件数だけで十分と判断せず、親子・中間表・複合キー・自己参照・三者循環・スキーマ間参照を含むデータで関係を確認する。規模・予算・保存と再読込・公開前後のプロセス停止は別の検証として扱う。実運用DBの全件複製や、自動的に関係を保つ部分抽出は行わない。

実行可能な例は`Tests/Management.Tests/MigrationDebug.cs`、`NativeRelationScenarios.cs`、`BatchSchema.cs`を参照する。比較環境ではAGENTSのメモリ監視・D/F出力・最大8CPU規約に従い、次のように絞って実行できる。

```powershell
tools/management/Invoke-Checks.ps1 -Configuration Debug -Filter 'FullyQualifiedName~Management.Tests.MigrationDebug'
```
